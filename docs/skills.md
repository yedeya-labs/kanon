# The agent skills

Kanon ships three skills for Claude Code that install Kanon and keep it healthy, from the agent you already work with ([ADR 0014](decisions/0014-adopter-audiences.md), audience 1; plan 0005 step L11), a fourth that starts a project for the Lead to plan ([#853](https://github.com/yedeya-labs/kanon/issues/853)), and a fifth that tells you what waits on you and keeps every decision asked of you on GitHub (`K-WORK-24`, `K-WORK-25`). The agent does the reading and the explaining; the `kanon` command and the rulebook stay the source of truth, and you decide every choice.

| Skill | Run it as | What it does |
|---|---|---|
| [adopt](../skills/adopt/SKILL.md) | `/kanon:adopt` | Installs Kanon in the repository you are in, new or already in use: a dry run of `kanon init` first, each choice explained and asked, the files written on a branch, the Apps created with you clicking **Create** and **Install**, every step only you can take walked through, and the pull request opened. Then it hands over to doctor. |
| [doctor](../skills/doctor/SKILL.md) | `/kanon:doctor`, or ask the agent whether Kanon is set up right | Runs `kanon doctor`, explains each finding, fixes what can be fixed from the checkout, and walks you through the rest, until the installation is healthy. |
| [mandate](../skills/mandate/SKILL.md) | `/kanon:mandate` | Starts a project from your idea or product document: it measures the document's claims against the code, asks the product questions the Lead may not answer itself (`K-PROJ-18`), writes the mandate, asks whether the project starts as soon as its brief merges, creates a roadmap milestone when the Stakeholder asks for one, files the tracking issue (`K-PROJ-15`) and dispatches the Lead's brief lane. On the brief's pull request, it finds the decisions the Lead marked answered that are yours, helps you rule on them, posts the rulings as one comment, dispatches the Lead's revise lane with a reset, and checks that each ruling landed before you merge. Start it with the brief's pull request to do only that half. |
| [inbox](../skills/inbox/SKILL.md) | `/kanon:inbox`, or ask the agent what is waiting on you | Runs `kanon inbox` ([`docs/status.md`](status.md#the-inbox)) and lists, with links, the pull requests ready for your merge and the decisions asked of you, read from GitHub each time, never from what the session remembers. The agent also loads it before it asks you to decide anything: it posts the decision on the issue or pull request it concerns, in Kanon's fixed form, labels it `decision:needed`, and only then asks you, with the link; when you answer, it records the answer there and takes the label off. It notifies nobody. |
| [upgrade](../skills/upgrade/SKILL.md) | `/kanon:upgrade` | Moves the repository's pins to the plugin's release, its stable tag once Kanon has promoted it and its candidate's tag until then: `kanon doctor --to` that release first, so you see what it needs before anything changes, then the pin bump on a branch, any question a newer release added to `kanon init`, the fixes through doctor, and the pull request, whose body lists what waits for the merge: a check to require once its job is on the default branch, the admin's bypass to remove, the `apps-check` run and the live checks, and, after a week of green runs, the Apps and secrets to delete. A repository pinned on a candidate is offered the move to Kanon's latest stable release, which doctor reports. |

**Only you can start** `/kanon:adopt`, `/kanon:upgrade` and `/kanon:mandate`: type the command in Claude Code. Each one writes your repository and walks you through steps only you can take, such as creating the Apps, typing a secret, answering a product decision and merging, so the agent can't start it on its own (each sets `disable-model-invocation`), and asking the agent to install or upgrade Kanon, or to start a project, won't start it. The agent may start doctor and inbox on its own: doctor changes nothing without asking, and inbox writes only the comment and label of a decision it is about to ask you.

## Why a plugin

The skills live in `skills/`, as a Claude Code plugin, `kanon`, not in a repository's `.claude/skills/`, so **a session has no `/kanon:*` until the plugin is loaded,** in Kanon's own repository too: Claude Code finds a plugin's skills only through a marketplace it knows. The plugin is what lets one copy of the skills reach every adopter at a release they choose, and Kanon's repository is also the plugin's marketplace. Pin it to an exact release, as you pin Kanon's actions and lanes (`K-ADOPT-11`), so the skills, the `kanon` command they run and the release they install are always the same one. You need Claude Code, `gh` signed in as someone who can administer the repository, and Node 24 or later: the skills run `kanon` through `npx`, from the release's tag, so nothing is installed in your repository.

## Declare it in the repository

The way to pin it is in the repository, in its `.claude/settings.json`, which Claude Code reads for everyone who works there ([Require plugins per repository](https://code.claude.com/docs/en/plugins/org#require-plugins-per-repository)). `kanon init` offers to write it (`--plugin`, the default, or `--no-plugin`; [`docs/init.md`](init.md)). The file `claude plugin marketplace add --scope project` and `claude plugin install --scope project` write, never committed and holding nothing else, `init` takes as its own and completes, with `"autoUpdate": true` and the `ref` at its pin ([`docs/init.md`](init.md#the-plugins-settings-file), [#1607](https://github.com/yedeya-labs/kanon/issues/1607)). Into any other settings file the project already has, merge the keys yourself, `init` reporting them (`plugin.declare`) and changing nothing there:

<!-- x-release-please-start-version -->

```json
{
  "extraKnownMarketplaces": {
    "kanon": {
      "source": { "source": "github", "repo": "yedeya-labs/kanon", "ref": "v0.45.0" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": {
    "kanon@kanon": true
  }
}
```

<!-- x-release-please-end -->

- **`extraKnownMarketplaces`** names the marketplace, Kanon's repository, and `ref` pins it to a release tag ([marketplace sources](https://code.claude.com/docs/en/plugins/marketplace-reference#marketplace-sources)). **`autoUpdate`** on its entry, which `init` writes ([#1578](https://github.com/yedeya-labs/kanon/issues/1578), the Owner's decision of 2026-11-02), has Claude Code update the installed plugin to that `ref` in the background, so the plugin each person runs follows the repository's pin ([Moving the plugin](#moving-the-plugin)); `kanon doctor` notes an entry without it (`plugin.auto-update-off`). **`enabledPlugins`** turns the plugin on for the repository ([`enabledPlugins`](https://code.claude.com/docs/en/settings-reference#enabledplugins)).
- **Each person trusts the folder first.** Claude Code honours a repository's marketplace only after the person accepts its workspace trust dialog, and ignores it, without a message, in a folder they haven't trusted, a `-p` run there included ([`extraKnownMarketplaces`](https://code.claude.com/docs/en/settings-reference#extraknownmarketplaces)). So the lanes, which run Claude Code on a fresh checkout, don't load it.
- **Moving the repository to a new release is one edit:** set `ref` to the new tag, as part of the upgrade's pull request. **Moving each person's installed plugin takes more:** Claude Code fetches the marketplace again at the new `ref` when a session starts, and, with `autoUpdate` on the entry, updates the installed plugin to it; without the key, or under a person's own `kanon` entry, it leaves the installed plugin where it was until it is updated ([Moving the plugin](#moving-the-plugin), below).
- **The release is where Kanon can see it.** `kanon doctor` reports a `ref` that differs from the release your callers pin, or the one you are moving to with `--to` (`plugin.version-mismatch`, [`docs/doctor.md`](doctor.md)), and a `ref` below Kanon's latest release (`plugin.below-latest`). Neither blocks. Dependabot doesn't read this file, so when it bumps the callers' pin, `lane-check` warns on its pull request that the `ref` differs from the callers' pin, without failing it ([`actions/lane-check`](../actions/lane-check/README.md)), doctor's finding gives the `ref` to set, and the upgrade skill sets it with the pin, whether it opens the upgrade's pull request or finishes Dependabot's ([`scripts/move-pins.mjs`](../scripts/move-pins.mjs) makes the same edit).
- **The plugin each person runs is where doctor can see it too,** on their own machine: doctor reads Claude Code's records of what it installed for the checkout, and reports a plugin older than the release it checks against (`plugin.behind`), with the steps that move it. It reads only those records and, of the person's user settings, the checkout's `.claude/settings.local.json` and the machine's managed settings and their drop-ins, only the entry of the declared marketplace under `extraKnownMarketplaces` (`plugin.user-override`, [#1577](https://github.com/yedeya-labs/kanon/issues/1577)), and on a machine without the records, as a CI runner, it says it didn't check.
- **A person's own `kanon` entry holds the plugin back.** `claude plugin marketplace add` records the marketplace under its name, `kanon`, in the person's user settings ([plugin loading](https://code.claude.com/docs/en/plugins/loading)). Claude Code's settings reference says the entry from the highest-precedence file wins whole, which the project's is over the user's ([`extraKnownMarketplaces`](https://code.claude.com/docs/en/settings-reference#extraknownmarketplaces)), but in practice the marketplace stays at the person's own `ref`: with a user entry at `v0.38.0` and the repository's at `v0.42.0`, in a trusted folder, neither `/plugin marketplace update` nor a new session moved it (Claude Code v2.1.316, [#1552](https://github.com/yedeya-labs/kanon/issues/1552)). So a person who added the marketplace themselves removes their own entry once the repository declares it ([Moving the plugin](#moving-the-plugin)), and `kanon doctor` names the entry (`plugin.user-override`). Claude Code also keeps one copy of a marketplace per person, so two repositories that pin the plugin to different releases move it back and forth as the person goes between them.

Kanon's own repository declares it the same way. Its `ref` is in the candidate form, and the release pull request moves it to the new candidate, `candidate-vX.Y.Z`, a tag that exists once that pull request merges: release-please rewrites only the version inside the value. Kanon's pin job then moves the callers to the same candidate, in `ci(deps): run Kanon on candidate vX.Y.Z`, and leaves the `ref`, which already names it ([`docs/release.md`](release.md#channels-candidates-and-stable)). Between the two merges the `ref` leads the callers' pin, and doctor reports the difference there, as it would in any repository the plugin leads.

Each skill runs `kanon` through an `npx` line that names its release's candidate tag, `npx --yes --package github:…#candidate-vX.Y.Z kanon …`, whichever release you installed the plugin at ([#1557](https://github.com/yedeya-labs/kanon/issues/1557)). The release pull request writes that tag, which exists once the pull request merges, and the promotion tags `vX.Y.Z` on the same commit, so the command runs the same code on a candidate and on its stable release. What the skills pin in your repository is still the stable release once Kanon has promoted it: `kanon init` pins `vX.Y.Z` when that tag exists ([`docs/init.md`](init.md#the-release-it-pins)), and so does the upgrade skill, whose target is `vX.Y.Z` once doctor's `.releases.stable` is that release. Where a later stable release superseded the candidate, which then never gets a `vX.Y.Z` tag, the skill has you move the plugin to that later release first. Before the promotion, during a candidate's soak, the upgrade skill's target is the candidate's own tag, `candidate-vX.Y.Z`, which exists, and running it again after the promotion offers the move to `vX.Y.Z` ([#1563](https://github.com/yedeya-labs/kanon/issues/1563)). Its `claude plugin marketplace add` line names `vX.Y.Z`; during a soak the candidate's tag takes its place there.

## Or install it yourself

Without a declaration yet, each person installs the plugin from their own checkout, at project scope:

<!-- x-release-please-start-version -->

```sh
claude plugin marketplace add --scope project yedeya-labs/kanon#v0.45.0
claude plugin install --scope project kanon@kanon
```

<!-- x-release-please-end -->

`--scope project` writes the pin into the repository's `.claude/settings.json`, which the adopt skill carries onto its branch and `kanon init` completes ([#1607](https://github.com/yedeya-labs/kanon/issues/1607)). Claude Code's default, user scope, writes it into your own settings instead, where it overrides every repository's own pin (above). Claude Code keeps one clone of the marketplace per person, so re-pointing it in one repository re-points it for all of them (above). Or, inside a Claude Code session, the same two as `/plugin marketplace add --scope project …` and `/plugin install --scope project kanon@kanon`. **Start a new Claude Code session** before `/kanon:adopt`, or run `/reload-plugins`, and the skills are there: a session open during the install still offers the skills it started with. To run a candidate ahead of stable, put its tag, `candidate-vX.Y.Z`, in place of the release ([`docs/install.md`](install.md#running-a-candidate)), and move back with `/kanon:upgrade`.

**A pin added at user scope lives in each person's configuration, not in the repository,** so Dependabot doesn't propose it, and `kanon doctor` sees it only on that person's machine (`plugin.behind`). To move it to a newer release, see [Moving the plugin](#moving-the-plugin).

## Moving the plugin

**The plugin stays at the release it was installed at until someone moves it,** or, with `"autoUpdate": true` on the repository's marketplace entry, until the `ref` moves, and the skills follow that release's rules, whatever the repository pins ([#1552](https://github.com/yedeya-labs/kanon/issues/1552)). `/plugin marketplace update` and `claude plugin update` don't move it past the pinned release: the marketplace is pinned to a tag, so an update fetches that same tag again and says it updated. Each skill checks its own release when it starts and stops with these steps when it is behind the repository's pin, or, for the adopt skill, behind Kanon's latest release (`kanon init --dry-run --json` reports it as `latest`, [`docs/init.md`](init.md)). Run `kanon doctor` on your machine to see what you run: its `plugin` field has the `ref` Claude Code fetched and the version it installed, and `plugin.behind` names the steps for your case.

**Declared in the repository.** The repository's `ref` moves with the upgrade's pull request. **With `"autoUpdate": true` on the `kanon` marketplace entry, the default `kanon init` writes** ([#1578](https://github.com/yedeya-labs/kanon/issues/1578)), that is all: Claude Code refreshes the marketplace and updates the plugin in the background, a few minutes into a session in the repository, and asks for `/reload-plugins` ([Configure auto-updates](https://code.claude.com/docs/en/plugins/install#keep-plugins-updated)). The `ref` still pins the release, so it follows the repository's pin and nothing newer. In our check on Claude Code v2.1.316 it moved the plugin to the project's tag about ten minutes into a session, with no entry of the person's own; step 1 still applies to a person who added the marketplace themselves, since their entry wins. Without the key, each person, in the repository's checkout, once it has the new `ref`:

1. **If you added the `kanon` marketplace yourself** (`claude plugin marketplace add`, from before the repository declared it), remove your own entry: `claude plugin marketplace remove kanon --scope user`. That removes only your user settings' entry and keeps the plugin installed; while it is there, the marketplace stays at your `ref` (above). `kanon doctor` reads that one entry of your user settings, and of the machine's managed settings, and names one that overrides the repository's pin as `plugin.user-override` ([#1577](https://github.com/yedeya-labs/kanon/issues/1577)).
2. **Start a new Claude Code session in the repository.** When a session starts, Claude Code fetches a declared marketplace whose source changed, and says `Plugins changed. Run /reload-plugins to activate.` A `claude plugin marketplace update kanon` from the shell didn't do it in our check; whether `/reload-plugins` in an open session does is not verified.
3. **Update the installed plugin:** `claude plugin update kanon@kanon`, in the repository's checkout. It moves the install for this checkout's scope, and prints `updated from <old> to <new>` and `Restart to apply changes.` Fetching the marketplace alone leaves the installed plugin where it was.
4. **Start a new session,** or run `/reload-plugins`, and the skills are the new release's.

These are the steps that moved the plugin in a check on Claude Code v2.1.316, with a configuration directory of its own, from `v0.38.0` to `v0.42.0` and on to `candidate-v0.43.0`. `"autoUpdate": true` replaces steps 2 to 4; a settings file that predates it, or one `init` didn't write, gets the key by hand (`plugin.auto-update-off` gives it).

**Installed by the person,** in their own Claude Code configuration, without the declaration: in your own terminal, in the repository's checkout, remove the marketplace, which uninstalls its plugin too, add it again at the release, and install the plugin, both at `--scope project`, so the pin goes into the repository's `.claude/settings.json` and not into your own settings, where it would override every repository's own pin (as [Or install it yourself](#or-install-it-yourself) says, [#1616](https://github.com/yedeya-labs/kanon/issues/1616)), then start a new session or run `/reload-plugins`, and run `/kanon:upgrade`. For another release, its tag takes this one's place in the second line:

<!-- x-release-please-start-version -->

```sh
claude plugin marketplace remove kanon
claude plugin marketplace add --scope project yedeya-labs/kanon#v0.45.0
claude plugin install --scope project kanon@kanon
```

<!-- x-release-please-end -->

The upgrade skill prints these lines for the release it moves to, and `kanon doctor`'s `plugin.behind` for the release it checks against.

## What they will and won't do

Each skill states these rules in its own instructions:

- **Adopt, doctor and upgrade drive only the `kanon` command's JSON output** ([`docs/cli-json.md`](cli-json.md)): `kanon init --json` ([`docs/init.md`](init.md)) and `kanon doctor --json` ([`docs/doctor.md`](doctor.md)), whose shapes are versioned contracts. They never read the command's prose to decide anything, so a skill and an integrator see the same interface.
- **They never merge,** approve, push to the default branch or bypass a ruleset. A skill that changes the repository's files opens a pull request, and you merge it; the mandate skill changes none, and the brief's pull request is the Lead's.
- **They never print a secret.** They never read a token or a private key. A secret's value is something you type into your own terminal.
- **Some steps only a person can take, and the skills say which:** clicking **Create** and **Install** for each App, generating an App's private key, widening an App's permissions, typing a secret's value, naming the project's people, and deciding whatever the rulebook gives a person to decide. The skill gives you the exact step and waits.
- **When a skill commits, you sign off the commits** (`git commit -s`, under your own name). Kanon's DCO check rejects an AI sign-off.
- **The mandate skill drives `gh` and the Lead's lanes, and carries method, not rules.** It reads Kanon's rulebook at the release your callers pin and cites each rule by its id, and it takes cost, paging, milestone and stack facts from your repository's own files, never from itself: a fact it needs that nothing states is a gap it reports. It never answers a decision the rulebook gives a person, never posts a review from your token, which would read as your verdict, and never uses `needs:human` to hold a project: to wait for a go-ahead it files the tracking issue with `lead:file-only`, so the issues are filed and none is dispatched until you remove the label (`K-PROJ-11`). It creates a milestone only when the Stakeholder places the project's work on a roadmap milestone that doesn't exist yet: it confirms the title and due date with you, creates it with your token before the Lead plans, since the brief guard accepts only a roadmap milestone that exists with a due date, and names it in the mandate (`K-PROJ-11`, `K-WORK-3`). It never creates a bucket or a milestone without a due date. Only the project's product work lands there; its pipeline items stay on their bucket (`K-WORK-11`).

## The friction log

**The adopt and upgrade skills keep a friction log, without being asked** ([#1607](https://github.com/yedeya-labs/kanon/issues/1607), the Owner's decision of 2026-11-05). Kanon's own adoption logs, [#1551](https://github.com/yedeya-labs/kanon/issues/1551) and #1607, were kept by hand, and only after someone asked for them, so the points before that were reconstructed from memory. Starting the log is no question, and it changes nothing in your repository.

- **Where:** one file per run, `~/.claude/kanon/friction/<skill>-<YYYY-MM-DD-HHMM>.md`. It is under `~/.claude`, rather than the system's temporary folder, because an install often needs a new Claude Code session or a restart partway through, and the log has to outlive both. It is outside every checkout, and never committed. The skill says its path once, at the start.
- **What goes in:** a command that was refused or failed, a retry, a finding whose stated cause was wrong, a step the skill had to improvise, an instruction that didn't match what happened, and a question you had to ask. Each item holds the step, the Kanon release, what happened, the exact error (trimmed to at most ten lines) and, where there is one, an unverified suggestion.
- **What never goes in:** a token, an App ID or Client ID, a secret's value, a private key, a path beyond a file's own name, and your repository's private names. The repository, its owner, people's logins and App slugs are written as `<repo>`, `<owner>`, `<person>` and `<app-slug>` by default, even in error lines and for a public repository, because Kanon's public text never names an adopter who hasn't said so. A name goes back in only where you say so when you review the draft.
- **At the end,** when the log holds an item, the skill shows you the whole draft and asks: **File it**, **Change it first** or **Don't file**. Before it shows the draft, it rewrites the log into the form Kanon's issues take (`K-WORK-14`), so what you review is exactly what is filed. Only on your yes does it file one issue on Kanon's repository, from your own account, with `gh issue create -R yedeya-labs/kanon`, and not through the file-issue skill. The issue has no labels; Kanon's triage gives those. With no yes, nothing is filed. Either way the file stays where it is, yours to delete.

## How they are kept honest

`tests/unit/skills.test.ts` holds each skill to the command or the lanes it drives, so a change to them that would break a skill fails Kanon's own build instead:

- every `kanon` command a skill names is one the CLI has, and every flag it passes is one that command's parser takes;
- every `kanon init` a skill runs carries `--json`, which an agent's shell needs (it has no terminal for `init`'s questions), and `--no-apps` when it writes, so the Apps' browser flow never starts unannounced;
- each skill's table of findings lists exactly the finding ids of [`docs/init.md`](init.md#the-findings) or [`docs/doctor.md`](doctor.md#the-finding-ids), so a new finding can't go unhandled;
- every field a skill reads, such as `.findings[].fix.commands`, is a field those pages document, and each skill's table of statuses and exit codes is theirs;
- the plugin ships `skills/` and nothing else: the repository's root is the plugin's root, so a `hooks/`, `.mcp.json` or other plugin component added there would reach every adopter's agent, and fails the test instead;
- each skill names the contract (`kanon-init/v1`, `kanon-doctor/v1`) its command prints, and runs `kanon` from the release it ships in;
- the mandate skill, which runs no `kanon` command, cites only rule ids the rulebook has, dispatches the Lead's brief and revise lanes only with inputs those lanes take, files through the filing skill, applies only labels in the taxonomy, and keeps its steps in order: the input's claims measured before any question, and the start-on-merge question asked before the tracking issue is filed;
- the upgrade skill carries each answer a newer release added whose only effect is a bullet in the adoption record that `init` keeps as it is, writing the bullet after a yes, or tells you plainly, and in the pull request's `## Left to do`, that your answer isn't in the repository ([#601](https://github.com/yedeya-labs/kanon/issues/601)): its table names every bullet `init` writes from an answer, so a new one can't be dropped silently;
- the inbox skill runs `kanon inbox --json` from the release it ships in, names the `kanon-status/v1` contract, reads only fields `docs/status.md` documents, handles exactly its exit codes, applies only the `decision:needed` label, and spells the ask's and the answer's form exactly as `scripts/lib/decision-asks.mjs`, which the inbox reads them with, does.

A skill step that a person still had to do by hand, when the skills ran Kanon's own migration (plan 0005 L5) or an adopter's (L6), is a gap in the skills, filed against L11 and fixed there.

## The lanes' skills

Two more skills ship in `skills/`, for agents rather than for you to type.

**[file-issue](../skills/file-issue/SKILL.md), the filing skill** ([#164](https://github.com/yedeya-labs/kanon/issues/164), `K-WORK-8`). It is how an agent files an issue: the agent chooses the labels, the one `sev:*` (`K-WORK-9`) and the subject, product or pipeline (`K-WORK-4`), and passes a milestone only when it transcribes one from a brief a person approved (`K-WORK-5`). It then runs `plan` in [`scripts/issue-triage-defaults.mjs`](../scripts/issue-triage-defaults.mjs), the module whose `decide()` the issue backstop runs, which chooses the milestone and any `gate-candidate` label, or refuses and says which rule, and prints the exact arguments of one `gh issue create` (`K-WORK-2`). So the routing has one copy, and no prompt restates it. **It checks the body too** ([#1247](https://github.com/yedeya-labs/kanon/issues/1247), `K-WORK-14`): the agent writes the body to a file and passes it as `--body <file>`, which `plan` requires, and `plan` refuses, by name, a body with no `## What must be true` heading, or with a remedy under any heading but `## Possible approach — UNVERIFIED, not acceptance criteria` (a "Suggested fix", "Proposed fix", "Fix", "Remedy", "Solution", or "Possible approach" in another form). The agent fixes the file and asks again, then files that same file with `--body-file`. The Overseer's and the telemetry Explorer's filing steps, which file what their agents wrote down, run the same check: the Overseer's holds such a finding in its audit issue, and the telemetry Explorer's refuses it. A lane's agent reads the skill by its path in Kanon's tree; the agent in your own Claude Code session may start it on its own when it is about to file an issue, since it is in the plugin and lets the model start it, but it is no command in your menu. Every Kanon lane whose agent files an issue goes through it: the Explorer's sweep, the code audit, verify-acs, merge reconcile and the Reviewer read the skill, and the Reviewer, whose shell is an allow-list, runs the `plan` command by the name `kanon-plan`, a wrapper its job puts on its PATH. The Lead's reconcile tick files a brief's issues from code, so it calls the same `plan` directly, with the brief's milestone as the one it transcribes. **Your own filers can point at it too:** an agent's instructions, a filing agent or a playbook of your own that files issues can say "file through `skills/file-issue/SKILL.md`" in place of its own routing table. [`tests/unit/filing-skill.test.ts`](../tests/unit/filing-skill.test.ts) holds the skill to the `plan` command, the flags it takes and the fields it prints, and fails when any lane prompt that files an issue doesn't send its agent to the skill or restates the routing.

**[upstream-finding](../skills/upstream-finding/SKILL.md)** ([plan 0006](plans/0006-upstream-findings.md) §4.1). The Overseer and the telemetry Explorer read it by its path in Kanon's tree, at the release the lane pins, before they write an upstream finding's `evidence` or `suggested_fix`: a fixed template, the hard rules that keep people, repositories and the adopter's own text out of it, and a self-check that sends the finding as codes only when the lane can't comply. It is no command in your menu, and the agent never starts it on its own. `tests/unit/skills.test.ts` holds it to the template's five parts, the hard rules and the self-check, and each lane's test holds the line in its prompt that sends the agent there.
