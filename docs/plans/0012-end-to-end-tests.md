## The plan in one paragraph

**Today.** Kanon's tests run inside Kanon's own repository. The unit and library suites stub `gh` and refuse the network (`vitest.config.ts`'s `stub-bin` and `offline` setup). The smoke workflows call every lane through `$/` with events each lane turns away and with secrets mapped to one that doesn't exist. They prove that the workflows resolve and their permissions fit, and they stop before any token is minted or any model is called. `lane-check` runs once, on a fixture adopter laid over the workspace. Nothing in Kanon installs Kanon into a second repository, runs `kanon doctor` against a real one, upgrades a real installation, or runs a lane end to end. The smoke workflows' own comments say what stands in for that: "the reference adopter's live run after each upgrade". Plan 0010's deploy lane will be rehearsed once, by hand, in a sandbox (its D12). Every probe Kanon has run on the platform, plan 0009's S0 and plan 0010's D0, was run by hand, and D0 could not run the Releaser's path because no App was installed there.

**Where it ends.**
- **A test organisation,** the Owner's, holding:
  - **the harness repository,** which holds the runner, the scenarios, the workflows and the driver App's key;
  - **throwaway scenario repositories,** created and deleted by the harness;
  - **a driver App,** which creates and deletes those repositories;
  - **test copies of the Author, the Judge and the Releaser.**

  All of these Apps are installed only there (Owner decisions 1 and 2, and the harness decision).
- **The harness tests Kanon from outside, as an adopter would** (the harness decision). It adopts Kanon's full pipeline itself, release lane included, and cuts its own releases, so a repository that lives for months exercises Kanon's releases, Dependabot's pin bumps and the upgrade path (decision 20). Its end-to-end runs still come from its `main`. Its runner's files are on its escalation paths as `always`, so agents propose a change and the Owner merges it (decision 17).
- **Kanon's product gains no test-only switch** (the no-leak rule). The product changes the tier needs are `init`'s pin fix (decision 5) and `provision.mjs`'s repeatable `--repository` (decision 28, [#1339](https://github.com/yedeya-labs/kanon/issues/1339)), and each stands on its own for adopters.
- **A scenario is data:** a directory `scenarios/<scenario>/` in the harness repository. It holds a starting tree, the steps to take, from a fixed vocabulary, and what must then be true. The expectations are read through `kanon doctor --json`, `kanon init --json` and the GitHub API.
- **The runner** creates `e2e-<scenario>-<run id>-<attempt>` in the test organisation. It lays the starting tree, runs the steps, polls each expectation against a deadline, records the result, and deletes the repository. **A janitor** deletes any leftover older than a few hours.
- **Every scenario repository pins the release under test,** as an adopter does, so the scenario runs the candidate's released code, not a branch's.
- **Two tiers:**
  - **no model,** the bulk: install per feature, doctor clean and broken per finding family, upgrade from the last two stable releases, `lane-check`, the deploy lane end to end, and the gates' refusals;
  - **a real model,** at most two scenarios a run, under the $2 cap (decisions 4, 6, 7 and 15).
- **Triggers** (decision 4):
  - every candidate, found by a 15-minute poll of Kanon's public releases (decision 19), as the gate;
  - a nightly run, held unless Kanon's `main` changed since the last nightly run or no nightly run has happened in seven days;
  - a dispatch.

  Never per pull request.
- **A hard release gate** (Owner decision 3, decisions 1 and 2): a candidate is promoted to stable, and Kanon's own pins move to it, only once the harness has reported green on the candidate's commit. The harness reports it as a check run from a Reporter App installed only on Kanon, which Kanon's promotion reads (decision 18, [§8](#8-the-release-gate)). No quarantine and no override (decisions 11 and 12).

**How it gets there.**
- **The Owner's setup and the probes come first** (E0). The Owner creates the organisation, the harness repository and the Apps. A maintainer then probes the platform there, because the plan rests on behaviours nobody has measured: an App creating and deleting repositories, the Releaser's release approved by the Owner, the free plan's job and rate limits, and a check run authenticated by its App.
- **In Kanon:** `init`'s pin fix (E1), and later the gate step (E11), which needs plan 0009's candidates and promotion (S3 to S5).
- **In the harness repository, offloaded as issues:**
  - its own adoption of Kanon's full pipeline, its release lane and Dependabot entry (E2);
  - the scenario format, the runner and the workflows;
  - the first scenario, plan 0010's D12 rehearsal, so the harness pays for itself on its first run;
  - install per feature and upgrade from the previous releases;
  - the verdict and its report;
  - then the doctor-broken families and the real-model tier, each joining the gate after a burn-in;
  - and the long-lived upgrade signal, which reads whether the harness itself keeps up with Kanon's stable releases (E14).

## 2. What the tier is, and what it is not

**It is** a test of Kanon as an adopter meets it: a fresh repository, the release's own callers, the release's own CLI, real Apps with real permissions, GitHub's real events, and doctor's verdict at the end. It tests what the unit suites can't:
- **the platform's answers:** eventual consistency, permissions, rulesets, environments, and events fired by an App rather than by the workflow token;
- **the joins between Kanon's parts:** `init` writes what `lane-check` accepts and doctor calls healthy; a lane's mint, setup, run, finish and recorded row happen in one run.

**It is Kanon-specific, not a Kanon feature** (the no-leak rule). Nothing in Kanon's product knows the tier exists:
- no input, choice, marker or mode is added for it;
- no lane, doctor check or collector behaves differently in a scenario repository;
- the harness reaches Kanon only through what any adopter uses: its releases, its CLI and its callers.

A product change the tier needs must stand on its own for adopters, as `init`'s pin fix does.

**It is not:**
- **a replacement for the unit and library suites,** which stay the place for every branch of every script, with their mutations. A scenario covers a path, not its edge cases;
- **a per-pull-request check.** A pull request's code is not a release, a scenario repository can only pin a release, and a run takes minutes to an hour ([§7](#7-triggers));
- **a test of the model's judgement.** The real-model tier checks that a lane ran, posted and recorded under its ceiling, not that its verdict was right ([§6.2](#62-a-real-model-under-2));
- **a test of an adopter's stack.** A scenario's hooks are trivial on purpose, as D12's are.

## 3. The test organisation, the harness repository and the Apps

**The organisation.** It is the Owner's, created for this and nothing else (Owner decision 1). "The test organisation" in this plan is its name until it exists. Its repositories are **public**:
- GitHub's free plan offers environment reviewers only on public repositories, as D0 measured;
- rulesets and free Actions minutes hold there too, as E0 measured ([§12](#12-what-is-not-confirmed-and-how-each-is-handled), items 6 and 11).

**The harness repository** (the harness decision). "The harness repository" is its name until the Owner chooses one at E0. It holds:
- the runner, the scenarios, the workflows and the janitor;
- three protected environments, each admitting only its default branch:
  - **`e2e`:** the driver App's key and the test Apps' keys;
  - **`e2e-model`:** only the real-model token, the Owner's Claude subscription OAuth token (`CLAUDE_CODE_OAUTH_TOKEN`), read by one job (decision 16);
  - **`e2e-report`:** only the Reporter App's key.

**It adopts Kanon's full pipeline, like any adopter** (decisions 17 and 20):
- **The install.** It runs `kanon init --feature full` at the candidate Kanon itself runs on, with the test Releaser and Kanon's release workflow, and moves to the stable tag when that candidate is promoted, by the upgrade skill, whose edit is Kanon's `scripts/move-pins.mjs` (`docs/release.md`); whether Dependabot proposes the move from a candidate pin is unverified. The Owner chose this over waiting for a stable release: the harness adopted Kanon on 2026-10-17 at `candidate-v0.41.0`.

A repository that lives for months exercises a run of releases, Dependabot's pin bumps and the upgrade path, which throwaway repositories can't.
- **Where the e2e runs come from.** They still run from the harness's `main`, not from its releases, so a fix to the harness reaches the gate at once.

- **Its lanes** run as the test Apps, on the Owner's subscription token, as Kanon's own lanes do (decision 21). So its own agent runs never spend the e2e tier's budget.

**The Apps:**
- **The driver App.** Created by the Owner, owned by the test organisation, and **installed only there,** on all its repositories. It is the only identity the runner acts as. Its permissions are Owner decision 1's, each read and write: create and delete repositories, Administration, Contents, Actions, Environments, Workflows, Issues and Pull requests. Decision 14 adds two more: Secrets (write), and the organisation's Administration (read). They serve the runner's own steps and probe 09's doctor run on the driver's full token, which found 0 checks `unchecked`.   - created by the Owner, owned by `yedeya-labs`, private, and installed only on Kanon's repository;

## 4. A scenario is data

### 4.1 The directory

In the harness repository:

```
scenarios/<scenario>/
  scenario.json     what the scenario is, below
  start/            the tree laid down as the repository's first commit
  steps.json        up to three phases, each a `kanon` segment then an `act` segment of verbs (§4.2, §5.2)
```

`scenario.json`:

| Field | Meaning |
|---|---|
| `id` | The directory's name: lowercase, digits and hyphens, at most 40 characters, so the repository's name fits. |
| `family` | `lane`, `install`, `doctor`, `upgrade` or `deploy`. |
| `tier` | `none` or `model` ([§6](#6-two-tiers)). |
| `gate` | Whether it counts toward the release gate. A new scenario starts `false`. It turns `true` in a pull request once it has passed ten consecutive runs, scheduled or dispatched ([§10](#10-flakiness), decision 24). Once `true`, it is never set aside: a broken gating scenario blocks releases until it is fixed (decision 11). |
| `apps` | The test Apps the scenario repository gets: any of `author`, `judge`, `releaser`. |
| `claude` | `none` or `subscription`: whether the scenario repository needs the real-model token. With `subscription`, the `model-key` job writes it ([§5.2](#52-the-jobs-and-which-secret-each-holds)). |
| `deadlineMinutes` | The whole scenario's deadline, at most 120. |

`start/` is copied as it is, with two substitutions and no others:
- `{{release}}`: the release under test, `candidate-vX.Y.Z` or `vX.Y.Z`;
- `{{repository}}`: the scenario repository's `<owner>/<name>`.

Nothing in `start/` runs on the harness's runner. It is data that becomes the scenario repository's tree, and its hooks run only in the scenario repository's own Actions.

### 4.2 The step vocabulary

The vocabulary is a closed set. Each verb is implemented once in the harness, with its own unit test against a stubbed `gh`. **Each verb belongs to one kind of segment** ([§5.2](#52-the-jobs-and-which-secret-each-holds)): the `kanon.*`, `register.write` and `pins.move` verbs run Kanon's code and belong only in a `kanon` segment; every verb that writes to GitHub with the harness's own code belongs only in an `act` segment; the `expect.*` and `run.await` verbs, which only read, may sit in either. The validator refuses a verb in the wrong kind of segment. A scenario that needs another verb adds it in a pull request, with its test. Every verb that waits takes a `deadline` in minutes, and polls ([§10](#10-flakiness)). Every verb that runs Kanon's code runs it at the release under test, fetched as an adopter fetches it (`npx --yes --package github:yedeya-labs/kanon#<release> kanon …`), in a `kanon` job, on that job's narrowed token ([§5.2](#52-the-jobs-and-which-secret-each-holds)).

| Verb | What it does |
|---|---|
| `kanon.init` | Runs `kanon init --json --yes --no-apps` with the given flags (`--feature`, `--review-trigger`, `--sensitive-data`, …) against a clone of the scenario repository, with telemetry and sharing declined (decision 8). The CLI writes only to the clone; the next `act` job pushes it. The document is kept for `expect.init`. |
| `repo.apply` | Does what `init`'s `steps-left` findings leave to a person, with the harness's own code, in an `act` segment (decision 23 (b)): creates the labels the release's `requirements.json` lists, read as data; creates the bucket milestones; sets squash-only merging; and creates the default branch's ruleset as `K-ADOPT-1` step 8 states it (squash-only merging is step 5, the milestones step 7). Once the pushed callers are on the default branch and a job there reports `Lane check`, a second `repo.apply` adds the ruleset's required `Lane check` rule, which `init` leaves as `ruleset.require-check`. It applies only what the kept `init` document's findings name. The next `kanon.doctor` holds the labels and the ruleset: a harness copy that drifts from Kanon's surfaces as doctor's `ruleset.missing` or `ruleset.rule-missing`, or a missing label, a test failure. Doctor checks neither the bucket milestones nor the merge settings, so a drift there fails nothing ([§11](#11-the-threat-model-stated-plainly)). |
| `kanon.doctor` | Runs `kanon doctor --json`, optionally `--to <release>`, from a clone of the default branch, and keeps the document. |
| `kanon.at` | Runs `init` or `doctor` at another release (`previous`, `previous-1`, or a tag): the upgrade scenarios' starting point. |
| `register.write` | Writes the App register's rows for the scenario's test Apps, through the library `kanon apps` writes them with, without a key ([§5.2](#52-the-jobs-and-which-secret-each-holds)). |
| `pins.move` | Runs Kanon's `scripts/move-pins.mjs` (plan 0009 S4), at the release under test, to that release. It is the upgrade skill's edit, without the skill. |
| `files.commit` | Commits files from the scenario's directory, or the clone the `kanon` segment left, or deletes paths, on a branch or the default branch. |
| `pr.open`, `pr.label`, `pr.merge` | Opens a pull request from a branch, adds or removes a label, or merges it. A merge goes through the front door, or as the driver where the ruleset lets a bypass actor through, which the scenario says. |
| `issue.open`, `issue.label` | Opens an issue, adds a label. |
| `workflow.dispatch` | Dispatches a workflow, such as `apps-check` before doctor. |
| `release.cut` | Merges the scenario repository's release pull request, and waits for the Release the test Releaser publishes. |
| `deployment.await-approval` | Waits until an environment's job is `waiting`, then cancels the run and holds that job to `cancelled`, on every trigger (decision 9, changed 2026-10-20). |
| `run.await` | Waits for a workflow's run on a given event and commit to complete. |
| `expect.init`, `expect.doctor` | Holds the kept document to a status, an exit code, finding ids present and absent, and the `unchecked` checks allowed. |
| `expect.run` | Holds a run to its conclusion and its jobs' names and conclusions. |
| `expect.check` | Holds a commit's check run or status to a name and a conclusion. |
| `expect.issue`, `expect.pr` | Holds an issue or a pull request to its state, labels, author's App slug, and a marker in a comment. |
| `expect.artifact` | Holds a run's artifact to its name. Used for a model lane's recorded row, which the lane uploads whether or not the repository sends telemetry. |
| `expect.api` | Holds one GET of the scenario repository's own API (a path under `repos/<the scenario repository>/`) to a JSON value at a pointer. The validator refuses any other path. |

### 4.3 What a scenario may expect

Expectations are read in this order:
1. **Through doctor's and `init`'s JSON first** (ADR 0014): a finding id, a status, an exit code, an `unchecked` check.
2. **Through the GitHub API second,** and only for what doctor doesn't report: a run's jobs, a check's conclusion, an issue's labels, a pull request's author, an artifact's name.
3. **Never through prose.** No expectation reads a message, a log line or a comment's wording. It reads only a field, or a marker Kanon already writes for its own reasons, such as the release-PR guard's `<!-- kanon-release-pr-guard … -->` or the Reviewer's role marker. **The rule the validator checks:** an expectation names only a JSON field (by name or pointer), a finding id, or a marker from the harness's list of known markers, and compares it to a value. No expectation takes free text to match, and no expectation reads a field that holds free text, such as a finding's message or a comment's body.

**No marker is added for the tests** (the no-leak rule). A scenario's expectations are therefore as stable as the contracts they read, and a contract change shows up as a failing scenario on the candidate that makes it.

**Doctor's `unchecked` is explicit.** A check the `kanon` job's read-only token can't run (probe 19 measured them on 2026-10-17: exactly `secrets`, since listing a repository's secret names needs admin access, so doctor exits 4, `incomplete`; [#968](https://github.com/yedeya-labs/kanon/issues/968), [run](https://github.com/kanon-e2e/harness/actions/runs/39051969423)) is listed in the scenario's `expect.doctor` as allowed. Anything else unchecked fails the expectation, so "incomplete" can never pass for "healthy" by accident.

## 5. The runner and the janitor

All of this lives in the harness repository (the harness decision). Kanon's repository holds none of it.

### 5.1 One scenario's life

1. **Name.** `e2e-<scenario>-<run id>-<attempt>`, at most 100 characters. The run id makes it unique across concurrent runs; the attempt across a re-run.
2. **Create** a public repository in the test organisation with the driver's token. It gets the topic `kanon-e2e` and a description naming the harness run that made it.
3. **Provision** the repository, as [§5.2](#52-the-jobs-and-which-secret-each-holds) says:
   - the `provision` job writes the scenario's App secrets;
   - for `claude: subscription`, the `model-key` job writes the real-model token;
   - the organisation member who reviews its environments is set.
4. **Lay** `start/` as the first commit of the default branch.
5. **Run** `steps.json` in order. A step that fails stops the scenario.
6. **Classify** the result:
   - `pass`;
   - `fail`: an expectation was false, or a deadline passed;
   - `infra`: an infrastructure error the runner classified and retried, still failing ([§10](#10-flakiness)).
7. **Delete** the repository, always on `pass` and `infra`. On `fail`, mark it with the topic `kanon-e2e-failed`, archive it, and leave it for 24 hours so its runs can be read (decision 13).
8. **Report** one JSON result, `kanon-e2e-result/v1`, uploaded as an artifact and written to the step summary. It holds the scenario, the release, the result, each step's duration and outcome, the first false expectation, and the repository's name.

**The one exception: the QA store's fixture** (decision 27). The `qa-store` scenario ([§9](#9-the-first-scenarios)) runs in the persistent `kanon-e2e/qa-store-fixture`, because the store's role trusts exact subjects only ([§3](#3-the-test-organisation-the-harness-repository-and-the-apps)). For it, steps 1, 2 and 7 change: the runner resets the fixture to the scenario's starting tree instead of creating a repository, and never deletes or archives it: on `fail` it leaves the fixture as the run left it, for reading, until the next run resets it. The fixture carries no `kanon-e2e` topic, so the janitor never touches it ([§5.3](#53-the-janitor)). One fixture holds one scenario at a time, which "One run at a time" ([§5.2](#52-the-jobs-and-which-secret-each-holds)) already gives.

### 5.2 The jobs, and which secret each holds

The harness repository's workflows follow `K-AGENT-49` as Kanon's `tests/unit/app-key-isolation.test.ts` holds it for the lanes. The harness's own workflow test copies those assertions, because Kanon's test reads only Kanon's workflows. Two rules:
- **No job that runs code holds a private key.**
- **Each job that runs code with the driver's token gets it from a mint of its own,** in the lanes' three levels:
  1. a job in the calling workflow calls a `-run` workflow;
  2. the `-run` workflow holds exactly two jobs: `mint`, and a call of a `-job` workflow that `needs: mint` and receives the sealed token through that call's `secrets:`;
  3. the `-job` workflow is one job. It declares the token as its `app-token` secret, runs the spine's receive step first (masked before any output, a stale attempt refused), does its work, and runs the spine's revoke last, under `always()`.

**No minted token is ever handed to two jobs.** One consumer revoking it would cut the other off, and not revoking it breaks the rule.

**The matrix and any concurrency sit on the level-1 call,** never inside the pair. So the mint waits with the job it serves, and never mints a token a wait could outlive.

**Each mint and each key-reading job declares its environment and reads its key itself.** A job that calls a reusable workflow can't declare an environment, so it can't read one for the job it calls ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 12). The called workflow declares each secret it reads under `on.workflow_call.secrets`, and its caller maps it by name: the caller's `${{ secrets.X }}` resolves in the called job's scope, so the caller holds nothing, but an undeclared secret reads empty (E0, item 12). Environment secrets' names take no hyphen.

**Kanon's code runs in a job of its own** (`K-AGENT-50`, decision 22). Inside one job, step order is not a boundary: a token in a job is reachable from any code that job runs. Kanon's CLI and scripts at the release under test are code a green-zone merge in Kanon can change ([§1](#1-today-measured)). So a scenario phase is two jobs, never one:
- **a `kanon` job** runs only the `kanon` segment's verbs. Its token is scoped to the one scenario repository, **read-only**: Contents (read), Issues (read), Administration (read), Actions (read), Pull requests (read), and no Workflows or Secrets at all (decision 23 (b)). Doctor runs on it. E0's item 9 found 0 `unchecked` on the driver's full token; probe 19, minting exactly this token, found exactly one: `secrets`, since listing a repository's secret names needs admin access, so doctor exits 4. The App-permission and organisation checks run on it (2026-10-17, [run](https://github.com/kanon-e2e/harness/actions/runs/39051969423)). So each scenario's `expect.doctor` lists `secrets`, and only it, as allowed ([§4.3](#43-what-a-scenario-may-expect)). The token is also what `init` needs to read the repository and name what its token can't do: it writes no label, milestone, ruleset or merge setting, and reports each as a step left to a person (`label.create`, `milestone.buckets`, `ruleset.create`, `merge.settings`, and later `ruleset.require-check`, status `steps-left`), as it does for any adopter whose token can't. It makes its own fresh clone of the scenario repository (Contents read), at the ref the run's state names, so it sees what the last `act` job pushed. Everything the CLI writes goes to that clone, and the clone's files cross to the next job as an artifact.
  **This job complies with `K-AGENT-50`:** it runs the code under test with no write permission. An earlier revision gave it Issues (write) and Administration (write) as an accepted departure (decision 23 (a)). E0 found that Administration (write) alone could grant a collaborator admin, and could switch the default branch to a branch holding a different workflow, so the Owner took the fallback (decision 23 (b), 2026-10-17).
- **an `act` job** runs only the harness's own verbs, from the harness's `main`. It never runs Kanon's code. Its token is scoped to the same repository, with Contents, Workflows, Issues, Pull requests, Actions and Administration (write). It does the steps that write through the harness's own code (opening and merging pull requests, cutting a release, waiting for an approval, and `repo.apply`'s labels, milestones, ruleset and merge settings), and it pushes what the `kanon` job wrote, **treating the crossing artifact as data:**
  - it clones the scenario repository itself, with its own git, into a directory of its own, and runs git only there;
  - it unpacks the artifact into a separate scratch directory and never runs git, or anything else, inside it;
  - it walks the artifact with `lstat` and takes only regular files whose path stays inside the tree. It refuses, and reports as `fail`, any symlink, device, hard-linked or out-of-tree path, and anything under `.git/`;
  - it copies those files' bytes into its own clone, commits them, and pushes.

  So a hook, a `core.fsmonitor` or `core.hooksPath` setting, or a symlink the `kanon` job left runs nothing and reads nothing in the `act` job. The run's state crosses as JSON, parsed against a schema.

`.github/workflows/e2e.yml` has a workflow-level `concurrency`, `group: e2e-${{ inputs.release || github.event.schedule }}`, `cancel-in-progress: false`. It reads only `github` and `inputs`, which are what a workflow-level group may read. `github.event.schedule` is the cron line that fired, so **the poll and the nightly each have a group of their own:**
- **the poll's group** holds one running poll and at most one pending one. A newer poll replacing a pending one loses nothing, because the newer one reads the same releases;
- **the nightly's group** never has a pending run, because a run ends before the next night: about 3 hours 20 minutes at full parallelism, longer in waves at E0's measured limit (**One run at a time,** below), which E4 holds inside the nightly interval. **So a due nightly is never cancelled by a poll,** which a shared group would do: GitHub keeps one pending run per group and cancels the older one when another queues;
- **a dispatch** shares the group of the release it names.

**A nightly and a candidate's run don't overlap** (the Owner, 2026-10-17, once E0 measured item 5). The groups stay separate, so a poll never cancels a due nightly, but each `plan` reads the harness's own runs before anything else: **a nightly gives way** to a candidate's run in flight, ending at `plan` with "skipped: a candidate's run covers tonight", since that run tests the same catalogue at the same or a newer release. It records no `main` head, so the next night isn't held and runs the install and doctor families at `main`'s head then: a night that gives way loses one night of `main`'s unreleased coverage, which the plan accepts; and **the poll leaves a candidate alone while a nightly is in flight,** as it does while the candidate's own run is, so the candidate's run starts at the first poll after the nightly ends. A dispatch stops at `plan` while either is in flight. So each run has the organisation's whole jobs-at-once limit ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 5), not half of it (**One run at a time,** below). A run that waited starts with `plan`, which re-reads the candidate's check runs and the harness's own runs **before any repository is created**, and stops if the candidate needs no run ([§7](#7-triggers)):

| Job | Holds | Runs |
|---|---|---|
| `plan` | nothing | Reads Kanon's releases and `main` (public), decides whether this run goes ahead ([§7](#7-triggers)), picks the release under test and the scenarios for the trigger and tier. **On a candidate's run, before it ends, it records the run's candidate:** it uploads an artifact named `e2e-candidate-<the candidate's tag>`, kept 90 days. A run's `run-name` can't carry the candidate, because it can read only `github` and `inputs` and `plan` picks the candidate. The artifact is written before `start` runs, so a run that fails at `start` is still counted ([§7](#7-triggers)). It writes two outputs: `scenarios`, the matrix of every scenario, and `model-scenarios`, those with `claude: subscription` (`[]` when there are none). |
| `start` | `needs: plan`; only on a candidate's run (otherwise `skipped`). In the `e2e-report` environment: the Reporter App's key, nothing else | Mints the Reporter's token for Kanon's repository and creates the check run `kanon-e2e` on the candidate's commit, `in_progress`, with this run's id as its `external_id`. It outputs the check run's id. **The token action and `gh` alone.** From this moment the poll sees the candidate as taken. **If it fails** (a rotated key, a lost installation), nothing else runs: every scenario job below needs `start` and has `needs.start.result != 'failure'` in its `if:`. `verdict` then files an issue in the harness, `the Reporter can't post`, and the run fails. |
| `provision` | Matrix entry per scenario; `fail-fast: false`; `timeout-minutes: 10`; `needs: [plan, start]`; `if: ${{ !cancelled() && needs.start.result != 'failure' }}`. In the `e2e` environment: the driver App's key and the test Apps' keys, and no Claude credential | Mints its **own** driver token, scoped to the new repository, with `actions/create-github-app-token`. Creates the repository, and writes each App's id and key with `gh secret set`. Its last step adds the topic `kanon-e2e-provisioned` with `gh repo edit --add-topic`. **No checkout, no `npx`, no script: the token action and `gh` alone.** That is the shape Kanon's guard already accepts for `apps-check.yml`'s `check`. |
| `model-key` | Matrix over `model-scenarios`; `fail-fast: false`; `needs: [plan, start, provision]`; `if: ${{ !cancelled() && needs.start.result != 'failure' && needs.plan.outputs.model-scenarios != '[]' }}`. Holds nothing | Calls `e2e-model-key-run.yml`. Why its `if:` has both parts: <ul><li>`!cancelled()`: an `if:` without a status function is read as `success() && …`, and a needed matrix job counts as failed when any one entry failed;</li><li>the non-empty test: an empty matrix is an error, not a skip.</li></ul> |
| `kanon-1`, `act-1`, `kanon-2`, `act-2`, `kanon-3`, `act-3` | Each a matrix entry per scenario; `fail-fast: false`; `if: ${{ !cancelled() && needs.start.result != 'failure' }}`. Hold nothing | Each `kanon-N` calls `e2e-kanon-run.yml`, each `act-N` calls `e2e-act-run.yml`. Their `needs:`, each with `plan` and `start` beside: <ul><li>`kanon-1`: `provision` and `model-key`;</li><li>`act-N`: `kanon-N`;</li><li>`kanon-2`: `act-1`, and `kanon-3`: `act-2`.</li></ul> |
| `verdict` | `needs:` `start` and the six phase jobs, so it can read `needs.start.result`; `if: ${{ !cancelled() }}`. Holds nothing beyond `issues: write` on the harness repository | Reads every scenario's result artifact, writes the summary table, decides the gate's answer ([§8.2](#82-what-the-gate-reads)), files or closes the red issue in the harness repository ([§8.3](#83-a-red-gate-how-it-is-reported-and-the-only-way-past-it)), and uploads `verdict.json`: `pass`, `fail` or `infra-only`. **It then exits non-zero unless the answer is `pass`.** The `verdict` job's own conclusion is what the gate reads ([§8.2](#82-what-the-gate-reads)), not the run's: another job can fail the run, a burn-in scenario's timeout for one, while the verdict is green. |
| `report` | `needs: [start, verdict]`; `if: ${{ always() && needs.start.result == 'success' }}`. In the `e2e-report` environment: the Reporter App's key, nothing else | Downloads `verdict.json` with `gh run download`, mints the Reporter's token, and completes the check run `start` created: `success` for `pass`, `failure` for `fail`, and `neutral` for `infra-only` or for a missing `verdict.json` (the run was cancelled or broke before judging). The summary links this run and the red issue. **The token action and `gh` alone** (decision 18). Its `if:` makes it post on red, on `infra` and on a cancelled run too, so no candidate is left `in_progress`. |

The pairs. Each `-run` workflow holds exactly `mint` and its call; each `-job` workflow is one job.

| Pair | `mint` | The `-job` workflow's one job |
|---|---|---|
| `e2e-kanon-run.yml` → `e2e-kanon-job.yml` | Declares `environment: e2e` and reads the driver's id and key from it. Runs `actions/create-github-app-token` with `skip-token-revoke`, scoped to the one scenario repository and narrowed to the `kanon` job's permissions above, and the spine's seal. No `needs:`, no `if:`; `timeout-minutes: 5` | `timeout-minutes: 20`. Receive; download the run's state (JSON); make a fresh clone of the scenario repository at the ref the state names; run the harness's runner for one `kanon` segment, which fetches and runs Kanon's code; upload the clone's tree and the state; revoke. It never holds a key. |
| `e2e-act-run.yml` → `e2e-act-job.yml` | As above, with the `act` job's permissions | `timeout-minutes: 30`. Receive; check out the harness at its default branch; download the `kanon` job's artifact into a scratch directory and its state; clone the scenario repository itself; take the artifact's files as data, as above; run the runner for one `act` segment; upload the state, naming the ref the next `kanon` job clones; revoke. **It runs no code of Kanon's:** the harness's workflow test refuses `npx`, a `kanon` command or a module from Kanon's tree in it, and the runner's tests hold the artifact's handling. |
| `e2e-janitor-run.yml` → `e2e-janitor-job.yml`, called hourly by `e2e-janitor.yml` | As above, unscoped, because it lists every repository | Receive; check out the harness at its default branch; run the janitor; revoke. |

**Phases are fixed at three, each a `kanon` job and then an `act` job.**
- **Why:** a matrix runs its entries in no order, so a scenario's phases can't be entries of one matrix; and Kanon's code and the harness's wide token must never share a job. A scenario's `steps.json` names its segments; the validator refuses one that needs more than three phases, and a verb in the wrong kind of segment.
- **Timing:**
  - a `kanon` job lasts at most 20 minutes and an `act` job at most 30, each under a token's hour;
  - a scenario's steps may take at most 120 minutes of the 150 the three phases give;
  - the token's hour counts from the mint, so a queue between a mint and its job spends it too. A token that expires that way fails a call, which the runner reports as `infra`, never as `pass`.
- **Exit status:** a runner that finishes exits 0 whatever the scenario's result, which is in its artifact. So one scenario's `fail` never stops another's phases. `verdict` is the one job whose exit carries the result into the run's conclusion.
- **A failure before the steps is `infra`, not `fail`.** The runner reports `infra` when:
  - the repository lacks the `kanon-e2e-provisioned` topic;
  - a `claude: subscription` scenario's repository lacks the token's secret;
  - the repository is already gone.
- **A repository's running time,** when every scenario runs at once, is at most about 3 hours 20 minutes: three 50-minute phases, plus at most 50 minutes of `provision` (10), the `model-key` pair (5 and 5) and the six phase mints (5 each). In waves it is longer (**One run at a time,** below). **Queueing is bounded by nothing,** since a timeout counts from a job's start. The janitor's margin of about an hour and forty minutes absorbs it. E13 measures both.
- **One run at a time.** A nightly gives way to a candidate's run, and a candidate's run waits for a nightly in flight (above), so the organisation's limits are sized for one run:
  - **Jobs at once** (item 5). Every scenario job's matrix (`provision`, `model-key` and the six phases) takes a `max-parallel`. A run's `max-parallel`, times the jobs one scenario holds at once, fits item 5's limit less one job, kept for the harness's own lanes and the janitor. Those jobs are its phase's job and the runs it waits on in its own scenario repository (`run.await`), which run in the same organisation, against the same limit. So a scenario's own runs are never starved by the phase jobs waiting on them.
  - **Repositories in an hour** (item 4). One run's repositories, its catalogue and its `infra` re-runs, fit item 4's limit.
  - **What a lower `max-parallel` costs.** With fewer entries at once than scenarios, a phase runs in waves. A job that `needs:` a matrix waits for all of its entries, so every repository waits for its phase's last wave, and its running time grows with the waves. E4 computes the longest running time at the chosen `max-parallel`. The janitor's cut-off follows it, as [§5.3](#53-the-janitor) defines it: that running time plus a margin for queueing.
  - **What an overlap still costs.** Two runs can still overlap: a nightly and a poll whose `plan` jobs read the runs in the same minute, before either has started, or a busy hour of the harness's own lanes. A run then queues. Queueing can push a `-job` past its mint's hour, or a repository past the janitor's cut-off, which deletes it mid-run. Either way the runner reports `infra`, never `pass`, so the gate stays safe. But a candidate's check run then completes `neutral`, and the poll's re-run spends one of its six runs ([§7](#7-triggers)). A dispatch started while another run is in flight stops at `plan`. E13 records how often an overlap still happens.
  - **The numbers, from E0** ([#968](https://github.com/yedeya-labs/kanon/issues/968)). Item 4 holds: 80 repositories were created in five minutes with no secondary limit, so 80 an hour is a lower bound, not the limit, and the harness's working value until E13 measures more. Item 5 fails: the free organisation ran at most 8 jobs at once, 7 steady, against GitHub's documented 20, with nothing else running and no cap in the probe. GitHub's documentation gives the free plan 20 and says its Support can raise limits; it says nothing of a lower limit for a new account. The likely cause, inferred and not measured, is the organisation's age: it was under three hours old (created 2026-10-16T18:04:53Z, per the organisation's API record; probe 5 ran at 20:41Z, [run](https://github.com/kanon-e2e/harness/actions/runs/38964079918)). So E4 makes the organisation's jobs-at-once limit a setting of the harness, not a constant, set from the measured value (6 for now, the lower end of 6 to 7), and sizes `max-parallel` and the janitor's cut-off from it as above. At that limit a run goes in waves, and is longer than the 3 hours 20 minutes it takes at full parallelism. **The arithmetic at that limit:** 6 less one is 5, and a scenario that awaits a run holds at least 2 jobs, so `max-parallel` comes to 2 (3 at 7). Had both runs been sized to overlap, half the limit would have left 1, a serial run, which is why they don't. A run's worst case is about the number of scenarios over `max-parallel`, times three 50-minute phases. E4 holds that a run at the chosen `max-parallel` ends inside the nightly interval, 24 hours since the nightly fires once a day, with the janitor's cut-off following it; once the catalogue grows past that, the Owner asks GitHub Support to raise the limit, or decides on a paid plan, before more scenarios turn `gate: true`. Probe 5 is re-run later, and the setting follows its answer.

**Why `register.write` and not `kanon apps --reuse`.** `--reuse` reads the App's key from a file, so the job that runs it would hold a key and run Kanon's CLI. So the register's rows are written without a key, and the secrets by `provision`'s `gh`. What this leaves untested end to end is `--reuse`'s key check, which its unit tests in Kanon keep.

### 5.3 The janitor

`e2e-janitor.yml` runs hourly and on dispatch, through its own pair ([§5.2](#52-the-jobs-and-which-secret-each-holds)). It lists the test organisation's repositories, and deletes each one that:
- carries the topic `kanon-e2e`, **and**
- was created more than its cut-off ago: a repository's longest running time plus a margin for queueing of about an hour and forty minutes. That is 5 hours at about 3 hours 20 minutes, and longer if E4's `max-parallel` makes the running time longer ([§5.2](#52-the-jobs-and-which-secret-each-holds), "One run at a time"). With the topic `kanon-e2e-failed`, the cut-off is that plus 24 hours (29 hours at 5), so a failed repository, marked at its run's end, is kept at least 24 hours (decision 13).

It never deletes a repository without the topic, and never the harness repository. It writes each deletion, and each repository it left, to its summary. A repository older than a day that it couldn't delete fails its run, so a leak is red within the hour rather than found later.

## 6. Two tiers

There is no stubbed tier (decision 6). Faking the model would need a switch in `agent-run` that adopters would carry, which the no-leak rule excludes. A model lane's wiring is proven only by the few real-model scenarios; the no-model scenarios cover everything else.

### 6.1 No model

The bulk, and every scenario of the gate's first version. Each scenario is a repository, a few `kanon` commands, a few events, and doctor's verdict. The catalogue's first scenarios are [§9](#9-the-first-scenarios)'s. The families grow to:
- **install:** one scenario per feature in `requirements.json`'s `features` (`review`, `build`, `full`), and one with the Python fixture as the starting tree. Each runs `kanon.init`, then an `act` segment that pushes its files and runs `repo.apply`, then `register.write`, `workflow.dispatch apps-check`, the second `repo.apply` for the `Lane check` rule, and `kanon.doctor`, then `expect.doctor` healthy;
- **doctor broken:** one scenario per finding category of `docs/doctor.md` (`pin`, `app`, `secret`, `declaration`, `caller`, `label`, `ruleset`, `id-token`, and `deploy` once plan 0010 ships it). Each starts from a clean install and breaks one thing: a secret deleted, a caller's grant narrowed, a label removed, or a ruleset rule switched off. It expects **exactly** that finding id, and no other blocking one;
- **upgrade,** from each of the last two stable releases: `kanon.at previous` installs, `kanon.doctor --to` lists, `pins.move` moves, the steps the findings name are committed, `repo.apply` does the GitHub settings they name, and `expect.doctor` is healthy at the release under test;
- **`lane-check`:** a pull request that changes a caller wrongly (an inexact pin, `secrets: inherit`) gets `Lane check` red, and a correct one gets it green;
- **gate refusals,** the lanes' own admission rules on real events:
  - a label applied by an identity outside the register starts nothing;
  - the Merger refuses a pull request with no verdict;
  - plan 0010's deploy gate refuses a release whose CI is red;
- **deploy:** the rehearsal ([§9](#9-the-first-scenarios)).

### 6.2 A real model, under $2

**The cap is the Owner's** (Owner decision 4): $2 for a run of the tier, nightly or on a candidate. How it holds (decision 7, changed):
1. **The lane's own ceiling bounds one run.** It is the hard bound per run, and it is $10 or more for every model lane ([§1](#1-today-measured)). No choice lowers it for the tests (the no-leak rule). A per-run hard cap comes only as the adopter feature [#891](https://github.com/yedeya-labs/kanon/issues/891) describes, judged on its own merit.
2. **The runner's ledger holds the $2 softly.** Before it starts a real-model scenario, the runner adds the scenario's expected cost to what this run's real-model scenarios have already spent.
   - The expected cost is the largest cost the scenario's last ten runs recorded, read from their result artifacts, times 1.5.
   - If the sum could pass $2, it refuses to start the scenario and reports `skipped: budget`.
   - Until a scenario has a recorded run, its first one is a dispatch the Owner starts, with nothing else running against the cap.
   - It is soft because a run that goes past its history can still spend up to its lane's ceiling, $30 for the Reviewer. The plan says so rather than calling it hard.
   - **Its dollars are the lanes' own cost reports:** the cost each run reports, which `--max-budget-usd` counts against too. On the subscription token they are Claude Code's reckoning of the run's cost, not a bill. The ledger and each lane's ceiling hold on them as they would on an API key ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 8).
3. **No dollar limit holds the month** (decision 16, changed 2026-10-16). The tier runs on the Owner's Claude subscription OAuth token, not on an API key, so there is no monthly spend limit to hold it. The hard monthly bound is the subscription's own usage limits: paid usage past them is off, so a run past them is refused, not billed ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 18, read 2026-10-17). The limits are shared: Kanon's own lanes already run on the Owner's subscription token, and the harness's own lanes will (decision 21), so the tier's runs and theirs draw on the same limits. A month in which one uses them up slows or stops the others until they reset. A leak of the token spends the Owner's subscription, not a spend-limited key ([§11](#11-the-threat-model-stated-plainly)).

**What the tier runs:** at most two scenarios a run (decision 15). It starts with the review lane on a one-line documentation pull request in a fresh install. Expectations are model-independent (decision 11):
- the run completed;
- a verdict of either kind was posted by the test Judge, read by its role marker;
- the run's telemetry artifact was uploaded (the lane records its row whether or not the repository sends it);
- the row's cost is under the lane's ceiling.

A run classified `unavailable` (the model was never reached, plan 0009 §2) is `infra`, which is retried, not failed.

**No telemetry is sent from a scenario** (decision 8, changed). The scenario repositories decline sharing and install no collector, so no test row reaches the hosted store. **The harness itself sends telemetry** (the Owner, 2026-10-17): it is a long-lived adopter whose own lanes do real work, so it opts in as any adopter does, `kanon init --telemetry --upstream-findings sent-with-evidence`, and its collector registers it on its first run (harness#11). It sends its upstream findings with their evidence too: what its Overseer and Explorer find about Kanon itself is the harness's purpose, and the repository is public, so the evidence holds nothing the scrub must hide that isn't public already. Its rows are Kanon's own, like Kanon's repository's, so **they must never count toward the three-adopter rule** ([`docs/telemetry.md`](../telemetry.md), `cross_adopter`): with Kanon and the harness, one real adopter would make a cell of three. So right after its first run registers it, the Owner sets its registration's own-figures label (`register.mjs set --repository kanon-e2e/harness --publish-own-figures-as <label>`), which leaves its rows out of every cross-adopter cell, as Kanon's own registration must be. The label also publishes the harness's own figures under it on the public metrics page, as one of Kanon's own projects ([`docs/metrics.md`](../metrics.md#the-public-metrics-page)); the harness declares them as `kanon-e2e-harness`. The other readers of the rule, #41's public signals and rises and the upgrade lag, leave out the same declaring keys, which the Owner's private job passes as the required `--own` ([`docs/telemetry.md`](../telemetry.md#kanons-own-bugs), [#1094](https://github.com/yedeya-labs/kanon/issues/1094)). The collector's end-to-end path stays covered by its own tests.

## 7. Triggers

| Trigger | Runs | Against |
|---|---|---|
| **A new candidate** (decision 19): the harness polls Kanon's public releases every 15 minutes. It runs for a `candidate-vX.Y.Z` pre-release whose commit has no `kanon-e2e` check run from the Reporter, or whose latest one completed `neutral` (not judged) more than an hour ago. **At most six runs for one candidate,** counted from the harness's artifacts named `e2e-candidate-<tag>`, one per run, which `plan` writes before anything else happens, whatever the run's outcome, check run or not. A check run `in_progress` means a run is in flight, and the poll leaves the candidate alone | every `none` scenario, and the real-model tier under its cap | the candidate: every scenario repository pins it, and every Kanon command runs at it |
| **Nightly** (decision 4, changed): scheduled once a night, and **held** unless Kanon's `main` head differs from the head the last nightly recorded, or no nightly has run in seven days | the same, against the latest candidate (or the latest stable release when no candidate is newer). Also the install and doctor families with the CLI at `main`'s head commit, pinning the release its `package.json` names. Those are `claude: none` scenarios, so unreleased Kanon code never runs in a repository that holds the real-model token | the seven-day floor catches the platform's drift in a quiet week |
| **Dispatch,** with a scenario id or a family, and a release | the named scenarios | the given release |
| A pull request, the merge queue, or a push to Kanon | **never** | — |

**Why two runs never overlap, by design.** Besides the guards below, a nightly gives way to a candidate's run in flight, the poll leaves a candidate alone while a nightly is in flight, and a dispatch stops at `plan` while either is ([§5.2](#52-the-jobs-and-which-secret-each-holds), "One run at a time").

**Why a run in flight is never doubled.** Every poll shares one concurrency group, so a poll that fires while a candidate's run is in flight waits for it (the newest waiting poll replacing an older one), and its `plan` then re-reads the check runs before anything else ([§5.2](#52-the-jobs-and-which-secret-each-holds)). The nightly has its own group, so a poll never cancels a due nightly. `start` posts the check run `in_progress` as the run's second job, so a dispatch sees the candidate as taken too, and its `plan` stops. `report` runs even on a red or cancelled run, so the check run never stays `in_progress`. A run whose `start` failed runs no scenario, and still counts toward the candidate's six runs, so a broken Reporter can't loop the catalogue.

**What re-runs a candidate.** A `success` or `failure` check run is final: a green candidate needs nothing, and a red one needs a fix and a new candidate (decisions 11 and 12). A `neutral` one (every failure `infra`, or the run broke before judging) is re-run by the poll, at most hourly, within the six runs a candidate gets; after that it waits for a dispatch, and the red issue says so. A dispatch can re-run any candidate.

**How "`main` changed" is read.** `plan` reads Kanon's `main` head through the public API, and the head the last completed nightly recorded in its result. A held night finishes `plan` and stops, at no cost beyond a minute of runner time.

**Why not `main` for the whole tier** (no third tag form, decision 4). A scenario repository can only pin a release: `lane-check` and doctor admit `vX.Y.Z` and `candidate-vX.Y.Z` and nothing else, and doctor stops with "nothing pins Kanon to an exact release" on any other ref. So `main`'s lanes can't run in a scenario repository until they are in a candidate. `main`'s CLI can. That is why the nightly runs it against the last release's requirements: it catches an `init` or doctor regression before the release pull request merges.

## 8. The release gate

**Owner decision 3:** no Kanon release ships unless the tier is green on its candidate. Under plan 0009, a release reaches adopters only by promotion: `vX.Y.Z` is tagged on the candidate's commit, and Dependabot proposes it. Until then the candidate reaches only Kanon's own pins and anyone who chooses to run ahead. So the gate sits where a candidate becomes a release anyone follows.

### 8.1 Where it hooks in

**Decided (decisions 1 and 2): a fifth promotion gate, and the pin job waits for green.**
- `scripts/promote.mjs` (plan 0009 S5) reads the gate. A red candidate stays a pre-release that is never promoted.
- The pin job (S4) opens `ci(deps): run Kanon on candidate vX.Y.Z` only once the gate is green, so the soak's 72 hours start on a candidate the gate passed.
- Kanon's repository gains only this step (the harness decision), in `promote.mjs` and the pin job.

**Before candidates exist** (decision 3): the tier runs ungated, nightly and by dispatch, against the latest release, until plan 0009's S3 to S5 exist. A release cut before E11 is not gated. The Owner chose this after seeing that holding every release would deadlock with the release hold on the telemetry store's token path: the deploy lane must itself ship in a release.

### 8.2 What the gate reads

`promote.mjs`'s fifth row, read from GitHub, never self-reported. Each condition below is needed:

| Gate | Holds when | Read from |
|---|---|---|
| **End to end** | <ol><li>The candidate's commit carries a completed check run named `kanon-e2e` whose App is the Reporter, by its App id, which Kanon records beside its other Apps. A check run of the same name from any other App or token is ignored.</li><li>The latest such check run concluded `success`.</li><li>The harness run it links (by its `external_id`) is a run of the harness repository's `e2e.yml`, on its default branch, whose **`verdict` job** concluded `success`, which it does only when the verdict was `pass` ([§5.2](#52-the-jobs-and-which-secret-each-holds)). The run's own conclusion is not read: a non-gating job can fail it while the verdict is green, and the gate and the check run must agree. Its recorded release is the candidate's tag and its commit.</li></ol> | `GET repos/yedeya-labs/kanon/commits/<sha>/check-runs?app_id=<the Reporter's id>`, and the linked run's jobs in the harness repository (public, read without a credential) |

**Why a check run, and why the cross-read** (decision 18):
- **A check run carries the App that made it, and nobody else can make one in its name.** A commit status's context can be posted by any token with Statuses (write), including Kanon's own workflow token, so a status would prove nothing about who posted it.
- **The cross-read means a leaked Reporter key can't promote a candidate alone.** A forged green check run fails condition 3 unless the harness repository also has a run for that candidate whose `verdict` job succeeded. A red verdict's job fails, so linking a real red run doesn't help a forger, and making a green run there needs write access to the harness.

**What `verdict` decides.** It passes when every scenario with `gate: true` is `pass` (there is no quarantine). Two cases need saying:
- **A gating scenario `skipped: budget` counts as missing,** and holds the gate. So the real-model scenarios start gating only once their measured cost fits two under $2 with the ledger's margin.
- **An earlier red run for the same candidate still holds the gate.** A green run doesn't clear it while an earlier run for that candidate failed with a `fail` (not `infra`) whose red issue is still open. A person closes that issue, with the cause, as plan 0009's fourth gate asks of an unexplained red. Until then `verdict` answers `fail`, so its job fails and the Reporter posts `failure`, whatever the latest run's scenarios did.

**The urgent path** (plan 0009 §7) skips the soak and the six-day spacing. **It doesn't skip this gate** (decision 12): an urgent fix is a candidate like any other. The no-model tier's duration on a candidate is not measured yet; E13 measures it.

### 8.3 A red gate: how it is reported, and the only way past it

- **One issue per candidate,** filed in the harness repository by `verdict`:
  - titled `e2e: candidate-vX.Y.Z is red`;
  - listing each failing scenario, its first false expectation, its kept repository's link (alive 24 hours) and the run.

  A later run of the same candidate edits it rather than filing another. A green run closes it only when every failure in it was `infra`; a `fail` needs a person to close it, with the cause.
- **The check run on Kanon's commit** links that issue, so a red gate is visible on the candidate's commit in Kanon.
- **`promote.yml`'s summary** names the gate, the check run and its issue whenever it holds a candidate.
- **The only way past a red gate is a fix and a new candidate** (decisions 11 and 12). There is no quarantine, no `override` input, and `urgent` doesn't skip it. A broken scenario is fixed in the harness repository, through its own review, and the Owner merges it there (decision 17). A re-run of the same candidate then reports again.

## 9. The first scenarios

In this order, each a step of [§14](#14-order-of-moves), so the harness proves itself on the scenario that needs it most:
1. **`deploy-rehearsal`: plan 0010's D12, automated.**
   - **Setup:** two declared environments, trivial hooks (a build that writes one file, a deploy and a smoke that check it), and no AWS. `release.cut` has the test Releaser publish the scenario repository's release, so the lane's trigger fires as it does for an adopter.
   - **Expected, as D12 states it:**
     - the run executes the gate, the probe, the build, both environments in order, and every `record` and `report` job;
     - the second environment waits for its reviewer;
     - the run lists the job names the reference deploy declares;
     - a failing smoke (a second release, with the smoke hook made to fail) files that environment's issue, and a third release that succeeds closes it;
     - doctor reports no `deploy.*` finding.
   - **The approval.** On every run, a candidate's included, the scenario waits until the second environment is `waiting`, then cancels the run and expects the job `cancelled`, as D0 measured. No person approves anything (decision 9, changed 2026-10-20). That the Owner can approve a release the test Releaser published, the path D0 could not measure, was measured once by probe 7.
2. **`install-review`, `install-build`, `install-full`:** `init`, then `repo.apply`, then doctor healthy, per feature. They need E1 released first: before it, `init` at a candidate writes `vX.Y.Z` pins, which don't exist yet.
3. **`upgrade-previous`:** install at the last stable release, with `repo.apply`, upgrade to the release under test, and doctor is healthy.
4. **`review-real`:** the first real-model scenario (decision 15). It joins the gate only after its burn-in, and only once the ledger's measured cost fits.
5. **`qa-store`:** the QA store, read through Kanon's lanes (decision 27, kanon-e2e/harness#67). It runs on every candidate, at the release under test, in the persistent fixture ([§5.1](#51-one-scenarios-life)). It installs the store hook, dispatches the dispatch sweep and an export, and expects the sweep's `cost-rows` to answer with no error and the export's manifest to read `store: present`. It reads fields only ([§4.3](#43-what-a-scenario-may-expect)) and runs no model, and joins the gate after its burn-in. An export comes from dispatching the Overseer or the code audit, and in both the agent's model job runs right after the `export` job, so the scenario cancels the run once `export` completes, as the deploy rehearsal cancels at production's wait. kanon-e2e/harness#120 designs how. The write path, `put`, runs only after a model run, so the harness's own code audit covers it weekly, and the long-lived upgrade signal (E14) gains a fourth question: is the harness's export `present`, and is its latest `put` green?

**D12 itself** stays plan 0010's, run by hand once, before the operator's repository adopts the lane (decision 15). Scenario 1 then re-runs it on every candidate, which D12 alone never would.

## 10. Flakiness

- **Every read after a write polls,** never sleeps. A step polls its predicate with a backoff from 2 to 30 seconds, until it holds or its deadline passes. GitHub's answers are eventually consistent: a new repository's installation, a ruleset's effect, a pull request's head (the release PR guard's own #86). A fixed sleep is either too short on a slow day or wasted on a fast one.
- **Retries only on infrastructure errors,** classified by the runner, never on an expectation. The errors it retries:
  - an HTTP 5xx;
  - a 403 or 429 with GitHub's rate-limit headers, after the wait they name;
  - a network error;
  - a repository name GitHub says exists (a re-run's leftover, renamed with the next attempt);
  - a model run classified `unavailable` (decision 11);
  - **a push event GitHub never delivered** (decision 26, 2026-10-22, kanon-e2e/harness#115). A step that waits on a push to the scenario repository's default branch (`release.cut`, and `run.await` on a `push` event) passes its deadline, and **no workflow run of any kind** exists for that commit's push. The step reads `infra`, naming the commit and that no push run was delivered, and the scenario is re-run whole, as below. If at least one push run exists for that commit, the passed deadline stays `fail`: a Kanon caller that ran and published nothing is a finding.

  Up to three times per call, with backoff. A false expectation is never retried: it is the finding. The undelivered push is read once, when the deadline passes, so it is not retried per call; it is retried by the scenario's re-run.
- **An `infra` scenario is re-run once,** whole, in a fresh repository, except `qa-store`, which re-runs in its fixture, reset to the starting tree ([§5.1](#51-one-scenarios-life)). If it is still `infra`, the gate can't claim green: the Reporter posts `neutral`, the gate holds the candidate and says why, and the poll re-runs it hourly, within the six runs a candidate gets, after which a dispatch does ([§7](#7-triggers)). It never counts as `pass`.
- **A deadline that passes is `fail`, not `infra`,** except where the push it waited on was never delivered (above). A lane that takes too long is a finding. Each deadline is set from E13's measured durations, at three times the slowest observed run.
- **Burn-in:** a new scenario joins the gate (`gate: true`) only after ten consecutive runs passed. A dispatched run counts like a scheduled one, as long as it ran the scenario against the latest release or a candidate (decision 24). The pull request that turns it on links them. Burn-in is how a scenario earns its place, before it can block anything.
- **No quarantine** (decision 11, changed). A gating scenario is never set aside: while it is broken, releases wait. The pressure goes where it belongs, on fixing the scenario or the product.
- **Measured, not assumed.** E13 records every scenario's pass rate, `infra` rate and duration over four weeks. A scenario under a 98% non-`infra` pass rate on unchanged code is a finding against the scenario.

## 11. The threat model, stated plainly

Almost everything with a credential now lives outside Kanon's repository, in the harness repository and the test organisation.

**Kanon's repository gains no secret,** and one installation: the Reporter, Checks (write) only (decision 18). Its key lives in the harness repository, so a leak of it can post check runs on Kanon's commits. The gate's cross-read ([§8.2](#82-what-the-gate-reads)) keeps such a check run from promoting a candidate on its own.

**What each credential can reach:**
- **One personal credential, the real-model token** (decision 16, changed 2026-10-16). The runner acts as the driver App, and the lanes in a scenario repository act as the test Apps. The real-model token is the Owner's Claude subscription OAuth token, the tier's only personal credential. No step acts on GitHub as the Owner or a maintainer. The Owner's only acts are the merges the escalation paths give the Owner (decision 17). Until 2026-10-20 they also included a click to approve a deployment on each candidate (decision 9, since changed).
- **The driver's key** is in the harness's `e2e` environment, read only by the pairs' `mint` jobs and by `provision`, which mints its own token and runs `gh` alone. **A minted token** reaches exactly one consuming job, through its pair's `secrets:`, masked, and that job revokes it when it ends. It never reaches a scenario repository: it is never written as a secret there, never passed to a workflow there, and no code from a scenario repository runs in a job that holds it.
- **The driver can reach only the test organisation,** because it is installed only there. A leaked driver token can create and delete throwaway repositories, and change the harness repository, but nothing of Kanon's or an adopter's.
- **The test Apps' keys** are in the `e2e` environment, read only by `provision`, and written as each scenario repository's own secrets. There the lanes' mint jobs read them as an adopter's do. They are deleted with the repository, except in the QA store's fixture, which outlives the run and keeps them between runs (below).

**What the driver token can do inside a scenario repository.** The real-model scenarios' repositories hold the Owner's subscription token as a secret. Code that can push a workflow there can make it read the token and send it anywhere. Two kinds of code run with a driver token, and they never share a job ([§5.2](#52-the-jobs-and-which-secret-each-holds), `K-AGENT-50`):
- **The harness's own runner and janitor,** in the `act` and janitor jobs, with Contents and Workflows write. They are on the harness's escalation paths as `always`, so the Owner merges every change to them (decision 17). The harness runs Kanon's full pipeline (decision 20), so agents propose, and the Owner decides.
- **Kanon's CLI and scripts, at the release under test,** in the `kanon` jobs. These are Kanon's code, merged under Kanon's own escalation paths, where `cli/` and most of `scripts/` are green ([§1](#1-today-measured)). A change the Merger lands there runs on the next candidate. Its token (decisions 22 and 23 (b)) is scoped to the one scenario repository and read-only, and no wider token is in its job. What it writes crosses to the `act` job only as data ([§5.2](#52-the-jobs-and-which-secret-each-holds)). **The residual risk, stated plainly:**
  - **Read access to that one repository,** while the code under test runs, and no write (decision 23 (b)). E0 measured Administration (write) without Workflows or Contents write ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 14). It couldn't write a workflow through the contents API, a push, a deploy key or a ruleset bypass, but two routes were open: it could make a login an admin collaborator, and it could switch the default branch to a branch holding a different workflow, which the `act` job's pushes can create. So the `kanon` job holds no write. **What this costs:** the tier no longer runs `init`'s own GitHub write calls. It runs `init`'s read and its naming of the steps its token can't do, and doctor checks what `repo.apply` set. `init`'s write calls stay covered by Kanon's unit tests and by every adopter's install. Doctor doesn't check the bucket milestones or the merge settings, so if `repo.apply`'s copy of those drifts from what `init` sets, the tier doesn't notice.
  - **What the CLI writes is pushed as written.** `init`'s job is to write the callers, and the `act` job pushes them. A malicious CLI could write a caller that reads the token, exactly as it could in any adopter's repository on that release. The harness adds no exposure an adopter on the candidate doesn't have, and `main`'s unreleased CLI runs only in `claude: none` scenarios, whose repositories hold no token ([§7](#7-triggers)).

  The model token is written by `model-key` before the first phase, so the CLI does run in a repository that holds it. That is why the narrowing matters, and why the draft's idea of writing the token after the last Kanon command is dropped: the job graph writes it first.

**The Owner's subscription token** (decision 16, changed 2026-10-16). The real-model token is the Owner's Claude subscription OAuth token, not a spend-limited API key. **A leak from a scenario repository gives whoever holds the token use of the Owner's subscription:** no dollar limit bounds what they spend; the subscription's own usage limits do, since paid usage past them is off ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 18, read 2026-10-17), so a leak costs the Owner's usage, not money. While it is used, Kanon's own lanes, the harness's lanes and the Owner's own use of the subscription draw on the same limits, and may stop until they reset. The ledger still holds $2 per run against honest runs; it doesn't bound a leaked token. What narrows the exposure:
- the token is held in one environment, `e2e-model`, which admits only the harness's `main`, and is read by one job, `e2e-model-key-job.yml`, whose steps the harness's workflow test fixes ([§5.2](#52-the-jobs-and-which-secret-each-holds));
- it is written only into the real-model scenarios' repositories, at most two a run (decision 15), and is deleted with them;
- on a suspected leak, the Owner revokes the token and makes a new one with `claude setup-token` ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 17). The revoke is claude.ai's **Settings → Claude Code → Authorization tokens**, which lists each token with its own revoke; a `setup-token` token shows the scope `user:inference` alone and its connection time, and nothing else names it. So the Owner notes when the harness's token is made, to find its row (measured 2026-10-17, [#968](https://github.com/yedeya-labs/kanon/issues/968)).

**Whether the subscription's terms allow this use in CI** is the Owner's to judge. Kanon's own lanes already run in CI on the Owner's subscription token, and the harness's own lanes will (decision 21); the tier adds one more such use. This plan makes no claim about the terms.

**The QA store's role** (decision 27, 2026-10-22). The test organisation holds no AWS credential: a store job assumes the role through OIDC, as an adopter's does. What the role trusts, and so what can reach the store, stated plainly:
- **Any job on the harness's `main` or the fixture's `main` that holds `id-token: write`,** not only the store jobs. The role trusts the default branch's ref, which names no job ([`docs/qa-store.md`](../qa-store.md#who-can-reach-the-store)). On the harness, `kanon doctor` lists every such holder, and the harness accepts each in its adoption record, as any adopter does.
- **Kanon's code under test, through the fixture.** The `qa-store` scenario pushes what `init` and the store hook write onto the fixture's `main`, as the `act` job pushes any `kanon` job's output ([§5.2](#52-the-jobs-and-which-secret-each-holds)). A malicious CLI at a candidate could write a workflow there that holds `id-token: write` and assumes the role. That is the same reach it has in any adopter's repository on that release.
- **What the role reaches** (`infra/qa-store/aws/template.yaml`): in the bucket, `s3:PutObject` and `s3:GetObject` on its objects and `s3:ListBucket` on the bucket itself; in the table, `dynamodb:PutItem`, `dynamodb:UpdateItem`, `dynamodb:GetItem` and `dynamodb:Query`, and `dynamodb:DeleteItem` held to the `COVERAGE` partition; and nothing else in the account. The stack sits in an account kept apart from Kanon's own store, so a misuse can read or spoil only the test organisation's QA data, never Kanon's or an adopter's.
- **The test Apps' keys in the fixture.** The fixture keeps the `qa-store` scenario's App secrets between runs, where a throwaway repository's die with it. A malicious CLI at a candidate, whose output the `act` job pushes onto the fixture's `main`, could write a workflow there that reads them. That is the reach it has in any scenario repository, and the keys reach only the test organisation, but the keys stay readable there between runs, where a throwaway repository's are gone when it is deleted, so the Owner rotates them if a candidate is ever found reading them.
- **No subject outside the two.** A pull request, another branch, a fork, an environment and any throwaway scenario repository are refused, as the trust table says.

**Public repositories.** A scenario repository's logs are public, as Kanon's are, and its secrets are not. A fork's pull request gets no secret (`K-AGENT-47`), and the lanes refuse a non-member's event, which the gate-refusal scenarios check.

**The harness's environments** each admit only the harness's default branch, so a branch's workflow can't read them. The harness's workflow test holds three things:
- each environment is named only by the jobs [§5.2](#52-the-jobs-and-which-secret-each-holds) lists;
- no `-job` workflow names a private key;
- no workflow runs on `pull_request`, `pull_request_target` or `merge_group` with a secret.

**This finding first came from the Lead's brief for #902,** where it was inferred, not verified. Moving the harness out of Kanon removed the parts about Kanon's own guard. What remains is where Kanon's code runs with a driver token, which decision 22 and the `kanon`/`act` split cover.

## 15. Cost

- **Actions minutes:** the harness and the scenario repositories are public, so their runs are free on the free plan (E0 measured it, [§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 6). The candidate poll runs 96 times a day for under a minute each, also free. Kanon's own new work is one more read in the daily `promote.yml`. Wall time is the real cost: a candidate's run is bounded by its longest scenario, the deploy rehearsal, which waits for CI, a reviewer and three releases. Not measured; E13 measures it.
- **The model** (decisions 4, 7 and 16):
  - **How many runs:** a nightly run happens only after `main` changed, or on the seventh quiet day. So a month has at most 31 nightly runs and as few as 4–5, plus one run per candidate, about 4–5 a month on the weekly cadence.
  - **Honest runs:** at $2 a run, that is at most about $72 a month, and as little as about $18 in a quiet month. These are the lanes' reported costs, not a bill: on the subscription token the tier adds no charge and uses the subscription's usage limits instead (decision 16, changed 2026-10-16): the subscription bills nothing past its limits, since paid usage past them is off ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 18, read 2026-10-17).
  - **The soft part:** a run that goes past its own history can spend up to its lane's ceiling ($30 for the Reviewer) before the ledger sees it.
  - **The hard bound** is the subscription's own usage limits: paid usage past them is off, so a run past them is refused, not billed ([§12](#12-what-is-not-confirmed-and-how-each-is-handled) item 18, read 2026-10-17). There is no monthly dollar limit. The tier's use comes out of the same limits Kanon's own lanes and the harness's own lanes use, so a heavy month for one slows or stops the others until the limits reset.
- **The QA store** (decision 27): a small on-demand table and a bucket in the Owner's AWS account, billed by AWS, not by GitHub. At the harness's volume, its own lanes' reports plus a `qa-store` scenario per candidate and nightly, it is in the range [`docs/qa-store.md`](../qa-store.md#cost-and-paging) gives for a store at the lanes' volume, well under $0.05 a month. The template creates nothing that bills while idle.
- **No stubbed tier and no recordings,** so neither costs anything (decision 6).
- **The harness's own lanes:** its full pipeline (decision 20) runs on the Owner's subscription token (decision 21), so its Implementer, Lead and review runs draw on the same subscription's usage limits as the e2e tier, but not on the tier's $2 ledger. Its releases cost nothing beyond the release workflow's minutes, free on a public repository.
- **The Owner's time:**
  - a merge for every change to the harness's runner (decision 17);
  - the first setup (E0).
- **Kanon's maintainers:** a release that changes a contract a scenario reads needs a harness pull request before its candidate can pass. That is the price of the gate having no quarantine (decision 11).

## Out of scope

- **Any test-only switch in Kanon's product:** a replay or stub mode, a test-only ceiling, a telemetry tag, a comment marker, a doctor waiver for tests (the no-leak rule).
- **A stubbed model tier** (decision 6).
- **Telemetry from scenario repositories** (decision 8).
- **A hard per-run cost cap for the tests.** It comes only as the adopter feature [#891](https://github.com/yedeya-labs/kanon/issues/891) describes, if it is judged worth it for adopters.
- **Per-pull-request end-to-end runs** ([§7](#7-triggers)).
- **Driving the adopt, doctor and upgrade skills through a model.** The scenarios drive their commands and the upgrade's edit. The skills' own conversations need a person, or a harness for Claude Code sessions, which is a plan of its own.
- **Private repositories and personal accounts.** The test organisation is an organisation with public repositories (Owner decision 1). So the fallbacks for a plan without rulesets or reviewers (`K-ADOPT-3`), and an adopter on a personal account (ADR 0013), stay with Kanon's unit tests.
- **Cloud credentials in the test organisation, and a deploy to a real cloud.** The harness holds no AWS credential of its own, and the deploy rehearsal's hooks are trivial, as D12's are. The QA store is in scope (decision 27): an AWS QA store stack, provisioned by the Owner with `infra/qa-store/aws/provision.mjs`, which trusts more than one repository since [#1339](https://github.com/yedeya-labs/kanon/issues/1339) (decision 28), whose role trusts exact default-branch subjects in the test organisation, and which a store job reaches by assuming that role through OIDC, as any adopter's does ([§3](#3-the-test-organisation-the-harness-repository-and-the-apps)).
- **Creating Apps through the manifest flow** (`kanon apps --apps`): it needs a person's click.
- **Load and scale testing** of the lanes.

### The decisions of 2026-10-22

26. **A push event GitHub never delivers is `infra`** (kanon-e2e/harness#115). When the runner merged a pull request and GitHub never delivered the push event, so that no workflow run of any kind exists for that commit's push, the step waiting on it reads `infra`: it is retried, and it never counts as a pass. If at least one push run exists for that commit, a passed deadline stays `fail`. The gating `deploy-rehearsal` read `fail` in the harness's nightly [39748361096](https://github.com/kanon-e2e/harness/actions/runs/39748361096) on `candidate-v0.42.0`: `release.cut` waited 15 minutes for a Release, and its merge commit had no push run at all, though every earlier merge in that repository had one. On a candidate's run, that turns the candidate red with no Kanon defect, and a person has to close the red issue ([§8.2](#82-what-the-gate-reads), [§8.3](#83-a-red-gate-how-it-is-reported-and-the-only-way-past-it)).
