## The plan in one paragraph

**Today.** Kanon governs how a change is written, reviewed and merged, and how a release is cut, then stops. Its rules already say how a release becomes a deploy (`K-SHIP-7` to `K-SHIP-10`), and each one is "enforced by a deploy workflow" that Kanon doesn't ship, so on every adopter those rules are prose. Kanon's own adoption record says so: "Deploy, production approval and announcement workflows (Kanon deploys nothing): not yet installed". Kanon's one deployed system, its telemetry stack, is deployed by hand by the Owner: render, package, deploy, read the outputs, deploy again with the verify switches, run `verify.mjs`, deploy again without them ([`docs/telemetry.md`](../telemetry.md), "Deploy" and "Verify").

**Where it ends.**
- **Two reusable workflows,** `deploy-release.yml` (the gate, the trust probe and the build) and `deploy.yml` (one environment), called from one caller in the adopter's repository. The lane runs **only on a published release whose commit is on the default branch and whose CI is green**, never on pull-request code, so a cloud credential exists only where reviewed code runs.
- **The adopter declares its environments,** as an ordered list in its adoption record: none, one, two or more (decision 2). **They form a straight line:** each environment deploys only after the one before it succeeded, on the same release. **The last one is production,** for the metrics and for a failure's severity; with one environment, that one is production. A pre-release runs the whole chain, as a stable release does (decision 4).
- **One build, one artifact.** A build job that holds no credential runs the adopter's build hook once, and every environment deploys that artifact (decision 8).
- **GitHub's OIDC token is the only cloud credential,** and each cloud role trusts its environment's subject, `…:environment:<name>`, which no other job in the repository can carry. The lane proves the binding on each run with a probe that expects a refusal, except under the `no-environments` fallback, where nothing can be proved and the probe is skipped (the probe decision).
- **One deploy per environment at a time, queued, never cancelled mid-run.**
- **The adopter keeps the command,** in three hooks at fixed paths, `.github/actions/build`, `.github/actions/deploy` and `.github/actions/smoke`, as it already keeps its toolchain in `.github/actions/project-setup`.
- **No model in the deploy path.** A failure is recorded as a `deploy` telemetry row and one deduplicated issue per environment, written by scripts. An opt-in, read-only diagnose lane, built with the deploy lane (decision 13), adds a diagnosis to that issue.
- **`kanon init`** writes the caller from the declared list, and **`kanon doctor`** checks the caller against the declaration, each environment, its protection, the subject form, the hooks, and the probe's last answer.
- **The hosted store dogfoods it, from the operator's repository:** that repository adopts the lane as any adopter does, and declares one environment, production (decision 14). Kanon's public repository gets no deploy job, and declares no environment. The operator's repository is private, and required reviewers aren't offered there on the organisation's plan, so its production deploy declares the `no-reviewers` fallback: the Owner starts each production deploy by dispatch ([§13](#13-the-fallback-where-the-plan-has-no-environments)). The Owner's remaining steps shrink to one-time setup, the register's data operations and that dispatch.

**How it gets there.** Probes in a sandbox first, because nine behaviours the lane rests on are not stated in GitHub's documentation; D0 measured them on 2026-10-14 ([#890](https://github.com/yedeya-labs/kanon/issues/890)) ([§14.2](#142-measured-in-d0-and-what-stays-unmeasured)). Then the rules, the declaration, the row, the lane, its build job, `init`'s caller, doctor and the diagnose lane, each with its tests and mutations; then the hosted store accepts the row and the metrics read it. The lane comes first, by the Owner's decision. Then a maintainer rehearses the released lane in the sandbox, with no AWS, and the operator's repository adopts it, through issues filed there, and its first deploy is plan 0008's token-path rollout. Until plan 0008's J9 that deploy still needs the private register, held as an environment secret and never in a tree ([§15.1](#151-the-register-and-the-first-lane-driven-deploy)).

## 3. The trigger

**The caller's triggers** (`K-LAYOUT-18`: the caller holds them; the lane names them):

```yaml
on:
  release:
    types: [published]
  workflow_dispatch:
    inputs:
      release: { type: string, required: true }   # an existing release's tag, to deploy again
```

**Every dispatch runs at its release's tag** ([the dispatch decision](#the-dispatch-ref), [#914](https://github.com/yedeya-labs/kanon/issues/914)): `gh workflow run deploy.yml --ref <tag> -f release=<tag>`. The gate refuses a dispatch whose `GITHUB_REF` isn't `refs/tags/<the release input>` (check 1), so no job of the lane carries the default branch's subject, `…:ref:refs/heads/<default>`, which an adopter's QA store and any other role trusting the default branch admit: every job carries the release tag's subject or its environment's.

**`published`, not `released`.** GitHub's events page says to "subscribe to `published` instead of `released` and `prereleased`" to catch both stable and pre-releases, and that `prereleased` doesn't fire for a pre-release published from a draft. A pre-release runs the whole chain, production included (decision 4): what reaches production is decided by its reviewer, not by the release's kind. For a `release` event, `GITHUB_SHA` is the "last commit in the tagged release" and `GITHUB_REF` is `refs/tags/<tag_name>`, so the lane's own workflow file is the caller **at the release's commit**, which is reviewed code.

**A release made with the workflow token deploys nothing.** GitHub: "With the exception of `workflow_dispatch` and `repository_dispatch`, other `GITHUB_TOKEN`-triggered events do not create workflow runs at all." `release.yml` creates the release with the Releaser's token when the caller maps it, and with the workflow token otherwise (`steps.releaser.outputs.token || github.token`), so **the deploy lane needs the Releaser** (decision 3). Doctor says so ([§12](#12-doctors-checks), `deploy.releaser-missing`).

**The gate job** runs first, in `deploy-release.yml`, holds no secret and no cloud credential (`contents: read`, `actions: read`, `deployments: read`), and runs `scripts/deploy-gate.mjs`. It refuses, by name, when any of these fails:

| # | Check | Refusal code |
|---|---|---|
| 1 | The release exists, is not a draft, and its tag resolves to `GITHUB_SHA` (for a dispatch: to the commit the `release` input's tag names, and the dispatch ran at that tag, `GITHUB_REF` = `refs/tags/<tag>`, [#914](https://github.com/yedeya-labs/kanon/issues/914)) | `draft`, `no-release` |
| 2 | That commit is reachable from the default branch: `git merge-base --is-ancestor <sha> origin/<default>` on a blobless fetch | `not-default-branch` |
| 3 | The environment list the caller passes is exactly the list the adoption record declares **at that commit**, in order ([§4](#4-environments-a-declared-chain-on-one-commit)) | `declaration-mismatch` |
| 4 | `ci.yml`'s `push` run on the default branch at that commit completed with every job `success` (`K-SHIP-8`); while it runs, the gate polls every 60 seconds, up to the CI wait the record declares at that commit, 90 minutes when it declares none (decision 9) | `ci-red`, `ci-timeout` |

Check 2 matters because a release can be published on any existing tag, and a tag can point anywhere. Plan 0008's J5 restricts who creates `v*` tags on Kanon; an adopter's tag form is its own (a component tag, `<component>-vX.Y.Z`), so the gate checks the commit, not the tag's name. Check 3 makes the declaration, not the caller, the source of truth: a caller edited by hand to skip an environment refuses on its first run, and doctor reports it before then ([§12](#12-doctors-checks)). Check 4 is `K-SHIP-8` turned into a mechanism: the release is cut by the same push whose CI is still running, so the gate waits rather than refusing a green run that hasn't finished. The CI wait is bounded at 360 minutes, a hosted job's limit ([§14.1](#141-confirmed)), since the gate polls inside one job.

**The supersede check runs in each environment's job,** not in the gate (it was the gate's check 4 in the draft). For a `release` trigger, the environment job refuses `superseded` when the commit is older than that environment's last successful deploy (the Deployments API's latest `success` status for the environment, compared by ancestry), so a queue that runs out of order ([§6](#6-concurrency)) never rolls an environment back unasked. It runs once the job holds its concurrency slot and its approval, which is the only point at which "the last success" can no longer change under it. A dispatch may roll back; its row says so ([§10](#10-the-deploy-row), decision 18).

## 4. Environments: a declared chain, on one commit

**The declaration** (decisions 2 and 9, open-question decision 1). The adoption record has a `## Deploy` section of its own. It holds the environments as an ordered list, the CI wait, the reference deploy's three bullets, moved there from `## Choices`, and the fallback's marker, each bullet in the one-code-span shape `scripts/lib/reference-deploy.mjs` reads today:

```markdown
## Deploy
- **Environments:** `staging`, `production`
- **CI wait:** `90`
- **Reference environment:** `staging`
- **Reference deploy workflow:** `deploy.yml`
- **Reference deploy job:** `staging / deploy`
- **Fallback:** `no-reviewers`
```

The CI wait is optional (90 minutes when absent). When a chain is declared, the reference environment is its first environment (open-question decision 6), which `init` writes; the record may name another declared environment on purpose. **The reference deploy stands on its own, as it does today** (`K-PROJ-11`, `K-LAYOUT-10`): an adopter that deploys with its own workflow and declares no Kanon chain keeps a `## Deploy` section holding only the three reference bullets, naming any workflow and job, and the reconciler reads it exactly as it reads the `## Choices` bullets now. The fallback's marker is present only where [§13](#13-the-fallback-where-the-plan-has-no-environments) applies, with one of two values: `no-environments` (the plan has no environments) or `no-reviewers` (environments, but no required reviewers). The record still states the fallback under `## Plan`, as `K-ADOPT-3` asks; the marker is what the lane and doctor read.

One parser, `scripts/lib/deploy-declaration.mjs`, reads the whole section, and every reader uses it: the gate (from the release's commit), `kanon init` (from the checkout), doctor, `lane-check`, and the reconciler, which reads the reference deploy through it instead of through `reference-deploy.mjs` (`K-PROJ-11`, from the default branch, as today). A list naming an environment twice, an empty code span, a wait outside 1 to 360 minutes, a reference environment that isn't in the list **when a list is present** (with no list, the reference names any environment, as today), the reference bullets not all three or none, a marker outside its two values, or a deploy bullet outside the section throws `DeclarationError` naming the file and the line. **The bullets move at once** (follow-up decision 1). The release that adds `## Deploy` reads the reference deploy from that section only, with no period of reading both places. The upgrade skill moves an adopter's bullets out of `## Choices`, and doctor reports any left there as a finding, `deploy.declaration-moved`, whose fix is that move. That check runs whether or not a chain is declared, since the adopter with its own deploy workflow and no chain is the one most likely to have the bullets to move. **No section, or no environment list, declares no environment** (decision 2, [§2](#2-what-kanon-owns-and-what-the-adopter-keeps)): no deploy lane at all. The record is directly inside `docs/qa/`, so a pull request that changes the chain escalates to a human (`K-MERGE-4`).

**The chain.** A straight line, no fan-out (decision 2): the environment at position *n* deploys only after the one at *n − 1* succeeded on the same release. **The last environment is production;** every other one is **pre-production**. With one environment, that one is production. The role is derived from the position by the lane, never passed in by the caller, so a caller can't relabel production. A fleet of production targets is the adopter's own policy ([ADR 0008 §4](../decisions/0008-installation-test-decisions.md)): its hook may fan out inside the last environment.

**The caller, written from the list.** `kanon init` writes `.github/workflows/deploy.yml` in the adopter's repository from the declaration (decision 2): one `release` job, then one job per environment, in order, each `uses:` Kanon's `deploy.yml` with that environment and its position, chained by `needs:`. For the declaration above:

```yaml
jobs:
  release:
    uses: yedeya-labs/kanon/.github/workflows/deploy-release.yml@vX.Y.Z
    with: { environments: 'staging production' }
  deploy-1:
    name: staging
    needs: release
    uses: yedeya-labs/kanon/.github/workflows/deploy.yml@vX.Y.Z
    with: { environment: staging, position: 1 }
  deploy-2:
    name: production
    needs: deploy-1
    uses: yedeya-labs/kanon/.github/workflows/deploy.yml@vX.Y.Z
    with: { environment: production, position: 2 }
```

Each job carries the called workflow's permissions, and the caller maps no secret: an environment secret resolves in the called job that sets `environment:` ([§7](#7-the-adopters-build-command-and-smoke-check)). Job keys are `deploy-<position>`, since an environment's name need not be a valid job key; `name:` carries the environment's name, so a run lists `staging / deploy` ([§14.2](#142-measured-in-d0-and-what-stays-unmeasured)). The list first reaches the record through the adopt skill's install question, answered as `kanon init --deploy-environments a,b`, which writes the `## Deploy` section and the caller together (open-question decision 2, [§17](#17-rules-and-docs-that-change)). When the list changes, the adopter edits the section and runs `kanon init` again, and the caller is rewritten; doctor reports a caller that no longer matches ([§12](#12-doctors-checks)), and the gate refuses it (check 3).

**`deploy.yml`, one environment.** Its first job, `declare`, holds `contents: read` alone and no credential, reads the declaration's fallback marker at the release's commit, and outputs it with `held`: true on a `release` run, under either marker, for the last environment, since under a fallback only the Maintainer's dispatch deploys it ([§13](#13-the-fallback-where-the-plan-has-no-environments), [#894](https://github.com/yedeya-labs/kanon/issues/894)). The hold lives in the lane, not in the caller, so the caller `init` writes is the same with or without a fallback. Its `deploy` job runs `if:` `held` is false, and sets `environment: ${{ inputs.environment }}`, or no environment when the declaration's fallback is `no-environments` ([§13](#13-the-fallback-where-the-plan-has-no-environments)), reads the declaration at the release's commit and fails `declaration-mismatch` unless the environment is at the given position (so the role it records is the declaration's), runs the supersede check ([§3](#3-the-trigger)), checks out `GITHUB_SHA` (with `persist-credentials: false`) for the hooks, downloads the build's artifact, runs the deploy hook, then the smoke hook. Its `record` and `report` jobs write that environment's row and its issue, unless `declare` held it ([§8](#8-after-a-deploy)).

**One build, one artifact** (decision 8). `deploy-release.yml`'s `build` job runs after the gate and the probe: when the gate succeeded and the probe either succeeded or was skipped under the `no-environments` marker, never after a failed or cancelled probe (its `if:` says so, since GitHub skips a job whose `needs` was skipped unless its `if:` lets it run). It holds no cloud credential, no `id-token`, no secret, and a `contents: read` token. It checks out `GITHUB_SHA`, runs `.github/actions/build`, which writes what the environments will deploy into `$RUNNER_TEMP/kanon-deploy-artifact/`, and uploads that directory once, as `kanon-deploy-build-<run id>-<attempt>`, with the SHA-256 of its archive as a job output. Every environment's job downloads that artifact and checks the digest before the deploy hook runs; a mismatch fails the job at the `build` stage. **Nothing is rebuilt per environment, and nothing is rebuilt from a different ref.** The build runs the adopter's own build tool, from the release's commit, with nothing to steal: splitting it from the deploy is what keeps the credential away from the build's dependencies.

**What the artifact must outlive.** A production job may wait up to 30 days for its reviewer ([§14.1](#141-confirmed)). The upload sets a retention of 35 days, the run's own limit; a repository whose artifact retention setting is shorter caps it, and doctor reports that as a note (`deploy.artifact-retention`). A deploy whose artifact has expired fails at the `build` stage, by name.

**A two-release flow fits without a special case.** Under channels like plan 0009's, a candidate is a pre-release and runs the whole chain (decision 4), production included, behind production's reviewer. Its promotion publishes a stable release **on the same commit**, which runs the chain again: a no-op for an unchanged stack (`aws cloudformation deploy` exits 0 on an empty change set by default, measured from CLI 2.36.8's help), recorded as a `redeploy`, which the metrics don't count as a change ([§11](#11-metrics)). **No environment is skipped** (open-question decision 5): the second run deploys every environment again, and production's reviewer is asked again. An approval is cheap next to a lane that decides on its own that a production deploy isn't needed.

**What GitHub gives the environments, as documented:**
- "All deployment protection rules must pass before a job referencing the environment is sent to a runner", and "a job cannot access environment secrets until one of the required reviewers approves it."
- Up to six required reviewers, of whom "only one … needs to approve"; an option to prevent self-review, which D0 measured against the run's actor ([#890](https://github.com/yedeya-labs/kanon/issues/890)): with it on, a maintainer can't approve any run their own token started, so neither a run they dispatched (decision 18's rollback included) **nor a release they published by hand**, since the `release` run's actor is the person who published it; only a release the Releaser App publishes is left for that maintainer to approve (not yet measured, [§14.2](#142-measured-in-d0-and-what-stays-unmeasured)). So for a project whose only reviewer is the person who dispatches or publishes, self-review prevention must stay off, or that person can neither deploy a release they published by hand nor roll back by dispatch (decision 18); a wait timer of 1 to 43,200 minutes; an option, on by default, to let administrators bypass the rules (Kanon's two environments both read `can_admins_bypass: true`).
- **Deployment branches and tags:** "No restriction", "Protected branches only", or "Selected branches and tags", with name patterns per branch or tag. The lane asks for selected refs on every declared environment: the release tags' pattern alone ([#923](https://github.com/yedeya-labs/kanon/issues/923)). No job of the lane runs at the default branch: a `release` run is at the tag, and a dispatch must be ([the dispatch decision](#the-dispatch-ref)). Admitting the default branch would let any job there that references the environment take its secrets and its role, for no lane's use.
- A job that references an environment "creates a deployment object", which is what the supersede check and doctor read.
- "A workflow may wait for up to 30 days on environment approvals", inside the 35-day limit on a whole run.

**Where the plan provides no environments, or no required reviewers,** see [§13](#13-the-fallback-where-the-plan-has-no-environments).

## 5. Credentials: OIDC bound to the environment

**The subject.** GitHub's OIDC reference: when a job references an environment, the subject is `repo:ORG-NAME/REPO-NAME:environment:ENVIRONMENT-NAME`, and "the environment specification takes precedence": the branch or tag is no longer in it. So a role whose trust condition is `StringEquals` on `token.actions.githubusercontent.com:sub` = `<prefix>:environment:<name>` and on `…:aud` = `sts.amazonaws.com` (AWS's GitHub example) can be assumed only by a job that references that environment, and that job runs only after its protection rules pass. Each declared environment has its own role, trusting its own subject. **Three consequences:**
- **No pull request can reach it:** a pull request's token says `:pull_request`, and the deployment branch policy refuses the ref anyway.
- **The deploy jobs can't reach the QA store or the telemetry writer,** whose roles trust the default branch's ref subject (`docs/qa-store.md`, `docs/telemetry.md`, "an environment replaces the ref in the token's subject"). The binding works both ways.
- **The reusable workflow sets the environment.** GitHub: "To use an environment secret in a reusable workflow, set `environment` on the job in the reusable workflow. The job that calls the reusable workflow can't use the `environment` keyword." The subject is still the caller's repository (plan 0008 §4.1: in a reusable workflow, `repository` and `ref` describe the caller); D0 measured that the environment is the called job's, and that it may come from an input: the `sub` is the caller's repository with the called job's environment, `job_workflow_ref` names the called workflow and `workflow_ref` the caller ([#890](https://github.com/yedeya-labs/kanon/issues/890)).

**The prefix** is what GitHub's API reports for the repository, classic or immutable, read by `scripts/lib/oidc-subject.mjs`, Kanon's one home for it (kanon#295). Kanon's own repository issues the immutable form ([§1](#1-today-measured)). GitHub's reference shows the immutable form only with a ref (`repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:…`); D0 measured its environment form as the same prefix with `:environment:<name>`, the ref gone, on a branch run and a tag run alike ([#890](https://github.com/yedeya-labs/kanon/issues/890)). A **custom subject template** (`use_default: false`) may leave the environment out of the subject entirely; doctor reports it ([§12](#12-doctors-checks)).

**AWS enforces part of this, and recommends the rest.** IAM's documentation: when GitHub's provider is the trusted principal, IAM rejects a trust policy whose `token.actions.githubusercontent.com:sub` condition is missing, null, or only a wildcard. It also says: "If you use GitHub environments in action workflows or in OIDC policies, we strongly recommend adding protection rules to the environment … Use deployment branches and tags to restrict which branches and tags can deploy to the environment." The lane is that recommendation as a mechanism.

**The trust probe** (decision 6). Kanon can't read an adopter's cloud trust policy, and doctor holds no cloud credential. So the lane proves the binding the only way GitHub allows: a `probe` job in `deploy-release.yml`, **without** an environment and with `id-token: write`, calls the deploy hook with `probe: 'true'` and the declared list, after the gate and before the build. The hook must try to obtain **each declared environment's** credential exactly as it would deploy, and **succeed only if every one is refused**. It prints one line for doctor, `kanon-deploy-probe/v1 {"staging":"refused","production":"refused"}` (one key per declared environment), as `apps-check` prints its line for doctor (`docs/doctor.md`, "A private App"). A credential obtained outside an environment fails the run before anything builds or deploys (`trust-unbound`).

**Where the probe finds each role** ([#862](https://github.com/yedeya-labs/kanon/issues/862)). The probe runs outside every environment, so an environment's own variables don't resolve in it: a role held only as an environment variable can't be found there. So every declared environment's role identifier must be readable outside its environment. **The adopter's hook decides where** (follow-up decision 2): Kanon requires only that each role is readable outside its environment, and its docs and the hook stubs suggest repository variables. A missing role still fails by name, through the hook's `unconfigured` answer. Holding it outside the environment doesn't weaken the binding: a role's ARN is an identifier, not a credential, and what refuses a job outside the environment is the role's trust condition on the token's `sub`, which no job can change. **Under the `no-environments` fallback the probe can't succeed:** every role trusts the release tags' subject ([§13](#13-the-fallback-where-the-plan-has-no-environments)), and the probe runs at a release tag with `id-token: write`, so it obtains every role and would fail `trust-unbound`. **So the lane skips the probe under that marker** (the probe decision), and doctor reports `deploy.trust-unproven` as a note naming the fallback, not a block: nothing outside an environment can be proved where no job is inside one, and the marker and doctor's note already state the weakness. **The hook must tell "refused" from "no role found".** For each environment it reports `refused`, `obtained` or `unconfigured`. Any answer but `refused` for every declared environment fails the probe: `obtained` as `trust-unbound`, `unconfigured` as `probe-unconfigured`, so a probe that tested nothing never reads as proof. The probe proves only that a job outside the environment is refused; that a job inside it is admitted is the deploy itself. **The probe's own subject is always a release tag's,** `…:ref:refs/tags/<tag>`: a `release` run is at the tag, and a dispatch must be ([§3](#3-the-trigger), [the dispatch decision](#the-dispatch-ref)), so the probe never carries the default branch's subject that an adopter's QA store trusts.

**The credential step is the deploy hook's first step, not the lane's.** On AWS it is `aws-actions/configure-aws-credentials` with the environment's role, which the hook reads from wherever it keeps it: since the probe must find the same role outside the environment (above), the docs suggest repository variables, which resolve in both jobs. That is how the operator's hook does it ([§15](#15-dogfood-the-hosted-store-deployed-from-the-operators-repository)). The lane names no cloud.

## 6. Concurrency

`deploy.yml`'s `deploy` job declares one group per environment (decision 2):

```yaml
concurrency:
  group: kanon-deploy-${{ github.repository }}-${{ inputs.environment }}
  cancel-in-progress: false
  queue: max
```

`deploy-release.yml`'s gate, probe and build hold no group: they deploy nothing, and two releases may build at once.

GitHub's documentation, read 2026-10-14:
- **By default a newer pending run cancels the pending one:** "By default, any existing `pending` job or workflow in the same concurrency group will be canceled and the new queued job or workflow will take its place." That is the default `queue: single`, "at most one … can be `pending`".
- **`queue: max`** keeps "up to 100 jobs or workflow runs" pending; "when the queue is full, any additional … are canceled", and it can't be combined with `cancel-in-progress: true`.
- **Order:** "first-in-first-out (FIFO) order according to the time each one started waiting", but "since the actual start time of a job or run may vary, ordering is not guaranteed." **That is why the supersede check exists** ([§3](#3-the-trigger)): a release-triggered run never deploys a commit older than the environment's last success.

`cancel-in-progress: false` means a running deploy is never cancelled by a newer one. A deploy cancelled by a person, or by the run's limits, is recorded as `cancelled` ([§10](#10-the-deploy-row)), never as "not red" (`K-SHIP-8`'s reason). **Not documented, measured in D0** ([#890](https://github.com/yedeya-labs/kanon/issues/890)): a job waiting for a reviewer **holds the group's slot**. While one run's production waited, a second run's production job stayed `pending`, not `waiting`, and moved to `waiting` only once the first was approved and finished. So a second release waits behind an unapproved first one, which the run's summary says. That is safe, since each queue holds one environment only. How `queue: max` orders two or more runs queued behind a waiting one was not measured; the supersede check covers any order ([§14.2](#142-measured-in-d0-and-what-stays-unmeasured)).

## 7. The adopter's build, command and smoke check

**Three hooks at fixed paths** (decisions 1 and 8), composite actions the adopter writes, like the project-setup hook (`docs/lanes.md`, "The project-setup hook"):

| Hook | Inputs, all strings | Runs in | Must |
|---|---|---|---|
| `.github/actions/build/action.yml` | `release` (the tag), `sha`, `output` (the directory to fill) | `deploy-release.yml`'s `build` job: no credential, no secret | Build what every environment will deploy from the checked-out commit, into `output`, and fail otherwise. It may run the project-setup hook first |
| `.github/actions/deploy/action.yml` | `environment` (a declared name), `role` (`production` or `pre-production`), `release`, `sha`, `artifact` (the downloaded build), `probe` (`'true'` or `'false'`), `environments` (the declared list, for the probe) | `deploy.yml`'s `deploy` job, and `deploy-release.yml`'s `probe` job | Obtain the environment's cloud credential and deploy `artifact`; with `probe: 'true'`, only try to obtain each listed environment's credential, from role identifiers it can read outside the environments, and report each as `refused`, `obtained` or `unconfigured` ([§5](#5-credentials-oidc-bound-to-the-environment)) |
| `.github/actions/smoke/action.yml` | `environment`, `role`, `release` | `deploy.yml`'s `deploy` job | Check the deployed system answers as the release expects, and fail otherwise |

**No outputs are read,** as for project-setup: the lane judges a hook only by whether it succeeded, and the build by the directory it filled. **What the hooks receive** (decision 7): the job's environment variables, from the environment and the repository (`vars`), as `env:`; and **exactly one secret, `KANON_DEPLOY_SECRET`**, an environment secret of any declared environment, which the lane passes as `env:` to the deploy hook's step alone, never to the build, the smoke hook, the probe or any other step, and which is empty when the environment holds none. It has to be the lane that passes it: GitHub doesn't give a composite action the `secrets` context, and an environment secret resolves only in the job that sets `environment:`, which is the lane's ([§5](#5-credentials-oidc-bound-to-the-environment)). OIDC needs no secret; the one slot exists for what a deploy can't get from its cloud role, such as the hosted store's register before plan 0008's J9 ([§15.1](#151-the-register-and-the-first-lane-driven-deploy), decision 16). A fixed name, never `toJSON(secrets)`, keeps doctor's stale-secret check working. GitHub masks a secret's value in the log; the hook must still write it nowhere but `$RUNNER_TEMP`.

**Why hooks and not the stack document.** The issue's sketch says "declared once in the stack declaration like the test runner". The test runner works there because ADR 0012 gives Kanon a closed table of runners and the command per runner; the stack document only names one of them (`- `tests/` `vitest` — tests: …`). A deploy has no such table: CDK, CloudFormation, Terraform and SAM each take a different set of arguments per stack, and a free command in a markdown file would be a setting that a script then executes. A hook is the adopter's code at a fixed path, reviewed like any other: every file under `.github/` is on the pipeline's escalation path (`K-MERGE-4`), so a change to the build or the deploy command always goes to a human (decision 1).

**K-AGENT-50.** The deploy job runs the adopter's code (the deploy hook, and whatever tool it calls) with a cloud credential. That is the one place a credential must meet code, and the build job exists so that the build's tools and dependencies don't (decision 8). What makes the meeting acceptable is the code: the release's commit, on the default branch (gate check 2), reviewed and green (check 4). `K-AGENT-50`'s guard already names jobs that run the default branch's reviewed code as outside the rule; `deploy-release.yml`'s `probe` and `build` and `deploy.yml`'s `deploy` join that list by shape, and the guard holds them to: no secret referenced but `KANON_DEPLOY_SECRET`, and that only in the deploy hook step's `env:` of `deploy.yml`'s `deploy` job (the probe and the build reference none), no App token, `contents: read` and no other write, `id-token: write` on `probe` and `deploy` alone, `persist-credentials: false`.

## 8. After a deploy

- **Every run writes its rows,** except for an environment `declare` held (below). Each `deploy.yml` call has a `record` job that runs `if: always()`, holds nothing but `actions: read`, reads its jobs' and steps' conclusions and the run's approvals, and uploads one `deploy` row for its environment as an artifact, `kanon-deploy-row-<run id>-<attempt>-<position>`, holding `kanon-deploy-row.json` ([§10](#10-the-deploy-row)). The name stays outside `kanon-telemetry-`, which the artifact-prefix guard of [#826](https://github.com/yedeya-labs/kanon/issues/826) keeps for the telemetry action's run rows. A run that stops before any environment (the gate, the probe or the build) never starts the environment calls, so `deploy-release.yml` has its own `record` job for that case, which writes **one row, for the first environment**, with that outcome and stage (open-question decision 4). One stopped release is not counted as N failures, and the metrics read deploy-stage rows only. The collector sends them, as it sends run rows (`K-OBS-13`).
- **A rejection is read from the approvals, not the job's conclusion** ([#890](https://github.com/yedeya-labs/kanon/issues/890)). A rejected environment job concludes a plain `failure`, with no steps and no log, exactly as a job that failed would read. So `record` reads `GET repos/{o}/{r}/actions/runs/{id}/approvals` and takes its environment's entry: `rejected` is refused, and records `outcome: rejected` at the `approval` stage; `approved` and `skipped` are admitted (an approval given with self-review unticked is listed as `skipped`). A waiting job whose run is cancelled concludes `cancelled`, and records `cancelled`. How a 30-day timeout reads is not measured ([§14.2](#142-measured-in-d0-and-what-stays-unmeasured)): until it is, a job that concluded `failure` with no steps and no `rejected` entry records `failed` at `approval`, never `ok`.
- **A held environment writes no row and files nothing** ([#894](https://github.com/yedeya-labs/kanon/issues/894)). When `declare` holds production on a `release` run under a fallback marker ([§13](#13-the-fallback-where-the-plan-has-no-environments)), its `deploy` job is skipped; `record` reads `held` and writes no row, and `report` neither files, comments nor closes. **Only a `declare` that succeeded with `held` true is a hold:** `record` and `report` read `declare`'s conclusion and output, never the `deploy` job's `skipped` conclusion, since a failed `declare` skips `deploy` too. A failed `declare` writes a row that isn't `ok`, and `report` files or comments as for any failure; which `failed_stage` that row records is [#886](https://github.com/yedeya-labs/kanon/issues/886)'s question. The run's summary says production waits for the Maintainer's dispatch. A held production is neither a deploy nor a failure, so it would only distort §11's production metrics, and an issue on every release would be opened and closed by routine. The Maintainer's dispatch then writes production's one row as usual.
- **A failure files one issue per environment** (decision 10), in a `report` job that runs `if: always()` once its environment's job ends, with `issues: write` on the workflow token, no checkout and no cloud credential. After a failure it files or updates that environment's issue; after a successful deploy it closes that environment's open issue, if there is one. One open issue per environment, found by a fixed title (`Deploy to <environment> failed`) and updated with a comment on each later failure, closed by the next successful deploy to that environment. Labelled `bug`, and `sev:high` for production (the last), `sev:medium` for every other environment. Its body holds the release, the stage that failed and the run's link, never a log line. A refusal files the same way, which is `K-SHIP-8`'s "announce a refusal"; a refusal or failure before any environment comments on the first environment's issue (open-question decision 4), `sev:medium`, or `sev:high` when the first is the only one.
- **No automatic rollback** (decision 10). A failed CloudFormation update already rolls back by itself, and its rollback triggers can watch alarms for up to 180 minutes after the resources deploy (AWS, "Roll back your CloudFormation stack on alarm breach"); that belongs in the adopter's stack. A rollback the lane would run is a second command, with its own failure. A person rolls back by dispatching the lane with an earlier release, which runs the whole chain with the same reviewers (decision 18).
- **The diagnose lane** reads the failure and adds to that issue, when the adopter opted in ([§9](#9-no-model-in-the-deploy-path)).
- **Announcement** (`K-SHIP-10`) stays out of this version ([Out of scope](#out-of-scope)).

## 9. No model in the deploy path

**Neither deploy workflow runs an agent:** no `agent-run`, no `claude-code-action`, no Claude credential, no App key. A guard test holds it (D4), because the deploy path is where an instruction hidden in a release note, a commit message or a log would meet a cloud credential.

**The diagnose lane is built with the deploy lane, opt-in, separate and read-only** (decision 13). `agent-deploy-diagnose.yml`, called on `workflow_run` of the deploy caller with `conclusion == failure`, runs as the Explorer App with `actions: read`, `contents: read` and `issues: write`, no `id-token`, no project-setup hook, and a shell allow-list that runs nothing from the tree, as the Lead's lanes do (`K-AGENT-50`'s last clause). It reads the failed run's log and the release's diff, and adds its diagnosis as a comment on the issue of each environment that failed in that run ([§8](#8-after-a-deploy)). It never deploys, re-runs or dispatches anything. `workflow_run` runs the default branch's copy of the diagnose caller and "is able to access secrets and write tokens, even if the previous workflow was not" (GitHub's events page), so it adds no new path for the release's code to reach a token. An adopter opts in by having `kanon init` write its caller, as for the other opt-in lanes; without that caller nothing runs and nothing is spent. A deploy log can hold resource names and account details, which the adoption record's `## Data` answer covers; the lane says so in its catalogue row.

## 10. The deploy row

A fourth row kind, `deploy`, version 1, in `actions/agent-telemetry/schema.mjs`, stored under `<key>#deploy`, a reserved partition like `work` and `finding` (decision 11). Every field is a number, a time, a boolean or a value from a closed list (ADR 0007, `K-OBS-16`):

| Field | Type | What |
|---|---|---|
| `schema_version`, `row_kind`, `tag`, `recorded_at` | as the run row | `row_kind: deploy` |
| `run_id`, `run_attempt` | as the run row | |
| `trigger` | `release` or `workflow_dispatch` | |
| `kanon_version` | as the run row | the lane's release |
| `role` | `production` or `pre-production` | the last environment of the declared chain is `production`, every other one `pre-production` (decision 11). Never the environment's name |
| `position` | count, from 1 | the environment's place in the chain |
| `outcome` | `ok`, `failed`, `smoke_failed`, `refused`, `rejected`, `cancelled` | `rejected`: a reviewer rejected, read from the run's approvals ([§8](#8-after-a-deploy)); an approval timeout too, once measured to read so |
| `failed_stage` | `gate`, `probe`, `build`, `approval`, `deploy`, `smoke` | absent when `ok`, present for every other outcome, so a stopped deploy always says where it stopped (§8's `record` rows carry "that outcome and stage"). A refusal records the stage that refused: `gate` for the gate's codes, `probe` for `trust-unbound` and `probe-unconfigured`, and `deploy` for `superseded`, which the environment's job checks after its approval and before the deploy hook, and for `not-maintainer`, the fallback's production dispatch by anyone but the Maintainer ([§13](#13-the-fallback-where-the-plan-has-no-environments)), which that job checks before the deploy hook. `build` covers the build hook, the upload, and an expired or mismatched artifact in the environment's job |
| `refusal` | the gate's codes (§3), `superseded`, `trust-unbound`, `probe-unconfigured` and `not-maintainer` (§13) | only with `refused` |
| `prerelease`, `redeploy`, `rollback` | boolean | `redeploy`: this commit already succeeded in this environment; `rollback`: older than the environment's last success (a dispatch only, §3) |
| `wait_ms` | count | from the run's start to the environment job's start: the gate, the build, the chain before it, the queue and the approval |
| `build_ms`, `deploy_ms`, `smoke_ms`, `duration_ms` | count | the build job (the same on every row of a run), the two hooks' steps, and the environment's job |
| `since_release_ms` | count | from the release's `published_at` to the end of this deploy: the release's lead time to this environment |

**Never in it:** the release's commit, the release's tag, the adopter's version, an environment's name, a URL, the reviewer, the role's ARN or any name from the cloud. (`tag` is the row's own `run`, `smoke` or `test`, and `kanon_version` is Kanon's release, as on the run row; neither is the adopter's. `role` is Kanon's closed word for the position, not a cloud role.) A release tag, a commit or an environment's name would let anyone who can read the adopter's public repository say whose row it is, which the opaque key exists to prevent. The schema test fails on any field outside this list, as it does for the other kinds. The rows are stored, and not published across adopters (decision 11).

## 11. Metrics

Plan 0003 measures cost, efficiency and escapes; it defines **no deploy metric** (measured: nothing in plan 0003 names deployment frequency or change-failure rate). The deploy rows add four, as views in `scripts/metrics/views.mjs` beside plan 0003's, computed from rows with `role: production` and `tag: run`, so on the last environment of each adopter's chain, whatever its length (decision 12):

| Metric | Formula |
|---|---|
| **Deployment frequency** | production rows with `outcome: ok`, `rollback: false` and `redeploy: false`, per week, as the median over the last 13 weeks |
| **Change-failure rate** | of production rows that reached the deploy stage (`ok`, `failed` at `deploy`, `smoke_failed`) and are neither a rollback nor a redeploy, the share that are `failed` or `smoke_failed`, or `ok` and followed by a `rollback` row before the next forward `ok` |
| **Time to restore** | from a production row that is `failed` at `deploy` or `smoke_failed` to the next `ok` production row, median |
| **Release lead time** | `since_release_ms` of forward `ok` production rows, median. It includes the time the release spent in the pre-production environments and waiting for production's reviewer |

**A change counts once, at its first production deploy** (the Owner's decision on [#895](https://github.com/yedeya-labs/kanon/issues/895)). A `rollback` row and a `redeploy` row are not changes: a rollback restores an older commit, and a redeploy puts a commit that already succeeded in production there again, whether a two-release flow's promotion ([§4](#4-environments-a-declared-chain-on-one-commit)) or a dispatch after an infrastructure fix. So, in each of the four views:

- **Deployment frequency:** neither counts.
- **Change-failure rate:** neither is in the share, as a change or as a failure. A redeploy's `ok` isn't a forward `ok`, so it doesn't end the look ahead: a change followed by its promotion and then a rollback counts as rolled back.
- **Time to restore:** both count. Their `ok` restores a failure, and their failure is one to restore.
- **Release lead time:** neither counts. Under a two-release flow the change's lead time is its pre-release's, from the pre-release's publication; the promotion's, from the stable release's, is left out.

Counted as changes, a two-release flow's promotions would double the frequency, halve the change-failure rate, and pool two lead times measured from two publications.

**What they can't see:** a production fault found days later and fixed forward, with no rollback and no failed smoke. Plan 0003's explicit reverts and linked fixes see some of those on the work-item side; joining the two would need a commit on the row, which [§10](#10-the-deploy-row) refuses. The views say so in their notes. Pre-production rows count in none of the four; a view of how often pre-production stops a release before production is a later choice, not this plan's. The hosted aggregate stores deploy rows from D9 and **publishes no cross-adopter deploy figure** until the Owner decides one (decision 11), under plan 0002's three-adopter rule.

## 12. Doctor's checks

In `cli/doctor.mjs`'s style: one id per finding, blocking or a note, a `fix` the person can run, `unchecked` with a reason when the token can't read it. **They run only when the adoption record declares at least one environment, or a deploy caller exists** (decision 2): an adopter with neither gets no `deploy.*` row but the three that concern the reference deploy (`deploy.declaration`, `deploy.declaration-moved`, `deploy.reference-undeclared`), which run for every adopter. `requirements.json` gains a `deploy` entry (the three hooks, the declaration, the caller's grants), built from the lane by `tests/unit/requirements.test.ts`, so doctor reads the release's own copy. "Production" below is the last declared environment.

| Id | Blocks | Holds when | Read from |
|---|---|---|---|
| `deploy.declaration` | yes | the record's `## Deploy` section parses: the environment list, the CI wait, the reference deploy and the fallback's marker ([§4](#4-environments-a-declared-chain-on-one-commit)) | `scripts/lib/deploy-declaration.mjs`, on the checkout |
| `deploy.declaration-moved` | yes | no reference-deploy bullet is left under `## Choices`; the `fix` moves it into `## Deploy`, as the upgrade skill does (follow-up decision 1) | the checkout |

## 13. The fallback where the plan has no environments

[ADR 0013](../decisions/0013-personal-accounts-and-two-apps.md): "nothing in Kanon may require" environments. GitHub's documentation: required reviewers and wait timers are "only available for public repositories" on Free, Pro and Team, and environments exist for private repositories only on Pro, Team and Enterprise. `K-ADOPT-3`'s fallback for production approval already exists: "a manually triggered workflow that only the Maintainer may run" (`K-SHIP-9`).

**The fallback** (decision 5), stated as weaker:
- **No environment exists** (the marker `no-environments`): `deploy.yml`'s one `deploy` job sets no environment, so the subject is the ref's. D0 measured that an empty `environment:` from an input leaves the job without an environment (`environment: null`), and GitHub creates none and doesn't fail ([§14.2](#142-measured-in-d0-and-what-stays-unmeasured), [#890](https://github.com/yedeya-labs/kanon/issues/890)), so one `deploy` job serves both forms. The roles trust the release tags' subject, `<prefix>:ref:refs/tags/<pattern>`, with `StringLike`. **No two environments of the chain can be told apart by the subject:** every one runs at a tag. So the last environment, production, runs only in a `workflow_dispatch` run at the release's tag (`--ref <tag>`, which every dispatch must be, [the dispatch decision](#the-dispatch-ref)), and its job refuses unless the Maintainer named in the adoption record started that attempt (`GITHUB_TRIGGERING_ACTOR`, else `GITHUB_ACTOR`, checked in `declare` and again in the `deploy` job, so a re-run by anyone else is refused too), with the refusal `not-maintainer` at stage `deploy` ([§10](#10-the-deploy-row)); a `release` run deploys the pre-production environments and stops before production. The stop is `deploy.yml`'s `declare` job holding production ([§4](#4-environments-a-declared-chain-on-one-commit)): its `deploy` job is skipped, no row is written and no issue is filed ([§8](#8-after-a-deploy)). A dispatch runs the whole chain (decision 18), so the Maintainer's dispatch deploys pre-production again (a no-op for an unchanged stack) and then production. With one declared environment, every deploy is the Maintainer's dispatch. That check is the lane's code at the release's commit, not the platform's. Since every dispatch runs at the release's tag, no `deploy` job under this marker carries the default branch's subject.
- **Environments exist but reviewers don't** (the marker `no-reviewers`; a private repository on Pro or Team): the environments and their subjects hold, and production's approval is the same Maintainer dispatch: a `release` run holds production in the same way, with no row and no issue. D0 confirmed the limit: required reviewers were offered on the sandbox only once it was made public ([#890](https://github.com/yedeya-labs/kanon/issues/890)). The hosted store's production is deployed this way ([§15](#15-dogfood-the-hosted-store-deployed-from-the-operators-repository), [the private repository's reviewers](#the-private-repositorys-reviewers)).
- **Doctor reports the fallback** as a note naming what is weaker: on the first form, any job running at a release tag with `id-token: write` can assume any environment's role, the trust probe among them, so the probe can't prove a binding there. **The lane skips the probe under `no-environments`,** and doctor's `deploy.trust-unproven` is a note naming the fallback (the probe decision, [§5](#5-credentials-oidc-bound-to-the-environment)). The adoption record states it under `## Plan`, as `K-ADOPT-3` asks, and marks it in `## Deploy` (open-question decision 1), which is how the lane and doctor learn it is in use. Under `no-environments`, `deploy.environment-missing` is a note, not a block ([§12](#12-doctors-checks)). **The tag path.** The lane's `github.actor` check runs only in the lane, while any workflow at a release tag reaches production's role (and, under `no-reviewers`, its environment secret). **Under `no-reviewers`, `deploy.tag-ruleset` blocks:** only a ruleset letting the Releaser and the Maintainer alone create, move or delete release tags closes that path. **Under `no-environments` it is a note** naming the path as weaker: that plan offers no rulesets (`K-ADOPT-3`), so the path stays open, and the note says so.

## 15. Dogfood: the hosted store, deployed from the operator's repository

**Where it lives** (the placement decision, [Owner decisions (2026-10-14)](#owner-decisions-2026-10-14)). Kanon's repository gets **no deploy caller, no deploy hooks, no declared environment and no AWS-credentialed job**. The operator's repository adopts the deploy lane as any adopter does: it pins a released Kanon, declares its environment, has `kanon init` write the caller, writes the three hooks, and holds the account's private inputs as its environment's secrets and variables. The hosted store is a service the operator runs, not part of what adopters pin. Its inputs never touch the public tree, and the lane is tested exactly as an adopter uses it, with no special case in Kanon.

**One environment, production** (decision 14). The operator's repository declares a chain of one: `production`, which is therefore the production role. There is no staging environment, no second AWS account and no second copy of the stack. The template names every resource and every IAM role, and IAM role names are unique per account, so a staging copy would have needed either a second account or a renamed stack; the Owner chose neither. What a staging copy would have caught is caught, instead, by the gate's green CI (the store's template and functions are tested in Kanon's CI before any release), by the build job, which assembles the function directory with no credential before production deploys, by the Owner's dispatch of each production deploy (the `no-reviewers` fallback, below), by CloudFormation's own rollback of a failed update, and by the smoke check right after. A one-environment chain is also the shape most small adopters will declare, so the dogfood tests it. So that the store's production is not the lane's first run, a maintainer first rehearses the released lane end to end in the D0 sandbox, with trivial hooks, a two-environment declaration and no AWS (open-question decision 7, D12).

### 15.1 The register, and the first lane-driven deploy

**Today's deployed stack** (as the Owner reported it on 2026-10-14) predates J2 to J4. It was last updated on 2026-10-12, has no `live` aliases and no `Audience` parameter, and has reserved concurrency 2 on the ingest function and none on the aggregate function. No Kanon release contains J2: no tag contains J2's commit (`4713555`), and the latest release, v0.39.0, predates J2, J3 and J4. So **the first release the operator's caller can pin carries J2, J3 and J4 together, and the first lane-driven deploy is plan 0008's token-path rollout:** the register table, J3's endpoints and J4's aggregate on the token, the aliases, the self-read role, `Audience`, `MinTokenVersion`, a fresh `CursorKey`, and reserved concurrency 2 on both functions (plan 0008 §9 steps 2 and 3a, and its decision 10). With one environment (decision 14), that deploy goes to production first time, on the Owner's dispatch (the `no-reviewers` fallback).

**Does the deploy still need register material once the table is imported?** Settled from the code and plan 0008: **yes until J9, no after it.**
- **Until J9 (vM+1),** `render.mjs` still renders each registered repository's writer, reader and aggregate-invoker roles, whose names carry the key (`kanon-telemetry-<key>-writer`). It also still writes `INVOKER_KEYS`, the one per-key environment value the aggregate function still reads after J4 (plan 0008, J4's status). The table doesn't feed the template: `register.mjs import` copies the file into the table, but `render.mjs` reads only the file. So every deploy from the first lane-driven one up to vM+1 needs the register file.
- **After J9,** `render.mjs`, `register.example.json`, the per-adopter roles and both functions' per-key environments are gone (plan 0008 §9 step 6). The template deploys with account-level parameters alone (`OwnerPrincipalArn`, `OperatorJobRoleArns`, `MinTokenVersion`, `ReservedConcurrency`, `CursorKey`), and none of them is register material. Plan 0008 §9 step 7 then deletes the file.

**Does it matter that the operator's repository runs Kanon's lanes?** Yes, for three reasons. Each is held by how the material is kept, not by the lanes being absent (decision 16):
- **The tree.** `docs/telemetry.md` ("Where the register lives") forbids tracking the register where lanes run, because the Reviewer reads the diff that adds it and every agent reads the checkout. The **environment secret `KANON_DEPLOY_SECRET` of `production`** ([§7](#7-the-adopters-build-command-and-smoke-check)) is in no tree and no diff, and never reaches the build job. The deploy hook writes it to `$RUNNER_TEMP`, outside the checkout, and deletes it in the same step.
- **Who can read the secret.** A repository secret reaches any workflow of a branch in the same repository, including one a pull request adds. An environment secret reaches only a job that references the environment, on a ref its deployment policy admits ([§4](#4-environments-a-declared-chain-on-one-commit)): the operator's release tags alone. **No reviewer stands in front of it:** the store's `production` declares the `no-reviewers` fallback ([the private repository's reviewers](#the-private-repositorys-reviewers)), so any job that references `production` on an admitted ref gets the secret and the deploy role with no approval. What holds production back is the lane's own code at the release's commit: a `release` run stops before production, and the production job refuses a dispatch from anyone but the Maintainer the record names ([§13](#13-the-fallback-where-the-plan-has-no-environments)). A job that references `production` on the default branch, or on any other branch, is refused by that policy: no lane needs a branch there, since every job of the lane runs at a release tag ([the dispatch decision](#the-dispatch-ref)), and nothing else of the operator's references `production` (the bootstrap stack is the Owner's own deploy, and the break-glass deploy is by hand). **The release tags are the one path:** a workflow on any branch's commit that references `production` and runs on `push: tags` gets `KANON_DEPLOY_SECRET` and the deploy role as soon as a release tag is created on that commit, and the lane's `held` and `github.actor` checks don't run there. Moving an existing release tag onto such a commit opens the same path. What closes it is **the operator's release-tag ruleset:** only the Releaser and the Maintainer may create, move or delete a tag matching the release pattern, which doctor's `deploy.tag-ruleset` blocks on under `no-reviewers` ([§12](#12-doctors-checks)). No agent job of Kanon's lanes references an environment, so none can read it.
- **The logs.** The operator's Explorer and Overseer, and the diagnose lane if the operator opts in, can read run logs with `actions: read`. So the hook prints no stack output (the outputs name `WriterRole<key>`). `render.mjs` already prints each entry by repository and never by key (kanon#628).

## 16. Security posture, stated plainly

- **Who can start a deploy:** whoever can publish a release (write access), and the Releaser. **What they can deploy:** a commit on the default branch with green CI, built once by a job with no credential. **Where:** each environment in the declared order, each only after the one before it succeeded; production, the last, only after its reviewer approves, or, under [§13](#13-the-fallback-where-the-plan-has-no-environments)'s fallback (the hosted store's case), only in the Maintainer's dispatch. A pre-release goes as far as a stable release (decision 4), so production's reviewer, or the Maintainer's dispatch under the fallback, is what stands between a candidate and production.
- **What the cloud credential can meet:** the deploy hook at the release's commit, the actions it calls, and the build's artifact. The build's own tools and dependencies run with no credential. The deploy job holds no App key, no App token, and a read-only workflow token. A compromised deploy command can damage the cloud account the role reaches; it can't push code, approve pull requests or move tags. A compromised build can put anything in the artifact, which the deploy then deploys: the build runs reviewed code from the release's commit, as the deploy does, and splitting them keeps the credential out of the build's reach, not the build's output out of the deploy's.
- **What a change to the deploy needs:** a human's approval of the pull request (every file under `.github/`, and the adoption record's declaration, escalate, `K-MERGE-4`), then a release, then, for production, a reviewer, or, under [§13](#13-the-fallback-where-the-plan-has-no-environments)'s fallback (the hosted store's case), the Maintainer's dispatch.
- **What is weaker, and where:** admin bypass is on by default (doctor's note); with self-review prevented, a maintainer can't approve a release they published by hand or a run they dispatched (D0), so a project whose only reviewer is that person keeps prevention off (`deploy.self-review`'s note); the fallback of [§13](#13-the-fallback-where-the-plan-has-no-environments) moves the split between environments from the platform into the lane's code under `no-environments`, and production's approval from the platform's reviewer into the lane's `github.actor` check under both markers, `no-reviewers` included, which is the hosted store's. That check covers only the lane's own workflow: under the fallback a release tag also admits any other workflow that references production (or, under `no-environments`, runs at a tag) to its role and secret. Under `no-reviewers` a ruleset restricting who may create, move or delete release tags guards that path, and `deploy.tag-ruleset` blocks without it ([§15.1](#151-the-register-and-the-first-lane-driven-deploy)); under `no-environments` the plan offers no rulesets, so the path stays open, which doctor's note names; the trust probe proves refusal outside each environment, not least privilege inside it; a pre-production environment with no reviewer deploys as soon as the one before it succeeds.

**Why this order.**
- **Probes first:** nine behaviours the lane rests on are not in GitHub's documentation, and two of them (the environment in a reusable workflow's subject, and an environment named by an input) decide whether the design holds at all.
- **The declaration before the lane and `init`,** because the gate, the environment job, `init` and doctor all read it, through one parser.
- **The row before the lane,** so the lane's first release already writes a valid row; **the store's intake before the release that writes it** (D9), as `docs/telemetry.md` requires of every row change.
- **The lane, its build, `init`'s caller, doctor and the diagnose lane in one release,** so the first adopter to declare an environment gets a caller written for it and is told what is missing before its first red run, and no release offers a lane that deploys without one build.
- **A rehearsal before the store's production** (open-question decision 7): with one environment, the store's first lane-driven deploy is a production deploy, so the lane's first end-to-end run is a sandbox's, at no cost and with no AWS.
- **The lane before the store's deploys** ([the order decision](#owner-decisions-2026-10-14)): the token-path rollout waits for the lane's release, and the operator's repository pins a release that carries both, so the store is first deployed by the lane exactly as an adopter's system would be.

## 19. Cost

- **Actions minutes:** a gate that polls CI for up to the declared wait (90 minutes by default) is the largest part; on a public repository the minutes are free, on a private one a release waits about as long as its CI, so the gate costs about one CI run's wall time in minutes. The build job costs one build per release, not one per environment. The deploy jobs cost what the adopter's command costs, once per declared environment. The build's artifact is kept up to 35 days, and counts toward a private repository's Actions storage.
- **The model:** one Explorer run per failed deploy run, for an adopter that opted into the diagnose lane (decision 13); nothing otherwise.
- **The hosted store:** no new running cost. It deploys to its one existing account (decision 14), so there is no staging account, no second copy of the store and no second budget alert. The bootstrap stack adds two IAM roles, which cost nothing, and an artifacts bucket holding a few templates and function packages, a few kilobytes to a few megabytes. **Not run against the price list;** it is in the cents a month at most by the shape of plan 0002's estimate. The diagnose lane's runs on the operator's repository, if it opts in, cost the Owner's model allowance per failed deploy.

## Out of scope

- **Announcing a deploy** (`K-SHIP-10`). `scripts/announce-deploy.mjs` exists, from the reference adopter; wiring it into the lane is a step of its own, after this one.
- **Fan-out between environments:** the chain is a straight line (decision 2). Many production targets are the adopter's hook's business inside the last environment ([ADR 0008 §4](../decisions/0008-installation-test-decisions.md)).
- **Clouds other than AWS** for the dogfood. The lane names no cloud; the hooks do.
- **An AWS-credentialed job in Kanon's repository** ([the placement decision](#owner-decisions-2026-10-14)).
- **Automatic rollback** by the lane ([§8](#8-after-a-deploy)).
- **A staging copy of the hosted store** (decision 14).
- **Publishing cross-adopter deploy figures** (decision 11).

Taken by the Owner on 2026-10-14. None is reopened here; the sections above state them.

### The order, and where the deploy lives

1. **The lane first** (the order decision). The deploy lane is built first, and then the telemetry stack's AWS deployments run through it, instead of the Owner deploying by hand. [§15.1](#151-the-register-and-the-first-lane-driven-deploy), [§18](#18-order-of-moves).
2. **The deploy lives in the operator's repository, not in Kanon's** (the placement decision). The operator's repository adopts Kanon's deploy lane like any adopter: it pins a released Kanon, declares the deploy command (rendering and deploying `infra/telemetry` at the pinned tag) and the smoke check, and holds the private inputs (the account, the owner role, register material) as its own environment secrets and variables. **Why:** the hosted store is a service the operator runs, not part of the framework adopters pin; its private inputs never touch the public tree; it tests the lane exactly as adopters will use it, with no Kanon special case; and Kanon's public repository gets no AWS-credentialed deploy job. The operator-side work is offloaded to the operator's repository as issues (D13). Two questions of the draft fall away with it: whether Kanon declares a reference environment for the store (Kanon has no deploy caller, so it declares none), and how Kanon's own production environment is protected (that environment is the operator's, and D13's issue sets it). [§15](#15-dogfood-the-hosted-store-deployed-from-the-operators-repository).
