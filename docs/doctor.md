# `kanon doctor`

`kanon doctor` says what a Kanon installation lacks, before a lane's first red run says it for you ([plan 0005](plans/0005-lean-installation.md) §5.5). Run it from your repository's checkout, through `npx` as the [install page](install.md) runs `kanon init`:

```bash
kanon doctor              # against the release your callers pin
kanon doctor --to v1.4.0  # before you merge the pin bump to v1.4.0 (or to a candidate, candidate-v1.4.0)
kanon doctor --json       # for a script or an agent
```

It reads the repository the way `kanon init` does, and compares it with the requirements file (`requirements.json`) that every release ships at its tag: the release your callers pin, or, with `--to`, the one you are moving to. It reads that file from Kanon's repository at the tag, so the release it checks against, pinned or `--to`, can be any from v0.28.0 on, the first that ships one.

**It writes nothing.** Every GitHub call it makes is a read, and it changes no file. `kanon init` fixes what can be fixed from the checkout; doctor says what is left, and how.

## What it checks

In the order it lists them, which is the order to fix them:

1. **The pin.** Every `yedeya-labs/kanon` reference under `.github/` names one exact release (`K-ADOPT-11`): a stable release, `vX.Y.Z`, or a candidate, `candidate-vX.Y.Z`, the same code before Kanon promotes it ([plan 0009](plans/0009-release-channels-and-api-key.md) §4). A candidate beside its own stable release is two releases (`pin.mixed`). A candidate pin is noted, without blocking, with Kanon's latest stable release beside it, read from `GET repos/yedeya-labs/kanon/releases/latest` (`pin.candidate`): running ahead of stable is allowed. Where the project declares the [kanon plugin](skills.md#declare-it-in-the-repository) in `.claude/settings.json`, also the plugin's: the `ref` of the marketplace whose source is Kanon's repository must be the release doctor checks against, because the skills run `kanon` from the release they ship in, and install that release (`plugin.version-mismatch`, [#376](https://github.com/yedeya-labs/kanon/issues/376)). It doesn't block, because no lane reads the plugin, and the two move at different times: the upgrade skill moves the `ref` with the pins, Dependabot moves the pins alone, and in Kanon's own repository release-please moves the `ref` ahead of them. A project that doesn't declare it gets a note; a settings file that isn't a JSON object makes the check `unchecked`.
2. **The Apps** the lanes you call run as, and the optional Releaser when your release caller maps its secrets, whether it reaches `release.yml` by Kanon's pin, `$/` or a local path ([#441](https://github.com/yedeya-labs/kanon/issues/441)): a register row for each of their roles, the roles of one App sharing one slug and no two Apps sharing one (`K-LAYOUT-6`, plan 0005 §3.4), and no `Other App` row, an App that isn't an agent, naming the slug of a role's row (`register.other-app-slug`, [#990](https://github.com/yedeya-labs/kanon/issues/990)), and each App's permissions at least the release's grant for it, read from `GET /apps/<slug>`, or, for a private App, from the latest `apps-check` run on the default branch ([below](#the-token-it-needs)). An App that holds more is listed, without blocking: each lane narrows its token to what it uses (`K-AGENT-46`). **`apps-check` still fails such an App,** because it requires the App's permissions to be exactly its own; the two differ on purpose (the Owner's decision 3 below).
   It also lists, without blocking, **an App left installed that no lane uses any more** (`app.unused`): one the App register's git history on the checkout once named, that its current copy doesn't, on a role's row or an `Other App` row, and that the owner still has an installation of, such as a per-role App left from before the two-App move (decided by the Owner, 2026-10-06). Delete it once the Apps that replaced it have run green for a week, and not while another repository's register still names it. If the token can't list the owner's installations, this check is `unchecked`, and says which token can.
3. **The secrets,** by name: each lane's, and each App's two (plan 0005 §3.5). **A secret of the checked release's that any workflow maps is needed too,** whatever its job calls: each of its Apps' two, the Releaser's when a release caller reaching `release.yml` by a local path or `$/` maps them, and a lane's ([#415](https://github.com/yedeya-labs/kanon/issues/415)). A missing one is `secret.missing`, naming the workflows that map it, and the callers of a lane that takes it but don't map it yet. For an App's secrets, its fix is two `kanon apps` lines, the person's to run ([#420](https://github.com/yedeya-labs/kanon/issues/420)): `--preflight` first, which checks the token and creates nothing, then the line that creates the App, or, when the register already names its slug, stores a new key for it, which the fix says is made under Credentials → Key pairs → New key on the App's settings page, with GitHub's page on it ([#637](https://github.com/yedeya-labs/kanon/issues/637)). When only the App's id is missing and the register names its slug, the fix is one `gh secret set <APP>_APP_ID -R <owner>/<repo> --body <id>` line instead: the id isn't secret, the line works at the Claude Code prompt with `!`, and it needs no new key. The id is filled in when GitHub shows the App; for a private App the line says to put in the App ID its settings page shows ([#625](https://github.com/yedeya-labs/kanon/issues/625)). A secret that isn't an App's is stored in the person's own terminal, or from a file, never with `!` at the Claude Code prompt, where `gh` reads no value and stores an empty secret without a word; the QA store's coordinates, which aren't secret, go on the line with `--body`. **Doctor reads only the names,** so it can't see an empty secret: for an App's, the `apps-check` run says so ([`docs/apps.md`](apps.md#checking-the-installations-later)). A secret that isn't Kanon's, or a per-role App's the checked release no longer has, is not doctor's to ask for. Nor is one a reusable workflow names only because its `on.workflow_call.secrets` declares it takes it, as a lane's own definition does: that reads what its caller passes, and the caller is what maps it. A per-role or retired App secret that nothing reads any more is listed as stale, without blocking (`secret.stale`). A secret counts as read when an App in use reads it, or when a workflow under `.github/workflows/` names it as `secrets.<NAME>` or `secrets['<NAME>']` anywhere outside its `on:`: in a job's `secrets:`, `env:`, `with:` or steps, or the workflow's own `env:`, whatever the job calls: a Kanon lane, the release workflow by its pin, a local path or `$/`, or nothing ([#414](https://github.com/yedeya-labs/kanon/issues/414)). A reusable workflow's own `on.workflow_call.secrets` declares what it takes and reads nothing. While a job passes on `secrets: inherit`, or a workflow can't be read, doctor can't tell what is read, so it lists no secret as stale and says why in a note. The same holds while a workflow reads secrets by a computed name or as a whole, such as `secrets[format('{0}_APP_ID', matrix.app.secret)]` or `toJSON(secrets)`, in an expression (`${{ }}` or an `if:`, never a script's own text), since that read can reach any secret ([#440](https://github.com/yedeya-labs/kanon/issues/440)). A workflow that runs only on `workflow_call` is the exception: its `secrets` holds only what its caller passes, which the caller names or inherits. Like the id-token holders, the workflows counted are the checkout's.
   **The Claude credential** ([plan 0009](plans/0009-release-channels-and-api-key.md) §11). A lane that runs a model takes one of a pair, `CLAUDE_CODE_OAUTH_TOKEN` (the subscription's token) or `ANTHROPIC_API_KEY` (an Anthropic API key), named by its `claude` field in `requirements.json`. Doctor reads the secrets' names and dates, never a value, and GitHub returns no value to read:
   - **The one a caller maps must be held** (`secret.missing`), and only that one: a repository on the key is never asked for the token. The fix names how to make it: `claude setup-token` for the token, with the line that switches every caller to a key (`kanon init --claude-auth api-key`), or the Claude Console, in a workspace for CI with a spend limit, for the key. Doctor lists the repository's own secrets, so an organisation secret shared with the repository isn't counted, and the message says so.
   - **One no workflow maps is stale** (`secret.stale`), such as the token after a move to the key. Its fix is the `gh secret delete` line, once the lanes have run green for a week on the one they map.
   - **The token's age** (`claude.token-age`). Where a workflow maps the token, doctor reads when its secret was last updated, from `gh secret list --json name,updatedAt`. Updated more than 335 days ago, it is a note: renew it before day 365. More than 365 days ago, it blocks: a subscription token lasts a year, and this one is at least that old. GitHub keeps the day a secret was last stored, not the day its token was made, so the token is at least that old, never younger. The year is [#579](https://github.com/yedeya-labs/kanon/issues/579)'s statement, not measured against a real token. A listing without the date makes the check `token-age` `unchecked`.
   - **Runs that never reached the model** (`claude.unreachable-runs`). For each caller that maps the token, doctor reads its last 20 runs (`gh run list`), and, for each failed one in the last 14 days, its failed jobs' annotations, looking for `agent-classify`'s notice, "the model was unreachable, not a failed run". GitHub stores its title as "the model was unreachable": the runner splits a workflow command's properties on every comma, and the title holds one, so doctor looks for the title as stored. At least two such runs is a note, naming them. A run can't tell its three causes apart: the subscription's usage limit, an Anthropic outage, or a configuration fault such as an expired token. So doctor names all three, never one, and says what the key option is. Each run counts once, however many of its jobs carry the notice. A caller with no runs yet counts none; a token that can't read the runs or the annotations makes the check `unreachable-runs` `unchecked` for that caller.
4. **The declarations** each lane reads (`K-LAYOUT-17`): a file that has no default must exist, and the stack document must hold `## Gates` exactly once. A missing playbook is Kanon's baseline, and is a note, not a finding (plan 0005 §5.2). Also the project-setup hook and every input the lanes pass it, the hooks only some lanes call, and the workflows a lane reads by file name (`ci.yml`). Where a workflow calls the Lead, the brief template it writes each brief from, `docs/projects/_template.md`, must exist; without it, `lead.template-missing`, which doesn't block (`K-LAYOUT-11`). One that differs from the checked release's [`rulebook/templates/brief.md`](../rulebook/templates/brief.md) is `lead.template-stale`, which doesn't block either: the adopter replaces the copy when Kanon's template changes, so after an upgrade that changes it, the Lead would write briefs from the old one while the brief guard holds them to the new release's rules ([#755](https://github.com/yedeya-labs/kanon/issues/755)). Line endings aside, the copy must be byte for byte the release's. Doctor reads the template from its own tree when it is that release, and otherwise from Kanon's repository at the tag; if it can't, the check is `brief-template` `unchecked`. An adoption record that says `Upstream findings: sent` or `sent with evidence` needs a workflow that calls Kanon's telemetry collector, which is the channel they travel over; without one it is `upstream.unsent` ([plan 0006](plans/0006-upstream-findings.md) §3.1). The reference deploy's three bullets (`K-PROJ-11`) are read from the record's `## Deploy` section alone, since [plan 0010](plans/0010-deployment-lane.md)'s D2; any left under `## Choices` is `deploy.declaration-moved`, for every repository, whether or not it declares a deploy chain.
5. **The callers:** each at its lane's file name (`K-LAYOUT-18`), mapping exactly the lane's secrets by name, passing only inputs the lane declares, granting at least the lane's permissions, and with the name or run-name a lane asks of its caller. A lane that runs a model takes one of a pair of Claude credentials, and its caller maps exactly one: both is `caller.claude-both`, neither `caller.claude-none`. The lane's first step, `agent-run`'s credential check, fails on either before the agent starts, and `lane-check` reports them from the release that adds its rule for the pair. Callers that map different credentials are allowed, and noted, naming which lanes run on which (`claude.mixed`). The review, implement-revise and merge-reconcile callers have fixed names too, and the two racers fixed job ids, which the merge gate tells their checks apart by: doctor reports them as `lane-check` does, without blocking against a release before 0.41.0 and blocking from it (`caller.name`, `caller.job-id`). The `apps-check` caller maps each App's secrets, and nothing its release doesn't take. A caller of Kanon's telemetry collector, which `kanon init --telemetry` writes, needs nothing beside it from the release that ships the token path ([plan 0008](plans/0008-self-service-registration.md) §8): its first run on the default branch registers the repository. So doctor reads the caller's last finished run on the default branch: none yet is `telemetry.not-run`; a run that skipped, green, because the release it calls doesn't publish the hosted store's URL is `telemetry.unpublished` ([#843](https://github.com/yedeya-labs/kanon/issues/843)); and a run that ended on the store's refusal, a 403, 410 or 429, which the collector says under the annotation title `telemetry-refused`, is `telemetry.refused`, with the run's own words; none of the three blocks. A caller that still passes the SigV4 path's `url:` or `writer-role:` without `audience:` is `telemetry.legacy-inputs`, which blocks: the collector refuses those inputs before it mints a token, so it sends and registers nothing (Owner decision of 2026-10-14, [#842](https://github.com/yedeya-labs/kanon/issues/842)); `lane-check` fails it on the pull request that moves the pin, from the release that adds its rule ([#845](https://github.com/yedeya-labs/kanon/issues/845)). Against an older release doctor asks nothing of the caller beyond its grant. The QA store's two secrets, `QA_STORE_ROLE_ARN` and `QA_STORE_BUCKET`, are the only secrets a caller may leave out: doctor asks for them only once the repository has a store hook, and lists a store-coupled caller that doesn't map them (`qa-store.unmapped`) and a repository that still holds them as variables (`qa-store.variables`), neither blocking. Since the release after v0.34.1 the lanes pass the hook no variables ([#479](https://github.com/yedeya-labs/kanon/issues/479)), so a store secret that only a variable holds is `secret.missing`, which blocks.
6. **The labels** of the taxonomy (`K-WORK-12`). A lane creates a label it needs on first use (plan 0005 §5.3), so a missing one doesn't block.
7. **The ruleset** on the default branch (`K-ADOPT-1` step 8), where the plan has rulesets. A private repository on a plan without them is a note: nothing on the platform enforces review there (`K-ADOPT-3`). **Before it asks you to require the status check `Lane check`, a job on the default branch must report it** ([#418](https://github.com/yedeya-labs/kanon/issues/418)): a job of a workflow that runs on `pull_request`, whose name, or its key when it has none, is exactly `Lane check`, and that neither calls a reusable workflow nor runs a matrix, since those report their checks under longer names. A step of another job reports nothing under that name. **The workflow must run on every pull request into the default branch** ([#446](https://github.com/yedeya-labs/kanon/issues/446)): GitHub never reports the check of a run its trigger skips, so a pull request it skips waits on a required check. A `paths` or `paths-ignore` filter skips some, and so does a `branches` filter that doesn't admit the default branch, a `branches-ignore` filter that matches it, and a `types` list without each of `opened`, `synchronize` and `reopened`. **Where a ruleset on the default branch has a merge queue, the workflow must run on `merge_group` too** ([#459](https://github.com/yedeya-labs/kanon/issues/459)): the queue waits for each required check on its own `merge_group` run, which a pull request's run doesn't count for, so a queued merge whose workflow has no `merge_group` trigger never gets the check. A `merge_group` trigger's `branches` or `branches-ignore` filter that skips the default branch, or a `types` list without `checks_requested`, skips it the same way. Doctor reads the default branch's workflows from GitHub, not from the checkout, because a job only a branch adds reports its check on that branch's pull request and on no other: a required check that nothing on the default branch reports blocks every other pull request, approved and green, until the branch merges. So when no job there reports it, doctor asks for the job first (`ruleset.check-unreported`), and for the rule (`ruleset.rule-missing`) only once the job is on the default branch; it reports a ruleset that already requires such a check too. If the token can't read the default branch's workflows, the check is `unchecked`, and doctor doesn't ask for the rule. Where your release caller maps the Releaser, also its bypass (`K-MERGE-8`, [#49](https://github.com/yedeya-labs/kanon/issues/49)): the Releaser App must be a bypass actor of each ruleset on the default branch, and the only one. Another actor's bypass, such as the admin role's, is asked off only against a release whose `dco` check passes the release PR the Releaser opens (its requirements file's `release.dcoExemptsReleaser`, [#337](https://github.com/yedeya-labs/kanon/issues/337)); against an earlier one it is a note, because that bypass is still what merges the release PR. GitHub shows a ruleset's bypass list only to someone who can edit it, so with another token this check is `unchecked`.
   **It says when bootstrap can end, and holds it ended** (`K-ADOPT-6`, [#706](https://github.com/yedeya-labs/kanon/issues/706)). Bootstrap ends when the Judge App is installed and the ruleset requires an approving review. Once the App register names the Judge App, a workflow on the default branch calls the review lane, so the Reviewer can approve there, and the ruleset still requires no approving review, doctor reports `ruleset.bootstrap-can-end`. Its fix is the command that requires one approving review, dismissed on a new commit (`K-MERGE-6`), sending the ruleset's rules as they are with the pull request rule's two settings changed, or the ruleset's page for an organisation's ruleset; then the end date in the adoption record, `ended YYYY-MM-DD` under `## Bootstrap` (`K-LAYOUT-10`). It waits for the review lane's caller to merge, as the required check waits for its job: an approval required before the Reviewer runs on the default branch is one nobody can give. A repository that stays in bootstrap on purpose waives it, with its reason. **Once the adoption record says `ended YYYY-MM-DD`, a ruleset that doesn't require an approving review is `ruleset.approval-off`**, whether the Judge App is still there or not, and on a plan without rulesets too: bootstrap never returns, so a lost approval is an incident to fix. It can't be waived.
8. **The id-token holders,** below.
9. **Chat notifications** ([plan 0011](plans/0011-notifications.md) §9, [`docs/notifications.md`](notifications.md)), only where a workflow calls a lane that notifies at the checked release: its requirements file's `notify` entry names the hook's path and inputs, the contract versions the release writes, each message kind's secret and the lanes that notify it (from their `notify` jobs), the one secret the kind secrets replace, `DIGEST_WEBHOOK`, and Kanon's two prebuilt hooks. A release without the entry, or whose lanes have no `notify` job yet, asks nothing here. Each finding sorts under its category above:
   - **No hook** at `.github/actions/notify/action.yml` is `notify.none`, a note: nothing posts, the digests' narratives are not written, and the project digest's health job still runs. Its fix writes Kanon's Slack hook or its generic webhook hook from the checked release, or names your own.
   - **A kind's secret not held** (`KANON_CHAT_PROJECT_DIGEST`, `KANON_CHAT_WEEKLY_DIGEST`, `KANON_CHAT_DEPLOY`) is `notify.kind-unset`, a note, once a hook exists: a kind not posted is a choice (decision 3). An organisation secret shared with the repository counts; on an organisation's repository doctor lists those (`GET /repos/<repo>/actions/organization-secrets`), and where the token can't, the check is `notify-secrets` in `unchecked`, never a finding. **No chat secret is ever `secret.missing`,** neither a kind's nor `DIGEST_WEBHOOK`.
   - **A notifying caller that still maps `DIGEST_WEBHOOK`,** which its lane no longer declares at the checked release, is `notify.legacy-secret`, which blocks, in place of `caller.secret-stale` for that one secret: GitHub refuses the call, so the lane doesn't start, health job included, until the line goes (the clean break, decisions 17 and 23). Its fix swaps the line for the kind's secret, stores the kind's secret, and adds a hook.
   - **The hook itself,** read from the checkout: a composite action declaring `secret` and `message-v<N>` for a version the release writes (`notify.hook-malformed`, blocking); one on an older version than the release's newest (`notify.hook-version-old`, a note); each `uses:` pinned to a version tag or a full commit SHA, and each `docker://` image to a digest (`notify.hook-unpinned`, blocking, `K-ADOPT-12`); every `uses: ./…` and every repository path a `run:` names, that exists in the checkout, under `.github/` or a `## Pipeline code` entry of `docs/qa/escalation-paths.md`, and no `run:` that installs packages (`npm ci`, `pip install`, `go mod download` and the like) (`notify.hook-unreviewed`, blocking). What doctor can't see stays the adopter's review's: a path built at run time, a file a reviewed script imports, code the hook downloads.
   - **A prebuilt hook pinned behind the callers** is `notify.hook-pin-behind`, a note, never blocking (decision 18): it works while it declares a version the callers' release still writes, and `kanon upgrade` moves it with them. **One pinned ahead of them** is `notify.hook-pin-ahead`, which blocks, as `lane-check` fails it: the hook's pin follows the callers', never leads it (`K-ADOPT-11`, [#958](https://github.com/yedeya-labs/kanon/issues/958)). A candidate counts as level with its stable release, as in `lane-check`. Its pin is not counted toward `pin.mixed`.
   - **The last post failed:** for each notifying caller, doctor reads the latest `notify` job that ran, on a completed run of the caller on the default branch from the repository itself, among its last 10 such runs, and the line the job prints, `kanon-notify/v1 {"hook":…,"kind":…,"outcome":…}`, as it reads `apps-check`'s. `failed` is `notify.failing`, a note. A token that can't list the runs or read the log makes the check `notify-runs` `unchecked`.

   Doctor says nothing of the branch exposure, the hook running on any branch's code (decision 22): [`docs/notifications.md`](notifications.md#security) states it.
10. **The deploy lane** ([plan 0010](plans/0010-deployment-lane.md) §12, [`docs/lanes.md`](lanes.md), "The deploy lane"). The adoption record's `## Deploy` section is read through the one parser every reader uses (`scripts/lib/deploy-declaration.mjs`), from the checkout. **Three checks concern the reference deploy and run for every repository:** a section that doesn't parse is `deploy.declaration`, which blocks; reference bullets left under `## Choices` are `deploy.declaration-moved` (above); and a record that declares no reference deploy, or, with a chain declared, names another job than the caller's for the reference environment, `<environment> / deploy` in `deploy.yml`, is `deploy.reference-undeclared`, a note: Kanon's own record gets it, since it deploys nothing, and a deliberate choice is kept with a waiver. **The rest run only where the record declares an environment or a deploy caller exists** (decision 2), and only against a release that ships the lane (its requirements file's `deploy` entry). "Production" is the last declared environment.
   - **The caller** (`deploy.caller-mismatch`, blocking, never waived): a `release` job calling `deploy-release.yml` with the declared list; then, per environment in order, a `deploy-<position>` job calling `deploy.yml` with that environment and position, passing `build: ${{ needs.release.outputs.build }}`, and needing the one before it and `release` (the first `release` alone); one release for every job, no other job, no second caller, and no caller at all when no environment is declared. A missing caller is reported too. Its fix is `kanon init`, which writes it from the list; `init`'s own caller gives no finding.
   - **The hooks** (`deploy.hook-missing`): `.github/actions/build`, `deploy` and `smoke` each have an `action.yml` declaring the inputs the lane passes. **The Releaser** (`deploy.releaser-missing`): the release caller maps its two secrets, since a release made with the workflow's token starts no run. **CI on push** (`deploy.ci-push-missing`): the default branch's `ci.yml` runs on `push` to it, which the gate waits for.
   - **The environments**, read from `GET repos/<repo>/environments`: each declared one exists (`deploy.environment-missing`, one finding per environment); production has a required reviewers rule (`deploy.reviewers-missing`), and each pre-production environment is named in a note, with whether it has one; every declared environment admits the release tags alone (`deploy.branch-policy`): "No restriction", "Protected branches only", or a selected rule of type `branch`, the default branch's included, from `GET repos/<repo>/environments/<name>/deployment-branch-policies`, is a finding ([#939](https://github.com/yedeya-labs/kanon/issues/939)), since no job of the lane runs at a branch. Production's reviewers rule without self-review prevention is `deploy.self-review`, never a block: with prevention on, a maintainer can't approve a run their own token started, a release they published by hand or any dispatch, so a project whose only reviewer is the one who publishes keeps it off. Production that lets administrators bypass its rules is `deploy.admin-bypass`, a note.
   - **The OIDC subject** (`deploy.subject-custom`, blocking): the repository's subject template, `GET repos/<repo>/actions/oidc/customization/sub`, is the default, or a custom one that keeps `context`, so each deploy job's subject names its environment.
   - **The trust probe** (`deploy.trust-unproven`). Doctor reads the `kanon-deploy-probe/v1 {…}` line the lane's `probe` job printed, from the latest completed run of the deploy caller that counts: this repository's own run, a `release` run or a `workflow_dispatch` run at a release's tag (the only ref the gate admits a dispatch at; one at the default branch never counts), whose commit is on the default branch (`GET repos/<repo>/compare/<sha>...<default branch>`), among its last 20 runs, and whose probe job ran. The line must list exactly the declared environments, each `refused`: an environment added since that run is unproven until the next. Before any such run it is a note; after one, a block.
   - **The artifact's retention** (`deploy.artifact-retention`, a note): at least 30 days, the longest an approval may wait, from `GET repos/<repo>/actions/permissions/artifact-and-log-retention`.
   - **The release tags' ruleset** (`deploy.tag-ruleset`): an active tag ruleset with the creation, update and deletion rules, so only those it lets bypass may create, move or delete a tag; one restricting creation alone doesn't pass.
   - **The fallback's marker** (plan 0010 §13) changes four of them, and says so in their messages: under `no-environments`, `deploy.environment-missing` and `deploy.trust-unproven` are notes (the lane skips the probe), and `deploy.tag-ruleset` stays a note naming the open tag path; under either marker, `deploy.reviewers-missing` is a note; under `no-reviewers`, `deploy.tag-ruleset` blocks, and can't be waived, since a release tag is then the one path to production's secret and role.
   - **Every job of the deploy caller at the pinned release is Kanon's** among the id-token holders (`kanon-lane`), as a store-coupled lane's caller is.

   A token that can't read the environments, a deployment-ref list, the subject template, the caller's runs, the retention or the rulesets makes that check `unchecked` (`deploy-environments`, `deploy-subject`, `deploy-runs`, `deploy-retention`, `deploy-rulesets`), never a finding.

Then it sets aside each finding the adoption record waives ([below](#waiving-a-finding)).

`lane-check` checks the callers too, on every pull request, against the release they pin. What doctor adds is the release you are about to pin, and what only GitHub knows: the secrets, the Apps' permissions, the labels and the ruleset.

## The token it needs

Doctor reads GitHub through `gh`, with `GH_TOKEN`, `GITHUB_TOKEN` or `gh`'s own login, in that order. A check its token can't run is listed under `unchecked`, with what would let it run, and the exit code is 4, never 0. A fine-grained token needs these permissions on the repository, a classic one the `repo` scope, and a workflow's token the same grants under `permissions:`, except where a row says only a classic token can ([what a fine-grained token can't read](#what-it-cant-read)):

| Check | What it reads | What the token needs |
|---|---|---|
| The pin, the declarations, the callers, the id-token holders | the checkout | nothing |
| The release's requirements, and Kanon's latest stable release | `requirements.json` in Kanon's public repository, at the tag, and `GET repos/yedeya-labs/kanon/releases/latest`, on every run, for `pin.candidate` and `releases.stable` | nothing beyond a login |
| `brief-template` | `rulebook/templates/brief.md` in Kanon's public repository, at the tag, only where a workflow calls the Lead and the checkout has `docs/projects/_template.md` | nothing beyond a login |
| The repository, the labels | the repository, its default branch, its labels and milestones | Metadata: read, Contents: read, Issues: read |
| `app-permissions` | `GET /apps/<slug>`; for a private App, the latest completed dispatched run of the `apps-check` caller on the default branch: its jobs and their logs | Actions: read |
| `secrets` | the secrets' names, never their values | Secrets: read (an admin's access, with a classic token) |
| `token-age` | when `CLAUDE_CODE_OAUTH_TOKEN`'s secret was last updated, from the same listing, never its value | Secrets: read, as `secrets` |
| `unreachable-runs` | each token caller's last 20 runs, and, for a failed one in the last 14 days, its jobs and their annotations | Actions: read, and Checks: read, which only a classic token (its `repo` scope) or a workflow's token holds: a fine-grained personal access token has no Checks permission, so with one, on a private repository, this check is `unchecked` whenever a token caller has a failed run in the window, whose failed jobs' annotations it reads |
| `telemetry-runs` | each telemetry collector caller's last finished run on the default branch, its jobs and their annotations | Actions: read, and Checks: read, which only a classic token (its `repo` scope) or a workflow's token holds: a fine-grained personal access token has no Checks permission, so with one, on a private repository, this check is `unchecked` once the caller has a finished run: it reads every job's annotations, whatever the run's conclusion, for the store's refusal |
| `notify-secrets` | the repository's secret names, as `secrets`, and, on an organisation's repository whose own secrets lack a kind's, the organisation secrets shared with it (`GET /repos/<repo>/actions/organization-secrets`), only where a workflow calls a notifying lane and a hook exists | Secrets: read |
| `notify-runs` | each notifying caller's last 10 completed runs on the default branch, their jobs, and the log of the latest `notify` job that ran | Actions: read |
| `ruleset` | the rulesets on the default branch | Metadata: read |
| `ruleset-bypass` | each ruleset's bypass list, and the Releaser's App id: from `GET /apps/<slug>`, or, for a private Releaser, from the owner's App installations | Administration: write: GitHub shows a bypass list only to someone who can edit the ruleset; for a private Releaser in an organisation, also the organisation's Administration permission (read) |
| `unused-apps` | the owner's App installations, only when the register's history names an App it no longer does | in an organisation, an owner's token with the organisation's Administration permission (read); a classic token's `admin:org` scope holds it too, but that scope is write, so prefer a fine-grained token |

**A private App** shows its permissions only to itself: `GET /apps/<slug>` answers 404 to a person's token and to a workflow's alike ([#417](https://github.com/yedeya-labs/kanon/issues/417)). The `apps-check` workflow reads each App's installation with the App's own key, and each App's job prints one line for doctor: `kanon-apps-check/v1`, then the App's key, the slug it minted and the installation's permissions as JSON. Not the App's id: `kanon apps` stores it as the `<APP>_APP_ID` secret, and the runner masks a secret's value in the log as `***`, so a line with it would not be JSON. Doctor reads that line from the latest completed run dispatched (`workflow_dispatch`) on the default branch, whose workflow is the reviewed one, and says in a note which run it read. A branch name alone doesn't hold that: a pull request from a fork's own `main` runs the fork's workflow under that name. Doctor therefore asks only for dispatched runs, which a fork can't start, and refuses a run from another repository or another event. So:

- **Run your `apps-check` caller after creating or changing an App** (`gh workflow run apps-check.yml -R <owner>/<repo>`), as [`docs/apps.md`](apps.md#checking-the-installations-later) already asks. A permission changed on an App's page since that run is not seen until it runs again.
- **It reads the permissions, not the verdict.** `apps-check` fails an App that holds more than its own permissions, and doctor still reads what that run found, so an extra permission stays a warning here (the Owner's decision 3 below).
- **`app-permissions` is `unchecked`** when there is no completed dispatched run on the default branch, when the run came from another repository or another event, when its job for the App printed no line (an `apps-check` from before #417 doesn't, nor one that couldn't mint the App's token), or when the run checked another slug than the register names now. The reason says to run `apps-check` again. A line the runner masked part of is `unchecked` too, and its reason says so; running again doesn't help there.
- **A private Releaser's bypass** needs the Releaser's id, which `apps-check` can't print and doctor never reads around the mask (`K-AGENT-47`). Doctor reads it from the Releaser's installation, in the owner's App installations, which only an owner of an organisation can list, with its Administration permission (read). With another token, or on a personal account, where GitHub lists installations only to a GitHub App's user token, `ruleset-bypass` is `unchecked` and its reason says why; on a personal account, look at the ruleset's bypass list yourself.

**The Apps left installed** (`unused-apps`) are the one check a repository's token can't run. Only an owner of an organisation can list its installations, so an owner runs doctor once with such a token, in their own terminal, after any move off an App. On a personal account, GitHub lists its installations only to a GitHub App's user token, which doctor doesn't use, so look on <https://github.com/settings/installations> yourself. The check runs only when the register's history names an App its current copy doesn't.

**A healthy Kanon reaches 0** with a token that holds every permission in the table: in Kanon's own repository, an owner's fine-grained token for the organisation, holding its Administration permission (read) as well, once `apps-check` has run on `main`. Kanon's repository is public, and GitHub answers a public repository's check runs to any token, so its fine-grained token reads the annotations it holds no Checks permission for. On a private repository with a telemetry caller, a fine-grained personal access token can't: `telemetry-runs` stays `unchecked`, and only a classic token (its `repo` scope) reaches 0 there ([below](#what-it-cant-read)).

### A person's fine-grained token

What a person's fine-grained personal access token needs on the repository, for each of the skills that drive `kanon` ([`docs/skills.md`](skills.md)), and what no such token can read ([#630](https://github.com/yedeya-labs/kanon/issues/630)). It is the token `gh` uses: `GH_TOKEN`, `GITHUB_TOKEN` or `gh`'s own login, in that order, so a `GH_TOKEN` left in the environment is the one that counts, and each skill names it, whose it is, and asks before it writes anything. A classic token holds all of it with the `repo` and `workflow` scopes. Metadata: read comes with every fine-grained token.

| Skill | What the token needs |
|---|---|
| `adopt`: `kanon init`, `kanon apps`, and the branch and pull request it opens | Metadata: read; Contents: read and write (the repository, its workflows, and the branch it pushes, when `git` pushes through `gh`'s credentials); Issues: read and write (the labels and the milestones); Pull requests: read and write (the pull request); Secrets: read and write (`init` lists them, and `kanon apps` and `gh secret set` write them); Variables: read (a QA store's coordinates); Administration: read and write (the merge settings, the ruleset, and the Releaser's bypass); Workflows: read and write (a branch that adds or changes `.github/workflows/`). In an organisation, the organisation's Administration permission (read) lets `init` find the Apps the owner already has (`ownerApps`); without it, `init` reads the other repositories' registers, with Contents: read on those. |
| `doctor`: `kanon doctor`, and the fixes it makes | To check, as the table above says: Metadata: read; Contents: read; Issues: read; Actions: read; Secrets: read; Variables: read (a QA store's coordinates left as variables, and the backlog feeder's valve: without it, doctor adds a note); Administration: read and write for `ruleset-bypass`, and the organisation's Administration permission (read) for `unused-apps` and a private Releaser. To fix, as `adopt` for what the fix writes: Contents and Workflows: read and write and Pull requests: read and write for the branch and its pull request, Issues: read and write for labels, Secrets: read and write for `gh secret set`, and Actions: read and write to dispatch `apps-check`. |
| `upgrade`: `kanon doctor --to`, the pin bump and its pull request | Metadata: read, and `doctor`'s, both to check and to fix; Contents and Workflows: read and write, since the bump changes `.github/workflows/`; Pull requests: read and write; Actions: read and write, to dispatch `apps-check` and to watch the runs after the merge (`gh run list`, `gh run view`); and Variables: read and write, for `qa-store.variables`' `gh variable delete` lines after the merge. Kanon's own releases and documents are public, so reading them needs nothing more. |

#### What it can't read

GitHub gives a fine-grained personal access token no Checks permission. On a public repository that costs nothing, since GitHub answers a public repository's check runs to any token, but on a private one such a token can't read them at all ([#630](https://github.com/yedeya-labs/kanon/issues/630)'s install was on a private repository):

- **Check runs, on a private repository.** `gh pr checks` and `gh pr view --json statusCheckRollup` fail with "Resource not accessible by personal access token". Read a pull request's runs through Actions instead, with Actions: read: its head from `gh pr view <number> --json headRefOid`, its runs from `gh run list --commit <sha>`, and a run's jobs from `gh run view <id>`. A skill never sends the person to `gh pr checks`; a person who wants it uses a classic token.
- **A run's annotations, on a private repository,** which are check runs. `unreachable-runs` reads them for a token caller's failed runs, so with such a token it is `unchecked` whenever there is one in the window. `telemetry-runs` reads them for every job of each telemetry caller's last finished run, whatever its conclusion, so with such a token it is `unchecked` on every run once the caller has run, and doctor can't reach 0. A classic token (its `repo` scope) runs both.
- **A private App's own page** (`GET /apps/<slug>`) answers 404 to any person's token, so doctor reads `apps-check`'s run instead (above).
- **A personal account's App installations,** which GitHub lists only to a GitHub App's user token: `unused-apps` and a private Releaser's bypass are `unchecked` there, whatever the token.

## The id-token holders

The QA store's role and the telemetry writer trust the default branch's ref, not an environment ([`docs/qa-store.md`](qa-store.md#who-can-reach-the-store), [`docs/telemetry.md`](telemetry.md#who-can-write)), so **every job on your default branch that holds `id-token: write` can assume them**, including your own jobs that hold it for another cloud. Kanon's guard holds Kanon's own workflows; yours are yours to check, and doctor lists them, counted as the guard counts them: a job's own grant, the workflow's when the job declares none, `permissions: write-all` at either level, and a job that calls a reusable workflow with such a grant.

- **A caller of one of Kanon's store-coupled lanes at the pinned release** is listed as Kanon's, and accepted: the grant reaches only the lane's store jobs and, in the Overseer, its `telemetry` job, each of which Kanon's guard holds. So is **a caller of Kanon's telemetry collector at the pinned release** (`kanon init --telemetry` writes one), whose one job that holds the grant the same guard holds; both are `kanon-lane` in `.idTokenHolders[].status`.
- **Any other holder** blocks until you either narrow its grant, or accept it under `## Choices` in the adoption record (`K-LAYOUT-10`), one bullet per job, naming the workflow file and the job's key, with the reason it holds the grant:

  ```markdown
  - **Accepted id-token holder:** `deploy.yml` job `deploy` (assumes the production deploy role)
  ```

  An acceptance in another shape, outside `## Choices` or written twice is malformed and blocks. One whose job no longer holds the grant is listed as stale, without blocking.

`kanon init` names the same jobs, with this check, before an install writes anything, and writes the acceptance the person gives with `--accept-id-token-holder` ([`docs/init.md`](init.md#existing-id-token-holders), [#631](https://github.com/yedeya-labs/kanon/issues/631)), so the adopt skill asks about each at its telemetry question, and doctor finds it already accepted.

Doctor counts the workflows of the checkout it runs from. Run it on your default branch for the count the roles see; it says so when you don't.

## Waiving a finding

Some findings your repository has decided to keep. A caller whose lane's file name is already taken by another workflow can't be renamed onto it, say: `git mv` would refuse, and forcing it would destroy that workflow. **Doctor knows no repository's special case.** Instead, any repository waives a finding it keeps, under `## Choices` in the adoption record (`K-LAYOUT-10`), one bullet per finding: the bold label, the finding's id as one code span, `on`, its subject as one code span, exactly as doctor reports it in `.findings[].subject`, and then in parentheses why the finding stands, on one line:

```markdown
- **Waived doctor finding:** `caller.misplaced` on `.github/workflows/review.yml` (agent-review.yml is the lane's own definition in this repository)
```

- **A waived finding doesn't count.** It moves from `findings` to `waived`, with the bullet's reason, so it no longer sets the exit code, and it stays in the document for whoever reads it.
- **A waiver is narrow.** It waives one finding id on one subject; nothing waives an id everywhere, or every finding on a subject. Where doctor reports more than one finding of an id on one subject, such as each missing secret on the repository, a waiver of a finding that lists items covers each of them for the items it names (the next bullet), and any other waiver covers each of them; `waived` lists each.
- **A waiver of a finding that lists items names them** ([#406](https://github.com/yedeya-labs/kanon/issues/406)). Some findings list several items in one message, and a later release can add one: a permission an App needs, a secret a lane takes. So a waiver of one of these names, after `for`, each item it waives, as one code span each, separated by commas, exactly as the finding's message names them:

  ```markdown
  - **Waived doctor finding:** `secret.missing` on `acme/widgets` for `CLAUDE_CODE_OAUTH_TOKEN` (the lanes run on the organisation's token, an organisation secret doctor doesn't list)
  ```

  Doctor waives only those. Any other item the finding lists, today or after an upgrade, stays a finding, written for those items alone, and says which bullet waives which items; `waived` lists the finding for the items each bullet names, in `.waived[].items`, with the bullet's line, `.waived[].line`. **Several bullets may waive items of one finding,** each with its own reason, but no item twice: a bullet naming an item another bullet of that finding names is malformed. An item a bullet names that doctor no longer reports makes the waiver stale. **A bullet of one of these findings that names no items is malformed** (the Owner, 2026-10-07), and waives nothing, because it would also waive whatever a later release adds: its fix is the bullet to write instead, naming the items doctor reports today, with the same reason. Before #406 such a bullet waived the whole finding; rewrite it as its fix says, keeping only the items the repository keeps. The ids, and what an item of each is:

  | Id | An item |
  |---|---|
  | `register.missing-row` | a role whose row is missing |
  | `register.split-slug` | an App whose roles name more than one slug |
  | `app.permission-missing`, `app.permission-extra` | a permission, such as `contents` |
  | `secret.missing`, `secret.stale` | a secret's name |
  | `declaration.section-missing` | a heading, such as `## Gates` |
  | `hook.input-missing` | an input |
  | `caller.secret-missing`, `caller.secret-stale` | a secret's name |
  | `caller.input-stale` | an input |
  | `caller.grant-missing` | a permission |
  | `apps-check.secret-missing`, `apps-check.secret-stale` | a secret's name |
  | `label.missing` | a label |
  | `qa-store.unmapped` | a secret |
  | `qa-store.variables` | a variable |

- **A waiver that matches nothing is listed as stale** (`waiver.stale`), without blocking, so a waiver doesn't outlive its finding. When the check that would report its finding couldn't run, doctor can't tell, and says so in a note instead.
- **A waiver in another shape is malformed, and blocks** (`declaration.malformed`): outside `## Choices`, with nothing in its parentheses, naming an id doctor doesn't report, naming no items of a finding that lists them, naming items of a finding that lists none, waiving one finding twice, or one item of it twice, or waiving a finding that can't be waived.
- **The person decides.** A waiver is a decision the rulebook gives to the project, in a file on its escalation path (`K-MERGE-4`). An agent may propose one; the person writes it, or accepts it with its reason.

An accepted id-token holder is this waiver's own form for `id-token.unaccepted`: the same `## Choices`, one bullet per job, a reason, malformed and stale alike. It keeps its own shape because doctor lists every holder with its status (`.idTokenHolders[].status`), and the acceptance is what makes one `accepted`.

### An App that holds more than Kanon grants

A repository whose App needs a permission beyond Kanon's shared grant declares it under `## Choices` in the adoption record (`K-LAYOUT-10`, `K-AGENT-3`), one bullet per App and permission: the bold label, the App's key (`author`, `judge` or `releaser`) as one code span, the permission and its level as one code span, and then in parentheses why the App holds it, on one line:

```markdown
- **Extra App permission:** `releaser` `workflows: write` (a candidate's pin pull request moves this repository's pins in .github/workflows)
```

- **Doctor then expects it of that repository's App, and of no other's.** An App without it is `app.permission-missing`, and the finding names the record; an App that holds it is no `app.permission-extra`. A permission held and not declared is still `app.permission-extra`.
- **`kanon apps` and `apps-check` read the same bullet,** so the App is created with it, its register rows show it, and the installation is checked against it ([`docs/apps.md`](apps.md)).
- **A declaration in another shape is malformed, and blocks** (`declaration.malformed`): outside `## Choices`, with nothing in its parentheses, naming an App Kanon doesn't have, a level other than `read` or `write`, or one App and permission twice.

### What can't be waived

Each of these is reported as before, whatever the record says, and a waiver of one is malformed:

- `declaration.malformed`, `waiver.stale` and `id-token.stale-acceptance`: they are about the adoption record itself, so a waiver could hide a broken or stale waiver.
- `upstream.unsent`: it is about the adoption record itself, which says findings are sent when nothing sends them, and `lane-check` fails it whatever a waiver says.
- `deploy.declaration-moved`: it is about the adoption record itself; the reconciler and `lane-check` read the reference deploy from `## Deploy` alone, and fail on bullets left under `## Choices` whatever a waiver says.
- `deploy.declaration`, `deploy.caller-mismatch`, `deploy.environment-missing`, `deploy.reviewers-missing` and `deploy.subject-custom`: they protect production ([plan 0010](plans/0010-deployment-lane.md) §12). A fallback marker turns some of them into notes, which still can't be waived: the marker is not a waiver, but a declared weakness the record states.
- `deploy.tag-ruleset`, **under the `no-reviewers` marker only**: there it is what guards production's tag path. Where it is a note, with no marker or under `no-environments`, it is waived like any other.
- `id-token.unaccepted`: accept the holder with its own bullet, above.
- `register.shared-slug`: one App would author and approve its own work, which defeats independent review (`K-LAYOUT-6`).
- `register.other-app-slug`: an `Other App` row naming an agent's App would re-label that App as one that isn't an agent (`K-LAYOUT-6`).
- `caller.secrets-inherited`: the lane would receive every secret of the repository (plan 0001 decision 7).
- `ruleset.missing` and `ruleset.rule-missing`: nothing would enforce review on the default branch (`K-ADOPT-1` step 8).
- `ruleset.bypass-extra`: an actor other than the Releaser could merge around review (`K-MERGE-8`).
- `ruleset.approval-off`: the adoption record says bootstrap ended, and bootstrap never returns: a ruleset that stopped requiring approval is an incident to fix (`K-ADOPT-6`).

## Decided by the Owner, 2026-10-06

1. **An id-token holder is accepted by one bullet per job** under `## Choices` in the adoption record (`K-LAYOUT-10`), as above.
2. **Exit code 4, `incomplete`, is separate from 0,** so a script never reads "couldn't check" as healthy.
3. **An App holding more than the release grants warns, and doesn't block** (`app.permission-extra`): each lane narrows its token to what it uses (`K-AGENT-46`). `apps-check`, which fails such an App, is unchanged; the divergence is deliberate.
4. **`--to` checks the target release only.** What the pinned release already needed shows up too, because it fails the target as well.
5. **The holders are counted on the checkout's workflows,** not on the default branch read through the API; doctor adds a note when the checkout is on another branch.
6. **A per-role App left installed after the two-App move is listed, without blocking** (`app.unused`), with the steps to uninstall and delete it in its fix.
7. **Any repository waives a finding it keeps with one bullet under `## Choices`,** one finding id on one subject with its reason, as above ([#390](https://github.com/yedeya-labs/kanon/issues/390)); doctor learns no repository's special case ([#389](https://github.com/yedeya-labs/kanon/issues/389)). A waived finding doesn't count toward the exit code and stays in `waived`; a stale waiver is listed; a malformed one blocks. Which findings can't be waived is listed above. Since 2026-10-07, a finding that lists items takes several bullets, each naming its items (below).
8. **A project may declare the kanon plugin in `.claude/settings.json`,** and doctor reports, without blocking, a declared release other than the one it checks against (`plugin.version-mismatch`, [#376](https://github.com/yedeya-labs/kanon/issues/376)). Under `--to` that is the release you are moving to, so the upgrade shows the plugin's edit beside the pin's. It can be waived like any other finding.

1. **A waiver of a finding that lists items names them, or is malformed** ([#406](https://github.com/yedeya-labs/kanon/issues/406)), from the release that ships this, not a later schema: a bullet that names none would hide what a later release adds. Its fix is the bullet to write, built from the items doctor reports today. The document's shape stays `kanon-doctor/v1`; what the adoption record accepts is the breaking change.
2. **Several bullets may waive items of one finding,** each with its own items and reason; two naming the same item are malformed.

## Exit codes

The same in both outputs.

| Code | Status | Meaning |
|---|---|---|
| 0 | `healthy` | Every check ran, and nothing blocking was found, or only findings the adoption record waives. |
| 1 | `findings` | At least one blocking finding that isn't waived, an id-token holder neither accepted nor narrowed included. |
| 2 | `usage` | A usage error: an unknown argument; a value flag followed by another flag where its value belongs (`--dir --json`, as an unset, unquoted variable leaves it: a value that begins with `-` is given as `--dir=<value>`); `--to` that is not an exact release; or `--help` with `--json`, since the usage text is no document. |
| 3 | `error` | It could not run: no checkout, the repository or a release's requirements file could not be read, nothing pins Kanon, or it stopped on an error it didn't expect. |
| 4 | `incomplete` | Nothing blocking was found, but at least one check could not run (the token can't list the secrets, say), so health can't be claimed. |

## The JSON output

`--json` prints one JSON document on standard output, and nothing else there. **Its shape is a contract** ([ADR 0014](decisions/0014-adopter-audiences.md), decision 2): the agent skills that wrap `kanon init` and `kanon doctor`, and any integrator, build on it. It follows the convention every `kanon` command's JSON shares ([`docs/cli-json.md`](cli-json.md): the opening fields, the error document, the finding's shape), and is versioned by its `schema` field, `kanon-doctor/v1`:

- **Within a version,** fields and finding ids may be added, and a consumer ignores what it doesn't know. Nothing is removed, renamed, retyped or given another meaning.
- **Anything else is a new version,** `kanon-doctor/v2`, shipped in a breaking release and named in its release notes.

`tests/unit/kanon-doctor.test.ts` holds the document's fields, the finding ids and the exit codes to the tables below.

Each of `pinned`, `to` and `checked` is an exact release, `vX.Y.Z` or `candidate-vX.Y.Z`. |

### A finding

| Field | Type | Meaning |
|---|---|---|
| `id` | string | Its stable id, from the table below. |
| `category` | string | `pin`, `app`, `secret`, `declaration`, `caller`, `label`, `ruleset`, `deploy` or `id-token`, in the order they are listed. |

### A waived finding

| Field | Type | Meaning |
|---|---|---|
| `id` | string | The finding's id. |
