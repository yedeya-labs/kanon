## Context

Kanon runs its own PR-title check, DCO check and release workflow, but none of its agent lanes. The lanes are being moved into Kanon from the reference adopter ([ADR 0009](0009-move-dont-rewrite.md), [plan 0001](../plans/0001-move-the-agent-lanes.md)). Once they are here, nothing yet runs them on the repository that ships them.

Kanon should be its own first adopter, because:
- **every lane change then runs on Kanon** before a release reaches any other adopter;
- **Kanon has no database and no app,** so its own runs test the stack-neutral path that every lane must support;
- **"this repository is maintained by the workflow it ships"** is the strongest evidence a public repository can give.

If Kanon can't adopt Kanon, then either a rule is wrong or Kanon is narrower than it claims ([ADR 0002](0002-standardise-dont-parameterise.md)).

## Decision

1. **The rollout is staged, and starts during the extraction.**
   - **After step 4 of plan 0001,** when the review lane is in Kanon, the Reviewer runs on Kanon's own PRs. The Reviewer makes no commits, so sign-off doesn't arise yet. From then on, each remaining extraction PR is reviewed by the lane it extracts. This is plan 0001's step 4b, and its App is created with `kanon apps` at step 4a ([#39](https://github.com/yedeya-labs/kanon/issues/39)).
   - **Stage 2, the Implementer.** Its preconditions are in the rulebook: delegated sign-off for the repository's own agents ([#23](https://github.com/yedeya-labs/kanon/issues/23), `K-AGENT-44`), and security as a principle, with its rules for untrusted content, least privilege and pinning ([#24](https://github.com/yedeya-labs/kanon/issues/24)). So Kanon calls the implement and implement-revise lanes from `implement.yml` and `implement-revise.yml`. A member starts it by labelling an issue `agent:implement`; it opens a pull request that the Reviewer reviews, answers the Reviewer's changes-requests on it, and the Owner merges (superseded 2026-10-12: the Merger merges inside Kanon's green zone, below). It needs the Implementer's App, which the Owner creates with `kanon apps`; until then the callers are inert (see Consequences).
   - **The Explorer, auditing Kanon's own code** (plan 0004 step 11a, its decision 13). Kanon calls the code-audit lane from `code-audit.yml`, on the lane's schedule and on a dispatch. It reads the `audit` areas of Kanon's stack document, which are Kanon's rules, docs, guards and scripts, and files the objective contradictions it finds between them on Kanon, as the explorer playbook's `## Code-reading mode` says. Kanon had no QA store hook, so the audit ran without memory and said the store was absent. Since [#423](https://github.com/yedeya-labs/kanon/issues/423) Kanon has one, which reads the store's role and bucket from repository variables (2026-10-07, the Owner's decision on [#430](https://github.com/yedeya-labs/kanon/pull/430)), so the audit has memory once Kanon's pin reaches a release whose lanes pass those variables to the hook. It ran as the Explorer's App, `kanon-explorer`, which the Owner created with `kanon apps` on 2026-10-05; since plan 0005's L5 (amended 2026-10-06) it runs as the Author App, `yedeya-labs-author`, in its Explorer role. The Explorer's second mode, reading the hosted telemetry's aggregates, waited for that store (plan 0004 step 14). Since 2026-10-07 ([#443](https://github.com/yedeya-labs/kanon/issues/443)) Kanon calls the telemetry lane from `explore-telemetry.yml`, weekly and on a dispatch: it reads the aggregate function's answer, never a row, and files what it finds on Kanon.
   - **The Overseer (amended 2026-10-06, [#423](https://github.com/yedeya-labs/kanon/issues/423)).** This stage was missing: plan 0004's decision 12 made the Overseer optional and adopter-scoped, and nothing decided whether Kanon runs it, so Kanon's adoption record said `not installed` and the capability watch (`K-SELF-16`, `K-SELF-17`), the review of each new agent-runtime release for features Kanon could adopt, never ran on the repository that ships the runtime's pin. The Owner decided four things on 2026-10-06:
     - **Kanon runs its own Overseer.** Kanon calls the Overseer's lane at its last release, like its other callers (Decision 2), as the Author App, `yedeya-labs-author`, in its Overseer role, whose row the [App register](../qa/agent-identities.md) already has.
     - **Its upstream findings are routed by a declared choice, not by self-detection.** Under plan 0004's decision 12, every finding the Overseer makes on Kanon is one only Kanon can act on, so every one would land as a draft in the audit issue's `## Upstream` section and none would be filed. Instead, a general choice in the adoption record, ``- **Upstream findings:** `filed here` `` under `## Choices` (`K-LAYOUT-10`), lets any repository have those findings filed in itself. Kanon declares it like any other repository would; no code checks whether the repository is Kanon. The choice files only in the repository that declares it, so ADR 0007's boundary is unchanged (plan 0004's decision 12, amended the same day).
     - **Kanon gets a QA store,** so the Overseer, and the code audit with it, have memory. The Owner provisions it with `infra/qa-store/aws/provision.mjs` for `yedeya-labs/kanon`, an AWS write under $0.05 a month ([the QA store](../qa-store.md)), and hands over its `RoleArn`, `TableName` and `BucketName`. Kanon then adds the store hook at `.github/actions/qa-store` with those outputs. Changed (2026-10-07, the Owner's decision on [#430](https://github.com/yedeya-labs/kanon/pull/430)): the role ARN and the bucket name carry the AWS account id, which stays out of the public tree, so the hook reads them from the repository variables `QA_STORE_ROLE_ARN` and `QA_STORE_BUCKET`, which every lane's store step now passes it, and names only the table and the region. Changed again (2026-10-07, the Owner's decision on [#433](https://github.com/yedeya-labs/kanon/issues/433)): a variable prints in every store job's log, so the two are repository secrets, which Kanon's callers map by name and the runner masks; the hook reads the variables only until the callers map the secrets. And again ([#479](https://github.com/yedeya-labs/kanon/issues/479), the Owner's decision on [#475](https://github.com/yedeya-labs/kanon/pull/475)): from the release after v0.34.1 the lanes pass the hook no variables at all, and Kanon's hook reads the secrets alone.
     - **It runs weekly, and when the agent runtime's version changes.** The caller keeps the lane's weekly schedule and its dispatch, and also runs when a change to the runtime's version merges: on Kanon, the `anthropics/claude-code-action` pin in `actions/agent-run`, which Dependabot proposes. Changed (2026-10-07, the Owner's decision on [#430](https://github.com/yedeya-labs/kanon/pull/430)): as built, the trigger is a merged pull request that moves the caller's own Kanon pin, on Kanon as for an adopter, because Kanon's lanes run the runtime of the release they pin, one release after a bump merges in `actions/agent-run`; and it audits only when that runtime is newer than the capability ledger's watermark. That is a general caller option any adopter can use (plan 0004's decision 12, amended), so a runtime upgrade gets its capability review without waiting for the week, and without depending on [#397](https://github.com/yedeya-labs/kanon/issues/397).

     The rule, the reader and the filing step for the choice come first ([#423](https://github.com/yedeya-labs/kanon/issues/423)'s first pull request). The install follows in a second, once the store exists: the caller with the runtime-version trigger, the store hook, a capability ledger, `docs/qa/capability-ledger.md`, seeded with the current runtime version as its watermark and kept by a human (`K-SELF-16`), and the adoption record saying `installed` with the choice declared. Until then the record says `not installed`. The falsifier: a dispatched Overseer run on Kanon files its rolling audit issue, its capability-watch section opens with a status line, and a finding only Kanon can act on is filed on Kanon.
   - **The Lead later, by the Owner's decision** (superseded 2026-10-12 by the full suite, below). It wasn't scheduled. Its App has existed since plan 0005's L5 (amended 2026-10-06): the Author App, `yedeya-labs-author`, holds the Lead role and has its register row, but Kanon has no Lead caller. The Lead's reconciler finds the Implementer's runs by the caller's file name, `agent-implement-revise.yml` (`K-LAYOUT-18`), which on Kanon is the lane itself. Turning the Lead on needs an answer to that first.
   - **No agent ever merges on Kanon** (superseded 2026-10-12, below). The repository is public and it is the product, so the Owner merged every pull request.
   - **The full suite, the Merger with it (amended 2026-10-12, the Owner's decision).** Kanon runs the full pipeline `kanon init` offers, as any adopter would: beside what it already ran (review, implement, implement-revise, rebase, the code audit, the Overseer, the telemetry Explorer and the collector), the triage lane, the dispatch sweep, merge reconcile, the Lead's brief, revise, split and reconcile lanes, the acceptance-criteria verifier and the Merger. The Owner decided four things:
     - **Installed through Kanon's own installer.** The callers are the ones `kanon init --feature full` writes, pinned to the release Kanon's other callers pin, at the paths the adoption record waives (`caller.misplaced`), since `agent-<lane>.yml` here is the lane itself. Where `init` tripped on Kanon, the installer was fixed in general, with no case for Kanon. The review and implement-revise callers take the names the Merger tells its own and the review event's checks apart by (`Review (Reviewer)`, `Implement (Implementer) — revise`), as an adopter's must.
     - **The Merger merges in a declared green zone.** Kanon declares its escalation paths in [`docs/qa/escalation-paths.md`](../qa/escalation-paths.md), the way any adopter does (`K-MERGE-4`, `K-LAYOUT-8`). Always the Owner's, whatever the file says: `.github/`, the markdown directly inside `docs/qa/`, `AGENTS.md`, `CLAUDE.md` and `.claude/`. The Owner's by Kanon's choice, each marked `always`: the rulebook, the decisions and the plans, the skills and the plugin manifest, the actions, the licence files, `package.json`, the lock file, the release configuration, the requirements file, the gate configuration, the stores' templates and trust code under `infra/`, and the library scripts that decide a verdict, gate a lane, mint or narrow what a token can do, or scrub what leaves a repository. Everything else is green: the Merger may merge an Implementer pull request the Reviewer approved there, with every check green. Kanon's lanes run the library at the release their callers pin, but three of Kanon's own workflows run this tree's code from the branch they run on, with a credential: `apps-check.yml` (the Apps' private keys), `metrics-page.yml` (the aggregate invoker role, then the Author's token for its pull request) and `agent-lanes-smoke.yml` (on the push to `main`, its lanes' store-cleanup jobs (`actions/qa-store/qa-store.mjs`) with the workflow token's write grants, and the implement-revise lane's implementer status (`actions/implementer-status`) with an App key mapped from `KANON_SMOKE_UNSET`, a secret that doesn't exist; their admission jobs (`scripts/lane-gate.mjs`) hold a read grant alone; corrected 2026-10-14, the Owner's decision on [#815](https://github.com/yedeya-labs/kanon/issues/815)). Their entry files and every local file those import are marked `always` too, so a green-zone merge never changes code that runs with a credential. So is the published metrics page, `docs/metrics/`. The Owner merges the rest, and every pull request a person opened.
     - **The production promotion is the weekly release pull request,** which the Owner merges, and the adoption record declares it human-gated (`K-LAYOUT-10`). Every path Kanon declares is marked `always`, so the declaration widens nothing: it records where the human gate on what reaches adopters is.
     - **What is left out:** the Explorer's sweep, which needs the sweep hook and an app to sweep, and the weekly digest, which needs the chat channel's webhook, `DIGEST_WEBHOOK`. Kanon has neither.
     - **The project digest, for its health job alone (amended 2026-10-14, the Owner's decision, [#813](https://github.com/yedeya-labs/kanon/issues/813)).** Owner decision 2026-10-14: Kanon calls the project digest for its health job alone (the scheduled-lane silence check), with no `DIGEST_WEBHOOK`; the weekly digest stays out. Its caller is `project-digest.yml`, with a `caller.misplaced` waiver and a self-pinning exemption like the other callers. Without the webhook the lane skips its model run ([#836](https://github.com/yedeya-labs/kanon/issues/836)), so the health job costs runner minutes and no model run.

     **What isn't answered yet.** The Lead's precondition above still stands for the library's re-delivery logic: it lists a lane's runs, and dispatches a re-review, by the lane's file name (`agent-review.yml`, `agent-implement-revise.yml`, `agent-lead-revise.yml`, `agent-lead-split.yml`), which on Kanon is the lane itself, so on Kanon it finds no run and its dispatch fails. The Owner turned the suite on with that known; the adoption record lists that mechanism as not installed, and the Overseer's playbook names the gap so it isn't filed as a death. The fix is general, not Kanon's: the readers find a lane's caller as `kanon init` does, from the record's waiver or the workflow that calls the lane.
2. **Kanon calls its own lanes at its last release tag, never through `$/`.** A PR that changes the Reviewer is then reviewed by the released Reviewer, not by itself. This is the bootstrap: the stable compiler builds the next one. It is the Kanon-specific case of a general rule, that a pull request never chooses the rules it is judged by ([#25](https://github.com/yedeya-labs/kanon/issues/25), `K-MERGE-17`). An adopter meets that rule through the lane's *inputs*; Kanon also meets it for the lane's *code*.
   - **Held below the two-App release until plan 0005's L5 (amended 2026-10-06).** v0.28.0 is breaking: its lanes take the Author's, the Judge's and the Releaser's secrets and read one register row per role, and Kanon has no Author or Judge App until [plan 0005](../plans/0005-lean-installation.md)'s L5. So Kanon's own pins, the judging callers among them, stay on v0.27.x, and Dependabot's entry ignores `yedeya-labs/kanon*` at `>= 0.28.0`. Until L5, "its last release" reads "its last release before v0.28.0". L5 waits on [#279](https://github.com/yedeya-labs/kanon/issues/279), so the hold has no fixed end date; L5 moves the pins and removes the ignore in the same change. This is the rollback this ADR already allows (pin the previous tag), applied ahead of the break.
   - **The hold ended at L5 (amended 2026-10-06).** L5 moved Kanon's pins from v0.27.0 to v0.29.0 through the upgrade skill, with the callers mapping the Author's and the Judge's secrets and the release caller the Releaser's, and removed Dependabot's ignore in the same change. "Its last release" means its last release again.
   - **Kanon follows the candidate channel (amended 2026-10-12, [plan 0009](../plans/0009-release-channels-and-api-key.md), Owner decisions 1 and 5).** Kanon releases weekly (`K-SHIP-7`, its adoption record's `Release cadence`), and from plan 0009's step S3 its release pull request tags a **candidate**, `candidate-vX.Y.Z`, a GitHub pre-release, which is promoted to the stable `vX.Y.Z` adopters pin only once it has run on Kanon (plan 0009 §2, §3). "Its last release" then reads "its last candidate": Kanon's callers, CI's `Lane check` job and the two judging checks pin each candidate the day it is cut, so every candidate runs on Kanon before any adopter's Dependabot proposes it. Dependabot proposes no candidate, so Kanon's pins move by a job in Kanon's own release caller (step S4), which opens `ci(deps): run Kanon on candidate vX.Y.Z` as the Releaser, moving every Kanon reference under `.github/` and the plugin's `ref`; when the candidate's `lane-check` fails on the moved callers, because a lane changed what its caller must map, pass or grant, the job opens it as a draft that lists each caller's change, and a person makes them on its branch ([#1074](https://github.com/yedeya-labs/kanon/issues/1074)); the Owner merges it, and its merge starts the candidate's soak. The rule is unchanged in spirit: a pull request is judged by the last cut, never by its own code; only the tag form differs, and no check reads whether the repository is Kanon (a candidate pin is a form any repository may use, `K-ADOPT-11`). Adopters, the reference adopter among them, follow stable unless they choose otherwise. Until S3 is built, Kanon's releases are tagged `vX.Y.Z` and its pins move by Dependabot, as above.
   - **Kanon's pins move only to a candidate the end-to-end gate passed (amended 2026-10-18, [plan 0012](../plans/0012-end-to-end-tests.md) §8.1, Owner decisions 1 and 2).** The pin job opens `ci(deps): run Kanon on candidate vX.Y.Z` only once the promotion's fifth gate passes on the candidate: a completed `kanon-e2e` check run by the end-to-end harness's Reporter App, by its App id, whose linked harness run's `verdict` job succeeded ([release.md](../release.md#the-promotion)). The push that cuts a candidate finds the gate holding, since the harness hasn't run yet; the Reporter's completed check run starts the release caller again, and the pin job runs then. So the soak's 72 hours start on a candidate the harness passed, and a red candidate never becomes Kanon's pin. There is no override, and a candidate cut before the gate was built is not gated (plan 0012 decision 3).
3. **Only members' PRs are reviewed.** Kanon is public, so a stranger's PR is input, never a trigger for a paid agent run (#24).
4. **Agent usage is out of Kanon's scope.** Whether an adopter shares one Claude subscription across its repositories or keeps them separate is the adopter's choice.

## Why the last release, and what it costs

- **What it costs:** a lane change is first exercised one release later, not on its own PR.
- **What bounds that cost:** Kolophon takes every release through Dependabot, so it runs each release first, and Kanon's next PR runs it too. A broken release therefore shows up within one PR, and is rolled back by pinning the previous tag.
  - **That premise does not hold today (amended 2026-10-06, [#294](https://github.com/yedeya-labs/kanon/issues/294)).** Kolophon runs no Kanon release: [plan 0001](../plans/0001-move-the-agent-lanes.md)'s step 6 was paused by the Owner on 2026-10-03, and Kolophon has no Apps. The Owner then decided on 2026-10-05 that Kanon is applied to its adopters only after [plan 0005](../plans/0005-lean-installation.md) is implemented (its decision 7, step L6), so no adopter runs each release first: the reference adopter's lane callers were still pinned to v0.23.0 on 2026-10-06, four releases behind. Until L6, what bounds the cost is weaker. Kanon's own pinned callers run a release only once Dependabot's bump of them merges, so a broken release shows up one release late, on Kanon's next PR after the bump, and only in what Kanon runs: the PR-title, DCO and `lane-check` checks, the review, implement and code-audit lanes, and telemetry. The lanes Kanon doesn't run (among them merge, lead, dispatch-sweep, triage, the Explorer's live mode and the digests) are run by nobody between releases, so a break in one of them stays unseen until an adopter takes that release. (Since 2026-10-12 Kanon runs all of them but the Explorer's sweep and the digests, and since 2026-10-14 the project digest's health job but not its post, one release late like its other lanes: decision 1, the full suite.) While decision 2's hold stood, it was weaker still: no bump to v0.28.0 or later arrived, so none of those releases ran on Kanon until L5 moved the pins on purpose (to v0.29.0, 2026-10-06, which ended the hold). Rolling back is unchanged: pin the previous tag. The bound returns at L6, when Kolophon starts on the lean model and runs Kanon's releases again.
- **Why not `$/`:** through `$/`, a PR's lane code would review that same PR. A PR that weakened the Reviewer would be reviewed by the weakened Reviewer, with only the Owner's merge left to catch it.

## Consequences

- **Plan 0001 gains step 4b:** turn the Reviewer on for Kanon's own PRs, pinned to the previous release, members' PRs only. Its falsifier: a review of a Kanon PR posts a verdict and its cost row.
- **Kanon's lane callers, CI's `Lane check` job, and the two checks below, are the only places in Kanon that name `yedeya-labs/kanon/…@vX.Y.Z`.** Everywhere else, Kanon reaches its own files through `$/` (plan 0001 §4). When step 4b adds the lane callers, the self-pinning test exempts them by name, and Dependabot proposes each new release to them, as it does for any adopter (it held back v0.28.0 and later until plan 0005's L5, which ended that hold: see decision 2; from plan 0009's step S3, Kanon's pin job moves them to each candidate instead, amended 2026-10-12). Step 4b also runs `lane-check` in CI at the same release, for the same reason as the two checks below: it judges the caller, so a PR can't bring its own.
- **The same bootstrap applies to the checks that judge a Kanon PR** ([#47](https://github.com/yedeya-labs/kanon/issues/47)). The required DCO and PR-title checks call `yedeya-labs/kanon/actions/dco@vX.Y.Z` and `…/actions/pr-title@vX.Y.Z`, never `$/`, so a PR can't weaken the check that passes it. The self-pinning test exempts exactly those two calls, `tests/unit/workflows.test.ts` fails if a required check other than a smoke run calls anything through `$/`, and Dependabot proposes each release to them in a group of their own, exempt from its cooldown (it held back v0.28.0 and later until plan 0005's L5, which ended that hold: see decision 2). The exemption is written out, because an entry with no `cooldown` gets Dependabot's default of 3 days, which held 13 releases back ([#233](https://github.com/yedeya-labs/kanon/issues/233)). The PR's own copies run in `judging-actions-smoke.yml`, which isn't required, so a broken change still turns CI red. A change to either action judges PRs from the release after it merges.
- **The Explorer follows, in two modes** ([plan 0004](../plans/0004-move-the-remaining-lanes.md), decision 13, decided by the Owner on 2026-10-03). The code audit of Kanon's own code is in place (Decision 1, step 11a), through `code-audit.yml` at Kanon's last release like the Reviewer's caller, and the self-pinning test exempts it by name, so a caller that reached the lane through `$/` fails that test. The hosted telemetry store went live on 2026-10-06, and since 2026-10-07 the Explorer also reads its aggregates for anomalies, through `explore-telemetry.yml`. Both file on Kanon.
- **The code audit runs from the merge of its caller.** The Explorer's App and its two secrets existed (2026-10-05), so the first scheduled run after the merge was a real audit; its store jobs found no hook and stored nothing. Since [#423](https://github.com/yedeya-labs/kanon/issues/423) they find Kanon's store hook, which reads the store's coordinates from repository variables (2026-10-07, the Owner's decision on [#430](https://github.com/yedeya-labs/kanon/pull/430)), and store each run once Kanon's pin reaches a release that passes the variables to the hook. Since plan 0005's L5 (amended 2026-10-06) the audit runs as the Author App, `yedeya-labs-author`, in its Explorer role, with the Author's two secrets. It files with labels Kanon must have first: `agent:explorer`, `qa:needs-triage`, `signal:contract`, `signal:security`, `signal:spec-violation` and `spec-delta`. Until [#279](https://github.com/yedeya-labs/kanon/issues/279) was fixed (closed 2026-10-05), the lane minted the Explorer's token in the agent's own job, one of `K-AGENT-49`'s listed exceptions; it now mints the token in a job that holds the key and runs nothing else (`code-audit-run.yml`), and hands it to the agent's job. A run spends the Claude subscription's quota like the Reviewer's (below), capped at 100 turns and $40 notional, every three days.
- **The Overseer runs from the merge of its caller (amended 2026-10-06, [#423](https://github.com/yedeya-labs/kanon/issues/423)).** On Kanon, `agent-overseer.yml` is the lane itself, so its caller takes another name, as the code audit's does, which needs a `caller.misplaced` waiver in the adoption record and an exemption by name in the self-pinning test. Its filing job files with the labels the lane uses (`pipeline-improvement`, `agent:overseer`, `capability`) in the *Development Automation* milestone, all of which Kanon has (checked 2026-10-06). A run spends the Claude subscription's quota like the code audit's, once a week and once per runtime-version change. Its runtime-version trigger, as built in #423's second pull request, is a merged pull request that moves the caller's own Kanon pin, since Kanon's lanes run the runtime of the release they pin, one release after a runtime bump merges in `actions/agent-run` (plan 0004's decision 12, amended). Its findings are about Kanon, so with `Upstream findings: filed here` they are filed on Kanon, as the code audit's are; nothing an adopter's Overseer finds reaches Kanon except by a human's hand.
- **The Explorer reads the telemetry aggregates from the merge of its caller (amended 2026-10-07, [#443](https://github.com/yedeya-labs/kanon/issues/443)).** On Kanon, `agent-explore-telemetry.yml` is the lane itself, so its caller is `explore-telemetry.yml`, with a `caller.misplaced` waiver in the adoption record and an exemption by name in the self-pinning test, as the Overseer's has.
