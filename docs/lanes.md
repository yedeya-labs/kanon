# Agent lanes

Kanon ships each agent lane as a **reusable workflow** ([plan 0001](plans/0001-move-the-agent-lanes.md), decision 1). An adopter writes, per lane, a short **caller** that holds the lane's triggers, and one **project-setup hook** that holds everything specific to its project. Kanon holds the rest: the admission rules, the round caps, the prompts and the model settings.

**What each caller maps, grants and needs.** Every caller maps its App's two secrets, by name (the Author's for the Implementer's, the Lead's, the Explorer's and the Overseer's lanes, the Judge's for the Reviewer's and the Merger's), and every lane that runs a model with one Claude credential: `CLAUDE_CODE_OAUTH_TOKEN`, the subscription's token, or `ANTHROPIC_API_KEY`, an Anthropic API key. Each such lane declares both as optional and marks them a pair with a `# ONE OF SECRETS:` line, so a caller maps exactly one, and the lane's `agent-run` step fails before the agent starts, naming the secrets, when it was handed both or neither ([plan 0009 §10](plans/0009-release-channels-and-api-key.md#10-the-secret-and-each-lanes-mapping)). The Merger, the reconciler, the dispatch sweep and the issue backstop run no model, so their callers map only the two. The digests run as no App, so their callers map the Claude credential and their chat secret: the project digest's `KANON_CHAT_PROJECT_DIGEST`, and the weekly digest's `KANON_CHAT_WEEKLY_DIGEST` ([plan 0011](plans/0011-notifications.md)); no lane takes `DIGEST_WEBHOOK` any more. The four store-coupled lanes also take the QA store's two secrets, `QA_STORE_ROLE_ARN` and `QA_STORE_BUCKET` ([the QA store](qa-store.md#provision-a-store), [#433](https://github.com/yedeya-labs/kanon/issues/433)): a caller maps both once the repository has a store hook, and may leave them out until then. It grants at least the permissions below, which are the most any of the lane's jobs declares for the workflow token (the App token's permissions are the App's, narrowed per lane by `K-AGENT-46`, and need nothing from the caller), and it needs the project documents below on your default branch (`K-LAYOUT-17`). A lane that reads no document still needs the project-setup hook if it checks out. [`tests/unit/lanes-doc.test.ts`](../tests/unit/lanes-doc.test.ts) fails when this table and the lanes disagree.

Most lanes call the shared lane workflow, `agent-lane.yml`, which is not called by an adopter directly. It runs as two jobs ([#274](https://github.com/yedeya-labs/kanon/issues/274)): `mint` uses your App's private key to mint the lane's token and runs nothing else, and `run` (`lane-agent-job.yml`) checks out, runs your hook and the agent with that token, never the key, and revokes the token when it ends. So the job running the agent can't reach the key, whatever it does to the runner (`K-AGENT-49`). Two things follow. To re-run a spine lane, use **Re-run all jobs**: **Re-run failed jobs** re-runs the agent's job alone, with the earlier attempt's token, which was revoked when that attempt ended, and its token step stops with that message. And the token is revoked as the job's last step, before any post step, so a post step of your project-setup hook can't use the `github-token` it was given. In the Actions UI a spine lane's agent job is therefore one level deeper: its name ends `… / run / run`, beside a `… / mint` job. The lanes that call the blocks themselves (review, rebase, lead-split, merge reconcile, verify-acs, the Explorer's sweep, the code audit, the Explorer's telemetry mode and the Overseer) run the same way since [#279](https://github.com/yedeya-labs/kanon/issues/279): the lane's agent job calls `<lane>-run.yml`, whose `mint` job holds the key and whose other job, `<lane>-agent-job.yml`, runs the agent with the token. So each of their agent jobs is two levels deeper in the Actions UI too: the review lane's ends `… / review / review / review`, beside `… / review / mint`, and the rebase lane's `… / resolve (<PR>) / resolve / resolve`, beside `… / resolve (<PR>) / mint`. **Re-run all jobs** applies to them as to the spine lanes. Of the other lanes, merge reconcile and the two digests call the blocks themselves and install nothing, so they never call your hook, and review, verify-acs, lead-split and rebase call the blocks around steps of their own. The Merger and the reconciler call no block and install nothing: each runs Kanon's scripts in your checkout, with its role's App token, and never calls your hook. The dispatch sweep does the same, after a store job that calls only the `qa-store` block. The issue backstop runs one of Kanon's scripts with its role's App token, and checks out the App register alone, for the Lead's persona. The code audit calls the blocks itself and installs nothing, between store jobs that call only the `qa-store` block. The Overseer calls the blocks itself and installs nothing, after a store job that calls only the `qa-store` block. The Explorer's telemetry mode calls the blocks itself and installs nothing, after a job that reads the aggregate function and nothing else.

**The review lane** has three things the others don't:
- **Its caller sets `run-name`,** ending with `${{ github.event.workflow_run.head_sha || github.event.pull_request.head.sha || inputs.pr_number }}`. A called workflow's `run-name` is ignored, and the review-run evidence finds a head's reviews by the last token of the run's title. `lane-check` holds the caller to it.
- **It reads your CI from `.github/workflows/ci.yml`.** A review label added while CI is still running defers to CI's completion, and the lane asks Actions about the runs of that file for the head. Your caller's `workflow_run` names that workflow.
- **It never reviews under the pull request's own instructions** (`K-MERGE-17`). Before any of the PR's code runs, it restores every input on the rule's list from your default branch: `AGENTS.md`, `CLAUDE.md`, `.claude/`, every markdown file directly inside `docs/qa/`, your project-setup hook, and every markdown document those link to or import. The PR's own copies are set aside under `.qa-pr/`, so the Reviewer still reads them as part of the diff, and a push that touches one re-opens an approved review. The specs under `docs/qa/specs/` come from the PR. Your own tests that read one of those files should read the `.qa-pr/` copy when there is one, or they will fail in the Reviewer's tree on a PR that changes it. A test or a tool that asks which files your commit pins should ask [`scripts/judging-inputs.mjs`](../scripts/judging-inputs.mjs) with `judgingInputs(gitReader('HEAD', root))`, which reads only tracked files. `diskReader` is the lane's tamper check, so it walks everything on disk, untracked and ignored files included. A worktree under your checkout, such as Claude Code's `.claude/worktrees/`, then counts as agent configuration, and so does every document it links to ([#1101](https://github.com/yedeya-labs/kanon/issues/1101)).

**The Reviewer's shell is an allow-list** ([#248](https://github.com/yedeya-labs/kanon/issues/248), `K-AGENT-24`). The Reviewer may run named `gh` subcommands, and otherwise only the commands Claude Code itself treats as read-only (`cat`, `grep`, `sed -n`, `jq`, read-only `git`), and may write only `qa-review-*.md` files in the runner's temp directory. Anything else is refused, including every interpreter, package manager and script in the tree. So a reviewer playbook of yours that asks the Reviewer to run a command outside that set gets a refusal: read the result from a CI check instead. **That list is the whole grant, because the Reviewer loads none of your project's Claude Code settings** ([#277](https://github.com/yedeya-labs/kanon/issues/277)). It runs with `--setting-sources user`, so your `.claude/settings.json`, `.claude/settings.local.json` and `.mcp.json` don't apply to it: no permission rule, `defaultMode`, `env`, hook or MCP server from them. A hook or an MCP server command runs without any permission check, so a formatter hook of yours would otherwise run the pull request's `package.json` beside the Reviewer's token. The same switch stops `CLAUDE.md`, project skills and project subagents from loading on their own, so the prompt tells the Reviewer to read `CLAUDE.md` and `AGENTS.md` itself. Put what the Reviewer must know in those files or in your reviewer playbook, not in a skill or an MCP server. Your other lanes still load your settings. **Its user settings start empty in every run, too** ([#283](https://github.com/yedeya-labs/kanon/issues/283)). `--setting-sources user` still loads the runner's own Claude Code settings in its home directory, and on a persistent self-hosted runner an earlier job could have left a hook, a permission rule or an MCP server there. So in a lane whose flags load no project settings (the Reviewer's and the Lead's), `agent-run` points the agent's user settings at a new directory under the runner's temp directory before the agent starts, and a hook or server in `~/.claude` or `~/.claude.json` doesn't reach it. **Run the agent lanes on GitHub-hosted or ephemeral runners anyway.** Kanon's agent jobs ask for `ubuntu-latest`, and a persistent runner that takes them keeps far more between jobs than Claude Code's settings: a job that ran a pull request's code before could leave `~/.gitconfig`, a replaced tool or a running process, and the next lane's token would be beside it. Nothing in a workflow can undo that.

**Why a caller grants more than `contents: read`.** "Grant at least" includes the permissions a lane's jobs use on the workflow token, not only the lane's top level. The implement lane's crash recovery writes issues, reads pull requests and reads its own run. The rebase lane's filter reads pull requests and its earlier runs' jobs. The split lane's gate edits the issue's labels. The review lane reads CI's runs for the head, and comments on a pull request opened without a review label.

## The features

A feature is a fixed set of lanes, with the Apps, secrets and person steps that follow from them ([plan 0007](plans/0007-guided-install.md) §2). The features are what to choose from instead of going lane by lane, and each contains the one before it. A lane marked conditional is in only when the hook it calls or the secret it takes exists. Releases is an add-on that goes with any feature: the Releaser App, on when the repository calls Kanon's release workflow (§2.4). Customise is choosing lane by lane from the catalogue below. A lane that acts only on what another lane made, such as `agent-implement-revise` on `agent-implement`, names that lane in its `requires`, and no feature holds it without that lane. The words are [`lanes.json`](lanes.json)'s `features`, which the requirements file copies. [`tests/unit/requirements.test.ts`](../tests/unit/requirements.test.ts) holds them to the lanes, and [`tests/unit/lanes-doc.test.ts`](../tests/unit/lanes-doc.test.ts) fails when this table and the features disagree. The secrets listed leave out the ones a caller may omit: the QA store's two, where the repository has no store hook (`K-OBS-17`), and the Overseer's `KANON_TELEMETRY_READER_ROLE`, deprecated and read by no job. The Overseer's cost read uses no role: its `telemetry` job reads your rows through the store's `GET /v1/rows/self` with GitHub's OIDC token, as [Where the rows come from](metrics.md#kanon-metrics-report) says, and that is the route that stays once [plan 0008](plans/0008-self-service-registration.md) J9 removes the reader roles.

## The lane catalogue

What each lane does, what it needs, what it costs (with the GitHub Actions runner-minutes it used on Kanon's own repository, which [`actions-minutes.md`](actions-minutes.md) breaks down by trigger) and when it is worth installing, by group, in the order the adopt skill (`/kanon:adopt`) asks about them ([#428](https://github.com/yedeya-labs/kanon/issues/428)). The review lane is the one recommended for every repository, and comes first; a lane already called is recommended too, and so is one recommended with a lane you choose. ## Asking the review lane again

One commit gets one verdict. The lane skips a head the Reviewer has already reviewed, and a run that waited behind another review of the same head stands down when that review posts ([#88](https://github.com/yedeya-labs/kanon/issues/88)). A new verdict on an unchanged commit comes only from a request made *after* the last one:

- **Push.** A new commit is reviewed when CI finishes on it. This is how a fix gets its review, so there is nothing to re-request.
- **A person re-applies `review:please`** after the verdict, to ask for another look at the same commit (for example after editing the PR body). The lane treats a label applied by a person as an explicit request. A label applied before the verdict landed is answered by that verdict.
- **Tooling dispatches the lane:** `gh workflow run <your review caller> -f pr_number=N`. A dispatch reviews regardless of labels, and its run records who asked. Like a label, it is answered by a verdict on the head that lands while it waits, so dispatch after the verdict, not during the review.

**Tooling must not churn the label.** Removing and re-applying `review:please` through a person's token is indistinguishable from that person asking. A churn that lands after the verdict spends a second full review on the same commit, and one that lands before it is wasted. A script that acts for a person dispatches instead, or waits for the push to do the asking. Apps can re-apply the label (the recovery in `K-MERGE-14` does), because a label applied by an App is never an explicit request.

**Any other label neither starts nor cancels a review** ([#627](https://github.com/yedeya-labs/kanon/issues/627)). On a pull request that carries a review label, a `labeled` event for any other label (a `sev:*`, `agent:reviewer`, `documentation`) runs in a concurrency group of its own and starts no review, so the labels the Reviewer applies after its verdict, or one a person adds mid-review, can't cancel the review that is running. On a pull request with no review label, such an event only checks whether to note the missing label.

## Merge reconcile skips a pull request with nothing open

The Reviewer ends every verdict with `<!-- qa:open-items N -->`: the actionable items it raised, this round or carried over, that are neither applied nor filed as an issue. When a pull request merges, or a review lands on one already merged, the merge-reconcile lane's `filter` job runs no model if every review on it is a Reviewer verdict (its App's login and its role marker) and the latest of them was read on the merged head and declares `0` ([#177](https://github.com/yedeya-labs/kanon/issues/177)). The latest decides, because its count includes what earlier rounds left neither applied nor filed. The run's summary says it skipped and names that verdict, with its `open-items 0`. Anything else runs the model as before: a review by a person or another App, a latest verdict with no marker (one from before the marker existed), a garbled one or a count above 0, a commit after it, or a pull request or App register the job could not read. The Reviewer's login is read from your App register on the default branch, so a pull request can't choose whose count is trusted.

**How it files.** For each finding a merge left unapplied and untracked, the agent chooses the labels (`follow-up`, `agent:reviewer`), one `sev:*`, and the subject: `pipeline` when the work is on the platform that builds and checks your project (its CI workflows and guards, its build tooling, its test harness, the Kanon lanes installed in it), and `product` when it is about the code your project ships, never by who raised it. A follow-up about both goes as `K-WORK-4` says: the platform wins. Your Reviewer playbook's "Capturing follow-ups" section, which this lane reads, may say where your project draws that line. It files each follow-up through the [filing skill](skills.md#the-lanes-skills), whose `plan` command chooses the milestone and any `gate-candidate` label and prints the arguments of one `gh issue create`. The lane's prompt names no milestone of its own (`K-WORK-8`). That section is the review lane's too, which still routes by its own prose until it moves onto the skill, so the merge-reconcile prompt tells its agent that the skill replaces whatever milestone the section names.

## Only members start a lane

Every lane starts real work only when the actor of its triggering event is a member: GitHub's `author_association` of `OWNER`, `MEMBER` or `COLLABORATOR`, or one of your agent Apps listed in the App register (`K-AGENT-45`). Two exceptions: on a schedule, the merge queue, and on the issue backstop, whoever opened the issue (the table below). The check is the first step of the lane's first job, [`scripts/lane-gate.mjs`](../scripts/lane-gate.mjs), before any token is minted (the Merger, whose review and sweep start different jobs, runs it first in each), so it runs on a private repository exactly as on a public one (`K-PRIN-20`).

| Event | The actor | How it is checked |
|---|---|---|
| A review | the reviewer | the review's `author_association` |
| A label | whoever applied it | their permission on the repository: triage or more |
| A merge (`pull_request: closed`) | whoever merged it | the same |
| A merge (`pull_request_target: closed`) | whoever merged it, `merged_by` alone (through a merge queue, the member who queued it) | the same. A pull request closed unmerged is refused ([#484](https://github.com/yedeya-labs/kanon/issues/484)) |
| A closed issue (`issues: closed`) | whoever closed it | the same |
| An opened issue (`issues: opened`), on the issue backstop alone | whoever opened it | not checked: admitted, an outsider included, since the backstop runs no model, reads no issue text and writes only a bucket and labels (Owner decision 2026-10-14, [#768](https://github.com/yedeya-labs/kanon/issues/768)). Every other lane refuses an opened issue |
| A dispatch | whoever ran it, re-runs included | the same; only write access can dispatch, so this refuses only an unregistered App |
| A pull request opened (`pull_request_target`) | whoever opened it | the same |
| A finished workflow (`workflow_run`) | whoever pushed the commit it ran on | the same |
| A finished CI run, on the review lane | whoever last applied a review label (`review:please`, `agent:triage` or `agent:implement`) that the head's open pull request carries now, read from its issue events | the same. With no such pull request or label, refused. A label added while CI runs waits for CI, so this is that label's actor, not the pusher, who on a dependency bot's PR is the bot ([#81](https://github.com/yedeya-labs/kanon/issues/81)). A fork's head is refused separately |
| A schedule | the user GitHub runs it as: whoever last changed the cron, or the default branch | the same, so a schedule set by someone who has since lost access is refused. Where merges go through a merge queue, GitHub runs every schedule as the queue, which is admitted on a schedule alone: only someone with write access (a member, or an App you installed) can queue a merge, and a schedule runs your default branch's code |
| Anything else | none | refused: no lane acts on it |

A login ending in `[bot]` is judged by the App register alone, read from your default branch, never from the pull request, except the merge queue on a schedule and whoever opens an issue on the issue backstop (above). A refused event leaves the lane's later steps and jobs skipped, with a notice and a step-summary line naming who was refused and why; it does not turn the run red. A failed API call or a malformed register does.

**With a merge queue, a merge does not start the merge lane's sweep, and starts the rebase lane only through its merged-pull-request trigger** ([#79](https://github.com/yedeya-labs/kanon/issues/79), [#484](https://github.com/yedeya-labs/kanon/issues/484)). The queue pushes the merge to your default branch, so the CI run on that push has `github-merge-queue[bot]` as both its `actor` and its `triggering_actor`, not the member who queued the pull request (measured on Kanon's own `main`). That is an App outside your register, so the gate refuses it with a notice, and the run stays green. The merge lane still sweeps on a review and within the hour. The rebase lane's caller also runs on `pull_request_target: [closed]` on your default branch, which fires once the queue has merged: the gate judges `merged_by`, the member who queued it, and refuses a pull request closed unmerged. `kanon init` writes that trigger; a caller written before it lacks it, and Dependabot's upgrade moves only the pin, so add it by hand or run `kanon init` again, and `kanon doctor` notes a rebase caller without it when your default branch has a queue. `merge_group` doesn't help: it fires before the default branch moves. Don't add the queue to your App register to admit it: the register lists your agents, and the queue would then be admitted on every push it makes. The schedules still run: each merge through the queue changes your default branch as the queue, so GitHub runs every schedule as it, and the gate admits the queue on a `schedule` event alone, because only someone with write access (a member, or an App you installed) can queue a merge, and a schedule runs your default branch's code (measured on Kanon's own `main`, 2026-10-07). Without a merge queue, the push is made by whoever merged, and the gate judges them as usual; a merge then starts the rebase lane twice, and the second run finds nothing the first didn't hand over. The lane catalogue says what a queue changes for the merge lane (`mergeQueue` in [`docs/lanes.json`](lanes.json)), so `kanon init --json` and the adopt skill tell you when you choose it on a repository with a merge queue, and `kanon doctor` notes it, without blocking, when you call it ([#452](https://github.com/yedeya-labs/kanon/issues/452)).

**Every lane carries the gate.** [`tests/unit/lane-gate.test.ts`](../tests/unit/lane-gate.test.ts) fails for a lane in Kanon without it, or with a step or job that can run past a refusal, and for a lane whose triggers it doesn't list.

**A lane refuses a caller that pins another Kanon version than your default branch** ([#69](https://github.com/yedeya-labs/kanon/issues/69), `K-MERGE-17`). On `pull_request_target`, GitHub runs the base branch's copy of your caller. On a stacked pull request that base is another pull request's branch, and its caller can pin another version. On `pull_request` and `pull_request_review`, it runs the pull request's own merge of your caller. So when the caller ran from anywhere but the default branch (another branch, a tag from a dispatch with `--ref`, or a pull request's merge ref), the gate reads that caller at the commit that ran and at your default branch, and compares every Kanon reference in them (each `uses:` of a `yedeya-labs/kanon` path, with its version). If your caller reaches the lane through a reusable workflow of your own repository (`uses: ./.github/workflows/lanes.yml`, or `$/…`), the gate follows it, to any depth (though `K-LAYOUT-18` refuses that shape, because the lane's runs are then filed under the top-level workflow's name), and compares the Kanon references of every workflow it reaches ([#118](https://github.com/yedeya-labs/kanon/issues/118)). If they differ, if the default branch has no such caller or lacks a workflow it calls, or if neither side holds any Kanon reference (the lane was reached through something the gate can't read, such as another repository's workflow), the lane is refused with a `Kanon pin: refused.` summary line. A run from the default branch reads nothing. A pull request never chooses the Kanon version that acts on it. **So on a pull request that bumps the pin, Dependabot's for example, the lanes it triggers on `pull_request` and `pull_request_review` (the revise and merge-reconcile lanes) refuse, visibly, until it merges. Merge reconcile on that pull request's own merge runs, because by then your default branch carries the new pin too.** Its review is unaffected, because the review lane runs from the base. **This holds only between versions that have the check.** The gate is Kanon at the version the running caller pins, so a base whose caller pins a release from before it runs a gate without it. Enforcing it from outside the lane is [#114](https://github.com/yedeya-labs/kanon/issues/114).

**A dispatch made with the workflow token is refused.** Its actor is `github-actions[bot]`, which is not in your App register. So no lane starts another that way. When an implement run hits its turn or budget cap, its crash recovery adds `qa:needs-split` with the Author App's token, minted for the Implementer and narrowed to Issues write, and that label's own event starts the split lane through the gate as a registered App. Its comment stays on the workflow token, so it never reads as the Implementer's. Only that label needs the App: if the token cannot be minted (a rotated key, an uninstalled App, an unset secret), crash recovery still retries the issue or stops it to a human on the workflow token, and only a due split fails, by name, with nothing changed ([#78](https://github.com/yedeya-labs/kanon/issues/78)).

**An implement run that ends green but leaves nothing turns red** ([#181](https://github.com/yedeya-labs/kanon/issues/181)). After a successful implement job, the lane checks what the run left: an open pull request that closes the issue, a `<type>/<number>-` branch pushed during the run, or a comment from the Implementer since the run started. If there is none, the run fails with the error `implement run left nothing`, and crash recovery takes over. For a project member that means a retry, posted as `github-actions` and capped like a crash's. An issue outside a project keeps its label and gets no comment, and the dispatch sweep retries it ([#254](https://github.com/yedeya-labs/kanon/issues/254)): it reads the jobs of the issue's latest implement run, and when that run failed its empty check and went on to crash recovery, it reports the issue as `ran-empty` and re-dispatches it within its usual attempt cap, even if the Implementer commented on an earlier run. That read needs the issue's cost rows, so a sweep that cannot read them treats the issue as before. A run that commented is never treated as empty, because the comment explains why the agent stopped. The revise lane turns a green run red too, if it pushed nothing and left no reply marker. Nothing retries that run.

**Both Implementer lanes re-point the line cites their diff moved before they push** ([#622](https://github.com/yedeya-labs/kanon/issues/622), `K-SELF-3`). Their prompts run Kanon's `citation-shift` with `--fix` against the pull request's base, with the `--path` list your CI passes it, and commit what it rewrites in the same push. So a push whose only problem is a moved `file:line` doesn't reach CI red. On your default branch the script has nothing to diff against its merge base, so you can also put it in your `lint` chain, where every gate run sees it.

## The caller

A caller holds `name`, `on`, `permissions` and one job, and nothing else (and `run-name`, which the review lane asks for):

<!-- x-release-please-start-version -->

```yaml
name: Implement (Implementer) — revise

on:
  pull_request_review:
    types: [submitted]
  pull_request:
    types: [labeled]
  workflow_dispatch:
    inputs:
      pr_number:
        description: PR to revise
        required: true
      reset:
        description: Clear the round cap for this run.
        type: boolean
        default: false
      max_turns:
        description: Raise the turn limit for this one run (docs/lanes.md, "The turn budget").
        required: false
      reason:
        description: Why this run raises max_turns. Required when max_turns is set.
        required: false

permissions:
  contents: read
  pull-requests: read
  issues: read
  statuses: read

jobs:
  revise:
    uses: yedeya-labs/kanon/.github/workflows/agent-implement-revise.yml@v0.42.0
    with:
      pr_number: ${{ inputs.pr_number }}
      reset: ${{ inputs.reset }}
      max_turns: ${{ inputs.max_turns }}
      reason: ${{ inputs.reason }}
    secrets:
      AUTHOR_APP_ID: ${{ secrets.AUTHOR_APP_ID }}
      AUTHOR_APP_PRIVATE_KEY: ${{ secrets.AUTHOR_APP_PRIVATE_KEY }}
      CLAUDE_CODE_OAUTH_TOKEN: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
```

<!-- x-release-please-end -->

- **Each caller has its lane's file name** (`K-LAYOUT-18`, [#207](https://github.com/yedeya-labs/kanon/issues/207)): the caller of `agent-implement-revise.yml` is `.github/workflows/agent-implement-revise.yml`, and so on. That file name is the rule, and `lane-check` fails a caller at any other path: it is where Kanon's scripts look for a lane's runs and where they start it (the Merger dispatches your review caller, the reconciler lists the runs of your revise callers, and the health check watches every `agent-*.yml`). The caller lookup below is the fallback that keeps a caller elsewhere findable, not a second way to name one. GitHub files a run under the top-level workflow, so the caller holds the triggers itself: `lane-check` also fails a caller that is a reusable workflow another of yours calls. A project that runs the review lane or the reconciler also keeps its CI at `.github/workflows/ci.yml`, whose runs both read.

  **A caller under another name still gets its runs found and its dispatches** ([#726](https://github.com/yedeya-labs/kanon/issues/726)). `lane-check` still requires the lane's file name for a caller outside Kanon's own repository; a `caller.misplaced` waiver in the adoption record is how a repository like Kanon, which hosts the lanes at those names, keeps its callers under others. Where a caller lives elsewhere, the scripts look it up on your default branch: the file at the lane's name if it calls the lane, else the file a `caller.misplaced` waiver names, else the first workflow by name that calls the lane, directly or through a reusable workflow of your own. A file only another workflow calls has no runs of its own, so a waived or lane-named file of that kind resolves to the workflow above it. That is the file whose runs they list (the review, revise and brief-revise recoveries) and that the Merger dispatches for a re-review, and the health check watches it beside every `agent-*.yml`. If no caller is found, or the default branch can't be read, they use the lane's file name as before and log why, so the recoveries keep their caps.
- **Four callers have fixed names** ([#53](https://github.com/yedeya-labs/kanon/issues/53)). GitHub reports a called lane's checks under its caller's `name:`, and the merge gate tells its own checks, and the review event's, from the rest by that name. Name the review lane's caller `Review (Reviewer)`, the merge-reconcile lane's `Merge Reconcile (Reviewer)`, the implement-revise lane's `Implement (Implementer) — revise` and the Merger's caller `Merge (Merger)`, and give the revise and merge-reconcile callers' one job the ids `revise` and `reconcile`. Each of the four lanes says its caller's name on a `# CALLER NAME:` line, and the two racers their job's id on a `# CALLER JOB:` line, which `lane-check`, `kanon init` and doctor read. Under another name the Merger waits on itself, so `lane-check` fails a Merger caller under any other name. Under another name or job id it waits on the other three, so `lane-check` checks them too ([#728](https://github.com/yedeya-labs/kanon/issues/728)): from Kanon 0.40.0 a review, merge-reconcile or implement-revise caller under another name, an earlier release's spelling included, or a revise or merge-reconcile job under another id, is a warning that says what to rename, and from Kanon 0.41.0 it fails. Rename them before you move your pin to 0.41.0.
- **Triggers are yours.** A reusable workflow can't declare its caller's events. The `github` context in a called workflow is the caller's, so the lane reads the triggering event exactly as it would in your own file.
- **Inputs pass through, by name.** `with:` passes your `workflow_dispatch` inputs as `${{ inputs.<name> }}`, and nothing else. That includes a raised turn limit, `max_turns`, and its `reason`, which come only from your dispatch ("The turn budget" below). On the other triggers they arrive empty, which the lane expects. Every lane also declares `smoke`, which your caller never passes, and `lane-check` fails a caller that does: Kanon's lanes smoke sets it so that its runs take concurrency groups of their own and never queue behind, or cancel, your real runs.
- **`permissions:` is the ceiling.** Each lane declares the permissions it needs, and a called workflow can only narrow what its caller grants. Grant at least what the lane declares, or the run fails to start.
- **Secrets are mapped explicitly, by their fixed names** ([plan 0001 §8](plans/0001-move-the-agent-lanes.md)): the App's `AUTHOR_APP_ID` and `AUTHOR_APP_PRIVATE_KEY` (the Implementer's, the Lead's, the Explorer's and the Overseer's lanes) or `JUDGE_APP_ID` and `JUDGE_APP_PRIVATE_KEY` (the Reviewer's and the Merger's), and one Claude credential, `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`, never both (plan 0005 §3.5, plan 0009 §10). The role-named secrets of earlier releases (`IMPLEMENTER_APP_ID`, `REVIEWER_APP_ID`, …) are gone: `lane-check` fails a caller that maps one, naming the secret it takes instead. Never `secrets: inherit`, which would hand every secret in your repository to Kanon's code. [`kanon apps`](apps.md) stores the two App secrets. `CLAUDE_CODE_OAUTH_TOKEN` is the token of the Claude subscription the agents run on. Make it with `claude setup-token`, signed in to that subscription, and store it yourself with `gh secret set CLAUDE_CODE_OAUTH_TOKEN -R <owner>/<repo>` in your own terminal, pasting it when `gh` asks for it: never with `!` at the Claude Code prompt, where `gh` reads no value and stores an empty secret without a word ([#625](https://github.com/yedeya-labs/kanon/issues/625)). Or read it from a file, with `< <file>` at the end of the line, and delete the file after ([the adopt skill's "Running `gh secret set`"](../skills/adopt/SKILL.md#running-gh-secret-set)). To run the lanes on an Anthropic API key instead, billed per token, store the key the same way as `ANTHROPIC_API_KEY` and map it in place of the token: `ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}`. Each caller chooses, so the Reviewer may run on a key and the Implementer on the token.
- **No `concurrency:`.** Each lane holds its own concurrency group. The same group on the caller would have the caller wait for itself. A run joins its lane's group before the lane's own checks can skip it, so every lane whose group a skip-only run can join keeps every pending run in order (`queue: max`), and such a run can't cancel a pending real one ([#552](https://github.com/yedeya-labs/kanon/issues/552)). Those lanes are rebase, implement-revise, Lead revise, merge reconcile, Merge, Lead reconcile, the dispatch sweep and the acceptance-criteria verifier. The rest give such runs a group of their own, or take only events that run.
- **One version.** Every Kanon reference in your repository pins the same exact version, and Dependabot proposes upgrades (`K-ADOPT-11`). The one pin that may lag is the notify hook's call to Kanon's prebuilt Slack or webhook hook, which follows the callers' ([plan 0011](plans/0011-notifications.md) decision 18): `lane-check` passes it behind them, with a notice, while it declares a contract version their release still writes, and fails it ahead of them or on a retired version. Move it with them. Write the `cooldown` out with `yedeya-labs/kanon*` excluded: an entry with none still gets Dependabot's default of 3 days, which holds back every release made in the last 3 days, and `lane-check` fails it ([#233](https://github.com/yedeya-labs/kanon/issues/233)).
- **An agent's commits pass your `dco` check with no hook code of yours** (`K-AGENT-44`). The lanes author each one as the lane's App, and add the `Signed-off-by:` of the person your default branch's `docs/qa/sign-off-delegation.md` names (`K-LAYOUT-14`). Recording that delegation is your decision; with none, an agent's commits fail the check ([`agent-setup`](../actions/agent-setup/README.md), [#234](https://github.com/yedeya-labs/kanon/issues/234)).

## The turn budget

Each lane that runs a model limits its agent's turns with `--max-turns`, and derives its dollar cap, `--max-budget-usd`, from that limit at $0.40 a turn, rounded up to the next $5 (`K-OBS-12`). The limit is Kanon's, in the table below, and you don't change it: nothing in your repository sets it ([ADR 0005](decisions/0005-roles-and-standard-lane-settings.md) §2, amended 2026-10-15). What a person may do is raise it for **one dispatched run**, when a run stopped at the limit on work that can't be divided ([#891](https://github.com/yedeya-labs/kanon/issues/891)):

```sh
gh workflow run agent-lead-revise.yml -f pr_number=123 -f max_turns=150 -f reason="one ruling touches the brief's scope, five issues and six spec clauses"
```

- **Two dispatch inputs, passed through.** Every lane in the table takes `max_turns` and `reason`, and its caller's `workflow_dispatch` declares both, optional, and passes them through: `max_turns: ${{ inputs.max_turns }}` and `reason: ${{ inputs.reason }}`. `kanon init` writes them on each such caller. `lane-check` fails a caller that writes a number for `max_turns`, or anything but its own dispatch input, one that passes `max_turns` without `reason`, and one whose dispatch gives either input a `default`: GitHub fills a default whenever a dispatch leaves its input out, as Kanon's own scripts do when they dispatch a caller, so it would raise every such run with a canned reason ([#1007](https://github.com/yedeya-labs/kanon/issues/1007)). On any other event the inputs arrive empty, and the lane runs at its limit.
- **Kanon fixes a ceiling per lane, twice its limit.** A raise moves the cost bound for one run, never removes it. The lane refuses, before any model call and with an error that names `max_turns`: a value above the ceiling, zero, a negative number or anything but a whole number; a raise with no `reason`; and a raise on a run that wasn't dispatched. Kanon never lowers a value to the ceiling for you. On the two digest lanes, whose narrative is best-effort, a refused raise leaves the digest without its narrative.
- **The dollar cap follows.** A raised run runs with `--max-budget-usd` derived from its `max_turns` at the same rate.
- **It is recorded.** The run's step summary says the raised limit, the lane's own, the dollar cap and the reason. Its telemetry row records the limit that bound it, `max_turns`, and so a configuration fingerprint that differs from the lane's other runs: a raised run reads as what it was.
- **The deploy-diagnose lane can't be raised:** its caller has no dispatch, since the lane reads the failed deploy from the event.

**Split or raise.** When a run stops at its turn limit, a plain re-run fails the same way, and the lane's error says so. Read the run's telemetry row first: its turn-budget line shows the turns it took against the limit, and the lane's earlier rows show whether its runs keep ending there (`terminal_reason: max_turns`). [`kanon doctor`](doctor.md) reads those rows for you, and reports a lane whose recent runs keep ending at its limit (`lane.turn-cap`), with the turns each run took against the limit and the ceiling. If the work is divisible, split it into parts each finishable in one run; for the implement lanes that is the default answer, and the split lane does it. If it is one change that can't be divided, such as a ruling that touches a brief's scope, several issues and its spec clauses together, re-dispatch that run with a higher `max_turns` and the reason. An adopter's ~500-line brief under its third round of revision is the worked example: the brief-revise lane stopped at its 90 turns, and the work was one ruling. Work that needs more than the ceiling wants splitting.

## Your first lane: the Reviewer

Install the review lane first. Its App is the one that ends bootstrap, on a plan with rulesets (`K-ADOPT-3`, `K-ADOPT-6`), and it needs no other lane. On one branch, add:

1. **The project-setup hook** (below), and `docs/qa/test-database.md` if your tests need a database. The review lane doesn't call the hook: it runs none of your pull request's code ([#185](https://github.com/yedeya-labs/kanon/issues/185)), and takes test results from your CI's required checks. [`lane-check`](../actions/lane-check/README.md) requires the hook anyway, because the lanes that install call it.
2. **The documents the review lane reads**: `docs/qa/stack.md`, `docs/qa/reviewer-playbook.md` and `docs/qa/explorer-playbook.md`, with the sections `K-LAYOUT-17` names.
3. **The caller**:

4. **[`lane-check`](../actions/lane-check/README.md) in CI**, and the Dependabot entry it asks for.
5. **The Apps:** run [`kanon apps --apps author,judge`](apps.md) from that branch's checkout, and commit the register rows it writes, one per role, each App's rows sharing its slug. ## Kanon's scripts

The lanes run Kanon's pipeline library (`scripts/`) from the runner's action cache, at the version you pinned, never from your checkout: a step finds it with [`kanon-path`](../actions/kanon-path/README.md) and runs `node "$KANON/scripts/<name>.mjs"`. The scripts read your repository's files at the paths in [chapter 11](../rulebook/11-repository-layout.md), relative to the working directory, so they run in your checkout. A workflow of your own that runs one of them does the same, which is how Kanon's guards reach your CI: `kanon-path` at the pinned tag, then `node "$KANON/scripts/<guard>.mjs"`, with Dependabot proposing the upgrades. The scripts use only Node's built-in modules, so neither your repository nor the step needs a `package.json`, an install or a package manager, whatever your project's language. Node is Kanon's runtime, not your project's, and `kanon-path` sets it up: the version in `engines` in Kanon's own manifest, pinned, rather than whichever Node the runner image carries. Its [README](../actions/kanon-path/README.md) says where to call it relative to your own toolchain.

## The project-setup hook

`.github/actions/project-setup/action.yml` is a composite action you write ([plan 0001 §5](plans/0001-move-the-agent-lanes.md)). Every lane that checks out calls it after the checkout and before the agent, with these inputs, all strings: `lane`, `install`, `database`, `browsers`, `issue-number`, `app-slug` and `github-token`. It installs your toolchain and dependencies, and, when `database` is `'true'`, sets up your schema against the database in `DATABASE_URL`. It is read from the checked-out tree, so on a lane that checks out a pull request it is that branch's copy, except on the review lane, which restores your default branch's copy first (`K-MERGE-17`). The verify-acs lane loads it from your caller's commit, because the release it verifies may predate it, and calls it in a job that holds no App token and no Claude token: that job runs the hook and the acceptance criteria and uploads the report, and the agent's job, which receives the token, runs none of the code it verifies ([#243](https://github.com/yedeya-labs/kanon/issues/243), `K-AGENT-50`). So on that lane the hook gets no `github-token` and no `app-slug`, and its post steps run in that job. **The Lead's lanes (`agent-lead.yml`, `agent-lead-revise.yml`) don't call your hook at all** (`project-setup: false` on the shared lane workflow, [#243](https://github.com/yedeya-labs/kanon/issues/243)): the Lead runs none of your code. Its shell is an allow-list like the Reviewer's: it writes only under `docs/`, runs Kanon's `kanon-brief-guard`, `kanon-spec-ids` and `kanon-spec-coverage`, commits and pushes to `origin`, and calls named `gh` subcommands, and it loads none of your project's Claude Code settings. On those lanes git checks each symlink in your tree out as a plain file holding the link's target, so the Lead can't write outside `docs/` through one ([#327](https://github.com/yedeya-labs/kanon/issues/327)); a link the Lead reads shows as its target's path, and a commit keeps it a link. So a Lead playbook of yours that asks the Lead to run your lint, tests or a package script gets a refusal; take those results from CI. The implementer's revise and conflict-resolution lanes still run the pull request's code beside their token: the revise lane runs your hook from the pull request's branch, and both lanes' agents run your gates on it. The Owner accepted that exposure (`K-AGENT-50`), and [SECURITY.md's "Accepted exposures"](../SECURITY.md#accepted-exposures) says what it exposes and what bounds it.

**The starting map.** When a lane passes an `issue-number`, your hook may write `.agent/starting-map.md` (`K-AGENT-41`). The implement lane's prompt reads it first if it exists, and nothing fails without it. Kanon's [`scripts/starting-map.mjs`](../scripts/starting-map.mjs) `--issue <n>` writes one from the issue and the spec clauses it cites.

The contract defines no outputs, and no lane reads any: a lane judges your hook only by whether it succeeded. The review lane doesn't call your hook at all ([#185](https://github.com/yedeya-labs/kanon/issues/185)).

## The test database

A lane gets a database only when your project declares one, in `docs/qa/test-database.md` (`K-LAYOUT-16`). With no file, your hook gets `database: 'false'` and `DATABASE_URL` stays unset. Declare `hook`, and your hook gets `database: 'true'`: it starts your database, whatever the engine, and writes `DATABASE_URL` before it returns. Kanon starts none and names no engine. The [`test-database`](../actions/test-database/README.md) block reads the declaration. Its README has the format and a worked example, a hook that starts Postgres. Add the declaration before, or with, the upgrade that brings it, then rebase your open pull requests: a lane that checks out a branch reads that branch's copy.

## The QA store

The code audit, the Explorer, the Overseer and the dispatch sweep remember earlier runs in a QA store in your own account (`K-OBS-17`). They reach it only through a hook you write, `.github/actions/qa-store/action.yml`, with five operations, each run in a store job of its own, which, besides the Overseer's `telemetry` job (held to its exact shape, and reading your telemetry rows, not the store), is the only kind of job in those lanes that holds `id-token: write`, so no agent job holds the store's credentials. The store trusts your default branch's ref, and no GitHub Environment. Kanon's AWS implementation provisions a store and is the hook's one `uses:` line. Without a hook, each lane runs without memory and says the store is absent. [The QA store](qa-store.md) has the contract, the setup and the AWS runbook.

## The stack document and the playbooks

The lanes' prompts state the process and never your stack. What your stack decides, they read from files you own, at fixed paths (`K-LAYOUT-17`): the **stack document**, `docs/qa/stack.md`, with `## Gates` and, when you have something to say there, `## Schema changes`, `## Data isolation` and `## Generated files`, and the **playbooks**, `docs/qa/triage-fix-playbook.md`, `docs/qa/reviewer-playbook.md`, `docs/qa/explorer-playbook.md` and `docs/qa/lead-playbook.md`, with `docs/qa/overseer-playbook.md` when you install the Overseer, and the capability ledger, `docs/qa/capability-ledger.md`, when you also turn its capability watch on. The rule says what each section holds.

**What you leave out is a documented default** ([plan 0005](plans/0005-lean-installation.md) §5.2). A stack-document section you omit, other than `## Gates`, means none: no schema, nothing to isolate, no generated files. A playbook you don't write is Kanon's baseline for the role, [`rulebook/templates/playbooks/`](../rulebook/templates/playbooks/) at the release you pin: the lane's `agent-setup` block puts it in place before the agent starts, keeps it out of the agent's commits, and says so in the job summary and in the agent's prompt, so an agent asked to write that playbook stages it with `git add -f`. Write your own, starting from a copy, when you want the Reviewer to check your project's own risks. `lane-check` fails when the stack document or a capability ledger a lane you call reads is missing, or the stack document has no `## Gates`, and names each default it takes.

**Your code areas.** The stack document may also say where your code and tests are, under `## Code areas`, one bullet per area: a path in backticks, for a `tests` tree optionally its runner in backticks, an em dash, its kind, a colon, and what it holds.

```markdown
## Code areas

- `src/` — code: the application
- `tests/` `vitest` — tests: unit and integration tests
- `e2e/` `playwright` — tests: the browser suite
- `src/server/services/` — audit: the service layer, where tenant scope and authorisation live
```

A `code` tree is your own source: `citation-shift` reads its comments, and the spec-id sweeps read its references. A `tests` tree holds tests and their fixtures: `doc-path-guard` doesn't read its files as claims, and every JavaScript or TypeScript file in it is a test whose title can cite a spec id (`K-SPEC-6`). The acceptance-criteria check runs those with the runner the tree names, `vitest` or `playwright`; a tree that names none is read and never run, so its criteria are not-run. A Kanon release older than the runner form fails by name on a tree that names one, so add the runner with, or after, the upgrade that brings it. An `audit` area is what the code audit reads first. Without the section, the guards read the whole repository, a test is what its language's convention calls one, in JavaScript and TypeScript a `*.test.*` or `*.spec.*` file, which nothing runs until you declare its tree's runner, and the audit reads your `code` trees, or the whole repository. So an undeclared tree is read, never skipped: declare the trees once a guard reads something it shouldn't. `lane-check` fails a malformed section by name, and so does each guard that reads it.

## The App register

The revise lanes find their own App's login in the App register, and the scripts the lanes run read every role's login from it, `docs/qa/agent-identities.md` (`K-LAYOUT-6`), read from your default branch. Each role a lane runs as needs one row there with its App slug in backticks. Since plan 0005's L4 the rows of one App's roles name that App's slug: the Author's four one, the Judge's two another, and the Releaser's, if you have one, a third. `lane-check` fails a register in which one App's roles name two slugs, or two of those Apps share one (§3.4). Each lane says which role it runs as on a `# KANON ROLE:` line, which `lane-check` reads.

Every post a lane writes as one of your Apps opens with a persona header and a hidden role marker, `**Implementer** <!-- kanon:role=implementer -->`, and every agent commit has the persona as its author name (plan 0005 §3.3). The Implementer's lanes also set a `kanon/role: implementer` commit status, from a job after the agent's, with a token narrowed to Commit statuses write. To have it set, grant your Author App (the Implementer's) **Commit statuses: Read & write** and record that broadened permission in the register (`K-AGENT-3`). The Author's manifest from `kanon apps` already includes it. Until then the job says so in the run's summary and changes nothing.

**Since plan 0005's step L4 both are required.** Every reader that tells two roles apart needs the role's marker beside the App's login. The agent is asked to write the header; for a review the lane does not rely on it. The review lane's stamp step signs the Reviewer's verdict with the header when the agent left it off, and when it can't, the run goes red by name rather than leaving a verdict no reader counts. Where an Implementer comment on an issue carries no marker, crash recovery says so in a warning. A lane whose role `agent-setup` can't resolve fails that step by name before its agent runs, instead of running an agent whose posts no reader would count. The Merger merges only a pull request whose head carries a `success` `kanon/role: implementer` status created by the Author App, and otherwise skips it as `not-the-implementer`; an unreadable status list waits. The revise and rebase lanes act only on a pull request whose head carries that status, and refuse any other by name, so a person's push takes a pull request out of the green zone and a person merges it. Both callers now grant `statuses: read`. Grant the permission to your Author App (the Implementer's) before you move the pin to this release, or every Implementer pull request waits for a person.

**The declaration.** List your environments, in deploy order, in the `## Deploy` section of `docs/qa/adoption.md`. The last one is production; every other one is pre-production. Each deploys only after the one before it succeeded on the same release:

```markdown
## Deploy
- **Environments:** `staging`, `production`
- **CI wait:** `90`
- **Smoke schedule:** `staging 0 3 * * *`
```

The smoke schedule is optional, and says how often the smoke check runs on an environment outside a deploy: one code span per environment, its name as the list spells it, then a five-field cron. Without the bullet, no environment has one. Each environment takes at most one cron, and no two environments take the same cron string, because the cron is what tells one scheduled run from another. Production may have one; an environment with required reviewers may not, since each of its runs would hold the deploy's slot while it waited for a person ([plan 0013](plans/0013-smoke-lifecycle.md) §4.3). **Nothing reads it yet:** the workflow and the caller that would run it are being built, and the lane's own smoke step, after each deploy, runs as it does today.

The CI wait is how long the gate waits for the release commit's CI, in minutes from 1 to 360; without it, 90. The gate never waits longer than 345 minutes, whatever the record declares, so the wait ends in `ci-timeout` inside the gate job's 360-minute limit rather than in a cancellation. The lane reads the section **at the release's commit**, through [`scripts/lib/deploy-declaration.mjs`](../scripts/lib/deploy-declaration.mjs), so the declaration that deploys a release is the one reviewed with it.

**The two workflows, and the caller.** [`deploy-release.yml`](../.github/workflows/deploy-release.yml) runs once per release: the gate, the trust probe, the build, and, when the run stops there, one row and one issue for the first environment. [`deploy.yml`](../.github/workflows/deploy.yml) runs once per environment: `declare`, then `deploy`, `record` and `report`, then `announce` and `notify`. Your caller, `.github/workflows/deploy.yml`, calls the first, then the second once per environment, each `needs:` the one before and the `release` job, whose `build` output it hands on. `kanon init` writes it from the declaration ([plan 0010](plans/0010-deployment-lane.md) step D6); for the declaration above it reads:

```yaml
name: Deploy
on:
  release:
    types: [published]
  workflow_dispatch:
    inputs:
      release: { type: string, required: true }
jobs:
  release:
```

Grant each job the permissions its workflow asks for (`requirements.json`'s `deploy` entry lists them), and map two secrets into each `deploy.yml` call, each by its own name, and no other: `KANON_DEPLOY_SECRET`, the deploy hook's, which GitHub resolves in the deploy job from the environment first ([#1049](https://github.com/yedeya-labs/kanon/issues/1049); a call that doesn't map it hands the hook an empty value), and `KANON_CHAT_DEPLOY`, to announce each deploy, which `kanon init` writes whatever its chat answer, so adding a notify hook later needs no change to the caller. The `release` job maps none. A run lists each environment's job as `staging / deploy`, the caller's job name then the lane's, which is what a reference deploy declaration names. Publish releases with the Releaser: a release the workflow token creates starts no run.

**Dispatch at the release's tag, always.** To deploy a release again, or to roll back to an earlier one, dispatch the caller at that release's tag, naming it as the input too: `gh workflow run deploy.yml --ref <tag> -f release=<tag>`. The gate refuses a dispatch run at any other ref, the default branch included, as `no-release`, before the probe or any environment runs. That way no job of the lane carries the default branch's OIDC subject, which your QA store's role, and any other role that trusts the default branch, would accept: every job carries the tag's subject or its environment's ([#914](https://github.com/yedeya-labs/kanon/issues/914)).

**The gate** refuses, by name, before anything deploys: `draft` or `no-release` (the release is a draft or missing, its tag moved, or a dispatch ran at another ref than the release's tag), `not-default-branch` (the commit is not on the default branch), `declaration-mismatch` (the caller's list is not the record's at that commit, in order), and `ci-red` or `ci-timeout` (`ci.yml`'s push run on that commit is not green, or still runs after the CI wait; `K-SHIP-8`).

**The hooks.** Three composite actions you write, as you write the project-setup hook:

| Hook | Inputs | Must |
|---|---|---|
| `.github/actions/build/action.yml` | `release`, `sha`, `output` (the directory to fill) | Build what every environment will deploy, from the checked-out commit, into `output`, and fail otherwise. It runs with no credential and no secret, and may run the project-setup hook first |
| `.github/actions/deploy/action.yml` | `environment`, `role` (`production` or `pre-production`), `release`, `sha`, `artifact`, `probe` (`'true'` or `'false'`), `environments` | Obtain the environment's cloud credential and deploy. With `probe: 'true'`, only try to obtain each listed environment's credential, and write the answer, one of `refused`, `obtained` or `unconfigured` per environment, as a JSON object to `$RUNNER_TEMP/kanon-deploy-probe.json` |
| `.github/actions/smoke/action.yml` | `environment`, `role`, `release` | Check the deployed system answers as the release expects, and fail otherwise |

The lane judges each hook by whether it succeeded. The deploy hook's step alone receives `KANON_DEPLOY_SECRET` in its environment: an environment secret of the environment it deploys, empty when the environment holds none. `deploy.yml` declares it as an optional secret, and the caller `kanon init` writes maps it on each environment's job as `KANON_DEPLOY_SECRET: ${{ secrets.KANON_DEPLOY_SECRET }}`. GitHub evaluates that expression in the deploy job's scope, where the environment's secret comes first, then the repository's, then the organisation's; a caller that doesn't map it hands the hook an empty value, whatever the environment holds ([#1049](https://github.com/yedeya-labs/kanon/issues/1049)). So keep it an environment secret only: an environment that holds none would hand the hook a repository or organisation secret of that name, and doctor notes either (`deploy.secret-repository`, `deploy.secret-organization`). GitHub masks it in the log; write it nowhere but `$RUNNER_TEMP`. `artifact` is the directory your build hook filled, downloaded and checked: deploy what it holds.

**The trust probe.** Before anything deploys, a job outside every environment, with `id-token: write`, runs your deploy hook with `probe: 'true'`. Each environment's cloud role must trust only that environment's OIDC subject, `…:environment:<name>`, so every attempt must be refused. The lane prints `kanon-deploy-probe/v1 {"staging":"refused","production":"refused"}` for doctor and goes on only when every declared environment answered `refused`: an `obtained` fails `trust-unbound`, and anything else, a missing answer included, `probe-unconfigured`. Keep each environment's role identifier where a job outside the environment can read it, such as a repository variable: an environment's own variables don't resolve in the probe. The lane reads no role itself; where your hook finds each is yours.

**One build, one artifact.** After the gate and the probe (or the gate alone, when the probe is skipped under the `no-environments` marker), the `build` job runs your build hook once, on the release's commit, and uploads the directory it filled as the artifact `kanon-deploy-build-<run id>-<attempt>`, kept 35 days, with the SHA-256 of its contents as the job's output. It holds `contents: read` and nothing else: no `id-token`, no secret, no environment, so your build's tools and dependencies never run beside a cloud credential. It never runs after a failed or cancelled probe. Every environment's job downloads that artifact by name, checks it against the build's digest before your deploy hook runs, and hands the hook its path: nothing is rebuilt per environment. An artifact that differs, or that expired because a production approval waited longer than your repository keeps artifacts, fails the environment at the `build` stage, before any hook runs. A build that fails stops the run there, with one row and the first environment's issue, as the gate and the probe do. Keep your repository's artifact retention at 35 days or more if a production approval may wait that long.

**Each environment.** `declare` checks the environment is at its position in the record, refusing `declaration-mismatch` otherwise before any reviewer is asked, and derives its role from it. `deploy` sets the environment, so GitHub runs it only after the environment's protection rules pass, and holds one concurrency group per environment, queued and never cancelled mid-run. Once it runs, it refuses `superseded` for a release older than the environment's last successful deploy; a dispatch of an earlier release rolls back, and its row says so. Then it downloads and checks the build, and your deploy and smoke hooks run on the release's commit.

**After each environment.** `record` writes a `deploy` row (its role and position, never its name) as the artifact `kanon-deploy-row-<run id>-<attempt>-<position>`. A rejected approval concludes the job as a plain failure, so `record` reads the run's approvals to tell a rejection from a failure. `report` keeps one issue per environment, titled `Deploy to <environment> failed`: a failure or a refusal files it, labelled `bug` and `sev:high` for production or `sev:medium` otherwise, or comments on the open one; the next success closes it. A rejection or a cancellation files nothing.

**The announcement** (`K-SHIP-10`, [plan 0011](plans/0011-notifications.md) step N9). Each environment announces its own deploy, after `report`. `announce` runs [`scripts/announce-deploy.mjs`](../scripts/announce-deploy.mjs) on the record's outcome and writes one `deploy` message: a deploy that landed names every release of the deployed tag's line (a tag may carry a prefix, `widgets-v1.2.3`) since the environment's previous successful GitHub deployment, as one Features, Fixes and Maintenance summary (`info`), or, under the `no-environments` fallback, where GitHub records no deployment, the deployed release alone; a failure (`failed` or `smoke_failed`) is `critical` on production and `warning` on any other environment, and names the release, the stage that failed, the run and the environment's issue. A refusal, a rejection, a cancellation or a held production announces nothing. `announce` reads the releases and the environment's deployments and writes nothing back, holds no chat secret, and runs only when your commit has a notify hook. `notify` hands the message to your hook with `KANON_CHAT_DEPLOY`, the one secret of the two your caller maps that it reads, and nothing else; without the secret it records `skipped`. A post that fails turns `notify` red and leaves every deploy job green, so a failure to announce is never reported as a deploy's. [`docs/notifications.md`](notifications.md) describes the hook and the message.

**Where the plan has no environments or no reviewers.** Mark it in the section, `- **Fallback:** \`no-environments\`` or `\`no-reviewers\`` ([plan 0010](plans/0010-deployment-lane.md) §13), and state it under `## Plan`. Under `no-environments` the jobs set no environment and the probe is skipped. Under either marker a published release deploys the pre-production environments and holds production: its job is skipped, no row is written and no issue touched, and the run's summary says production waits for the Maintainer's dispatch. The Maintainer the record's `## People` table names then dispatches the caller at the release's tag (`gh workflow run deploy.yml --ref <tag> -f release=<tag>`). A dispatch started by anyone else still deploys every pre-production environment, but its production step is refused. The lane checks whoever started the attempt, so a re-run of the Maintainer's dispatch by someone else is refused at production too, including a re-run of the failed jobs alone.

## The deploy diagnose lane

The deploy lane runs no model ([plan 0010](plans/0010-deployment-lane.md) §9). Its companion, `agent-deploy-diagnose.yml`, is a model lane that reads a deploy after it failed, opt-in and separate: it runs as the Explorer, on `workflow_run` of your deploy caller (`Deploy`), and acts on a run whose conclusion is `failure` only. A successful, cancelled or skipped deploy run starts the lane, and its gate job skips.

- **What it reads.** Its `gate` job, with no model and the workflow token's `actions: read` and `issues: read`, finds the issues the deploy run's `report` jobs filed or commented on: open, titled `Deploy to <environment> failed`, labelled `bug`, and holding the line `Run: <the run's link>` written by `github-actions[bot]`, in the body or in a comment made since the run started. No such issue, and no agent runs. Otherwise it reads the last lines of each failed job's log, cut to a fixed size, and hands them to the agent in its prompt ([`scripts/deploy-diagnose.mjs`](../scripts/deploy-diagnose.mjs)). The agent reads the release's diff with read-only git and `gh release`.
- **What it may do.** It comments its diagnosis on those issues, once each, and nothing else: its App token holds `contents: read` and `issues: write`, and its shell, as the Lead's lanes run it (`K-AGENT-50`), is an allow-list that runs nothing from the tree, with `gh issue comment <number> --body` allowed for exactly the issues the gate found. It deploys, re-runs, dispatches, labels and closes nothing; it holds no `id-token`, no environment and no deploy secret, and runs no hook.
- **What reaches the model.** A deploy log can hold resource names and account details. Your adoption record's `## Data` answer says what may reach the model; install this lane only where it covers your deploy logs. GitHub masks secrets in a log before it stores it.
- **Installing it.** It is in no feature: `kanon init --lanes …,deploy-diagnose` writes its caller beside the deploy caller, and only when deploy environments are declared ([init.md](init.md#the-deploy-lane)). Without the caller nothing runs and nothing is spent. `workflow_run` runs the default branch's copy of the caller, whatever the release's code holds, so the lane gives the release's code no path to its token.

**Its caller,** as `kanon init` writes it, is named `Deploy diagnose (Explorer)`, runs `on: workflow_run` with `workflows: [Deploy]` and `types: [completed]` and nothing else (no `workflow_dispatch`: the lane reads the failed run from the event), grants `actions: read`, `contents: read` and `issues: read`, and has one job, `diagnose`, that `uses:` the lane at your pinned release and maps `AUTHOR_APP_ID`, `AUTHOR_APP_PRIVATE_KEY` and your Claude credential. `Deploy` is the deploy caller's `name:`: rename one and you must rename the other.

## The red-test check

On an agent-authored pull request, one labelled `agent:implement` or `agent:triage`, the red-test check reverts the non-test part of the change to the merge base, re-runs the changed tests, and fails when they still pass (`K-MERGE-13`). A person's pull request is not subject to it, and concludes skipped. It is not a lane: [`red-test.yml`](../.github/workflows/red-test.yml) runs no agent and takes no secret, so `lane-check` holds its caller only to the pin. Call it from a caller of your own on `pull_request`:

<!-- x-release-please-start-version -->

```yaml
name: Red-test

on:
  pull_request:
    types: [opened, synchronize, reopened, labeled, unlabeled]

permissions:
  contents: read

jobs:
  red-test:
    uses: yedeya-labs/kanon/.github/workflows/red-test.yml@v0.42.0
```

<!-- x-release-please-end -->

- **It runs your tests your way.** The `verify` job calls your project-setup hook (`lane: red-test`, `install: 'true'`, the database your `docs/qa/test-database.md` declares), then runs each changed test file on its own, with the runner its [code area](#code-areas) names, or pytest or `go test` for a Python or Go test ([ADR 0012](decisions/0012-test-conventions-by-language.md)). A JavaScript test in no `tests` tree that names a runner is reported, never run, and a Playwright tree is out of its scope. It reverts every changed file in a language Kanon's test conventions read, or a shell script, except a test runner's own configuration.
- **Its verdicts.** `PASS` when a changed test fails an assertion against the reverted source, and `PASS, weakly` when one only fails to load; `BLOCKED` when every changed test still passed; `UNVERIFIABLE` when a changed file was left unreverted (a doc, a migration, a runner config) or an unreverted test helper could explain a load failure; `INCONCLUSIVE` when the runner reported nothing. All but the passes fail the check. The `Red-test scope` job decides first, so a diff with no test or no source to revert concludes skipped, never green.
- **A scope job that fails fails `Red-test verification` too, never skips it** ([#1186](https://github.com/yedeya-labs/kanon/issues/1186)). A ruleset counts a skipped required check as passing. So when the scope job can't decide, for example because the `## Code areas` on your default branch can't be parsed or there is no merge base, the verification job still runs. Its first step fails with "Red-test scope failed", before your hook runs, and the scope job's log says why. Every agent pull request then fails the check until the scope job passes again, which usually means fixing the declaration on your default branch. A pull request can't cause this, because the declaration is read from the default branch.
- **A pull request with no behaviour change is skipped, never red** (`K-MERGE-13`). Its test is a characterization test, locking behaviour that is already correct, so it can't fail on a revert. The scope job says "no behaviour change to revert" when the change outside tests and documentation (`.md`, `.markdown`, `.rst`, `.adoc`) is only comments or whitespace, in JavaScript, TypeScript, Python or Go files present before and after with the same mode, or when there is none. Anything it can't prove that of is verified as before: a shell script, JSX, a comment a tool reads (a shebang, `//go:build`, an `@jsx` pragma), or a config, migration or manifest beside it. It also skips on the run that applying `test:characterization` starts, when a person applied it. An App's label is ignored, and so is the label on any other run, because only the labelling's own event names who applied it, so after a push a person applies it again. `unlabeled` in the caller's `types` lets removing it start a verification. Either way, the pull request states the mutations that turn its new test red, and the Reviewer asks for them. The Merger doesn't count a skipped run as superseding an earlier failed one on the same head, so when the label comes after a red run, a person merges.
- **The verifier script is Kanon's,** at the version your caller pins, so a pull request can't change it. It tests the pull request's head commit, not GitHub's merge ref.
- **It judges with your default branch's code areas, not the pull request's** (`K-MERGE-17`, [#761](https://github.com/yedeya-labs/kanon/issues/761)). Which files are tests, and which runner runs them, come from the `## Code areas` of `docs/qa/stack.md` on your default branch. The scope job reads them before any of the pull request's code runs and hands them to the verification job, which reads nothing from its own tree. A pull request whose `tests` trees or runners differ from both the default branch's and its merge base's fails `Red-test verification` with "Refused: this pull request changes the code areas the check judges with", before your hook runs. It is never skipped: judged by the old areas, a pull request that adds its first `tests` tree would skip tests its new declaration makes runnable. So a new `tests` tree or runner lands first, in a pull request of its own that the red-test check doesn't judge (one without `agent:implement` or `agent:triage`), and the tests that use it come after; otherwise the Merger refuses it, and a person merges it (`K-MERGE-4`). Where you have made `Red-test verification` a required check, landing the tree first is the only route, since `K-MERGE-8` allows no bypass. Rewording an area, or changing a `code` or `audit` area, doesn't refuse. A branch that is only behind a default branch whose areas changed is judged by the default branch's.
- **Your tests, install and hook still come from the pull request,** because the check runs the pull request's tests with its toolchain. The verifier runs on Kanon's Node by absolute path, so a hook that puts another `node` first on the PATH doesn't run it. The pull request's code still shares the runner with the verifier, so a pull request built to defeat the check could forge a test runner's report. The check catches a test that proves nothing, not a pull request built to defeat it (`K-MERGE-13`); a hostile pull request is the job of review and the escalation paths. A pull request that changes your hook touches an escalation path (`K-MERGE-4`), so a person merges it.

## The Merger

The merge lane merges a pull request with no person in the loop only inside the green zone (`K-MERGE-4`): an `agent:implement` or `agent:triage` pull request the Implementer authored, approved by the Reviewer on its current head, with every check green, no escalating path or label, and no invariant promoted to `[confirmed]` (`K-SPEC-9`). It merges through the front door with the Judge App (the Merger's), never as a ruleset bypass actor, and runs no model. It squashes the pull request, pinned to the head it judged, and then checks that the issues it declared closed. Where a merge queue sets the strategy on the pull request's base, it adds the pull request to the queue instead, with the same pin, and leaves one already there; the queue merges it, and the declared issues close then, as when a person queues it ([#1102](https://github.com/yedeya-labs/kanon/issues/1102)). It adds the pull request to the queue directly, so it doesn't need auto-merge allowed on your repository. Its caller:

- **Is named `Merge (Merger)`.** `lane-check` fails it under any other name, because the lane would wait on its own check.
- **Keeps four triggers.** A review is what it acts on. CI completing on your default branch is its sweep, because a merge there changes every other open pull request's mergeability. The hourly `schedule` is a floor for the day nothing merges. A dispatch with `pr_number` and `apply` is the only dry run: without `apply`, it reports each verdict and changes nothing.
- **Grants `contents: read`.** Every write is made with the Judge App's token, minted for the Merger.

**It follows a queued pull request to its outcome** ([#1104](https://github.com/yedeya-labs/kanon/issues/1104)):

- **It records the head it queued.** After adding the pull request to the queue, it comments that it did, with a marker naming the head.
- **It doesn't queue an ejected head again.** The queue runs its checks on the pull request on top of your default branch and the pull requests ahead of it, so it can remove a pull request whose own checks are green. Where the queue has removed one after the Merger queued that same head, the Merger escalates it as `queue-ejected`, naming the queue's reason, instead of adding it back on every sweep. You decide: add it to the queue again yourself if it was a flake, or push a fix. A new head lifts the Merger's `needs:human` and is judged from scratch. The queue's removal event can't say which head it turned away (on a merge it names the merge commit, and on a conflict nothing), so the Merger's marker is what ties the removal to the head. If the Merger can't read its comments to find the marker, it waits rather than queuing the pull request again.
- **It checks the declared issues once the queue merges.** Each sweep lists the pull requests merged as the Merger in the last day and checks that their declared issues closed, as it does right after a squash. GitHub records a merge through the queue as the merge of whoever queued the pull request, and closes the issues as them. A miss is commented once per pull request. A dry run and a run on one pull request skip this.
- **Its summary counts what happened.** A queued pull request is listed under `queued:`, apart from `merged:`, and a merge that found the head had moved is listed under the waits.

**A check that fails after the approval goes back to the Implementer first** ([#1100](https://github.com/yedeya-labs/kanon/issues/1100), `K-MERGE-9`). When the Reviewer has approved the head of the Implementer's pull request and a check then fails on it, there is no changes-request for the revise lane to answer. So the Merger hands the head back once instead of escalating:

- **It comments, then labels.** The comment names each failed check, with the `gh run view <run> --log-failed` command for its log, and carries a marker for the head. Then the Merger removes and re-adds `agent:revise`, which starts the revise lane. The comment comes first because the revise lane looks for its marker.
- **Once per head.** The marker is the record. A sweep within 20 minutes of the hand-back waits for the lane's run. Once the run has registered, the gate waits on it like any other running check. If the same head is still red after that, the Merger escalates `checks-failed` to `needs:human` as before, so the label now means the Implementer tried. A head whose hand-back record can't be read escalates rather than being handed back again.
- **Only a failed check.** A cancelled check still escalates as `checks-cancelled` (re-run it), and a pull request that isn't the Implementer's is never the Merger's to merge.
- **The fix is reviewed.** The revise lane's push dismisses the approval, so the Reviewer reviews the new head before anything merges.
- **It names a fix command it knows.** When every failed check failed on one step, with a failure Kanon's list of fix commands knows, the comment names each by its key. The revise lane then runs those commands instead of a model ([The revise lane](#the-revise-lane), [#1173](https://github.com/yedeya-labs/kanon/issues/1173)). The Merger reads each check's failed log with `gh run view --job <id> --log-failed`; a log it can't read names nothing.

**What the gate doesn't wait on.** It never counts its own run's jobs (the checks whose run is `GITHUB_RUN_ID`) as unsettled, so the run an approval triggers merges a green-zone pull request even though GitHub reports it `UNSTABLE` because of that same run ([#812](https://github.com/yedeya-labs/kanon/issues/812)). The review that woke it and the jobs that start on the same review event aren't checks it requires, but while one of them is still running GitHub reports `UNSTABLE`, and the gate waits on it like any other running check, another Merger run included.

**If your production promotion is human-gated, you may let the Merger merge your high-risk paths** ([#158](https://github.com/yedeya-labs/kanon/issues/158), `K-MERGE-4`). Where every production deploy already waits for a person's approval, say so under `## Choices` in your adoption record, and name what holds the approval:

```markdown
- **Production promotion:** human-gated (the `production` environment's required reviewer)
```

The Merger reads it from your default branch, so the pull request that adds it is judged without it, and escalates anyway, because it changes `docs/qa/`. Once merged, a pull request that touches only your `## Escalation paths` merges in the green zone. Everything else still escalates: `.github/`, the `docs/qa/` documents, `AGENTS.md`, `CLAUDE.md`, `.claude/`, your `## Pipeline code` (each directory there, such as `scripts/pipeline/`, and each single file, such as `scripts/release.mjs`, which covers that file and nothing else; a library your own lanes run only at a pinned release is product, not pipeline code (`K-MERGE-4`), since it reaches them only through its release and the pin bump under `.github/`), a high-risk path you mark `always`, and a high-risk path that is also a judging input (a document your instructions link to). Without the bullet, which is the default, every escalation path escalates, and every sweep says so.

**Mark the code that keeps the promotion gated `always`.** The opt-in relaxes every high-risk path outside `.github/`, including code that decides whether the promotion is gated at all: infrastructure that manages the environment's required reviewers, the cloud role trust that lets only the gated job deploy, or a deploy script an ungated job runs. Unmarked, a pull request that removes the gate merges in the green zone. Put `always` in backticks after the entry's category, and the entry keeps escalating ([#344](https://github.com/yedeya-labs/kanon/issues/344)):

```markdown
## Escalation paths

- `^infra/environments/` `infra` `always` — the production environment's required reviewers
- `^infra/` `infra` — the rest of the infrastructure
```

A Kanon release older than the marker fails by name on an entry that carries it, rather than reading it without it, so add the marker with, or after, the upgrade that brings it. Kanon doesn't check that the environment really has a required reviewer, or that no deploy can skip it: make the declaration only if both hold. The human gate moves to the promotion, where one approval covers every change in the deploy.

On a review, the lane first reads the Merger's and the Implementer's logins from the App register on your default branch, in a job of their own. That job starts no runner for a review on a pull request that is closed, a draft or carries neither lane label. The sweep needs no login, so CI's completion, the schedule and a dispatch start the Merger's own job alone, and bill one runner each.

## The reconciler

The Lead's reconcile lane drives an approved brief to done (`K-PROJ-*`): each tick files the issues the brief proposes, labels them for the Implementer in the brief's order, and closes the project once its merges are deployed to your reference environment. It also re-delivers a review that never landed and a brief pull request's unanswered changes-request, and reports a pull request that is red and unreviewed. A review run that exited zero without posting a verdict counts as one that never landed: the tick re-applies `review:please` once for that head, after the same cool-down as a run the model never answered, so a red head whose only review went silent gets one more review attempt. If that run goes silent too, the head is reported and not retried again ([#622](https://github.com/yedeya-labs/kanon/issues/622)). It runs no model. Its caller:

- **Keeps four triggers:** `pull_request: [closed]` and `issues: [closed]`, so a merge starts the next tick; an hourly `schedule`, the heartbeat that recovers an event that never arrived; and a dispatch with `project` and `apply`, which without `apply` is a dry run.
- **Grants the reads its pre-filters use** on the workflow token: `issues`, `pull-requests`, `checks`, `statuses` and `actions`, all `read`. Without one, a read fails and the tick goes red rather than reading as idle.
- **Passes no budget.** A tick takes at most six chargeable actions across every open project, a constant of the lane.

It needs the Author App (the Lead's), with `Actions: Read` on the installation (the tick probes it before the deploy phase), and your reference environment's deploy declaration (above).

**Filing a project without dispatching it** ([#1113](https://github.com/yedeya-labs/kanon/issues/1113)). Label a project's tracking issue `lead:file-only` when its issues are to be built some other way, by a person or a local session. Each tick still files the brief's issues, mirrors `project:<n>`, tracks open, blocked and closed issues, follows the deploy and closes the project, but labels no issue `agent:implement`: its summary says the label is on, and names each issue eligible for dispatch. An issue you label `agent:implement` yourself is still dispatched by that label, and the tick follows it like any other in-flight issue. Remove the label and the next tick dispatches what is eligible. It isn't `needs:human`: on a tracking issue that label means a tick escalated something no tick can fix, and it stops every phase, filing included, until you remove it.

## Verify acceptance criteria

The verify-acs lane runs the tests that cite one project's acceptance criteria, at the release the reconciler names, and has the Explorer file one bug for each criterion that failed. It reads your playbook's "Targeted-invariant mode" section, or Kanon's baseline when you keep no playbook.

**What runs is Kanon's script on Kanon's Node; what it runs is your project's** ([#1185](https://github.com/yedeya-labs/kanon/issues/1185)). The criteria job runs `scripts/verify-acs.mjs` from the runner's action cache at the version your caller pins, on the Node `kanon-path` set up before your hook, by absolute path, so a hook that puts another `node` first on the PATH doesn't run it. The rest comes from the project under test, by design: this lane verifies your code, so it isn't a judging lane (`K-MERGE-17`). From the release it checks out come the project's brief and its acceptance criteria, the tests that cite them, the `## Code areas` of your stack document, which name each test's runner, and the install and the runners themselves. From your caller's commit come your project-setup hook and your test-database declaration, because the release may predate them. That code shares the runner with the script, in a job that holds no App token and no Claude token (`K-AGENT-50`), so it could change the report the agent reads; the lane guards against a release whose criteria fail, not against a project built to fool its own verification.

**How it files.** The agent chooses each finding's labels, its one `sev:*`, and its subject: `pipeline` when the failed criterion and its citing test are about the platform that builds and checks your project (its CI workflows and guards, its test harness, the Kanon lanes installed in it), and `product` when it is about the code your project ships, never by who found it. A finding about both goes as `K-WORK-4` says: the platform wins. Your playbook's "Targeted-invariant mode" section may say where your project draws that line. It files each finding through the [filing skill](skills.md#the-lanes-skills), whose `plan` command chooses the milestone and prints the arguments of one `gh issue create`. The lane's prompt names no milestone of its own (`K-WORK-8`), and neither should your playbook's section.

## The revise lane

The revise lane answers the Reviewer's changes-request on the Implementer's own pull request, capped in rounds. It also fixes an approved head whose checks failed, when the Merger hands it back ([The Merger](#the-merger)). On `agent:revise` with an approval standing on the head, it acts only when a comment by the Merger's App carries the hand-back marker for that head, read from your App register's `Merger` row, and it tells its agent to fix the failed check and nothing else. A person's `agent:revise` on an approved head still skips. A hand-back counts as a round, so the round cap still applies: past it, the lane skips and the Merger escalates. It acts only on a pull request whose head carries the `kanon/role: implementer` status ([The App register](#the-app-register)), and refuses any other by name. It checks out the pull request's branch, runs your project-setup hook from it, and its agent runs your gates on the code before it pushes, in the job that holds the Author App's token and the Claude token. The Owner accepted that exposure (`K-AGENT-50`); [SECURITY.md's "Accepted exposures"](../SECURITY.md#accepted-exposures) says what it exposes and what bounds it.

**A hand-back whose failed checks all have a fix command runs no model** ([#1173](https://github.com/yedeya-labs/kanon/issues/1173)). Some failures have one mechanical fix, and the check's own output says what it is: `citation-shift` prints its `--fix`. Kanon keeps a list of them in `scripts/lib/fix-commands.mjs`, which starts with `citation-shift`. When the Merger hands back a head, it reads each failed check's log, and when every failed check failed on one step with a failure that list knows, its comment names each one by its key in the list. The revise lane then runs those keys' commands before any model run:

- **The command is Kanon's, never the check's.** The lane looks each key up in the list and runs the list's command, Kanon's own script, with no shell. A key that isn't on the list runs nothing. For `citation-shift` that is `citation-shift.mjs --fix` against the pull request's merge base, with every `--path` your workflows pass the script, and then the script without `--fix`, which must pass.
- **It pushes what the commands rewrote, and runs no model.** One job checks out the branch with the workflow's read token and runs the commands. A second job holds the Author App's token, checks nothing out, and commits the rewritten files over the API onto the head the Merger handed back. The commit is the App's and carries your delegate's sign-off, and the branch moves only if it is still at that head. Neither job runs your project-setup hook or any of your code. The lane comments with its round marker, so the hand-back counts as one round, as the model's run would. The push dismisses the approval, so the Reviewer reviews the new head before anything merges.
- **Anything else runs the model, as above.** That covers a mixed failure, where a check outside the list failed or a job failed on more than one step, and the Merger names no key. It also covers a command that fails or changes nothing, a check still red after its command, and a branch that moved since the hand-back.

## The rebase lane

The rebase lane resolves a merge conflict on the Implementer's pull request, so its CI, review and revision can resume (`K-AGENT-34`). Its agent merges your default branch into the pull request's branch as the Author App, resolves what conflicts and pushes a merge commit, never a force-push. A fixed job after the agent's then carries the `kanon/role: implementer` status to the head it pushed, when the head it started from carried one and every commit on the first-parent path between them is the App's ([The App register](#the-app-register)). Its caller keeps four triggers: CI completing on your default branch, a pull request merged into it (`pull_request_target: [closed]`, which starts it after a merge through a merge queue, [#484](https://github.com/yedeya-labs/kanon/issues/484)), a daily `schedule` as a floor, and a dispatch with `pr_number`. It acts only on a pull request whose head carries the status, and refuses any other by name.

**The merged-pull-request trigger takes nothing from the pull request but its merge** ([#484](https://github.com/yedeya-labs/kanon/issues/484), `K-AGENT-48`). `pull_request_target` runs with your secrets on any pull request, a fork's included, so the lane acts on it only when `merged` is true and the base is your default branch, and the gate judges `merged_by`, who needed write access to merge or queue it. Closing a pull request unmerged, which its author can do, starts nothing. The workflow that runs is your caller on the default branch and the lane at the release it pins. Every checkout takes no `ref`, which on this event is your default branch, and the pull requests the lane resolves come from its own list of open ones, each the Implementer's with its head on your repository, never a fork's and never the one that closed. A merge starts the lane before GitHub has recomputed the other pull requests' mergeability, so the lane reads them again, for up to a minute, while any is still computing.

**Leave a conflict on an Implementer pull request to the lane.** The status is bound to the head the Implementer's run pushed ([#324](https://github.com/yedeya-labs/kanon/issues/324)), so a person's rebase, or a person's merge of the default branch, gives the pull request a head without it. The pull request then leaves the Implementer's chain: the revise lane refuses its next changes-request, the Merger skips it as `not-the-implementer`, and this lane refuses it too, so a person finishes it ([#448](https://github.com/yedeya-labs/kanon/issues/448)). Install the rebase lane with implement or triage, and dispatch it for the pull request when a conflict can't wait for the next run.

**Its agent runs the pull request's code beside its token.** The lane runs your project-setup hook from your default branch, but its agent then checks out the pull request's branch, merges your default branch into it and runs your gates on the result, in the job that holds the Author App's token and the Claude token. The Owner accepted that exposure (`K-AGENT-50`); [SECURITY.md's "Accepted exposures"](../SECURITY.md#accepted-exposures) says what it exposes and what bounds it.

## The dispatch sweep

The Lead's dispatch sweep reconciles the two lanes that a label starts, implement and triage (`agent:implement`, `qa:needs-triage`). An event that never arrived starts nothing, so once a day it re-derives each open labelled issue's state from GitHub: it re-dispatches an issue whose run never happened, or whose question a person answered, up to two attempts; stops one whose latest run hit its turn or budget cap; and reports what waits on a person. On the same run it takes `gate-candidate` off each open issue the Stakeholder has decided, placed on a roadmap milestone or labelled `gate:declined` (`K-WORK-10`). It runs no model. Its caller:

- **Keeps two triggers:** a daily `schedule` (the reference adopter's is `40 4 * * *`), which applies, and a dispatch with `apply`, which without `apply` is a dry run.
- **Grants `contents: read` and `id-token: write`.** The OIDC token is for the lane's store job alone, which reads the cost rows through your store hook. The sweep's own job declares no `id-token`, and no job declares an environment: the store trusts your default branch's ref ([Who can reach the store](qa-store.md#who-can-reach-the-store)). GitHub refuses to start a called job that asks for more than its caller grants, so the grant is needed with or without a store hook; without one, nothing uses it.

**Its cost rows.** An attempt is charged per re-dispatch it made, so it reads 14 days of the two lanes' cost rows to discount a dispatch whose run never reached the model, and to find a run that hit its cap.
- **With a store hook** ([The QA store](qa-store.md)), it reads them through the hook's `cost-rows` operation, and its summary says "Cost rows from the QA store" and "Cost rows read" with a count per lane.
- **Without one**, it reads the lanes' run artifacts (each run of a Kanon lane uploads its telemetry row), and its summary says so. Your repository's artifact retention caps how far back that reaches, and when it is shorter than the 14 days the summary says how much of the window it covered. Settings, Actions, General, "Artifact and log retention" sets it.
- **A read that fails** charges every dispatch, and the summary's line says why.

It needs the Author App (the Lead's), with `Issues: write`, `Pull requests: read` and `Actions: read` on the installation. Until the App's secrets are set, the sweep skips with a warning instead of going red.

## The backlog feeder

The sweep can also feed the Implementer from your backlog ([#609](https://github.com/yedeya-labs/kanon/issues/609)). Each reviewer follow-up is already a spec, with a file cite, a failure scenario and a severity, so after its reconcile the sweep may label up to `QA_BACKLOG_FEED` of them `agent:implement` (`scripts/backlog-feed.mjs`). It is off until you set that repository variable: unset or `0` reads and writes nothing, and the run's summary says the valve is closed. Setting it is the human decision `K-WORK-19` asks for, made once for the repository rather than once per issue, and the bounds below are what keep it one. `kanon doctor` reports the variable's state as a note.

- **Only into a free slot.** It counts the implementer slots in use across every open `agent:implement` issue, as the reconciler counts them: an issue parked on a person (a stop the sweep reads as waiting on a person, `qa:needs-info` or `qa:human-action`) holds none. It feeds nothing once the reconciler's shared cap (`QA_LEAD_GLOBAL_WIP`, default 3) is reached, and nothing while an issue it fed still holds a slot. So projects keep priority, and fed issues go through one batch at a time.
- **What it feeds.** An open issue labelled `follow-up` and `agent:reviewer`, at `sev:medium` or `sev:low`, on a bucket milestone named in `QA_BACKLOG_MILESTONES` (comma-separated, default `Product Backlog`; a milestone with a due date is a roadmap milestone and never fed). It skips an issue carrying `agent:implement`, `qa:needs-info`, `qa:human-action`, `qa:needs-split`, `blocked`, `qa:needs-triage`, `qa:verify` or `gate-candidate`, a project member (a `<!-- qa:project N -->` marker or a `project:N` label), one it fed before, and one the Implementer already posted on, whoever dispatched it. `sev:medium` goes before `sev:low`, then the oldest first.
- **What it writes.** It adds `agent:implement` and then a comment of the Lead's carrying `<!-- qa:backlog-feed -->`, which names the tick and why this issue was chosen. The marker is its only state. To take an issue back, remove the label: it is never fed again.
- **A dispatch is a dry run** unless you tick `apply`, as for the sweep. The summary always says the slots in use, the candidates, and the issue chosen and why, or why nothing was fed.

**What it costs.** Each fed issue costs about one implementer run, two or three review rounds and a merge check: about $15 at API prices, measured on the reference adopter. One a day is about $450 a month of your Claude subscription's quota, and no cloud: the feeder itself runs no model. An issue whose acceptance needs a person's act, such as a vendor portal or live credentials, costs one implementer run that stops.

## The issue backstop

Every issue has a milestone from the moment it is filed (`K-WORK-1`), but some filing paths can't set one: an issue form, or an issue a person files in the web interface and forgets to place. The issue backstop gives such an issue a bucket ([#768](https://github.com/yedeya-labs/kanon/issues/768)). When an issue is opened, it reads the issue's labels and milestone as they are then, never its title or body, and asks [`scripts/issue-triage-defaults.mjs`](../scripts/issue-triage-defaults.mjs), the one copy of the routing, what to write ([`scripts/issue-backstop.mjs`](../scripts/issue-backstop.mjs)). It runs no model. It writes:

- **A bucket, only on a bare issue** (`K-WORK-4`): *Development Automation* for an issue labelled `pipeline-improvement`, *Product Backlog* for every other. It never writes a roadmap milestone (`K-WORK-5`), and never changes a milestone an issue has, so an issue filed with its milestone in one call (`K-WORK-2`) keeps it.
- **`gate-candidate`,** on a `follow-up` + `agent:reviewer` issue at `sev:critical` or `sev:high` that lacks it, on the product bucket (`K-WORK-10`). The issue stays on its bucket.
- **`qa:needs-severity` and a comment with the severity rubric,** on a `follow-up` + `agent:reviewer` issue with no `sev:*` (`K-WORK-9`), unless it already carries the label.

Each write is made only when it is missing, so running it again on the same issue writes nothing new. It acts only at opening: a milestone cleared later is not restored. A filing agent asks the same module first, through the [filing skill](skills.md#the-lanes-skills), so an issue it files arrives with its milestone and labels already chosen by the same rule. On such an issue the backstop also logs a shadow line: what `plan` would have chosen, beside what the filer chose. Its caller:

- **Keeps two triggers:** `issues: [opened]`, which applies, and a dispatch with `issue_number` and `apply`, which without `apply` is a dry run that says what it would write.
- **Grants `contents: read`.** Every write is on the App token.

It needs the Author App (the Lead's), with `Issues: write` on the installation, and the two bucket milestones, which `kanon init` creates with [`kanon milestones`](install.md). It buckets an outsider's issue too: on an opened issue its membership gate admits whoever opened it, the one lane that does (`K-AGENT-45`'s exception, Owner decision 2026-10-14), because it runs no model, reads no issue text and writes only a bucket and labels. A dispatch is still a member's.

## The code audit

The Explorer's code-reading mode reads your code and your specs every few days, and files a bug only on an objective contradiction: a consumer that can't work, a security anti-pattern, a bypassable contract, or code that contradicts a promoted invariant (`K-WORK-9`'s rubric rates it). It reads what your stack document declares under `## Code areas` (above), and the playbook's "Code-reading mode" section. Its caller:

- **Keeps two triggers:** a `schedule` (the reference adopter's is `30 7 */3 * *`) and a dispatch with no inputs.
- **Grants `contents: read`, `issues: read`, `actions: write` and `id-token: write`.** The OIDC token is for the lane's two store jobs alone, and `actions: write` for the job that deletes the store's export after the audit. The audit job itself declares neither, and no job declares an environment ([Who can reach the store](qa-store.md#who-can-reach-the-store)). GitHub refuses to start a called job that asks for more than its caller grants, so the grants are needed with or without a store hook.

**Its memory.** With a store hook ([The QA store](qa-store.md)), the audit widens its coverage from the store's code-reading ledger, read through the hook's `export` before the agent, and its report is written through `put` after it, red run or green. Without one, it runs without memory: the export says the store is absent, the agent chooses areas from the history alone, and `put` is skipped with a notice.

**Its report.** The agent writes `qa-audit-summary.json` on its first turn and re-writes it after each area. The workflow stamps the measured duration, the trigger and the commit, and counts the lines cited itself. A run that wrote no report, or one that doesn't parse, is recorded as such and then turns red; a run whose agent exited non-zero after a complete report stays green with a warning. A run whose agent exited zero, ending its own turn, without the final write that marks its report complete stays green with a warning too: no cap and no error cut it short, so the workflow marks it complete and stores it as `complete: true` with `ended_unmarked: true`, which says the agent never made that write. A run a cap or an error cut short keeps its report's `complete: false`, with `ended_unmarked` false, and its job is red. Both warnings name the turn cap the agent ran under, a dispatched run's raised `max_turns` included.

**How it files.** The agent chooses each issue's labels, a bug's one `sev:*`, and its subject: `pipeline` when the bug is about the platform that builds and checks your project (its CI workflows and guards, its test harness, the Kanon lanes installed in it), and `product` when it is about the code your project ships, never by who found it. A bug about both goes as `K-WORK-4` says: the platform wins. Your playbook's "Code-reading mode" section may say where your project draws that line. It files each issue through the [filing skill](skills.md#the-lanes-skills), whose `plan` command chooses the milestone and prints the arguments of one `gh issue create`. The lane's prompt names no milestone of its own (`K-WORK-8`), and neither should your playbook's section.

It needs the Author App (the Explorer's), with `Contents: Read` and `Issues: Write` on the installation.

## Explore the telemetry

The Explorer's telemetry mode (`agent-explore-telemetry.yml`, plan 0004 step 14) reads Kanon's hosted telemetry once a week, through the aggregate function ([The aggregate function](telemetry.md#the-aggregate-function)), and never a row. The function answers only what may be published (plan 0002 §6.1): cross-adopter cells of at least three adopters, the own figures of each adopter that declared them publishable, and the last week's failure signals, by lane, reason, stage, Kanon error and Kanon version, with how many adopters each affected. The agent looks for anomalies the fixed rules of [#41](https://github.com/yedeya-labs/kanon/issues/41) would miss, and "no findings" is a good run.

**Who can install it.** A repository registered with Kanon's telemetry store, by its collector's first run, whose registration sets `aggregate_invoker`, which Kanon's operator sets on request. The lane reads the aggregate function's token URL with GitHub's OIDC token (plan 0008 §3.6): no role, no secret and no variable. The function admits the token only from this lane at a Kanon release, on your default branch, for a registration with `aggregate_invoker`, and refuses anything else with its code (403 `invoker`, 404 `not-registered`), which the run names, red. While the hosted store's URL is not published in the release you pin, the lane says so in a notice and stops after its gate, green. For a self-hosted store, set two repository variables together: `KANON_AGGREGATE_TOKEN_URL`, its `AggregateTokenUrl` output, and `KANON_TELEMETRY_AUDIENCE`, its `Audience`; one without the other stops the gate, by name.

Its caller:

- **Maps three secrets by name:** the Author App's two and `CLAUDE_CODE_OAUTH_TOKEN`, never `secrets: inherit`. Before plan 0008 J5 it also mapped `KANON_AGGREGATE_ROLE`; the lane still declares it, read by no job, so a caller that maps it keeps starting when its pin moves, and drops it then (§9 step 4). The release after removes it.
- **Keeps two triggers:** a weekly `schedule` (Kanon's is `30 6 * * 2`) and a dispatch with no inputs. A dispatch from a branch other than your default one is skipped, because the store admits the default branch's token only.
- **Grants `contents: read`, `issues: read`, `actions: read` and `id-token: write`.** The OIDC token is for the lane's `aggregate` job alone, which mints a fresh token for the store's audience, sends it to the function's token URL with a `GET`, checks the answer, and hands it to the agent's job as an artifact kept one day. The agent's job declares no `id-token`, and no job declares an environment.

**What the log shows** ([#433](https://github.com/yedeya-labs/kanon/issues/433)). The token is masked before anything prints, and never written. The hosted store's URL is in Kanon's public tree, and is not a credential: the token is the gate. A self-hosted store's URL is masked by the read before its first request, so on a public repository it appears once per run, in the read step's header. The lane reads its two variables by name, never every variable.

**Who files what.** The agent's token reads only. It writes its findings to `qa-telemetry-findings.json`, each naming the signals and cells it rests on, and a job of its own with no agent checks each finding against the same aggregate and files or drafts it (`scripts/telemetry-file.mjs`):
- **Drafted, unless you file them yourself.** Every finding is about Kanon's lanes, so it goes by your adoption record's ``- **Upstream findings:** `filed here` `` choice under `## Choices` (`K-LAYOUT-10`), as the Overseer's do. The lane's gate job reads it from your default branch before the agent runs, so the agent can't change it. With `filed here`, the job mints a filing token and files each finding in your repository. Without it, each checked finding is written into the run's summary, rendered exactly as it would be filed, and nothing is filed and no filing token is minted; you may file one on Kanon by hand. Nothing is ever filed in another repository.
- **Or sent to Kanon, if you opt in** ([plan 0006](plans/0006-upstream-findings.md) §3): `sent` or `sent with evidence` drafts each finding as `drafted` does, and also sends it to Kanon's telemetry store, as codes, or as codes and scrubbed evidence. Both need the telemetry opt-in, a caller of Kanon's telemetry collector; without one `lane-check` and `kanon doctor` report `upstream.unsent`. The lane writes each such finding as a row and uploads it as a `kanon-finding-*` artifact (plan 0006's F3), and the collector sends those rows (F4). With `sent with evidence`, the filing job also mints a read-only token (issues and pull requests: read) and reads the participants of your latest issues and pull requests and your collaborators, as the Overseer does, so the scrub removes their logins from the text; if it can't read them, every text is withheld and the findings are sent as codes only ([#606](https://github.com/yedeya-labs/kanon/issues/606)).
- **The figures come from the aggregate, not the agent.** Each finding must name entries of the aggregate exactly, and the step renders their figures into the issue. The agent's title and body may hold no digit other than an issue reference, a rule id, or a model or Kanon version the aggregate names, and nothing shaped like an adopter key or a stored partition. A finding that breaks a rule is refused by name, never filed or drafted, and the job turns red after the rest.
- **The Explorer's filing gate** (`K-AGENT-9`): a finding that rests on a failure signal is a `bug` (`agent:explorer`, `qa:needs-triage` and its `sev:*`), and one that rests on cost cells alone is a `spec-delta` (`agent:explorer`), each in the bucket your milestone routing gives its labels (`K-WORK-4`; *Product Backlog* for these labels). An open `agent:explorer` issue with the same signature (what it rests on, without the figures) gets a comment with the week's figures instead of a second issue. At most three new issues a run.

It needs the Author App, minted for the Explorer, with `Contents: Read`, `Issues: Write` to file, and `Pull requests: Read` for the scrub's names with `sent with evidence`.

## The digests

Two lanes post a summary to a chat channel. Each writes a few sentences with a model first, and posts its numbers without them if that step fails. Neither mints an App token: they read with the workflow token.

- **The daily project digest posts through the notify job** ([chat notifications](notifications.md)). Its `digest` job writes one Kanon notification and uploads it, holding no chat secret; its `notify` job hands it to the hook you keep at `.github/actions/notify/action.yml`, with your `KANON_CHAT_PROJECT_DIGEST` secret and no other. Without the hook or the secret it posts nothing, and its run stays green.
- **The weekly digest posts through the notify job too** (plan 0011 step N8). Its `digest` job writes one `weekly-digest` message and uploads it, holding no chat secret; its `notify` job hands it to the same hook, with your `KANON_CHAT_WEEKLY_DIGEST` secret and no other. Without the hook or the secret, its gate skips the `digest` job, so no model runs, and its run stays green.

**`DIGEST_WEBHOOK` no longer reaches either digest** (plan 0011 decision 17, a clean break). Neither lane declares it, and GitHub refuses to start a caller that passes a secret the lane doesn't declare, so a digest caller that still maps `DIGEST_WEBHOOK` runs nothing, the project digest's health job included. Drop that line and map the lane's own secret, `KANON_CHAT_PROJECT_DIGEST` or `KANON_CHAT_WEEKLY_DIGEST`, in the same edit that moves the caller's pin; `kanon doctor` names a caller that hasn't (`notify.legacy-secret`). GitHub never shows a secret's value, so fetch the webhook's URL from your chat system again to store it under the new name.

- **The daily project digest** (`agent-project-digest.yml`) is for the developer: where each open project in `docs/projects/` has got to, and what is stopped and why. Its caller keeps a daily `schedule` and a dispatch with `dry_run`. Its narrative is a model run, made only when the digest will be posted or printed by a dry run: the lane's gate reads whether the notify hook exists and whether `KANON_CHAT_PROJECT_DIGEST` is set, and without both it skips the `digest` job and runs only the health job, at no model cost ([#836](https://github.com/yedeya-labs/kanon/issues/836), [plan 0011 §8](plans/0011-notifications.md#8-no-hook)). A dry run writes the message, its plain text and the Slack hook's payload to the run's summary, and posts nothing. Schedule it after the reconciler's hourly tick, so it reads the freshest state.
- **Its health job** rides the same tick. It files one `pipeline-improvement` issue in *Development Automation* naming every lane caller (`.github/workflows/agent-*.yml`) that is red on every recent run, and keeps it until they recover, because GitHub's own failure notification goes to a run's actor, which on a schedule is nobody who reads it. Where an Overseer is installed (`agent-overseer.yml`), it also files one when no weekly Overseer audit has landed in nine days. And it files one naming every lane caller with a `schedule` that has gone far longer than its cron without a scheduled run ([Schedules are best effort](#schedules-are-best-effort)). It needs `actions: read` and `issues: write`, which the caller grants. It runs with or without a hook or a chat secret, and never posts a chat message: the issue is the record (plan 0011 decision 13). A dry run prints its table and files nothing.
- **The weekly digest** (`agent-weekly-digest.yml`) is for a stakeholder outside the day-to-day work: the week's milestone burndown and what was delivered, in plain language, and nothing pending. Name its reader with a `- **Weekly digest audience:** …` bullet under `## Choices` in your adoption record (`K-LAYOUT-10`), read from your default branch; without it, the narrative is written for "a stakeholder who follows the project from outside the day-to-day work". Its caller keeps a weekly `schedule` and a dispatch with `week_end` (the end of the 7-day window, an ISO date) and `dry_run`. A dry run writes the message, its plain text and the Slack hook's payload to the run's summary, and posts nothing.

## Schedules are best effort

GitHub runs a `schedule` late, and drops some of its ticks, when Actions is busy ([GitHub's docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#schedule)). On Kanon's own repository and another one, over the week to 2026-10-13, an hourly cron fired four to six times a day, in batches four to ten hours apart, and a daily cron fired six to nine hours late ([#813](https://github.com/yedeya-labs/kanon/issues/813)). GitHub also disables a public repository's schedules after 60 days without activity, runs a schedule as whoever last changed its cron (so it stops when that account does), and reads it only from the workflow file on your default branch. A schedule that stops leaves no run, so nothing turns red.

So a lane's schedule is a floor for a lost event, not its retry. What re-asks each lane that waits for its next sweep:

| Lane | What it waits for on its sweep | What re-asks it besides the schedule |
|---|---|---|
| Merge | a pull request whose merge state or checks haven't settled | a review submitted on it, and CI completing on your default branch (not after a merge through a merge queue). Its retry is being reworked in [#812](https://github.com/yedeya-labs/kanon/issues/812) |
| Lead, reconcile | the next phase of a project, a crashed run to retry once its cool-down has passed, a review that never landed, the rest of a tick's budget | any pull request or issue closing in the repository, a dispatch, and, with the re-ask below, a real run of the review, implement-revise, Lead revise or implement lane completing |
| Rebase | a conflicting agent pull request | CI completing on your default branch, and a pull request merged into it |
| Dispatch sweep, and its backlog feeder | an implement or triage run whose label event never arrived; a free implementer slot | a dispatch, and, with the re-ask below, a real run of the implement or triage lane completing |
| Merge reconcile | nothing: it has no schedule | a review, and a merge |
| Telemetry collector | the rows since its last successful sweep | nothing, and nothing is lost: each sweep reads back to the last successful one |
| Explore, code audit, explore the telemetry, Overseer, digests | their cadence | nothing is waiting on them; a late run is a late report |

**The re-ask: the dispatch sweep and the reconciler are also asked by the lanes they cover** ([#813](https://github.com/yedeya-labs/kanon/issues/813)). A lost label event leaves no run to notice it, and a crashed run is retried only once its cool-down has passed, which no close event marks. So both lanes take an optional `workflow_run` trigger on the callers whose runs they recover, by those callers' `name:`. `kanon init` writes it in each caller it writes ([#833](https://github.com/yedeya-labs/kanon/issues/833)), naming each covered caller by the `name:` of the one the repository already has, and by the name `init` gives it where there is none yet ([#1023](https://github.com/yedeya-labs/kanon/issues/1023)). `init` never overwrites a caller, so one written before that, or one whose covered callers you renamed since, shows as `differs` in its run, with the names in the diff; add or correct it under `on:`:

```yaml
# In the dispatch sweep's caller
  workflow_run:
    workflows: ["Implement (Implementer)", "Triage (Implementer)"]
    types: [completed]
```

```yaml
# In the reconciler's caller
  workflow_run:
    workflows: ["Review (Reviewer)", "Implement (Implementer) — revise", "Lead (Lead) — revise", "Implement (Implementer)"]
    types: [completed]
```

- **Only a real run asks.** A run whose jobs all skipped, such as the implement lane on a label that isn't its own, concludes `skipped`, and the lane skips its re-ask at no runner cost. A run of the lane's own caller is never admitted, so a lane can't re-ask itself, whatever its caller lists.
- **The cadence is kept.** Those lanes complete far more often than the cron ticks. The sweep sweeps on a re-ask only when no run of its caller has swept in the last 20 hours, because its re-dispatch cooldown assumes a daily sweep. The reconciler ticks on one only when no run of its caller has ticked in the last 45 minutes ([`scripts/reask-due.mjs`](../scripts/reask-due.mjs)). A re-ask that declines leaves the lane's working job skipped, so it doesn't count, and the next re-ask after the window acts. A listing that can't be read runs the lane.
- **That window is also the loop guard.** A sweep's re-dispatch starts an implement run, and a tick's re-delivery starts a review or a revise run. When that run completes, it finds the sweep's or tick's own run inside the window, and stops there.
- **What it needs.** The reconciler reads its caller's runs on the workflow token, which its caller already grants `actions: read`. The sweep mints the Lead's App token, narrowed to `Actions: read`, which that App already holds, so neither caller grants more. GitHub runs a `workflow_run` workflow only three levels down a chain, so a review started by CI's completion can still re-ask the reconciler.
- **What remains on the schedule.** In a repository where nothing else runs, nothing re-asks, and the schedule is the floor. A schedule that stops is named by the health job below, within 14 hours for an hourly cron and 60 for a daily one. Kanon's own callers take the re-ask once they pin the release that carries it. Before that release, the lanes skip a `workflow_run`, and a skip-only run would still replace a pending real one.

**The daily health job notices a schedule that has stopped.** For each lane caller with a `schedule` (the files it watches for red runs), it reads the workflow's state and its newest run started by `schedule`, and names it in one `pipeline-improvement` issue when that run is older than twice the cron's longest gap between ticks plus 12 hours: 14 hours for an hourly cron, 60 for a daily one, 14.5 days for a weekly one. A schedule is measured from the newer of that run and the last commit to its file on the default branch, because a push to the file re-registers its schedule, so a `schedule` added to an old caller is not named before its first tick is due ([#818](https://github.com/yedeya-labs/kanon/issues/818)). A workflow with neither is measured from when GitHub registered it. One that GitHub disabled is named too; one a person disabled is listed in the run's summary and not escalated. The issue is refreshed when the set changes and closed once every schedule it names has fired, or had its file changed, inside its bound. It runs in [the project digest's health job](#the-digests), on that lane's own daily schedule, so it needs the project digest installed, and it can't see its own schedule stop.

## The Explorer's sweep

The explore lane (`agent-explore.yml`) has the Explorer triage a sweep of your running product and file what it finds. What it sweeps, with which tool and in which tiers, is your product, so the sweep is yours: a composite action at `.github/actions/explore-sweep/action.yml`, the **sweep hook** (plan 0004 decision 5). The lane sets the project up through your project-setup hook, with `lane: explorer`, `browsers: 'true'` and the database your test-database declaration gives, then calls the sweep hook with one input, `tier`, and reads one file it writes, `qa-explore-summary.json`. [The Explorer's sweep](explore-sweep.md) has the hook's contract and the summary's format. A summary that is missing, malformed, or for another commit or tier is no sweep: the run goes red by name, the agent doesn't run, and nothing is recorded.

Its caller:

- **Keeps two triggers:** a daily `schedule`, and a dispatch with `tier`, passed through. Blank sweeps every tier.
- **Grants `id-token: write`,** for the lane's store jobs alone, and `issues: read` and `actions: read` for the quality and telemetry reads. The Author App's token, minted for the Explorer, files the issues.

**How it files.** The Explorer chooses each bug's labels and its one `sev:*`, and files it through the [filing skill](skills.md#the-lanes-skills), whose `plan` command chooses the milestone and prints the arguments of one `gh issue create`. The lane's prompt names no milestone of its own (`K-WORK-8`).

**The change gate.** A scheduled run on a commit your QA store already holds a green full sweep of is skipped, and the skip is recorded, so a quiet day costs one short job, not a sweep. A dispatch always sweeps. The store's answer is read in a store job, through your store hook (`last-green`), and the run's summary is recorded the same way (`put`). Without a store hook the lane always sweeps, says the store is absent, and records nothing.

## The Overseer

The Overseer is optional. It audits your pipeline once a week from the aggregate: precision per signal, follow-up leakage, backlog dynamics, the QA store's runs and coverage, workflow history, the cost trend and the prompt-cache facts where your repository sends telemetry, and the capability ledger where your adoption record turns the capability watch on (`K-SELF-9`). It keeps one rolling audit issue, titled `[pipeline] audit-summary — Overseer audit #N`, and closes the one before it (`K-SELF-11`). Say whether you install it with one bullet under `## Choices` in your adoption record (`K-LAYOUT-10`):

```markdown
- **Overseer:** `installed`
```

or `not installed`. `lane-check` fails a record that doesn't say, or that says `installed` with no `agent-overseer.yml` caller, or `not installed` with one. Its caller:

- **Keeps two triggers:** a weekly `schedule` (the reference adopter's is `0 7 * * 1`) and a dispatch with no inputs.
- **May add the runtime-version trigger** ([#423](https://github.com/yedeya-labs/kanon/issues/423)), which `kanon init` writes: a merged pull request on your default branch that changes the caller file itself, written `pull_request_target: types: [closed]` with `branches:` your default branch and `paths:` the caller's own path. Your agent runtime is the Claude Code CLI that the Kanon release you pin installs, so it moves only when Dependabot moves that pin. It audits only where your adoption record turns the capability watch on (below); otherwise it runs only the gate job, which says so. On that merge the lane's gate job compares the runtime of the release it now runs with your capability ledger's watermark (`K-LAYOUT-7`), read from your default branch, and audits only when the runtime is newer, compared part by part as numbers; the same version or an older one (a rollback) skips the audit, and the run says so in its summary. When it audits, the agent is told the trigger, and the capability review is due whatever the week. **The QA store isn't read on this trigger:** your store's role trusts only your default branch's ref, and a `pull_request_target` token's subject names the pull request, so the export is `degraded`, which the audit expects and doesn't report as a finding. The weekly run reads the store. Anything it can't read, such as a ledger with no bare watermark, makes the audit run. The membership gate judges the member who merged, `pull_request.merged_by` (on a merge-queue merge, the member who queued it); a pull request closed unmerged is turned away. Keep the ledger's watermark folded in from the audits' `Ledger delta`, or each later upgrade with the same runtime audits again.
- **The capability watch is your choice, off by default** ([#477](https://github.com/yedeya-labs/kanon/issues/477)). The capability review reads the agent runtime's changelog, and your runtime is the one your Kanon release pins, so every finding it could make is one only Kanon can act on: Kanon's own Overseer runs it, once, for everyone. A repository that maintains its own runtime pin turns it on with ``- **Capability watch:** `on` `` under `## Choices` in `docs/qa/adoption.md` (`K-LAYOUT-10`). Without it the audit's `### Capability watch` section says the watch is off by choice, the runtime-version trigger runs only its gate job and skips, and you need no capability ledger (`lane-check` and `kanon doctor` say so in a notice). The lane's gate job reads the choice from your default branch before the agent runs, and stops by name on a malformed bullet.
- **Grants `contents: read`, `issues: read`, `actions: write` and `id-token: write`.** The OIDC token is for the lane's store job and its `telemetry` job alone, and `actions: write` for the jobs that delete the store's export and the telemetry reports after the audit (`delete-telemetry`). The audit job itself declares neither, and no job declares an environment ([Who can reach the store](qa-store.md#who-can-reach-the-store)).

**Who files what** (plan 0004 decision 12). The agent's token reads only. It writes its audit and its findings to a file, each finding naming its subject, and a job of its own, on a fresh runner that runs no agent and checks out nothing, files them on a token of its own (`scripts/overseer-file.mjs`), then deletes the file's artifact:
- **A finding you can act on** (a declaration, a playbook, a hook, an App or its permissions, cost, a schedule, labels, milestones, test or spec coverage) is filed in your repository as a `pipeline-improvement` issue, in *Development Automation*.
- **A finding only Kanon can act on** (a lane's behaviour, a guard, a rule, Kanon's library) is never filed in your repository. It goes under the audit issue's `## Upstream` heading, as a draft you may file on Kanon by hand, after checking it names nothing of your project (ADR 0007). The heading is there every week, empty or not.
- **Unless your adoption record says they are filed in your repository:** ``- **Upstream findings:** `filed here` `` under `## Choices` (`K-LAYOUT-10`) files each of them in your repository instead, for a repository that can act on them itself. It never files in another repository. A finding whose subject the step doesn't know stays a draft. The lane's gate job reads the choice from your default branch before the agent runs, so the agent can't change it; without the bullet they are drafts.
- **Or sent to Kanon, if you opt in:** `sent` or `sent with evidence` keeps each draft, and also sends the finding to Kanon's telemetry store over the telemetry channel, as codes, or as codes and scrubbed evidence ([plan 0006](plans/0006-upstream-findings.md) §3). Both need a caller of Kanon's telemetry collector; without one `lane-check` and `kanon doctor` report `upstream.unsent`. The lane writes each such finding as a row and uploads it as a `kanon-finding-*` artifact (plan 0006's F3), and the collector sends those rows (F4).
- **A capability investigation** is filed only while the capability interlock is clear, counted by `scripts/capability-interlock.mjs`, and at most one a week (`K-SELF-17`).

**What it reads.** Its playbook, `docs/qa/overseer-playbook.md`, with the sections `K-LAYOUT-17` names; the capability ledger, when your record turns the capability watch on; with a store hook, the store's `overseer` export ([The QA store](qa-store.md)), including the recall clusters your hook writes; and, when your repository sends telemetry, the week's token trend and cache-TTL facts, which a job of the lane computes from your own rows in Kanon's hosted telemetry store, read with GitHub's OIDC token, and hands the agent as two files, never rows ([The Overseer's cost view](telemetry.md#the-overseers-cost-view), [#470](https://github.com/yedeya-labs/kanon/issues/470)). Nothing is set for it: the lane reads your rows only when a workflow on your default branch calls Kanon's telemetry collector, your consent, and otherwise the audit says the read is `not configured`, as it does before the collector's first run registers you. On the runtime-version trigger the read isn't attempted, since the store refuses that token, and the audit says it was `not run on this trigger`. For a self-hosted telemetry store, set two repository variables together: `KANON_TELEMETRY_TOKEN_URL`, its `IngestTokenUrl` output, and `KANON_TELEMETRY_AUDIENCE`, its `Audience`. The lane still declares `KANON_TELEMETRY_READER_ROLE`, read by no job, so a caller that maps it keeps starting; drop it when your pin reaches the release that reads with the token. Without a store it audits from GitHub alone, and says the store is absent.

It needs the Author App (the Overseer's), with `Contents: Read`, `Issues: Read & write`, `Pull requests: Read` and `Actions: Read` on the installation: the workflow history is the one place a run that died writing nothing is visible.

## Checking it

Run [`lane-check`](../actions/lane-check/README.md) in CI. It fails on a caller that holds more than the above, a caller that isn't at its lane's file name, a review or reconciler caller without `.github/workflows/ci.yml`, a review caller whose `run-name` doesn't end with the head SHA, or a Merger caller not named `Merge (Merger)`, passes a setting instead of an input (a number for `max_turns` included, `max_turns` without `reason`, or a `default` on either dispatch input), maps the wrong secrets, grants too little, or pins a second version; on a missing or incomplete hook, or a missing sweep hook for an explore caller; on a missing stack document, or a missing capability ledger where the adoption record turns the capability watch on, or a stack document without `## Gates` or with a section twice; on a malformed test-database declaration, escalation file, exemptions file, deploy declaration (a reference-deploy bullet left under `## Choices` included) or production-promotion declaration; on an adoption record whose Overseer bullet, or its default `not installed`, the callers contradict; on a role missing from the App register, a register whose Apps' roles name two slugs or share one, or a caller that maps a role-named App secret; and on a missing Dependabot entry.
