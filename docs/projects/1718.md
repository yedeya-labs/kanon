# Project brief — An opt-in upgrade lane that carries a repository to each new Kanon release

The mandate is [#1718](https://github.com/yedeya-labs/kanon/issues/1718)'s body (`K-PROJ-15`). This brief doesn't reopen the five constraints that body lists. One of them is itself a choice: the lane "takes over Dependabot's Kanon pull request, or says how to turn Dependabot's `kanon` group off, rather than open a second one". The mandate leaves open which of those the lane does, what the opt-in looks like, and whether a release's caller changes are a scope-first bail. It also says the Reviewer reviews the upgrade, which leaves open who restarts the Implementer on a change request. Those are decisions 1 to 4 and 7 in §7, each awaiting the Owner.

## 1. The real problem

**One root cause: moving the pins is automated, but knowing what a release needs from the callers is not.** That knowledge lives in two places only: `kanon doctor --to <release>`'s findings, and the interactive upgrade skill that a person runs. These commands re-run on `main`:

- **Dependabot moves only the `uses:` refs.** `git grep -n "Dependabot's upgrade pull request moves only the" -- actions/lane-check/README.md` shows `lane-check` turning such a pull request red, telling the person to run `/kanon:upgrade`, and listing what only a person can do. So today every release that changes a caller ends with a red check and a person at a keyboard.
- **The edit is already one script.** `git grep -n "the skill and Kanon's own pin job make the same edit" -- scripts/move-pins.mjs` shows `move-pins.mjs` serving both the skill and Kanon's own pin job. It is `pipeline` `always` (`git grep -n "move-pins" -- docs/qa/escalation-paths.md`).
- **The Implementer can already write workflow files.** `git grep -n "Workflows write for the three Implementer lanes" -- docs/lanes.md` shows the push job holding Workflows write, so this project needs no new grant for the Implementer's agent or its push job (`[LANE-13]`, `[LANE-14]`).
- **A person's step already has a waiting room.** The implement lane labels a scope-first bail `decision:needed`, and a member's reply restarts the run (`K-AGENT-13`, `K-WORK-24`; `git grep -n "Your reply restarts it" -- docs/lanes.md`). The mandate's "person-only step" reuses this as it is.
- **The Owner already merges anything that moves a pin.** Every file under `.github/` and `.claude/` is an escalation path that no declaration can remove (`K-MERGE-4`). So the "Owner, never the Merger" constraint holds today. This project pins it with a test (`[LANE-34]`) and builds no new gate.

So the fix is one systemic piece: a lane that turns "a release is out" into an Implementer issue, with the Implementer carrying out what the skill does (pins, plugin `ref`, callers) and stopping on what only a person can do. Point fixes, such as more `lane-check` hints or a smarter Dependabot entry, would leave a person running the skill on every release.

**Six findings of mine, each shaping an item or a decision:**

1. **"Take over" can't mean pushing onto Dependabot's branch.** The push job refuses any branch that already exists on GitHub, except a revise lane's own (`[LANE-15]`). Widening that to a branch another bot wrote would be a security change for no gain. So the Implementer opens its own pull request, and the lane closes Dependabot's with a link (`[LANE-30]`, decision 1).
2. **Turning Dependabot's `kanon` group off is a rule change.** `K-ADOPT-11` requires the Kanon entry, and `lane-check` fails a repository without one (`git grep -n "has no github-actions entry for" -- actions/lane-check/lane-check.mjs`). Letting an opted-in adopter turn the group off amends that rule, and the rule is the Owner's (decision 1, `[LANE-31]`).
3. **The revise lane refuses the upgrade pull request on its own triggers.** A pull request that moves the pin is refused by the lanes it starts on `pull_request` and `pull_request_review` until it merges (`K-MERGE-17`; `git grep -n "refuse, visibly, until it merges" -- docs/lanes.md`). A dispatch from the default branch runs the default branch's pin, and is admitted. So a change request is revised by a dispatch (`[LANE-33]`). Making one needs Actions write, which the Author App, the upgrade lane's App, doesn't hold: `rulebook/agent-permissions.json` gives it `"actions": "read"`, and only the Judge App holds write (`docs/qa/agent-identities.md`). Kanon has avoided granting it for dispatches until now (`git grep -n "RE-ADDING the label, not by workflow_dispatch" -- scripts/dispatch-sweep.mjs`). So who makes the dispatch is an authority choice, and it is the Owner's (decision 7).
4. **A release's caller changes are bail-list changes.** A new `permissions:` grant or secret mapping is an auth or credential change (`K-AGENT-13`'s bail list). Read literally, nearly every upgrade would stop for a plan. Whether the release, not the Implementer, decides those changes is the Owner's call (decision 3, `[LANE-28]`).
5. **The Implementer runs at the old release, and the knowledge is at the target.** The implement lane runs from the default branch, at the pin being replaced. So the Implementer reads the target's own `kanon doctor --to <target> --json` and the target's `lane-check`, as the skill does with `npx`, rather than anything the old release knows (`[LANE-27]`). The first release that ships the lane can't carry an adopter to itself. Adopters reach it the way they do today.
6. **The choice's reader becomes credential-reachable code.** `lane-check` will read the new bullet, and Kanon's pin job runs `lane-check` from this tree with the Releaser's key (`git grep -n "imported by the pin job's check" -- docs/qa/escalation-paths.md`). So the reader joins that `always` entry, and Issue A is the Owner's merge.

**Reconciliation gaps: none in the area this project touches.** `kanon-spec-coverage` reports 0 `[confirmed]` clauses with no test in any area, and `LANE` has none. There is no uncited `[confirmed]` clause for an Issue A to close. The report exits 1 on `main` for an unrelated reason (§8). The project seeds `[LANE-22]` to `[LANE-37]` in [`docs/qa/specs/lanes.md`](../qa/specs/lanes.md), allocated with `kanon-spec-ids --apply`.

## 2. Scope

**This project is:**
- the `Kanon upgrades` choice, its one reader, and the target it resolves for `stable` and `candidates`;
- a no-model upgrade lane that files or retargets one `Upgrade Kanon to <target>` issue for the Implementer;
- the Implementer's upgrade: pins, plugin `ref` and callers, with a person's steps held under `decision:needed`;
- taking over Dependabot's Kanon pull request, and letting an opted-in adopter turn the `kanon` group off;
- the Reviewer's reading of an upgrade pull request, its revision by dispatch, and a test that the Merger never merges it;
- the install question, the `lane-check` and doctor checks, and the docs (install, lanes, upgrade skill), each item carrying its own tests and docs.

**It is not:**
- **Merging, ever.** No path lets the Merger or any agent merge the upgrade. The green zone is unchanged.
- **A person's steps.** The lane never types a secret, widens an App's permission, deploys intake, or answers a new install question on the adopter's behalf. It lists them.
- **Each person's installed plugin.** The pull request moves the repository's declared `ref`. Moving each person's own installation stays as the skill's step 9 says.
- **Kanon's own repository.** Kanon doesn't call the lane: its candidate pin job and its Dependabot entry stay exactly as they are (`[LANE-24]`, decision 11).
- **Dependabot's other groups.** Third-party action bumps are untouched.
- **Retiring the upgrade skill.** People still run it, and it gains a section on the lane (`[LANE-37]`).
- **Rolling back a bad upgrade.** A revert is a person's, as for any merge.
- **Upgrading into the first release that ships the lane.** That release arrives as today, by Dependabot or the skill (§1, finding 5).

**Specific to this project's definition of done:**
- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **A live run is owed by a person.** Kanon doesn't call the lane, so the tests are the only proof inside this repository. The Maintainer closes #1718 once a stable release carrying Issue F is out, `verify-acs` is green, and one opted-in adopter has received an upgrade pull request from the lane. The reconciler stops at the deploy phase, because Kanon declares no reference environment (`K-PROJ-11`), as it did for #1327 and #1373.
- **Routing.** The lane, its checks and its docs ship to adopters, so every item is `enhancement` on Product Backlog (`K-WORK-4`), as the tracking issue is.

## 4. Cost

**Once, building it.** There are six pull-request items, A to F. `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/agent-implement.yml .github/workflows/review-agent-job.yml` shows the Implementer's ceiling is $120 and the Reviewer's $30. So the worst case is **$720** of implementer runs and **$180** of first-round reviews, before revisions. That is a ceiling, not an estimate.

**Recurring, on Kanon: $0.** Kanon doesn't call the lane (decision 11), and nothing else in this project runs on a schedule here. Actions minutes on Kanon's public repository are free (`gh api repos/yedeya-labs/kanon --jq .visibility` prints `public`).

**Recurring, on an opted-in adopter.** This is the adopter's spend, and `docs/lanes.json`'s cost line tells them before they opt in:
- **The daily tick.** A no-model job of about a minute, inferred, not measured: about 30 Linux minutes a month on a private repository, and $0 on a public one.
- **Per stable release, one implement run and one review.** The ceilings are $120 and $30, plus a revise run (ceiling $120) when the Reviewer requests changes. The cadence is measured by `gh api "repos/yedeya-labs/kanon/releases?per_page=40" --jq '.[] | select(.prerelease==false) | .tag_name + " " + .published_at'`. Candidates began with `candidate-v0.41.0`, published 2026-10-16T14:11Z (the same command with `prerelease==true`). From then to 2026-11-09, it lists one stable release, `v0.42.0` on 2026-10-28. So I plan against one upgrade a week as a ceiling, and the measured rate since candidates is well under it.
- **Under `candidates`,** one more upgrade per candidate that passes the end-to-end gate. The same command with `prerelease==true` lists five candidates from 2026-10-16 to 2026-11-09, `candidate-v0.41.0` to `candidate-v0.45.0`.
- **Model cost of the lane itself: none.**

**The Owner's time:**
- a merge on every item, A to F (§6);
- an answer to each item's plan stop, six in all (decision 4);
- on each adopter, one merge per upgrade, which is the mandate's own constraint;
- on each adopter, depending on decision 7: under (a), one App permission change before the lane can revise; under (c), one dispatch per change request; under (b), nothing more.

## 5. Observability

**Add:**
- **The lane's step summary.** It names the choice it read, the pin, the target or why there is none, the issue it filed, retargeted or left alone, and any Dependabot pull request it named or closed (`[LANE-25]`, `[LANE-26]`, `[LANE-30]`). A failed read fails the run, which `workflow-health` and the project digest's health job already report for a lane caller that keeps failing.

**Skip:**
- **A new alarm or metric.** Kanon pages on nothing (`docs/qa/adoption.md`, Choices). An upgrade that waits on a person is already visible: the issue carries `decision:needed`, which `kanon inbox` lists, and the pull request waits for a person's merge, which the needs-the-Owner view lists (`[STAT-10]`, `[STAT-16]`).
- **A telemetry field for upgrades.** The implement run's existing row already records the run and its cost.

What would change this: an adopter whose upgrade issue sits open for more than two stable releases. That would argue for the digest naming a stale upgrade, filed as an issue then.

## 6. Blast radius — what will need a human

**The scope-first bail list.** Every item is an **auth, credential or security change**:
- A adds credential-reachable code to the pin job's closure (§1, finding 6).
- B adds a lane that holds the Author App's token and labels work for an agent.
- C directs an agent to rewrite the workflows that hold every lane's secrets and grants.
- D gives that lane Pull requests write to close Dependabot's pull request, and amends `K-ADOPT-11`.
- E changes what the Reviewer is told to accept, and gives a fixed step Actions write to dispatch the revise lane: on the Author App, a broadened grant, or on the Judge App, a new use of the grant it holds (decision 7).
- F changes what `lane-check`, a required check, fails.

The Implementer stops on each, and the Owner answers its plan (decision 4). There is **no data migration and no destructive schema.**

**Escalation paths this project touches** (`docs/qa/escalation-paths.md`):

| Item | Path | Why it goes to the Owner |
|---|---|---|
| A | `docs/qa/escalation-paths.md` (the reader's `always` entry) | directly in `docs/qa/` (`K-MERGE-4`) |
| A, D, F | `actions/lane-check/` | `^actions/` `always` |
| B, C, E | `.github/workflows/` (the new lane, the implement lane's prompt, the review prompt) | under `.github/` (`K-MERGE-4`) |
| C, D | `rulebook/` (`K-AGENT-13` if decision 3 says so; `K-ADOPT-11`) | `^rulebook/` `always` |
| E, if decision 7 is (a) | `rulebook/agent-permissions.json` (the Author App's `broadened` record) | `^rulebook/` `always`; App permissions are agent authority (`K-PROJ-18`) |
| E, if decision 7 is (a) | `docs/qa/agent-identities.md` (the Author roles' Actions column) | directly in `docs/qa/` (`K-MERGE-4`) |
| C, F | `skills/upgrade/` | `^skills/` `always` |
| B, F | `requirements.json`, if the new lane changes what it derives | `always` |

**Green:** `cli/` (`init.mjs`, `doctor.mjs`), the new lane's own script under `scripts/`, `docs/` outside `docs/qa/`, and `tests/`.

**A person's step on every opted-in adopter, if decision 7 is (a).** Their Owner updates their Author App to Actions: Read & write and accepts the change on its installation, before the lane can revise. No agent can do this, and Issue F's docs and doctor must name it. Under (b) or (c) no adopter changes an App.

**Softer items:**
- **An agent edits the workflows that judge every later pull request.** That is the mandate. The Owner's merge, the Reviewer reading against the release notes (`[LANE-32]`) and the target's `Lane check` are the three readings it gets.
- **The target's code runs before the merge.** The Implementer runs the target's `kanon doctor` with its own read token, and CI runs the target's `lane-check`, as on Dependabot's pull request today. Under `candidates`, that code is a candidate that passed the end-to-end gate but isn't promoted (`[LANE-23]`).
- **A revise run at the old release edits a pull request moving to the new one** (`[LANE-33]`). It reads the issue and the change request, and the Reviewer reads its result again.

**What the Reviewer should escalate rather than approve:**
- an upgrade pull request that changes a line outside the pins, the plugin `ref`, the callers and the declarations the target asks for (`[LANE-27]`);
- an Implementer that wrote a secret's value, or guessed a person's answer (`[LANE-28]`);
- any lane push to a Dependabot branch (`[LANE-30]`);
- any code path that reads the repository's name to decide (`[LANE-24]`);
- any token holding Actions write other than the one step decision 7 names, and any agent's token holding it at all (`[LANE-33]`).

## 7. Decisions

Decisions 1 to 4 and 7 change a rule, what an agent may do, an App's authority, or the product's behaviour, so each is the Owner's, and each is still open. Decisions 5 and 11 restate the mandate. Decisions 6 and 8 to 10 are technical, and I settled them (`K-PROJ-18`).

1. **How the lane and Dependabot share Kanon's pins. ⛔ OPEN, awaiting the Owner.** Recommended: (a).
   - **(a) Take over, and allow off.** The lane names Dependabot's Kanon pull request on the upgrade issue, and closes it with a link once the upgrade pull request is open (`[LANE-30]`). With the opt-in, an entry that ignores Kanon is also accepted, and doctor notes one still proposing it (`[LANE-31]`). This amends `K-ADOPT-11`'s "upgrades arrive as Dependabot pull requests", carried into Issue D. One pull request per release either way, and an adopter who keeps the group loses nothing.
   - **(b) Take over only.** No rule change, but every release then opens a Dependabot pull request that the lane closes: one closed pull request of noise per release.
   - **(c) Require the group off.** Cleanest, but it imposes a Dependabot change on opting in, and the mandate says Kanon suggests and never imposes.
   - **(d) Say how to turn the group off, and take over nothing.** The mandate's other branch. The docs and doctor tell an opted-in adopter how, and the lane never touches Dependabot's pull request, so `[LANE-30]` goes. It still amends `K-ADOPT-11` as (a) does, and an adopter who keeps the group gets two pull requests per release, which (a) avoids.
   - Pushing onto Dependabot's branch is not an option (§1, finding 1).
2. **The choice's shape and the candidate channel. ⛔ OPEN, awaiting the Owner.** Recommended: one `## Choices` bullet, `Kanon upgrades`, with `off`, `stable` or `candidates`, absent meaning off (`[LANE-22]`). Under `candidates`, a candidate is a target only once the Reporter App's `kanon-e2e` check run passed on its commit (`[LANE-23]`). So "a candidate the end-to-end gate held" never reaches an adopter even then. The alternative is two bullets, an on/off and a channel, which is one more thing `lane-check` must hold consistent, for no case the three values miss.
3. **Is a caller change the release dictates a scope-first bail? ⛔ OPEN, awaiting the Owner.** Recommended: (a).
   - **(a) No.** Only a person's step holds the issue (`[LANE-28]`). The release, reviewed by Kanon, decides those lines, and the adopter's Owner reads them at merge. Issue C amends `K-AGENT-13`'s wording to say so.
   - **(b) Yes, every upgrade bails with its plan.** That is two Owner touches per release, a plan and a merge, where the mandate implies one.
4. **How the bail-listed items are built. ⛔ OPEN, awaiting the Owner.** Recommended: dispatch them; the Implementer's plan stop is the Owner's checkpoint, as #1373's decision 6 had it. The alternative is `lead:file-only` on #1718, with the Owner building each item in a session of their own.
5. **Who merges the upgrade pull request. ✅ ANSWERED (mandate): the Owner, never the Merger.** `K-MERGE-4` already escalates every file under `.github/` and `.claude/`, which no declaration removes, so no new gate is built. `[LANE-34]` pins it with a test, and the pull request's body says it (`[LANE-29]`). Carried into Issue E.
6. **What starts the lane. ✅ ANSWERED (Lead, technical): a daily schedule and a dispatch, with no Dependabot event.** A trigger on Dependabot opening a pull request would need a membership-gate exception for `dependabot[bot]` (`K-AGENT-45`). The daily tick finds Dependabot's pull request anyway, and Dependabot itself runs daily. The lane runs as the Lead, as the dispatch sweep does. Carried into Issue B.
7. **Who makes the dispatch that revises a change request. ⛔ OPEN, awaiting the Owner.** Recommended: (b). A dispatch from the default branch is the only way the revise lane runs on an upgrade pull request (§1, finding 3; `K-MERGE-17`), and a dispatch on the workflow token starts nothing. It needs Actions write, which only the Judge App holds today. Every option grants or uses agent authority (`K-PROJ-18`), so this one is the Owner's.
   - **(a) Broaden the Author App.** The upgrade lane mints a token narrowed to Actions write and dispatches. This changes `rulebook/agent-permissions.json` (a `broadened` entry with its reason, `K-AGENT-3`) and `docs/qa/agent-identities.md`. It is also a step only a person can do on every opted-in adopter: updating their Author App's permissions and accepting the change on its installation. It undoes a choice Kanon made on purpose, since the dispatch sweep churns a label rather than hold this grant.
   - **(b) The Judge App makes it.** A fixed step on the review side, after a change request on an upgrade pull request, mints a Judge token narrowed to Actions write and dispatches the revise lane. That is the grant the merge gate already uses to re-dispatch the review lane on a COMMENT verdict (`git grep -n "re-dispatches the review lane" -- .github/workflows/agent-merge.yml`).
