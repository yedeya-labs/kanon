# Project brief — Kanon status as a hosted MCP server and a status API

The mandate is [#1327](https://github.com/yedeya-labs/kanon/issues/1327)'s body (`K-PROJ-15`): its reasons, its market check and the Owner's decisions of 2026-10-22, which this brief doesn't reopen. They are a hosted remote MCP server from the first release, one status core that stores nothing, read-only first, no IDE and no paging, and configurable rather than special-cased. The issue's five open questions are decisions 1 to 6 below, and they stay open for the Owner.

## 1. The real problem

**One root cause: Kanon computes each part of this state already, but only inside the lane that acts on it.** Every view the mandate asks for has a pure decider on `main`. Each one is fed by its own `gh` reads, which are interleaved with the lane's I/O, so nothing outside the lane can ask the question. These re-run on `main`:

- **The deciders exist and are exported.** `git grep -n -E "^export (async )?function (phaseOf|mergeVerdict|checkPartition|verdictOnHead|classifyWorkflow|parseProposed|check)\b" -- scripts/` finds:
  - the reconciler's phase (`lead-reconcile.mjs`);
  - the Merger's verdict and check partition (`merge-gate.mjs`);
  - verdict currency (`review-recovery.mjs`, over `review-trailer.mjs`'s stamped commit);
  - lane health (`workflow-health.mjs`);
  - the brief's decomposition parser (`project-closure.mjs`);
  - the promotion's gates (`promote.mjs`).
- **The reads are not shared.** The reconciler's project read, `readWorld`, isn't exported (`git grep -n "function readWorld" -- scripts/lead-reconcile.mjs`). `git grep -l -E "(execFileSync|execFile|spawn)\('gh'" -- scripts cli actions | wc -l` counts the modules that shell out to `gh`, and `git grep -l api.github.com -- scripts cli` lists the few that call the API with `fetch`.
- **A hosted function has no `gh` and no checkout.** Every reader that shells out, or reads `docs/projects/` from disk, can't run there.
- **Nothing exposes any of it yet.** `git grep -n kanon-status -- cli scripts` prints nothing, `cli/kanon.mjs` dispatches `init`, `doctor`, `apps`, `milestones` and `metrics` alone, and `git grep -il modelcontextprotocol` prints nothing.
- **Kanon has no runtime dependency.** `git grep -n '"dependencies"' -- package.json` prints nothing, which `K-SELF-8` asks of the scripts an agent runs.

**So the systemic fix is one read layer, not five features.** The fix is a status core under `scripts/status/` that takes an injected reader and feeds the existing deciders, so each view is a projection over them:
- a status answer can't disagree with what the Merger or the reconciler will do;
- an answer's correctness is the decider's, which is already tested;
- the CLI passes a `gh`-backed reader, the server passes a `fetch`-backed reader holding the person's token, and the tests pass a recording reader.

Writing a second judgement of "mergeable" or "blocked" beside the deciders would give a rule two homes (`K-PRIN-2`), so `[STAT-7]` and `[STAT-4]` forbid it.

**What only a person can settle is the hosting half.** Three things decide the server's shape: how it authenticates, where it runs and whose repositories it reads. All three are decisions of the Owner's (§7, decisions 1 to 6). The items for the server are written to my recommended answers. If an answer differs, I rewrite those items on this branch before the merge.

**One finding that is mine.** A hosted server relays an adopter's private repository content (titles, labels and check names) through Kanon's own infrastructure. ADR 0007 governs what Kanon *stores* and says nothing about what it *relays*. So the data boundary is a decision too (decision 4), not an implementation detail.

**Reconciliation gaps: none in the areas this project touches.** It creates two spec areas, `STAT` ([`docs/qa/specs/status.md`](../qa/specs/status.md)) and `MCP` ([`docs/qa/specs/mcp.md`](../qa/specs/mcp.md)), with 24 `[seed]` clauses, all new. `kanon-spec-coverage` reports 0 `[confirmed]` clauses with no test in any area. It exits non-zero today for an unrelated reason, an unrecorded locked floor for `ETE` (§8).

## 2. Scope

**This project is:**
- the status core and its five views: project progress, pull-request readiness, lane health, release status and what needs the Owner;
- `kanon status --json` (`kanon-status/v1`, following [`docs/cli-json.md`](../cli-json.md)) with its prose form;
- a hosted, remote, read-only MCP server whose tools are the same five views;
- its authentication, its CloudFormation template and its deploy hooks;
- the Owner's setup and first deploy;
- one measurement once it runs.

**Docs ride with the feature.** Every item updates the docs it changes. The new topic page is `docs/status.md`, with its field and tool tables held to the code (`[STAT-12]`). It is linked from `README.md`, `docs/architecture.md` and `docs/install.md` (`[STAT-13]`).

**It is not:**
- **Write actions.** That means no merge, label, dispatch or comment from either surface (`[MCP-3]`). Each comes later, one at a time, on the same core (the mandate).
- **A progress page, an IDE view, or paging.** The answers link out to GitHub.
- **A local-only stage, or a stdio MCP server.** The hosted server is settled. The CLI is the status API's second surface, not a stage of the server.
- **Storage, history or trends.** The core reads now and keeps nothing (`[STAT-1]`). Trends are the telemetry store's and `kanon metrics`'s.
- **Cross-repository answers.** For example, "everything that needs me across all my repositories". Every tool takes one repository. A later issue can add an aggregate tool once tenancy (decision 3) says whose repositories one person may span.
- **Notifications or MCP subscriptions.** The digests and the notify hook already push.
- **A skill that wraps `kanon status`,** and GitHub Enterprise Server.
- **The operator's private repository.** Its deploy caller and hooks are the Owner's (Issue J). Agents run no AWS command (`docs/telemetry.md`).

**Specific to this project's definition of done:**
- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Two items are a person's.** Issue J is the Owner's setup and Issue K a measurement, both `qa:human-action`.
- **How it closes.** Kanon declares no reference environment (`docs/qa/adoption.md`, Choices), so the reconciler stops this project at its deploy phase, by name (`K-PROJ-11`). Decision 9 is how it closes instead.
- **No roadmap placement.** Every item files into a bucket, so `K-PROJ-14` asks for nothing.
- **Routing.** Both surfaces are product that any adopter can use, so every code item is `enhancement` on Product Backlog (`K-WORK-4`). The tracking issue carries `pipeline-improvement` on Development Automation. If the Maintainer reads the project as product, #1327 would move to `enhancement` and Product Backlog. The Lead doesn't label.

## 4. Cost

**Recurring, on decision 2's recommended hosting:**
- **The function and its URL:** the Lambda free tier covers the Owner's own use (decision 3), and a Function URL has no fee.
- **The KMS key:** $1 a month, plus requests at $0.03 per 10,000.
- **Logs:** cents. There is one line per request (`[MCP-8]`), kept 30 days.
- **The App's secret:** an SSM `SecureString` parameter, which is free in the standard tier.
- **Total:** about **$1 to $2 a month**, which is an estimate. Issue K measures it. I propose a **$5 a month ceiling** on the account's existing budget alert.
- **GitHub:** $0. Every read is the person's own token, counted against that person's hourly limit, not against an App's.
- **The model:** $0 to Kanon. The MCP client is the person's own Claude.

**Once, building it:** nine pull-request items, A to I. `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/ | sort | uniq -c` shows the Implementer's ceiling is $120. So the worst case is about **$1,080** of implementer runs before revisions, plus each review capped by its own ceiling. That is a ceiling, not an estimate.

**If tenancy opens to any adopter** (decision 3's option b), requests grow with adopters. The free tier then stops covering it at about a million requests a month. Decision 3 brings that back to the Owner before it happens.

**The Owner's time:**
- Issue J: one App, one register row, a deploy caller change and a dispatch;
- each merge decision 7 and decision 8 send to the Owner;

## 5. Observability

**Add:**
- **The deploy smoke** (`[MCP-11]`): a failed deploy or smoke files the deploy lane's failure issue in the operator's repository, as the telemetry store's does;
- **one log line per request** (`[MCP-8]`), which Issue K reads.

**Skip:**
- **Paging and alarms.** The mandate says "no paging", and Kanon defines nothing that pages (`docs/qa/adoption.md`, Choices). A server that is down shows as an error in the person's own MCP client, which is the one person it serves. This matches the telemetry store's "No alarm" (`K-OBS-4`). Decision 2 puts that to the Owner with the hosting.
- **Telemetry rows.** There is no new row kind, so nothing changes under ADR 0007's stored-data rules.

The trigger that would change this is decision 3 opening the server to other adopters. A failure would then reach people other than the Owner, and an alarm would earn its place.

## 6. Blast radius — what will need a human

- **Issue I** creates a KMS key and holds the App's client secret.
- **Issue J** creates a new App and installs it.

## 7. Decisions

Decisions 1 to 6 are the questions #1327 left open. Decisions 7 and 8 change who merges and how an agent builds, which are the Owner's. Decision 9 is the Maintainer's closure rule. Decisions 10 to 12 are technical, and I settled them (`K-PROJ-18`). The Owner, the Maintainer and the Stakeholder are one person (`docs/qa/adoption.md`). Each open decision carries my recommendation, and §3 is written to it.

1. **Authentication and token custody. ⛔ OPEN, awaiting the Owner.** The options:
   - **(a) Recommended:** the server is the MCP authorisation server in front of a read-only GitHub App's user-to-server OAuth flow. It issues its own short-lived access tokens and longer refresh tokens, and both carry the person's GitHub tokens encrypted under a KMS key. So Kanon stores no token at rest (`[MCP-6]`). A leaked token can read no more than the App's read-only grant intersected with what that person can read, and can write nothing.
   - **(b)** The person pastes a read-only fine-grained personal access token as a bearer token. It is simpler, but I infer that claude.ai and the phone need an OAuth flow, so it fails the mandate's "reachable from claude.ai and the phone".
   - **(c)** Kanon mints installation tokens with the App's private key. I advise against it: it is a long-lived key spanning every installation, and answers would no longer be limited to what the person can see.

   Carried into Issue H and `[MCP-4]` to `[MCP-6]`.
2. **Hosting, cost and who deploys. ⛔ OPEN, awaiting the Owner.** The options:
   - **(a) Recommended:** Kanon's AWS account in `eu-central-1`, beside the telemetry store. It is one function behind a Function URL, deployed by the operator's repository through Kanon's deploy lane, with production dispatched by the Owner, as `docs/telemetry.md` does. It costs about $1 to $2 a month under a proposed $5 ceiling, with no alarm (§5).
   - **(b)** Another platform, which means a new vendor account, credentials and runbook.

   Carried into Issues I and J and §4.
3. **Tenancy. ⛔ OPEN, awaiting the Owner.** The options:
   - **(a) Recommended:** the Owner's repositories first. The status App is created private to `yedeya-labs`, and GitHub then lets only that account install it. So tenancy is enforced by GitHub, not by an allow-list in Kanon's code (`[MCP-7]`).
   - **(b)** Any adopter from day one: a public App, which brings other adopters' private content through Kanon (decision 4) and the cost growth in §4.

   Opening it later is making the App public, after a decision of its own. Carried into Issue J.
4. **What may pass through Kanon's server. ⛔ OPEN, awaiting the Owner.** ADR 0007 governs what Kanon stores, not what it relays. My recommendation:
   - answers carry numbers, states, labels, titles, check names and links;
   - comment and issue bodies are read in memory only to find a marker, and never returned or logged (`[MCP-8]`, Issue F);
   - nothing is kept;
   - Issue H records this as an amendment to ADR 0007.

   The stricter alternative drops titles, which makes the answers hard to read on a phone.
5. **Rate limits and freshness. ⛔ OPEN, awaiting the Owner.** The options:
   - **(a) Recommended:** read live on every call, with a per-person cache of at most 60 seconds in the warm function, using GitHub's conditional requests. Every answer carries its read time (`[MCP-9]`).
   - **(b)** Longer TTLs.
   - **(c)** A cache shared between people. I advise against it: one person's answer could reach another.

   Issue K measures whether (a) holds.
6. **Sequencing against the end-to-end release gate and the deploy lane. ⛔ OPEN, awaiting the Owner.** The deploy lane is delivered: `gh issue view 610 --json state` reads `CLOSED`. The end-to-end gate ([#902](https://github.com/yedeya-labs/kanon/issues/902)) is open. My recommendation is to run this project in parallel, because it touches no release path. Issue J then deploys from the latest stable release that carries Issue I. If the gate holds candidates for long, the Owner may deploy a candidate to the operator's repository, which is no adopter's pin. The alternative is to wait for #902 to close.
7. **Who merges the status core and the server. ⛔ OPEN, awaiting the Owner.** The options:
   - **(a) Recommended:** `^scripts/status/` and `^infra/status/` are `always`, added by Issue A. This follows the precedent that code linked into a hosted function is the Owner's (the `scripts/metrics/` entry). It costs the Owner a merge on every item from A to I.
   - **(b)** Only `^infra/status/`, leaving the core green. A core change would then reach the server through the release pull request and the Owner's deploy dispatch, both human gates, but unread.
8. **How Issues H and I are built, given the scope-first bail. ⛔ OPEN, awaiting the Owner.** The Implementer stops on any auth or credential change, by its lane's prompt. The options:
   - **(a) Recommended:** dispatch them anyway. The Implementer posts its plan and stops, which is the Owner's checkpoint, and the Owner then answers on the issue.
   - **(b)** Build them in the Owner's own session, with `lead:file-only` on #1327 from the moment the server's handler is merged.
9. **How this project closes. ⛔ OPEN, awaiting the Maintainer.** Kanon declares no reference environment, so the reconciler stops at the deploy phase. My recommendation follows #902's decision 18: accept the stop, and the Maintainer closes #1327 by hand once Issue K's numbers are posted and `verify-acs` is dispatched green.
10. **One read layer, the deciders reused. ✅ ANSWERED (Lead, technical): the core takes an injected reader and calls the existing deciders, and never re-derives their judgement (§1).** The CLI's reader uses `gh`, the server's uses `fetch` with the person's token, and the tests' reader records. Carried into Issues A to G.
11. **No new dependency. ✅ ANSWERED (Lead, technical): the server speaks MCP's small JSON-RPC surface with Node's built-ins, as the telemetry functions do (`git grep -h "^import" -- infra/telemetry/function/` imports only `node:` modules and local files).** This keeps `package.json`, an Owner path, unchanged and `K-SELF-8` intact. If the protocol's authorisation half proves too large to write by hand, Issue H says so on its issue, and adding a dependency becomes the Owner's call there.
12. **Two spec areas and this decomposition. ✅ ANSWERED (Lead, technical): `STAT` holds the core and the CLI, and `MCP` holds the server, with ids allocated by `kanon-spec-ids --apply` and every clause `[seed]`.** The views follow one per item, after the CLI, so each has a surface and a test from its first merge.
