# Project brief — Kanon status as a hosted MCP server and a status API

The mandate is [#1327](https://github.com/yedeya-labs/kanon/issues/1327)'s body (`K-PROJ-15`): its reasons, its market check and the Owner's decisions of 2026-10-22, which this brief doesn't reopen. They are a hosted remote MCP server from the first release, one status core that stores nothing, read-only first, no IDE and no paging, and configurable rather than special-cased. The issue's five open questions are decisions 1 to 6 below. The Owner answered them on 2026-10-23, with decisions 7, 8 and 13, and the Maintainer answered decision 9 (§7).

## 1. The real problem

**One root cause: Kanon computes each part of this state already, but only inside the lane that acts on it.** Every view the mandate asks for has a pure decider on `main`. Each one is fed by its own `gh` reads, which are interleaved with the lane's I/O, so nothing outside the lane can ask the question. These re-run on `main`:

- **The deciders exist and are exported.** `git grep -n -E "^export (async )?function (phaseOf|mergeVerdict|checkPartition|verdictOnHead|classifyWorkflow|parseProposed|check)\b" -- scripts/` finds:
  - the reconciler's phase (`lead-reconcile.mjs`);
  - the Merger's verdict and check partition (`merge-gate.mjs`);
  - verdict currency (`review-recovery.mjs`, over `review-trailer.mjs`'s stamped commit);
  - lane health (`workflow-health.mjs`);
  - the brief's decomposition parser (`project-closure.mjs`);
  - the promotion's gates (`promote.mjs`).
- **The reads are not shared.** The reconciler's project read, `readWorld`, isn't exported (`git grep -n "function readWorld" -- scripts/lead-reconcile.mjs`). `git grep -l -E "(execFileSync|execFile|spawn)\('gh'" -- scripts cli actions | wc -l` counts the modules that shell out to `gh`, and `git grep -l api.github.com -- scripts cli` lists the few that call the API with `fetch`.
- **A hosted function has no `gh` and no checkout.** Every reader that shells out, or reads `docs/projects/` from disk, can't run there.
- **Nothing exposes any of it yet.** `git grep -n kanon-status -- cli scripts` prints nothing, `cli/kanon.mjs` dispatches `init`, `doctor`, `apps`, `milestones` and `metrics` alone, and `git grep -il modelcontextprotocol` prints nothing.
- **Kanon has no runtime dependency.** `git grep -n '"dependencies"' -- package.json` prints nothing, which `K-SELF-8` asks of the scripts an agent runs.

**So the systemic fix is one read layer, not five features.** The fix is a status core under `scripts/status/` that takes an injected reader and feeds the existing deciders, so each view is a projection over them:
- a status answer can't disagree with what the Merger or the reconciler will do;
- an answer's correctness is the decider's, which is already tested;
- the CLI passes a `gh`-backed reader, the server passes a `fetch`-backed reader holding the person's token, and the tests pass a recording reader.

Writing a second judgement of "mergeable" or "blocked" beside the deciders would give a rule two homes (`K-PRIN-2`), so `[STAT-4]`, `[STAT-7]` and `[STAT-14]` forbid it.

**What only a person can settle is the hosting half.** Three things decide the server's shape: how it authenticates, where it runs and whose repositories it reads. All three were the Owner's to decide (§7, decisions 1 to 6). On 2026-10-23 the Owner accepted my recommendation on each, and the items for the server are written to those answers.

**One finding that is mine.** A hosted server relays an adopter's private repository content (titles, labels and check names) through Kanon's own infrastructure. ADR 0007 governs what Kanon *stores* and says nothing about what it *relays*. So the data boundary was a decision too (decision 4), not an implementation detail. The Owner answered it, and Issue H records the answer in ADR 0007.

**Reconciliation gaps: none in the areas this project touches.** It creates two spec areas, `STAT` ([`docs/qa/specs/status.md`](../qa/specs/status.md)) and `MCP` ([`docs/qa/specs/mcp.md`](../qa/specs/mcp.md)), with 25 `[seed]` clauses, all new. `kanon-spec-coverage` reports 0 `[confirmed]` clauses with no test in any area. It exits non-zero today for an unrelated reason, an unrecorded locked floor for `ETE` (§8, #1329).

## 2. Scope

**This project is:**
- the status core and its five views: project progress, pull-request readiness, lane health, release status and what needs the Owner;
- `kanon status --json` (`kanon-status/v1`, following [`docs/cli-json.md`](../cli-json.md)) with its prose form;
- a hosted, remote, read-only MCP server whose tools are the same five views;
- its authentication, its CloudFormation template and its deploy hooks;
- the Owner's setup and first deploy;
- one measurement once it runs.

**Docs ride with the feature.** Every item updates the docs it changes. The new topic page is `docs/status.md`, with its field and tool tables held to the code (`[STAT-12]`). It is linked from `README.md`, `docs/architecture.md` and `docs/install.md` (`[STAT-13]`).

**It is not:**
- **Write actions.** That means no merge, label, dispatch or comment from either surface (`[MCP-3]`). Each comes later, one at a time, on the same core (the mandate).
- **A progress page, an IDE view, or paging.** The answers link out to GitHub.
- **A local-only stage, or a stdio MCP server.** The hosted server is settled. The CLI is the status API's second surface, not a stage of the server.
- **Storage, history or trends.** The core reads now and keeps nothing (`[STAT-1]`). Trends are the telemetry store's and `kanon metrics`'s.
- **Cross-repository answers.** For example, "everything that needs me across all my repositories". Every tool takes one repository. Tenancy (decision 3) is the Owner's repositories only. A later issue can add an aggregate tool, and if tenancy ever widens, a decision of its own says whose repositories one person may span.
- **Notifications or MCP subscriptions.** The digests and the notify hook already push.
- **A skill that wraps `kanon status`,** and GitHub Enterprise Server.
- **The operator's private repository.** Its deploy caller and hooks are the Owner's (Issue J). Agents run no AWS command (`docs/telemetry.md`).

**Specific to this project's definition of done:**
- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Two items are a person's.** Issue J is the Owner's setup and Issue K a measurement, both `qa:human-action`.
- **How it closes.** Kanon declares no reference environment (`docs/qa/adoption.md`, Choices), so the reconciler stops this project at its deploy phase, by name (`K-PROJ-11`). The Maintainer accepted that stop (decision 9). The Maintainer closes #1327 by hand once Issue K's numbers are posted on it and `verify-acs` is dispatched green.
- **No wait on the end-to-end gate.** The project runs in parallel with #902 (decision 6), and no item depends on it.
- **No roadmap placement.** Every item files into a bucket, so `K-PROJ-14` asks for nothing.
- **Routing.** Both surfaces are product that any adopter can use, so every code item is `enhancement` on Product Backlog (`K-WORK-4`). The tracking issue keeps the routing the Maintainer gave it (`pipeline-improvement`, Development Automation); nothing in this brief depends on it.

### Issue C — Add the pull-request readiness view
**Milestone:** Product Backlog · **Labels:** `enhancement`
**Depends on:** Issue B (it adds its section to the document and its rows to the page)

Acceptance criteria:

- `[STAT-6]` — checks, verdict currency, criteria and the merge gate's verdict.
- `[STAT-7]` — an Implementer's pull request is ready only when the merge gate's verdict function says so.
- `[STAT-14]` — any other pull request is a person's to merge, and ready only on the gate's check partition, no conflict, a current approval and, for a brief, no open decision. The conflict test was added when the Owner overturned decision 13 (§7).

It feeds `mergeVerdict` the pull-request shape `readPr` builds, read through the injected reader. A shared fixture holds the two shapes together. For a pull request the gate skips as not the Implementer's, it composes `checkPartition`, `verdictOnHead` and the brief guard's own decision read, and, since the Owner overturned decision 13, the shared conflict detector `conflictState`, and applies no readiness condition of its own (decision 13, §7). That read is not `checkBrief`: `checkBrief` reports an open decision only as problem text among every other brief problem, and without a milestone list it adds a problem for every item that names a roadmap milestone rather than a bucket (`milestoneProblem`). So this item moves `checkBrief`'s open-decision loop into one exported function of `brief-guard.mjs`, which `checkBrief` then calls and the view calls too. The function takes a decisions section's body and whether the brief is pre-standard, and returns its open decisions. It keeps in one place both rules the loop applies: an answered mark wins over an open one in the same headline, and a pre-standard brief is not checked. The view finds the section with `briefSections` and the `decisions` entry of `REQUIRED_SECTIONS`. It learns whether a brief is pre-standard by reading `docs/qa/exemptions.md` through the injected reader at the default branch and parsing it with `parseExemptions` (`scripts/lib/exemptions.mjs`). When the file is missing, as it is on Kanon, the view uses `defaultExemptions`, which is what `readExemptions` falls back to. It can't use `isPreStandard` or `readExemptions` for that, because both read a checked-out tree, which the hosted server doesn't have. `brief-guard.mjs` is green and `exemptions.mjs` is an Owner path, so the item changes the first and only imports from the second. If the shape can't be built without changing `merge-gate.mjs` or `review-trailer.mjs`, both Owner paths, the pull request says so and goes to the Owner. Docs: the view's rows in `docs/status.md`.

## 4. Cost

**Recurring, on the hosting the Owner chose (decision 2):**
- **The function and its URL:** the Lambda free tier covers the Owner's own use (decision 3), and a Function URL has no fee.
- **The KMS key:** $1 a month, plus requests at $0.03 per 10,000.
- **Logs:** cents. There is one line per request (`[MCP-8]`), kept 30 days.
- **The App's secret:** an SSM `SecureString` parameter, which is free in the standard tier.
- **Total:** about **$1 to $2 a month**, which is an estimate. Issue K measures it. The Owner set a **$5 a month ceiling** (decision 2), watched by the account's existing budget alert, which Issue J sets to cover it.
- **GitHub:** $0. Every read is the person's own token, counted against that person's hourly limit, not against an App's.
- **The model:** $0 to Kanon. The MCP client is the person's own Claude.

**Once, building it:** nine pull-request items, A to I. `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/ | sort | uniq -c` shows the Implementer's ceiling is $120. So the worst case is about **$1,080** of implementer runs before revisions, plus each review capped by its own ceiling. That is a ceiling, not an estimate.

**If tenancy ever opens to any adopter,** requests grow with adopters. The free tier then stops covering it at about a million requests a month. The Owner chose the Owner's repositories only (decision 3), so opening it is a later decision of its own, which brings that cost back to the Owner before it happens.

## 5. Observability

**Add:**
- **The deploy smoke** (`[MCP-11]`): a failed deploy or smoke files the deploy lane's failure issue in the operator's repository, as the telemetry store's does;
- **one log line per request** (`[MCP-8]`), carrying the tool, the duration and the number of GitHub requests it made, which Issue K reads.

**Skip:**
- **Paging and alarms.** The mandate says "no paging", and Kanon defines nothing that pages (`docs/qa/adoption.md`, Choices). A server that is down shows as an error in the person's own MCP client, which is the one person it serves. This matches the telemetry store's "No alarm" (`K-OBS-4`). The Owner accepted "no alarm" with the hosting (decision 2).
- **Telemetry rows.** There is no new row kind, so nothing changes under ADR 0007's stored-data rules.

The trigger that would change this is a later decision opening the server to other adopters, which decision 3 doesn't do. A failure would then reach people other than the Owner, and an alarm would earn its place.

## 7. Decisions

Decisions 1 to 6 are the questions #1327 left open. Decisions 7 and 8 change who merges and how an agent builds, which are the Owner's. Decision 9 is the Maintainer's closure rule. Decisions 10 to 12 are technical, and I settled them (`K-PROJ-18`). Decision 13 came from the review: which pull requests count as mergeable is product behaviour, so it is the Owner's. The Owner, the Maintainer and the Stakeholder are one person (`docs/qa/adoption.md`). That person answered decisions 1 to 9 in a comment on this brief's pull request on 2026-10-23, accepting my recommendation on each, and I transcribed the answers here (`K-PROJ-17`). The same comment opened with "every recommendation in §7 is accepted", which is how decision 13 is answered; decision 13 says what is ambiguous about that. The options each decision weighed stay below, as the record of what was chosen against. §3 to §6 are written to the answers.

1. **Authentication and token custody. ✅ ANSWERED (the Owner, 2026-10-23): (a), the server is the MCP authorisation server in front of a read-only GitHub App's user-to-server OAuth flow, and no token is stored at rest.** The options were:
   - **(a) Recommended, and chosen:** the server is the MCP authorisation server in front of a read-only GitHub App's user-to-server OAuth flow. It issues its own short-lived access tokens and longer refresh tokens, and both carry the person's GitHub tokens encrypted under a KMS key. So Kanon stores no token at rest (`[MCP-6]`). A leaked token can read no more than the App's read-only grant intersected with what that person can read, and can write nothing.
   - **(b)** The person pastes a read-only fine-grained personal access token as a bearer token. It is simpler, but I infer that claude.ai and the phone need an OAuth flow, so it fails the mandate's "reachable from claude.ai and the phone".
   - **(c)** Kanon mints installation tokens with the App's private key. I advise against it: it is a long-lived key spanning every installation, and answers would no longer be limited to what the person can see.
