# Project brief — Author lanes commit through GitHub's API, so every commit is verified as the App's

The mandate is [#1373](https://github.com/yedeya-labs/kanon/issues/1373)'s body (`K-PROJ-15`). The Owner made four decisions on 2026-10-23, and this brief doesn't reopen them: GitHub-verified commits, #1358's gap accepted until this ships, start on merge, and one breaking release with no setting. The mandate left one question open, how the rebase lane works without a merge commit. Decision 2 answers it: the rebase lane keeps its merge commit, because the API can create one. Decision 1 reads the mandate's constraint, and needs the Owner's confirmation. Decisions 3 to 6 are new, and need the Owner (§7).

## 1. The real problem

**One root cause: "the App wrote this commit" is an email in the commit, because the agent makes its commits with plain git.** GitHub signs nothing an agent pushes, so the only witness to authorship is a field that anyone with push access can set. These commands re-run on `main`:

- **Agent commits are unsigned today.** `gh api repos/yedeya-labs/kanon/pulls/1369/commits --jq '.[].commit.verification.reason'` prints `unsigned` for an Implementer pull request. The same read on #1328, a Lead brief, prints `unsigned` four times.
- **The agent pushes, not a fixed step.** `git grep -n "git push" -- .github/workflows/lane-agent-job.yml` finds only the dry-run probe in a comment. The Lead lanes allow the agent `git push origin` (`git grep -n '"Bash(git push origin:\*)"' -- .github/workflows/`), and the Implementer's agent has an unrestricted shell. The rebase lane's agent runs `git merge` and pushes the merge commit (the prompt in `rebase-agent-job.yml`).
- **The status trusts the email.** `git grep -n -E "byApp|verification" -- actions/implementer-status/implementer-status.mjs` shows `byApp` comparing `commit.author.email`, and nothing reads `verification`. The carry's first-parent walk (`K-AGENT-2`) uses `byApp`, and so does `open` mode's head check.
- **An API commit made with the App's token is verified.** `gh api repos/yedeya-labs/kanon/pulls/1152/commits --jq '.[].commit.verification | "\(.verified) \(.reason)"'` prints `true valid` for the Releaser's `createCommitOnBranch` commit. `git grep -n "no custom author or committer" -- actions/dco/dco.mjs` gives the condition: GitHub signs an App's commit only when the App's own token created it through the API with no custom author or committer.
- **Kanon already commits through the Git Data API with the Author App's token.** The revise lane's no-model fix does it in a job with the key and no checkout (`git grep -n -E "git/(blobs|trees|commits|refs)" -- scripts/revise-fix.mjs`), split from the job that ran the fix (`K-AGENT-49`). This is the pattern to generalise, rather than `release-please.yml`'s `createCommitOnBranch` (decision 7).

**So the systemic fix is one producer and one consumer.** One helper turns the agent's local commits into API-created commits, and one push job runs it after every Author lane's agent. Then `carryDecision` reads GitHub's verification instead of the email. Point fixes per lane would leave four ways to commit, where the Owner asked for one.

**Four findings of mine, each shaping an item:**

1. **A naive re-creation launders a person's commit.** In #1358's case, the agent re-fetches mid-run and builds on a person's commit. A helper that re-created every commit in `start..HEAD` would re-create the person's commit too, now verified as the App's. That is worse than today's gap. So the helper re-creates only the commits the repository doesn't already have, and keeps every other commit as it is (`[LANE-6]`). The person's commit stays unverified, and the carry stops at it.
2. **The persona can't stay the commit's author name.** `git grep -n GIT_AUTHOR_NAME -- actions/agent-setup/agent-commits.sh` shows the persona set as the author name (`K-AGENT-1`, plan 0005 §3.3). A custom author forfeits GitHub's signature (the `dco.mjs` comment above). `gh api repos/yedeya-labs/kanon/pulls/1152/commits --jq '.[].commit.author.name'` prints the bot's name, `yedeya-labs-releaser[bot]`. That makes `K-AGENT-1` a rulebook change, which is the Owner's (decision 3).
3. **"A step the agent can't rewrite" means the agent no longer pushes, or opens its own pull request.** `K-AGENT-49` says that inside one job, step order is not a boundary. So the re-creation runs in a job of its own, and the agent's token loses `contents: write` (decision 1, recommended). A lane whose agent opens a pull request now has the push job open it (`[LANE-15]`).
4. **The order keeps every intermediate `main` working.** An API commit keeps the App's noreply email as its author (`gh api repos/yedeya-labs/kanon/pulls/1152/commits --jq '.[].commit.author.email'`). So the email-based carry keeps passing while the lanes move over one at a time, and the carry switches to verification only after every lane that feeds it has moved.

**Reconciliation gaps: none in the area this project touches.** `kanon-spec-coverage` reports 0 `[confirmed]` clauses with no test in any area, and `LANE` has none at all. The project seeds `[LANE-6]` to `[LANE-21]` in [`docs/qa/specs/lanes.md`](../qa/specs/lanes.md). The status's existing tests (`tests/unit/implementer-status.test.ts`) cite no spec id, only rulebook rules, so there is no uncited `[confirmed]` clause for an Issue A to close.

## 2. Scope

**This project is:**
- the verified-commit helper, and the revise lane's `fix-push` moved onto it;
- a push job after the agent in every Author lane that commits: the spine's lanes (implement, triage-fix, implement-revise, Lead brief and Lead revise), the rebase lane, the Lead's split lane, and Kanon's metrics page;
- the agent's job token narrowed to drop `contents: write` and `workflows: write`;
- `carryDecision` and `open` mode reading GitHub's verification, with the email walk deleted;
- the docs, the rulebook amendments, the release's breaking-change notes, and the accepted exposure removed.

**It is not:**
- **Signing commits people make,** or **requiring signed commits by ruleset.** Both are excluded by the mandate. A ruleset is an adopter's choice, which `docs/lanes.md` may mention (Issue F).
- **Trimming the Lead lanes' shell allow-list.** `git push origin` stays on the list, and fails at GitHub for lack of the grant. Changing the flags requires a fresh grant-probe battery (`K-AGENT-50`'s enforcement, `tests/unit/reviewer-grant-probe.test.ts`). That is a follow-up issue of its own, filed by Issue F, not done here.
- **Closing `K-AGENT-50`'s two accepted exceptions.** The revise and rebase agents keep a write token, for comments and labels, beside the code under test. This project narrows that token, and Issue F rewrites the exception's wording to match, but taking it away entirely is separate work.
- **The Releaser's commits.** They are already verified, and they aren't an Author lane's.
- **#1358 itself.** PR #1375 records it as an accepted exposure, and that PR closes it. This project removes the exposure, which is what Issue F's `[LANE-21]` checks.

**Specific to this project's definition of done:**
- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **One breaking release.** The release pull request is held from Issue B's merge until Issue F's (decision 4), and Issue F's pull request carries the `BREAKING CHANGE:` footer with the upgrade steps.
- **How it closes.** Kanon declares no reference environment, so the reconciler stops at the deploy phase, as it did for #1327 (`K-PROJ-11`). The Maintainer closes #1373 once that stable release is out and `verify-acs` is green.
- **Routing.** On Kanon the subject is who the work is for. The lanes, the library helper, `actions/implementer-status`, the rules and the docs adopters read are what an adopter receives, and they ship as a breaking release with upgrade steps. So Issues A, B, C, E and F are `enhancement` on Product Backlog (`K-WORK-4`), as #1327's brief had it. Issue D is routed by its larger part, the split lane every adopter runs; its metrics-page half is Kanon's own plumbing. The tracking issue keeps the routing the Maintainer gave it (`pipeline-improvement`, Development Automation), and nothing in this brief depends on it.

## 3. Decomposition

### Issue A — Build the verified-commit helper, and move fix-push onto it
**Milestone:** Product Backlog · **Labels:** `enhancement`

Acceptance criteria:

- `[LANE-6]` — only commits the repository lacks are re-created; a fetched commit is kept as it is.
- `[LANE-7]` — the same tree id: paths, contents, deletions and modes; a submodule change is refused.
- `[LANE-8]` — the message byte for byte, trailers included; no author, committer or signature sent.
- `[LANE-9]` — every created commit read back verified as the App's before any branch moves.
- `[LANE-10]` — create, fast-forward or refuse; force only in replace mode; its outputs.
- `[LANE-11]` — no re-upload of a parent's blob; pacing; bounded secondary-rate-limit retries.
- `[LANE-12]` — `fix-push` goes through the helper.

The helper is `scripts/lib/verified-commits.mjs`, with a command-line entry the push jobs run at the pinned release through `kanon-path`. It takes a git object store and a range, not a working tree, so the push job never checks out the agent's branch. It uses the Git Data API (blobs, trees with modes, commits, refs), as `revise-fix.mjs` does, and that file's `pushChange` becomes a caller of it.

This item also adds `^scripts/lib/verified-commits\.mjs$` to `docs/qa/escalation-paths.md` as `always`, if decision 5 is answered that way. Otherwise Issue D adds it, because the metrics page runs the helper from this tree (decision 5).

Its tests run against a recording API double. The first live proof is `fix-push`'s next run, which `[LANE-9]` makes fail loudly rather than push an unverified commit.

Not in this issue: any lane's wiring but `fix-push`, or the status.

### Issue B — Push the spine lanes' commits from a push job, and stop the agent pushing
**Milestone:** Product Backlog · **Labels:** `enhancement`
**Depends on:** Issue A (the push job runs the helper)

Acceptance criteria:

- `[LANE-13]` — on the spine's lanes: the agent's job token holds no `contents: write` and no `workflows: write`.
- `[LANE-14]` — on the spine's lanes: the push job runs after the agent's job, even a failed one; no agent, no project code; the helper.
- `[LANE-15]` — the push job opens the pull request from the agent's request.
- `[LANE-16]` — on the spine's lanes: the implementer status reads heads and base from the push job, never the agent's job.

This covers the lanes on the spine (`agent-lane.yml` and `lane-agent-job.yml`): implement, triage-fix, implement-revise's model path, the Lead's brief and the Lead's revise. Issues C and D hold the rebase and split lanes to `[LANE-13]` and `[LANE-14]`. The push job holds the key and mints its own token, as `fix-push` does, so the mint-and-agent pair `K-AGENT-49` holds stays two jobs. The push job's token carries `workflows: write` only because a commit may touch `.github/workflows/`. When the agent's job failed and wrote no request, the push job still moves the branches it left, by the helper's rules (`[LANE-10]`) and never the default branch, opens no pull request, and says so in its step summary. That keeps today's outcome, where a crashed agent's mid-run pushes survive. Two points this item settles, and the brief leaves to its Implementer: where the push job gets the branch and the head `[LANE-10]` must be given when there is no request, and whether it refuses a branch that existed before the run, as `[LANE-15]` does only for a request. Without that refusal, this path could fast-forward a pre-existing non-default branch, which is no wider than today, where the agent's token can push to any branch.

Each lane's prompt changes from "push and open a pull request" to "commit, and write the request". The same pull request amends `K-AGENT-1` to decision 3's answer, and updates `tests/unit/agent-commits.test.ts` to match. The Lead lanes' flags stay byte for byte (§2).

Not in this issue: the rebase lane, the split lane, the metrics page, or the status's trust in verification.

## 4. Cost

**Once, building it.** There are six pull-request items, A to F. `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/ | sort | uniq -c` shows the Implementer's ceiling is $120, so the worst case is **$720** of implementer runs before revisions, plus each review under its own ceiling. That is a ceiling, not an estimate.

**Recurring:**
- **One more job per Author lane run that commits.** It is a mint, an artifact download and a few dozen API requests. I estimate about one runner minute, but I haven't measured it. On Kanon it costs **$0**: `gh api repos/yedeya-labs/kanon --jq .visibility` prints `public`, and Actions minutes on public repositories are free. On an adopter's private repository it costs one Linux minute per such run, cents a month at any lane volume Kanon has seen. That is inferred, and Issue F's notes say it.
- **The agent's job loses its push.** It saves nothing measurable.
- **GitHub's API: $0.** The requests count against the Author App's installation rate limit, not a person's. The largest Author pull request so far changed 50 files: `gh pr list -R yedeya-labs/kanon --state all --author "app/yedeya-labs-author" --limit 300 --json changedFiles --jq 'map(.changedFiles) | max'`. A push of that size is about 55 requests.
- **The model: no delta.** Prompts change wording, not length.

**The Owner's time:**
- a merge on Issues B to F, since each touches `.github/`, `actions/`, `rulebook/` or `docs/qa/` (§6), and on Issue A only under decision 5's (a), which adds its entry to `docs/qa/escalation-paths.md`;
- the plan stops decision 6 describes;
- holding one release pull request for the project's length (decision 4).

## 5. Observability

**Add:**
- **The push job's step summary.** It names each commit it created, its verification, and the branch it moved, or why it moved nothing (`[LANE-9]`, `[LANE-10]`). A refused push fails the job, so the lane's run is red, and `workflow-health` already reports a red lane run.

**Skip:**
- **A new alarm or metric.** Kanon pages on nothing (`docs/qa/adoption.md`, Choices), and a failed push is a red run in the lane that owns it, which a person already sees (`K-OBS-4`).
- **A telemetry row for verification.** An unverified commit can now only come from a person's push. The status refusing to carry across one is the designed outcome, and it is already in the status job's summary.

What would change this is a push job that fails on secondary rate limits more than once a week. Issue A's bound would then go back to the Owner as an issue.

## 7. Decisions

Decisions 1 and 2 answer the mandate's constraint and its open question. Decisions 1 and 3 to 6 change what an agent may do, a rule, a release, who merges, or how an agent builds, so each is the Owner's. Decisions 7 and 8 are technical, and I settled them (`K-PROJ-18`).

1. **Where the re-creation runs. ⛔ OPEN, awaiting the Owner's confirmation.** The mandate requires "a step the agent can't rewrite, holding the App token the agent job doesn't otherwise expose". Under `K-AGENT-49`, only a separate job is such a step. The consequences are my reading of that constraint, not the Owner's words, and they change what an agent may do, so they are the Owner's to confirm (`K-PROJ-17`, `K-PROJ-18`).
   - **(a) Recommended:** a push job after the agent's job, holding a token the agent's job no longer has. The agent's token drops `contents: write` and `workflows: write` (`[LANE-13]`), and the push job opens a lane's pull request (`[LANE-15]`). Carried into Issues B, C and D.
   - **(b)** A step inside the agent's job. It is weaker: the agent could still push plain commits, and the carry would only catch them afterwards. It also misses the mandate's first line, "every commit … is verified".
2. **How the rebase lane works without a merge commit. ✅ ANSWERED (Lead, technical): it keeps the merge commit, made through the API with two parents.** The Git Data API's create-commit takes a list of parents. Replaying the commits onto the base, or squashing them, would both rewrite the branch, which `K-AGENT-34` and `K-MERGE-15` forbid, and would drop the Reviewer's stamp on the head it read. Keeping the merge changes no rule. That a two-parent API commit is verified is inferred, not measured (§8). `[LANE-9]` makes the first run prove it. If it isn't verified, Issue C stops, and the fallback goes to the Owner on its issue: a replay that rewrites the branch, which would amend both rules. Carried into Issue C and `[LANE-17]`.
3. **The persona as a commit's author name (`K-AGENT-1`). ⛔ OPEN, awaiting the Owner.** GitHub verifies an App's commit only with no custom author (§1, finding 2).
   - **(a) Recommended:** commits are authored by the App's bot account. The persona stays where readers see it: every post's header and role marker. Issue B amends `K-AGENT-1` to say so.
   - **(b)** Also add a `Kanon-Persona:` trailer to each commit. That is new machinery for a name nothing reads.
   - **(c)** Keep the persona as the author name. The commits are then unverified, which defeats the project.
4. **Keeping it to one breaking release. ⛔ OPEN, awaiting the Owner.** The promotion turns any candidate into a stable release once its gates pass (`docs/release.md`). So a candidate cut mid-project could reach adopters with half the change.
   - **(a) Recommended:** the Owner merges no release pull request from Issue B's merge until Issue F's. Every item goes to the Owner anyway (§6), so the Owner already sets the pace. The hold starts after Issue A, which is library code only and safe to release on its own.
   - **(b)** Let candidates be cut. Every intermediate `main` works (§1, finding 4), but adopters would see the push change and the author change before the breaking note, which the Owner's decision rules out.
5. **Who merges the helper. ⛔ OPEN, awaiting the Owner.** The helper decides what GitHub will sign as the App's, which is the property the green zone will rest on.
   - **(a) Recommended:** `^scripts/lib/verified-commits\.mjs$` is `pipeline` `always`, added by Issue A, as the role marker's and the merge gate's files are.
   - **(b)** Leave it green until Issue D. The lanes run the library at a pinned release, so a change reaches them only through a release, which is still the Owner's merge, but unread. The metrics page doesn't: its `page` job checks out the run's ref, which a manual dispatch may set to any branch, and runs that tree's files with the Author App's key, and from Issue D that includes the helper. So `tests/unit/credential-reach-guard.test.ts` needs the helper's `always` entry once Issue D lands, and Issue D adds it. Under (b), only Issue A's merge leaves the Owner: it touches `scripts/`, `scripts/lib/` and `tests/`, all green, so the Merger may merge it once the Owner has answered its plan stop (decision 6).
6. **How the bail-listed items are built. ⛔ OPEN, awaiting the Owner.** Every item is on the Implementer's scope-first bail list (§6).
   - **(a) Recommended:** dispatch them anyway. The Implementer posts its plan and stops, which is the Owner's checkpoint, and the Owner answers on the issue. This is the answer #1327's decision 8 gave.
   - **(b)** Put `lead:file-only` on #1373 and build the items in the Owner's own session. That contradicts "start on merge" only in who builds, not in when.
7. **The Git Data API, not `createCommitOnBranch`. ✅ ANSWERED (Lead, technical).** The mandate asked whether `createCommitOnBranch` keeps a file's mode.
