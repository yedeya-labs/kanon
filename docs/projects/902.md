# Project brief — End-to-end tests in throwaway repositories, gating every release (plan 0012)

The mandate is [#902](https://github.com/yedeya-labs/kanon/issues/902)'s body (`K-PROJ-15`). The design is plan 0012, [`docs/plans/0012-end-to-end-tests.md`](../plans/0012-end-to-end-tests.md), merged from [PR #903](https://github.com/yedeya-labs/kanon/pull/903) as `92a11e2` on 2026-10-14. This brief turns its order of moves (its §14, steps E0 to E14) into issues, and cites the plan by section rather than restating it. The Owner's four decisions before the draft are settled and not reopened here:
- a test organisation with its own driver App;
- test copies of the Author, Judge and Releaser, installed only there;
- the tier as a hard release gate;
- a $2 cap per run on the real-model tier.

The Owner answered the plan's seventeen questions on 2026-10-14 (§7), and took two new decisions that restructure it:
- **the no-leak rule:** the tier adds no test-only switch to Kanon's product;
- **the harness's home:** a separate repository in the test organisation, which tests Kanon from outside, as an adopter would.

So most of the work is now offloaded to that repository as issues. Kanon keeps E1 (`init`'s pin fix) and E11 (the promotion gate). The Maintainer's answers of 2026-10-15 close decisions 18 and 19, and add a third Kanon item that isn't one of the plan's steps: the App register learns a role for an App that isn't an agent, so the Reporter can be registered (decision 22, Issue U).

## 1. The real problem

**One root cause, not fifteen steps.** Nothing Kanon runs installs Kanon into a second repository. So every behaviour that shows only in an adopter's repository is first seen by an adopter. Each of these re-runs on `main`:

- **No harness exists.** `git ls-files tests/e2e scripts/e2e` prints nothing, and no workflow of Kanon's creates a repository anywhere.
- **The smoke workflows say what stands in for one.** `git grep -l "reference adopter's live run" -- .github/workflows/` names `agent-lanes-smoke.yml` and `agent-blocks-smoke.yml`. Their comments say that a model call is proven only by the reference adopter's run after each upgrade.
- **`init` writes a pin that can't resolve at a candidate.** `git grep -n kanonRelease -- cli/callers.mjs` shows the pin is `v` plus `package.json`'s version. At a candidate's commit that tag doesn't exist yet. This is a product bug for anyone running ahead of stable, not only for tests (plan §1, decision 5).
- **No lane run fits under the $2 cap.** `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/ | sort | uniq -c` shows every ceiling between $10 and $120, and no lane takes a lower one from its caller. Under the no-leak rule none is added (decision 7). So the $2 holds softly per run, through the harness's ledger, and hard only per month, through the key's spend limit (plan §6.2).
- **The App register can't hold the Reporter.** `K-AGENT-3` requires the register to list every App installed on the repository, "agent or not", and Issue A installs the Reporter on Kanon. But `git grep -n -A2 "export const ROLES" -- scripts/app-register.mjs` lists eight roles, with no Reporter and no role for any other App, and `parseAppRegister` throws on a row whose role isn't one of them. `git grep -l parseAppRegister -- scripts/ actions/ cli/` shows what reads the register through it, the lanes' membership gate (`scripts/lane-gate.mjs`), the lanes' persona step (`actions/agent-setup/persona.mjs`) and `lane-check` among them. Those run at the release their callers pin, so a Reporter row on `main` would fail them until a release that knows the role is pinned (decision 22).
- **The promotion the gate hooks into doesn't exist.** Plan 0009's candidate pre-release, pin job and `promote.mjs` (its S3 to S5) are unbuilt. Only S2's admission of `candidate-vX.Y.Z` is built: `git grep -n "candidate-v" -- actions/lane-check/ cli/doctor.mjs` finds it, and neither `scripts/promote.mjs` nor `.github/workflows/promote.yml` exists. So the gate (E11) can't land before plan 0009's S5, and until then the tier runs ungated (decision 3).

So the plan is the systemic fix: **one harness** (format, runner, workflows), with scenarios as data, whose verdict the gate then reads. It is not a set of point checks. The harness lives in its own repository and reaches Kanon only through what any adopter uses: its releases, its CLI and its callers (plan §2). Kanon's product gains two changes, each of which stands on its own for adopters, so each passes the no-leak rule and goes to Product Backlog: `init`'s pin, a bug adopters hit too, and the register's role for an App that isn't an agent, since adopters install such Apps too (decision 22). The draft's three product switches (an `Agent replay` choice, a `Run ceiling` choice and a `Telemetry tag` choice) are dropped under the no-leak rule (decisions 6, 7 and 8).

**A finding this brief raised, inferred and not verified, which the plan now carries in its §11.** Code that runs holding the driver token can push a workflow to a scenario repository, and the real-model scenarios' repositories hold the Anthropic API key as a secret. The harness's move settles the half about harness code: the harness's own escalation paths mark its runner `always`, so the Owner merges every change to it (decision 17). The other half remains, and the plan states it as residual risk. Kanon's CLI and scripts, at the release under test, run in the harness's `kanon` job. `cli/` and most of `scripts/` are green in Kanon's `docs/qa/escalation-paths.md`, so a change the Merger lands there runs on the next candidate. That job's token is narrowed (plan decision 22). It still holds Issues and Administration write, a departure from `K-AGENT-50` the Owner accepted on throwaway repositories only (plan decision 23), which Issue B's probe 14 checks.

**Kanon has had no spec layer until now.** `git ls-files docs/qa/specs` is empty on `main`, and the adoption record says so. This brief creates four areas: `ETE` (the gate), `CLI` and `REG` (the App register) with live `[seed]` clauses, and `LANE`, which holds only clauses retired before the merge (decision 20). The harness's behaviour is specified in the harness repository, not here. So `kanon-spec-coverage` names no reconciliation gap in any area this project touches. It reports 0 `[confirmed]` clauses with no test, and 46 Bare clauses, all of them new here. Nine are live `[seed]` clauses: `CLI-1`, the five `ETE` gate clauses and the three `REG` clauses. The other 37 are `[retired]`: the draft's harness clauses and its three product choices, kept so their ids are never reused (decision 20). There is no Issue A for a gap.

## 2. Scope

**This project is** plan 0012's steps E0 to E14, in two places.

**In Kanon,** built by Kanon's lanes:
- `init`'s pin fix (E1, Issue G);
- the App register's role for an App that isn't an agent, which the Reporter's row needs (decision 22, Issue U);
- the release gate on plan 0009's promotion (E11, Issue O).

**In the harness repository,** offloaded as issues there (plan §14), each tracked here by a human-action item:
- the harness's adoption of Kanon's full pipeline (E2);
- the scenario format, the runner, the janitor and the workflows (E3, E4);
- the first scenarios: the deploy rehearsal, install and upgrade (E5 to E7);
- the verdict, the red issue and the Reporter's check run (E8), and the burn-in (E9);
- the real-model tier under $2 (E10);
- the doctor-broken, `lane-check` and refusal families (E12);
- the long-lived upgrade signal (E14).

**Around both:** the Owner's setup and the platform probes (E0), and the four-week measurement (E13).

**It is not:**
- **Any test-only switch in Kanon's product** (the no-leak rule). That means no replay or stub mode, no test-only ceiling, no telemetry tag, no comment marker and no doctor waiver for tests. So there is no stubbed tier (decision 6), and no telemetry from scenario repositories (decision 8).
- **A hard per-run cost cap for the tests.** It would come only as the adopter feature [#891](https://github.com/yedeya-labs/kanon/issues/891) describes, judged on its own merit (decision 7).
- **Plan 0009's S3 to S5** (candidates, the pin job, `promote.mjs`). They are [#575](https://github.com/yedeya-labs/kanon/issues/575)'s, and they hold the gate through Issue C rather than joining this project. Until they exist the tier runs ungated, and a release cut before Issue O merges is not gated (decision 3).
- **The deploy lane** ([#610](https://github.com/yedeya-labs/kanon/issues/610), plan 0010). This project starts only once that lane is delivered. Issue A is the start gate, and every other item waits on it except Issue U, which comes before it: the Reporter is installed only once Kanon's lanes pin a release that can register it (decision 22).
- **Plan 0010's D12.** It stays a hand rehearsal (decision 15). Issue H's scenario repeats it on every candidate.
- **Per-pull-request runs, driving the skills through a model, private repositories, personal accounts, cloud credentials, the App manifest flow, and load testing.** These are all plan 0012's "Out of scope". Driving the skills through a model would come back only as a plan of its own.
- **Creating the test organisation, the harness repository or the Apps.** That is the Owner's (Issue A), and no agent is asked to.

**Specific to this project's definition of done:**
- **Every live clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Kanon's lanes build only Issues G, U and O.** Every other item is `qa:human-action`. Kanon's reconciler never dispatches it, and a human closes it with its evidence: the harness issue's link and the run or pull request the item names (decision 21).
- **Some evidence is live, not a unit test.** Scenarios pass by dispatch in the harness, and gating needs ten consecutive passes, scheduled or dispatched. The unit tests that cite Kanon's ids are what `verify-acs` reads. The harness's own tests cite the harness's own spec ids, which Kanon's `verify-acs` doesn't read.
- **How it closes.** Kanon declares no reference environment, so the reconciler stops this project at its deploy phase (`K-PROJ-11`). The Maintainer closes #902 by hand once Issue S's numbers are posted and `verify-acs` is dispatched green at the first gated stable release (decision 18).
- **No roadmap placement.** Every item files into a bucket, so `K-PROJ-14` asks for nothing.
- **The tracking issue's routing.** #902 carries no kind label (`K-WORK-23`), and most of the work is platform work, which wins a tie (`K-WORK-4`). A human should label #902 `pipeline-improvement` and move it to Development Automation. The Lead doesn't label.
