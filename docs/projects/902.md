# Project brief — End-to-end tests in throwaway repositories, gating every release (plan 0012)

The mandate is [#902](https://github.com/yedeya-labs/kanon/issues/902)'s body (`K-PROJ-15`). The design is plan 0012, drafted in [PR #903](https://github.com/yedeya-labs/kanon/pull/903) on `docs/plan-0012-end-to-end-tests`, read there with `git show origin/docs/plan-0012-end-to-end-tests:docs/plans/0012-end-to-end-tests.md`. This brief turns its order of moves (its §14, steps E0 to E14) into issues, and cites the plan by section rather than restating it. The Owner's four decisions of 2026-10-14 in the plan (a test organisation with its own driver App; test copies of the Author, Judge and Releaser installed only there; the tier as a hard release gate; a $2 cap per run on the real-model tier) are settled and not reopened here. The plan's seventeen questions for the Owner stay open in §7.

## 1. The real problem

**One root cause, not fifteen steps.** Nothing Kanon runs installs Kanon into a second repository. So every behaviour that shows only in an adopter's repository is first seen by an adopter. Each of these re-runs on `main`:

- **No harness exists.** `git ls-files tests/e2e scripts/e2e` prints nothing, and no workflow of Kanon's creates a repository anywhere.
- **The smoke workflows say what stands in for one.** `git grep -l "reference adopter's live run" -- .github/workflows/` names `agent-lanes-smoke.yml` and `agent-blocks-smoke.yml`. Their comments say that a model call is proven only by the reference adopter's run after each upgrade.
- **`init` writes a pin that can't resolve at a candidate.** `git grep -n kanonRelease -- cli/callers.mjs` shows the pin is `v` plus `package.json`'s version. At a candidate's commit that tag doesn't exist yet. This is a product bug for anyone running ahead of stable, not only for tests (plan §1, decision 5).
- **No lane can run without a model.** `git grep -il replay -- actions/agent-run/` prints nothing, so the stubbed tier needs a new mechanism (decision 6).
- **No lane run fits under the $2 cap.** `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/ | sort | uniq -c` shows every ceiling between $10 and $120, and no lane takes a lower one from its caller (decision 7).
- **A test row already has a home.** `git grep -n "TAGS" -- actions/agent-telemetry/schema.mjs` lists `run`, `smoke` and `test`, but a lane in an adopter's repository has no way to say it is a test (decision 8).
- **The promotion the gate hooks into doesn't exist.** Plan 0009's candidate pre-release, pin job and `promote.mjs` (its S3 to S5) are unbuilt. Only S2's admission of `candidate-vX.Y.Z` is built: `git grep -n "candidate-v" -- actions/lane-check/ cli/doctor.mjs` finds it, and neither `scripts/promote.mjs` nor `.github/workflows/promote.yml` exists. So the gate (E11) can't land before plan 0009's S5.

So the plan is the systemic fix: **one harness** (format, runner, workflows), with scenarios as data, which the gate then reads. It is not a set of point checks. The product changes it needs (`init`'s pin, the replay choice, the run-ceiling and telemetry-tag choices) are separate items because adopters get them too, and they go to Product Backlog.

**A finding this brief raised, inferred and not verified, which the plan now carries in its §11 (`661ce57`).** The scenario pair's job, `e2e-scenario-job.yml`, runs Kanon's scripts holding the driver token. That token has Contents and Workflows write on every scenario repository. The real-model scenarios' repositories hold the Anthropic API key as a secret (plan §5.2, §11). So a green-zone change under `scripts/e2e/` could push a workflow to a scenario repository that reads that key. `tests/unit/credential-reach-guard.test.ts` requires every file a credential-holding job runs to escalate or to be reached only at a pinned release. I didn't read how it treats a checkout at a release tag. Decision 17 asks the Owner who merges harness code.

**Kanon has had no spec layer until now.** `git ls-files docs/qa/specs` is empty on `main`, and the adoption record says so. This brief creates three areas, with `[seed]` clauses only: `ETE` (the tier and the gate), `CLI` and `LANE` (decision 20). So `kanon-spec-coverage` names no reconciliation gap in any area this project touches. It reports 0 `[confirmed]` clauses with no test, and 42 Bare `[seed]` clauses, all of them new here. There is no Issue A for a gap.

## 2. Scope

**This project is** plan 0012's steps E0 to E14:
- the test organisation's setup and the platform probes;
- the scenario format, the runner, the janitor and the workflows;
- the first scenarios: the deploy rehearsal, install, upgrade and review-replay;
- the verdict and its red issue, the burn-in, and the release gate on plan 0009's promotion;
- the doctor-broken, `lane-check` and refusal families;
- the real-model tier under $2, and the four-week measurement.

It also includes the three adopter-facing choices the tiers need, and `init`'s pin fix.

**It is not:**
- **Plan 0009's S3 to S5** (candidates, the pin job, `promote.mjs`). They are [#575](https://github.com/yedeya-labs/kanon/issues/575)'s, and they hold the gate through Issue C rather than joining this project. If the Owner chooses decision 3(b) (hold every release until they exist), that is a change to #575's schedule, not to this brief.
- **The deploy lane** ([#610](https://github.com/yedeya-labs/kanon/issues/610), plan 0010). This project starts only once that lane is delivered. Issue A is the start gate, and every pull-request item waits on it.
- **Plan 0010's D12.** It stays a hand rehearsal, as decision 15 recommends. Issue H repeats it on every candidate.
- **Per-pull-request runs, driving the skills through a model, private repositories, personal accounts, cloud credentials, the App manifest flow, and load testing.** These are all plan 0012's "Out of scope". Driving the skills through a model would come back only as a plan of its own.
- **Creating the test organisation or its Apps.** That is the Owner's (Issue A), and no agent is asked to.

**Specific to this project's definition of done:**
- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Some evidence is live, not a unit test.** Scenarios pass by dispatch and gating needs ten scheduled passes. That evidence is linked on each pull request. The unit tests that cite the ids are what `verify-acs` reads.
- **No roadmap placement.** Every item files into a bucket, so `K-PROJ-14` asks for nothing.
- **The tracking issue's routing.** #902 carries no kind label (`K-WORK-23`), and most of the work is platform work, which wins a tie (`K-WORK-4`). A human should label #902 `pipeline-improvement` and move it to Development Automation. The Lead doesn't label.

## 4. Cost

**What is added in recurring spend:**
- **Model:** at most $2 a night and $2 per candidate (Owner decision 4). That is about $62 a month of nights plus $8 to $10 for four or five candidates, so at most about $72 a month, and less when the ledger skips.
- **The spend-limited API key's monthly limit:** about $75. This is a backstop, not the cap, and its exact figure is decision 16.
- **Actions minutes:** $0, *if* public repositories in a free organisation run free (probe 6 in Issue B). If they don't, the Owner sets a budget before Issue F merges.
- **The stubbed and no-model tiers:** $0 in model spend.

**What is added once:**
- **Each recording:** one real-model run of the recorded lane, at most that lane's own ceiling. For the review lane today that is $30, from `git grep -h -o -- "--max-budget-usd [0-9]*" -- .github/workflows/ | sort | uniq -c`, or less under a run ceiling once Issue Q ships. A release that changes what a lane parses repeats this.
- **Building it:** 15 pull-request items, each implementer run capped by its own `--max-budget-usd`. The same grep shows the Implementer's ceiling is $120, so the worst case is about $1,800 of runs before revisions. That is a ceiling, not an estimate.

**Time:**
- **The Owner:** the one-time setup (Issue A), and one approval click per candidate (decision 9).
- **Maintainers:** Issue B's probes and Issue S's measurement.

Nothing here is a new cloud resource on Kanon's AWS account. There is no QA store, telemetry store or AWS in the test organisation (plan "Out of scope").

## 5. Observability

**Add:**
- **The red issue:** `e2e: candidate-vX.Y.Z is red`, `bug` and `sev:high` (`[ETE-18]`).
- **`promote.yml`'s summary line** naming the gate that held a candidate (`[ETE-34]`).
- **The janitor's failing run** when a test repository outlives a day (`[ETE-11]`).

These are the tier's whole signal set, and each lands with its item.

**Skip paging.** Kanon has no pager and no `docs/observability.md`: `git ls-files docs/observability.md` prints nothing. These signals are issues and red runs, which the Owner already reads.

**A stopped nightly run needs no detector.** It shows up as a held promotion, because the gate passes only on a green run at the candidate's commit (`[ETE-31]`).

**Skip a telemetry row for `e2e.yml` itself.** It isn't a lane, and its result document and artifacts already carry each scenario's outcome. The scenario repositories' lane rows are `tag: test` (`[LANE-5]`), which every read already filters out.

The trigger that would change this: a second adopter-facing release channel. Then a held candidate would need to reach someone other than the Owner.
