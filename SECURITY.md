# Security

Kanon runs agents with write access to repositories, so security problems in it matter. Examples include a way for untrusted input to reach a write-capable agent, a workflow that leaks a token, or a check that can be bypassed.

**Please don't report them in a public issue.** Use GitHub's private vulnerability reporting instead (the **Security** tab, then **Report a vulnerability**). You'll get an acknowledgement, and a fix is released as a normal Kanon version, which adopters receive as a Dependabot upgrade.

## Accepted exposures

Kanon keeps a pull request's code away from any credential that can write: a job that runs the code it is testing holds no App token and no other secret ([`K-AGENT-50`](rulebook/03-agents.md)). Two lanes are exceptions, and the Owner accepted them on 2026-10-05. A lane's `notify` job, which runs your notify hook beside one chat secret, is a third, smaller one, accepted on 2026-10-14 and stated [in its own subsection](#the-notify-jobs-chat-secret). This section says what they expose and what limits it, so you can judge it for your own repository.

### Which lanes, and what runs

- **The revise lane** (`agent-implement-revise.yml`) answers the Reviewer's changes-request on the Implementer's own pull request. It checks out the pull request's branch and runs your project-setup hook (`.github/actions/project-setup`, which installs your toolchain and dependencies) from that branch. Its agent then edits the code and runs your project's gates (lint, type check, tests) on it before it commits.
- **The rebase lane** (`agent-rebase.yml`) resolves a merge conflict on the Implementer's pull request. It runs your project-setup hook from your default branch, then its agent checks out the pull request's branch, merges your default branch into it, and runs your gates on the result before it commits.

In both, the pull request's code (its install scripts, its build and its tests) runs on the same runner, in the same job, as two credentials:

- **The Author App's installation token**, which the agent comments and labels with. It reads your code and can't write it.
- **The Claude token** (`CLAUDE_CODE_OAUTH_TOKEN`, or `ANTHROPIC_API_KEY` if you use one), which the agent runs on.

So code in that pull request that turns hostile, through a compromised dependency or a test written from injected text, could read either one while the job runs.

### Why it is accepted

The agent has to test what it commits, and post what it found, in the job that ran it. Running the tests in a separate job would take the test results away from the agent that answers the review or the conflict, and the lane would no longer fix what it found. The code that runs was written by the same App, with the same permissions, in the lane that opened the pull request, so it reaches no identity or permission its author didn't already hold. And the Claude token sits beside the pull request's code in the implement lane that wrote it too, so these two lanes add no new holder of it.

Two risks remain:

- Another agent with write access to code can push to the Implementer's branch: Kanon's Lead, Explorer and Overseer share the Author App, and you may have given another App that access. Code one of them planted would run with the Implementer's token, which can comment, label and read your code, but writes no code and no workflow file. The status check under "What bounds it" narrows this, because a lane refuses a branch whose latest commit lacks the Implementer's status.
- Anyone who reads the Claude token can run models on your account until you rotate it. It gives no access to your repository.

### What bounds it

- **The token is short-lived and narrow.** A separate job, which runs nothing else, holds the App's private key and mints the token; the key never reaches the job that runs the code ([`K-AGENT-49`](rulebook/03-agents.md)). The token is for your repository alone, carries only contents read, and issues and pull requests write ([`K-AGENT-46`](rulebook/03-agents.md)), is revoked as the job's last step, and expires within an hour if revocation fails.
- **Only the `push` job writes code, and it runs nothing of yours.** The agent's commits reach your branch only through a `push` job after the agent's job, which mints the only token in the lane with contents and workflows write. It runs no agent and none of your code, and checks nothing out. It re-creates each commit through GitHub's API, so GitHub verifies it as the Author App's, and moves only the pull request's own branch, from the head the agent's job started from, never by force ([How an Author lane commits](docs/lanes.md#how-an-author-lane-commits)).
- **Only members start a lane.** Before any token is minted, the lane checks who caused the event (the reviewer, whoever applied the label or ran the dispatch, whoever pushed or merged) and refuses anyone who isn't the repository's owner, a member or collaborator, or one of the Apps you registered ([`K-AGENT-45`](rulebook/03-agents.md)).
- **Only the Implementer's own pull requests.** Each lane acts only on a pull request the Implementer opened whose latest commit carries the `kanon/role: implementer` status that the Author App sets in a fixed step, never an agent. A person's push removes that status, so the lane refuses the pull request from then on, and a person finishes it. The status carries to a new head only across commits GitHub verified as the Author App's, so a person's commit under the App's email ends it too, even one the agent fetched during its run.
- **Forks get nothing.** A fork's pull request is never the Implementer's, so both lanes refuse it. The revise lane runs on `pull_request` and `pull_request_review` events, which GitHub runs without secrets for a fork's pull request ([`K-AGENT-47`](rulebook/03-agents.md)). The rebase lane's `pull_request_target` trigger reads only that a pull request merged and who merged it, and never checks out or runs that pull request's code. The pull requests it does resolve must have their head on your repository: it refuses one on a fork, or one whose repository it couldn't read, before its agent's job checks anything out ([`K-AGENT-48`](rulebook/03-agents.md)).

Every other lane that runs your project's code either runs it in a job with no write credential, or starts from your default branch's reviewed code, with one stated exception: a lane's `notify` job runs your notify hook from whatever branch the run is on, beside one chat secret ([below](#the-notify-jobs-chat-secret)). Four lanes run your project-setup hook from it in the job that holds the Author App's token and the Claude token: the implement and triage lanes (`agent-implement.yml`, `agent-triage.yml`), whose agents then test the code they write in that run, and the Lead's split lane (`agent-lead-split.yml`) and the Explorer (`agent-explore.yml`), whose agents write no code. To avoid the revise and rebase lanes' exposure, don't install the revise and rebase lanes: a changes-request or a conflict on the Implementer's pull request then waits for a person.

### The `notify` job's chat secret

A lane that posts a message to people in chat posts it from a `notify` job of its own, which runs your notify hook (`./.github/actions/notify`) at the run's commit, whatever branch the run is on ([`K-OBS-19`](rulebook/08-observability-and-cost.md)). The Owner chose that over running only your default branch's hook, with the risk stated ([plan 0011](docs/plans/0011-notifications.md), decision 8). Kanon's `notify` block, which runs the hook, is built, and four lanes run it in their `notify` jobs: the daily project digest (`agent-project-digest.yml`) since plan 0011's step N7, the weekly digest (`agent-weekly-digest.yml`) since step N8, the deploy lane (`deploy.yml`), which announces each environment's deploy, since step N9, and the release announcement (`agent-release-announce.yml`), which announces each published release, since [kanon#1190](https://github.com/yedeya-labs/kanon/issues/1190). The deploy lane's `notify` job is a job of its own, after the deploy: it never holds the environment's cloud credential or `KANON_DEPLOY_SECRET`. No lane posts through `DIGEST_WEBHOOK` any more ([`K-OBS-19`](rulebook/08-observability-and-cost.md)'s Enforced by).

- **What it holds.** One message kind's chat secret (`KANON_CHAT_PROJECT_DIGEST`, `KANON_CHAT_WEEKLY_DIGEST`, `KANON_CHAT_DEPLOY` or `KANON_CHAT_RELEASE`) and a workflow token that reads contents and nothing more.
- **Who can reach it.** Anyone who can push a branch and dispatch a notifying lane on it. They change the hook on their branch to print or send the secret, dispatch the lane there, and the `notify` job runs their hook with it; nothing reviews the branch first. That includes an agent whose App can push a branch and dispatch a workflow, even without GitHub's `workflows` permission, because the hook is not under `.github/workflows/`. **Publishing a release is a second way in,** where the release announcement is installed: a release runs the lane at its tag's commit, so whoever can tag an unreviewed commit and publish a release on it runs that commit's hook with `KANON_CHAT_RELEASE`. It takes the same write access as pushing and dispatching.
- **What bounds it.** The job holds no App key or App token, no Claude credential, no OIDC grant and no other secret, so a leaked chat secret lets its holder post to that kind's channel, and nothing more. No `notify` job is in a workflow a pull request can start, so a fork's pull request never runs a hook. On your default branch, a change to the hook escalates to a person before it merges ([`K-MERGE-4`](rulebook/04-review-and-merge.md)), as does every path the hook runs that you declare under `## Pipeline code` ([`K-LAYOUT-8`](rulebook/11-repository-layout.md)); a path it runs from outside `.github/` that you don't declare does not.

[`docs/notifications.md`'s security section](docs/notifications.md#security) states this in full, with what still protects your default branch's scheduled runs. To avoid it, install no hook: without one, nothing posts through the contract and no `notify` job runs a hook.
