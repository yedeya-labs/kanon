# `lane-check`: check an adopter's lane callers

Fails unless the repository's Kanon lane callers, project-setup hook, App register and Dependabot entry follow the lane rules in [docs/lanes.md](../../docs/lanes.md) ([plan 0001 §6](../../docs/plans/0001-move-the-agent-lanes.md)). It holds only the permanent rules:

- **Each lane caller** (a workflow with a job that calls a Kanon lane, `yedeya-labs/kanon/.github/workflows/agent-<lane>.yml`, never the spine `agent-lane.yml`) holds only `name`, `run-name`, `on`, `permissions` and one job, and no `concurrency`. When the lane says what its caller's `run-name` must end with (the review lane does, on a `# CALLER RUN-NAME ENDS WITH:` line), the caller's ends with exactly that, as its last token. It is at `.github/workflows/<lane>.yml`, its lane's own file name, and is not itself a reusable workflow, because Kanon's scripts find a lane's runs by that file name and GitHub files a run under the top-level workflow (`K-LAYOUT-18`; in Kanon's own source tree, where that path holds the lane, its caller is exempt). When the lane reads a workflow of yours by its file name (a `# READS WORKFLOW:` line; the review lane and the reconciler read `ci.yml`), that workflow exists. When the lane says what its caller's `name` must be (the Merger's does, on a `# CALLER NAME:` line, because `merge-gate.mjs` tells its own checks from the rest by it), the caller has exactly that name. The review, merge-reconcile and implement-revise lanes say their callers' names on `# CALLER NAME:` lines too, and the revise and merge-reconcile lanes their calling job's id on a `# CALLER JOB:` line (`revise` and `reconcile`), because `merge-gate.mjs` reads those names and ids; a test holds the lines to the gate's own constants (`caller-names.mjs`, [#728](https://github.com/yedeya-labs/kanon/issues/728)). For these three, another name or id is a `::warning`, naming the expected one, until Kanon 0.41.0 (its `FAILS_FROM`), and a failure from it. `FAILS_FROM` is the one switch: from that release on, the same check fails.
- **That job** holds only `uses`, `with`, `secrets` and `permissions`. It passes only its own inputs through by the same name, a raised turn limit included: `max_turns` only as `${{ inputs.max_turns }}`, never a number, and only with `reason: ${{ inputs.reason }}` beside it ([#891](https://github.com/yedeya-labs/kanon/issues/891); docs/lanes.md, "The turn budget"), and with no `default` on either input in its `workflow_dispatch`, which GitHub would fill on every dispatch that leaves it out ([#1007](https://github.com/yedeya-labs/kanon/issues/1007)); it maps exactly the secrets the lane declares, each to one repository secret (never `secrets: inherit`), except that it may leave out an optional secret the lane marks `# OPTIONAL SECRET:`, such as the QA store's two or the Overseer's telemetry reader role ([#433](https://github.com/yedeya-labs/kanon/issues/433)), and of the Claude credential pair the lane marks `# ONE OF SECRETS:`, `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY`, maps exactly one, the one it runs on: both or neither fails, naming the lane, the caller and the two secrets, never a value (plan 0009 §10; a lane without the line, from an earlier release, keeps the rule of exactly its declared secrets), and grants at least the permissions the lane declares, at its top level or on any of its jobs.
- **A call to any other Kanon workflow is not a lane caller.** The [release workflow](../../docs/release.md)'s caller maps the optional Releaser's secrets or none, and the [`apps-check`](../../docs/apps.md#checking-the-installations-later) caller maps its own Apps', so neither is held to the rules above, only to the pin below and to `secrets`: a job that calls any Kanon workflow maps each secret by name or passes none, never `secrets: inherit` ([#152](https://github.com/yedeya-labs/kanon/issues/152)).
- **A caller of Kanon's telemetry collector** passes neither `url:` nor `writer-role:` without `audience:`, from a release whose `requirements.json` says `telemetry.token`. The caller is judged against the release it pins, so only when the check runs at that pin, as the action always does: a run without `ACTION_REF`, such as Kanon's own test of its tree, whose caller lags at the last release, judges nothing here. Those are the SigV4 path's inputs, which that release's collector refuses before it mints a token, but only on the default branch, after the pull request that moved the pin merged. This fails that pull request instead, a Dependabot bump included, naming the job and the inputs, never their values, and both fixes: `kanon init --telemetry` again, or `audience:` beside `url:` for a store of your own. It is the condition `kanon doctor` reports as `telemetry.legacy-inputs` ([#845](https://github.com/yedeya-labs/kanon/issues/845)).
- **Every Kanon reference** under `.github/` pins one exact version, and it is the version this check runs at. An exact version is a stable release, `vX.Y.Z`, or a candidate, `candidate-vX.Y.Z` (`K-ADOPT-11`); a candidate beside its own stable release is two versions. One pin follows the others instead of matching them: the notify hook's (`.github/actions/notify/action.yml`) call to one of Kanon's prebuilt hooks, `yedeya-labs/kanon/actions/notify/slack` or `…/webhook` ([plan 0011](../../docs/plans/0011-notifications.md) decision 18). Pinned behind the callers, it passes with a `::notice`, as long as it declares a contract version (a `message-v<N>` input) the callers' release still writes; that is doctor's `notify.hook-pin-behind`, a note. Pinned ahead of the callers, or behind them on a contract version their release no longer writes, it fails. It is still an exact version, and any other Kanon reference in the hook is held to the one version like the rest.
- **The project-setup hook** exists at `.github/actions/project-setup/action.yml`, is a composite action, and declares every input Kanon's lanes pass it.
- **The hooks only some lanes call** exist, as composite actions, when a caller calls one of those lanes: the Explorer's sweep hook, `.github/actions/explore-sweep/action.yml`, for an explore caller (plan 0004 decision 5). A lane names each on a `# NEEDS HOOK:` line.
- **The App register** (`docs/qa/agent-identities.md`) has one row, with an App slug in backticks, for every role a caller's lane runs as (its `# KANON ROLE:` line). The rows of one App's roles name one slug, and the Author, the Judge and the Releaser name three different ones (plan 0005 §3.4). An `Other App` row, an App installed that isn't an agent, names a slug no other row names (`K-LAYOUT-6`).
- **Every broadened App permission has its reason.** A register row whose permission is broader than its App's grant (with the extras your adoption record declares) carries a numbered `[^N]` footnote, and every footnote marker in the table resolves ([`docs/apps.md`](../../docs/apps.md), `K-LAYOUT-6`).
- **No role-named App secret.** A caller that maps `IMPLEMENTER_APP_ID`, `REVIEWER_APP_ID` or another role's secret fails by name, with the `AUTHOR_` or `JUDGE_` secret the lane takes instead (§3.5).
- **The project documents a called lane reads** exist, and the stack document has `## Gates` exactly once and each of its other three sections at most once (`K-LAYOUT-17`). Which documents a lane reads is read from the lane itself. A missing playbook isn't a failure: the lane reads Kanon's baseline for it, and this says so. Neither is an omitted `## Schema changes`, `## Data isolation` or `## Generated files`, which means none.
- **The test-database declaration** (`docs/qa/test-database.md`), when there is one, has exactly one `**Test database:**` line declaring `none` or `hook`, never an engine (`K-LAYOUT-16`). No file is valid: it declares no database.
- **The escalation and exemptions files** (`docs/qa/escalation-paths.md`, `K-LAYOUT-8`, and `docs/qa/exemptions.md`, `K-LAYOUT-15`), parse with the same readers the guards and the Merger use, at your pinned version, and a malformed one fails by name with the reader's own message ([#153](https://github.com/yedeya-labs/kanon/issues/153)). A missing file or section is Kanon's default (only the pipeline's own paths escalate; nothing is exempt), and the reader's line naming it is printed.
- **The deploy declaration** in the adoption record (`docs/qa/adoption.md`'s `## Deploy`, `K-LAYOUT-10`), when the record exists, parses with the reader the reconciler uses, and a malformed declaration fails by name, as does a reference-deploy bullet left under `## Choices`, from where the bullets moved (plan 0010 D2). A record that declares no reference environment passes here: the reconciler fails on it when a project reaches its deploy phase (`K-PROJ-11`).
- **Whether the production promotion is human-gated** (`K-MERGE-4`, `K-LAYOUT-10`, [#158](https://github.com/yedeya-labs/kanon/issues/158)), when the adoption record has a `**Production promotion:**` bullet, parses with the reader the Merger uses, and a malformed one fails by name: one outside `## Choices`, written twice, in another shape than `human-gated (<what gates it>)`, or with nothing in its parentheses. A record without the bullet is Kanon's default, where every escalation path escalates.
- **Whether the Overseer is installed** (`K-LAYOUT-10`, plan 0004 step 13). The Overseer is optional, so the adoption record may have an `**Overseer:**` bullet under `## Choices`, its value `installed` or `not installed`, and it says what is true: `installed` with a caller of `agent-overseer.yml`, `not installed` without one. A record without the bullet, or no record, is Kanon's default, `not installed`, and this says so. A bullet in another shape fails, and so does a value, declared or the default, that the callers contradict: a caller of the Overseer needs a record that says `installed`.
- **Where the Overseer's upstream findings go** (`K-LAYOUT-10`, `K-SELF-11`, [#423](https://github.com/yedeya-labs/kanon/issues/423)), when the adoption record has an `**Upstream findings:**` bullet, parses with the reader the Overseer's lane uses, and a malformed one fails by name: one outside `## Choices`, written twice, in another shape, or with a value other than `drafted`, `filed here`, `sent` or `sent with evidence`. A record without the bullet is Kanon's default, `drafted`: findings only Kanon can act on are drafts in the audit, never issues. `sent` and `sent with evidence` travel over the telemetry channel, so a record that says either with no workflow calling Kanon's telemetry collector fails too, naming both fixes: opt in to telemetry, or choose `drafted` (`upstream.unsent`, [plan 0006](../../docs/plans/0006-upstream-findings.md) §3.1).

**What it takes as a default it names**, one `::notice` each, so a repository that relies on a default is told so on every run ([plan 0005](../../docs/plans/0005-lean-installation.md) §5.2). The last line counts them: `lane-check: N lane caller(s) pass, with M documented default(s) taken`.
- **`.github/dependabot.yml`** has a `github-actions` entry for `/` that groups `yedeya-labs/kanon*`, prefixes its commits `ci`, and excludes `yedeya-labs/kanon*` from its `cooldown`. An entry with no `cooldown` fails: Dependabot then applies its default of 3 days, which holds back every Kanon release made in the last 3 days ([#233](https://github.com/yedeya-labs/kanon/issues/233)). Every entry that would open a Kanon upgrade pull request, a `github-actions` entry that reaches a Kanon reference and neither leaves Kanon out of its `allow` nor ignores every Kanon update, whether or not it has the group, the prefix and the cooldown exemption, reaches every file that holds a Kanon reference counted toward the one version, the same entries `kanon doctor` holds ([#1111](https://github.com/yedeya-labs/kanon/issues/1111)): Dependabot reads `.github/workflows/` from `/`, and a composite action, such as the project-setup hook, only from the action's own directory, so an entry for `/` alone leaves the hook's pin behind on every upgrade pull request, and the one-version rule fails it. The failure names the files and the `directories:` line that reaches them, `directories: ["/", "/.github/actions/*"]` for the hooks under `.github/actions/`. A Kanon reference in a file Dependabot never updates, neither a workflow directly in `.github/workflows/` nor an action's `action.yml`, fails by its own name ([#1105](https://github.com/yedeya-labs/kanon/issues/1105)). Each of those entries also **groups Kanon** ([#1126](https://github.com/yedeya-labs/kanon/issues/1126)): Dependabot opens an update no group takes in as a pull request of its own, one per dependency and per directory, and each Kanon lane's workflow is a dependency of its own, so an ungrouped entry splits the upgrade into pull requests that each fail the one-version rule, however well it reaches. The first group that takes in Kanon's actions (`yedeya-labs/kanon`) and its lanes' workflows (`yedeya-labs/kanon/.github/workflows/...`) has to be one group, taking in every update to them: no `update-types` short of all three, no `dependency-type`, no `group-by`. The failure names the entry and the fix, the `kanon` group `kanon init` writes, `kanon: { patterns: ["yedeya-labs/kanon*"] }`, or an `ignore` of `yedeya-labs/kanon*` for an entry not meant to propose Kanon. Where the entry already has a group named `kanon`, the fix changes that group instead of adding a second, which would be a duplicate key: its `patterns` set to `["yedeya-labs/kanon*"]`, any `exclude-patterns`, `update-types`, `dependency-type`, `group-by` or `applies-to` removed, and the group moved first ([#1159](https://github.com/yedeya-labs/kanon/issues/1159)).

What a lane declares, and what the hook must accept, is read from Kanon's own files at the version you pinned, so the check and the lanes can't disagree.

**A red pull request that only moves Kanon's references points to `/kanon:upgrade`** ([#1106](https://github.com/yedeya-labs/kanon/issues/1106)). Dependabot's upgrade pull request moves only the `uses:` refs, so when a release changes what the callers need, such as a secret, a permission, an input or a trigger, it opens red. On such a pull request, after the failures, lane-check says that the release changes what your callers need and to run `/kanon:upgrade` on the branch. It then lists the changes in two parts: what only a person can do (a repository secret to add, or to store under its new name, and any App permission the release adds, which `kanon doctor` names), and what the upgrade skill does (the failures themselves: the mappings, the `permissions:` blocks, the inputs, the triggers). It prints one more `::error` that says the same in a line, and writes the same to the job's summary, which the pull request's checks show. How it knows the pull request only moves Kanon's references:

- **From the diff, first.** It reads the pull request's base from the event's payload (`GITHUB_EVENT_PATH`) and diffs it against the checkout. `actions/checkout` leaves one commit, so when the base isn't there it fetches that one commit from `origin`, with the token the checkout already keeps for `contents: read`, or none on a public repository. No new permission or input is needed. The pull request only moves the references when, in every file it changes, each line it removes or adds is the `uses:` line of a Kanon action or workflow, and the lines it adds are the lines it removes with other refs. A file added, deleted, renamed or binary, or any other line, and it doesn't.
- **From the branch, when the base can't be read.** A pull request from a Dependabot branch for GitHub Actions (`GITHUB_HEAD_REF` starting with `dependabot/github_actions/`) counts, since Dependabot changes only the refs.

On a `pull_request` or `pull_request_target` run and nowhere else. A pull request that changes anything else, a run that passes, and a `merge_group` or `push` run print what they always printed.

## Use it

<!-- x-release-please-start-version -->

```yaml
name: Lane check

on:
  pull_request:
  merge_group:

permissions:
  contents: read

jobs:
  lanes:
    name: Lane check
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v7
      - uses: yedeya-labs/kanon/actions/lane-check@v0.43.0
```

<!-- x-release-please-end -->

- **Check out first.** It reads your repository's files.
- **`yq`.** It parses YAML with `yq` (mikefarah v4), and checks it in one Node process. GitHub's hosted runners have `yq`; a self-hosted runner must provide it. Node is Kanon's own: the action's first step puts the Node major Kanon declares on the `PATH`, as every lane does. That Node, and `KANON`, stay set for the rest of the job, so run the check in a job of its own, as above, or before your own toolchain's setup.
- **No inputs.** Everything it checks is a fixed path or is read from the lanes ([ADR 0002](../../docs/decisions/0002-standardise-dont-parameterise.md)).
- Pin the same exact Kanon version as your lanes, and let Dependabot propose upgrades (`K-ADOPT-11`).
- **Run it locally** from a Kanon checkout at your pinned tag, in your repository's root: `KANON_ROOT=<kanon checkout> ACTION_REF=<tag> bash <kanon checkout>/actions/lane-check/lane-check.sh`. It needs `yq` (mikefarah v4) and Node 24 on your `PATH`.
